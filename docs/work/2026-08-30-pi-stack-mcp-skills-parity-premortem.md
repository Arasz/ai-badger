# Pre-mortem — pi stack parity: MCP config + skills discovery (aib-pi-stack-mcp-skills-parity, MoE lane 3)

**Date:** 2026-08-30 · **Input attacked:** `2026-08-30-pi-stack-mcp-skills-parity-plan.md` (M1–M6, Q1–Q3, risks 1–5) against research F1–F15/H1–H3/D1–D4, pi 0.84.4 dist source, fork source, live `~/.pi/agent/settings.json`, and the 8 scaffolded projects on this machine.
**Headline:** the plan's central trust narrative is built on a false premise. `ctx.isProjectTrusted()` is **true in headless runs for scaffolded projects** — pi short-circuits trust resolution to `true` when a project holds no pi-trust-requiring resources, and the scaffold never writes any. M2's "headless arms nothing until /trust" story (Q1 framing, risk 3, ADR negative consequence, migration step 4) is wrong in the safe direction — but it is still wrong, and the plan would enshrine it in tests, ADR, and support.json.

---

## 1. Per-option verdicts

**D1a — fork reads project `.mcp.json` directly (M1). Verdict: REJECT-WITH-CONDITION.**
Deciding attack (measured, not hypothetical): the plan's "remote shapes are user-owned and never generated" is contradicted on this machine — `ai-raccoon/.mcp.json` and `job-search-ai-assistant/.mcp.json` both carry a `rider` server with `type:"http"`, `url:"http://127.0.0.1:64482/stream"`. The plan's converter *skips* those with a warning; the fork already ships `StreamableHTTPClientTransport`/`SSEClientTransport` (`src/McpClient.ts:2-4,88,92`), so mapping `http|sse → remote` is mechanical and the skip is a self-inflicted parity hole in exactly the projects where "same server set as Claude Code" is the AC. Conditions: (a) map claude `type:"http"/"sse"` + `url` → fork `type:"remote"` (or owner explicitly accepts the skip and support.json says "local stdio only" — see Q4); (b) `tools:["*"]` → "no filtering" is pinned by test (verified trap: `McpToolAdapter.convertToPiTool` runs `new RegExp("*")` → `SyntaxError`; the throw escapes the per-tool loop into the per-server `catch` in `index.ts`, killing *every tool of every scaffolded server*, visible only under `--mcp-debug`); (c) `command` string→array splitting (quoted args) pinned; (d) unparseable `.mcp.json` ⇒ global-only fallback + warning, never a partial arm.

**D1-i — `ctx.isProjectTrusted()` only, no auto-trust (M2). Verdict: REJECT-WITH-CONDITION on the mechanism's *documentation*, APPROVE on the mechanism itself.**
Deciding attack (pi dist source, `dist/core/trust-manager.js:8-17,150-166` + `dist/main.js:571-582` + `dist/core/project-trust.js:15-17`): trust-requiring resources are exactly `.pi/{settings.json,extensions,skills,prompts,themes,SYSTEM.md,APPEND_SYSTEM.md}` and `.agents/skills` in cwd or any ancestor — **not** `.mcp.json`, **not** `.ai-badger/`, **not** `.pi/agents/` (the scaffold's persona dir). `resolveProjectTrusted` returns `true` *before* consulting trust.json, extensions, or `defaultProjectTrust` when no such resource exists, and `main.js` computes `projectTrusted = (!hasTrustRequiringResources || trustStore.get(cwd) === true)`. Every scaffolded project on this machine (measured: all 8 have only `.pi/agents/` inside `.pi/`) therefore resolves **trusted in every mode, including `-p`/json/rpc**. Consequences the plan must absorb:
- The stated headless gap ("fresh scaffolded projects arm zero MCP servers headless until trust granted") is false for this scaffold's output. Migration step 4 ("trust bootstrap") and the ADR's headline negative consequence are dead weight for the common case.
- The gate is *vacuous today, live tomorrow*: the moment a user adds `.pi/settings.json` (a project theme/model tweak — an ordinary act) or any ancestor gains `.agents/skills`, `isProjectTrusted()` flips to false headless (no trust.json exists, ask→false) and the project's MCP servers **silently vanish** from every `-p` run. That coupling is user-invisible and arbitrary — the plan must name it, test both cases, and decide whether to smooth it.
- What trusting actually unlocks (the judge question): project `.pi/settings.json`, `.pi` resources, missing project packages, project-local extensions — nothing the ai-badger stack needs. Auto-trust (D1-ii) was disproportionate for a second reason the plan didn't know: a `project_trust` handler **only fires when the project has trust-requiring resources** (`shouldResolveProjectTrust` gates the whole resolution, `main.js:574`; `resolveProjectTrusted` early-returns before `emitProjectTrustEvent`). For minimal scaffolded projects the adapter's auto-trust would be dead code; it would only bite in the fragile case. Q1-(i) survives, but with corrected semantics.
- Honest framing that must replace the plan's: the fork serves users *without* the ai-badger adapter too — for them the gate is real security (the `ConfigLoader.ts` docstring stays true); inside the ai-badger stack the gate is consistency-with-pi, not a boundary (the adapter already executes project-declared hook *shell commands* ungated — see D2a).

**D2a — adapter contributes `<cwd>/.ai-badger/skills` via `resources_discover`, ungated (M3). Verdict: APPROVE-WITH-CONDITION.**
Deciding attacks: (a) H1 is now source-verified — `dist/core/agent-session.js:1920-1941` runs `extendResourcesFromExtensions` unconditionally after `session_start` with no `hasUI`/mode gate; contributions are honored in `-p`/json/rpc. (b) The trust-model attack: pi's own classification trust-gates **skills** (`.pi/skills`, `.agents/skills` are in the trust-requiring list) and does **not** gate `.pi/agents`. The subagent precedent is therefore *half* honest: reading `.pi/agents/*.md` via fs matches pi's own classification for that path; M3 extends ungated loading to a content class pi explicitly gates. The precedent proves the channel exists, not that pi blesses the extension. The honest risk anchor is not "pi-consistent" — it is that the adapter has executed project-declared **shell commands** from `.ai-badger/hooks/hooks.json` ungated in every mode since ADR-0022 (`adapter/index.ts:44,64-71,131-146`: `runGate` spawns with `cwd: ctx.cwd`); skills are strictly weaker than what already runs. Condition: the ADR must record the asymmetry in exactly that shape — *divergence from pi's gating of skills, deliberate, calibrated by the pre-existing hooks-command channel; the effective trust decision for ai-badger-equipped pi is installing the adapter user-globally* — and the live `pi -p` smoke test stays in P2 despite the source read.

**D3 — adjustments repurposed migration-only (M4). Verdict: REJECT-WITH-CONDITION.**
Deciding attacks (live-state measured): (a) **Name-keyed removal destroys user edits to same-named entries.** All 8 projects declare overlapping names (`code-review-graph`, `hermes`, `ai-raccoon`, `semantica`, most `playwright`); the global `mcp` key is one shared snapshot. "Removal is keyed to names the scaffold itself declared; user-added entries never touched" is true only for *different names* — a user who added `env` or changed `args` on a same-named entry gets their edit deleted, not superseded. The scaffold knows exactly what it would have written (`adjust_mcp.py:_server_entry`): removal must be **shape-aware** — remove only where the entry matches the generated shape (name + command; tolerate legacy key drift), else warn-and-leave. (b) **Cross-repo upgrade hazard:** P5 covers this machine only. Any other machine (or a future user) whose repo-B scaffold updates land while the installed `~/.pi/agent/extensions/` adapter/fork predates project-scope reading gets *zero MCP at all* after cleanup — the old fork reads only global `mcp`. The removal must be version-gated: detect the installed extension and skip-with-warning when it cannot read `.mcp.json` yet. (c) `--no-install` printing the removal proposal is honest and must be preserved (it is). (d) Atomicity: `pi_settings.write_settings` is atomic; note the fork's `saveDisabledTools` is a bare `writeFileSync` read-modify-write that can race a scaffold's `os.replace` (pre-existing, F13-adjacent — owner call whether P1 fixes it as a drive-by).

**D4 — sequencing per F11 (M6). Verdict: APPROVE.**
No file-overlap attack found: P1 (fork) is fully independent; P2's gate correctly re-anchored to the pbi-move *branch/merge* after the named worktree vanished from disk; P3's files (`adjust_mcp.py`, `adjust_skills.py`, `pi_settings.py`) are untouched by pbi-move's repo-B surgery. The one residual: P3's *runtime* behavior depends on the repo-A artifact users have installed — covered by the M4 version-gate condition, not by merge order.

## 2. Ranked risks (max 7)

1. **Wrong trust semantics enshrined.** Plan, tests, ADR, and support.json would document "headless arms nothing until /trust"; measured pi behavior is the opposite for scaffolded projects and flips silently when trust-requiring resources appear. Every downstream artifact inherits the lie. *(Mitigation: MUST-1.)*
2. **User-invisible divergence without config-source visibility.** `/mcp-status` today reports only names + health. Untrusted-gate, not-declared-in-`.mcp.json`, skipped-remote-shape, and global-fallback are indistinguishable to the user; the first `.pi/settings.json` user to lose MCP headless gets no signal. *(Mitigation: MUST-2.)*
3. **`tools:["*"]` → `filterPatterns` pass-through** throws `RegExp("*")` per tool and fails the whole server, debug-only visible — the plan's risk 5 is real and must stay a pinned test, not a mitigation note. *(Mitigation: MUST-3.)*
4. **Lifecycle re-registration on `/new`, `/resume`, `/fork`.** Verified latent bug (per-session init genuinely fixes it: `session_shutdown` → `clearModuleState()` with nothing rebuilding). New hazard: duplicate `registerTool`/`registerCommand` on repeated `session_start` is unpinned pi behavior, and per-session full reconnects add spawn churn; cwd can change across `/resume` so config must be re-derived from `ctx.cwd` each time, never cached.
5. **Migration strands other machines.** Repo-B cleanup without a project-reading fork installed ⇒ zero MCP; only this machine is covered by P5. *(Mitigation: M4 version-gate.)*
6. **User-edit destruction on same-named global entries** during cleanup (shared 5-name snapshot across 8 projects). *(Mitigation: M4 shape-aware removal.)*
7. **Support.json overclaim.** "Same server set as Claude Code" is already false for 2 live projects unless remote mapping lands (D1a condition); "headless-safe" without the trust precondition is the other overclaim direction.

## 3. MUST findings (security hole or lie if wrong)

1. **Trust semantics must be documented as measured:** the fork arms project servers iff pi's project-trust resolution for `ctx.cwd` is true at `session_start`; scaffolded projects without pi-trust-requiring resources resolve true **in all modes including headless** (pi dist: `trust-manager.js` resource list excludes `.mcp.json`/`.ai-badger/`/`.pi/agents/`; `main.js` short-circuit `!hasTrustRequiringResources → true`). The gate bites only when `.pi/{settings.json,extensions,skills,prompts,themes,SYSTEM.md,APPEND_SYSTEM.md}` or ancestor `.agents/skills` exists, or a saved `false` decision exists. Tests must pin BOTH cases (minimal scaffolded project `-p` ⇒ arms; project with `.pi/settings.json`, no trust.json, `-p` ⇒ global-only). Writing/docs/tests claiming "headless arms nothing until /trust" is a lie-by-documentation that P5's smoke test would silently validate against the wrong model.
2. **`/mcp-status` must reveal config source per server** (`project:.mcp.json` / `global settings` / `skipped:unsupported-shape` / `untrusted-project`) plus a count of skipped entries, and the `session_start` notify strings must name the merged source. Without this, D1a's divergence is invisible by construction.
3. **`tools:["*"]` and empty `tools` must map to "no filtering"** — never to `filterPatterns` (verified `SyntaxError` path); glob-ish hand edits translate to regex; every `RegExp` construction try/caught with skip-and-warn; per-server failure must be visible without `--mcp-debug` once it can be caused by a scaffold-generated file.
4. **Support.json `mcpServers` row must say:** fork reads project `.mcp.json` at `session_start`, converted claude→fork format; gated by pi project trust (scaffolded projects without pi-trust-requiring resources arm in all modes); **local stdio entries — plus remote only if Q4 lands**; global `mcp` key is user-owned fallback, no longer scaffold-written. **Lies:** "same servers as Claude Code" (unqualified), "the scaffold merges into settings.json", "headless-safe" without the trust sentence. The `skills` row must name `resources_discover` + ungated + the ADR-recorded asymmetry; "trust-gated" there would be a lie.
5. **M4 removal must be shape-aware and version-gated** — never delete a same-named entry whose shape the scaffold doesn't recognize as its own; never remove global entries while the installed fork predates `.mcp.json` reading (warn instead). Otherwise migration is a user-config destroyer (risk 6) or an MCP-eraser (risk 5) on machines P5 never touches.
6. **ADR-0023 must record the skills asymmetry honestly** (D2a condition wording), and additionally: a `project_trust` auto-trust handler would fire **only** for projects that already have trust-requiring resources (`main.js:574` gate) — dead code for minimal scaffolded projects — so Q1-(ii) must not be described as "headless parity immediately."
7. **ADR-0022 boundary holds — record why.** Nothing in M1–M4 needs manifest `pi` keys or static registration: `.mcp.json` is read at event time exactly like `hooks.json` (dynamic arming), `registerTool` in `session_start` is pi's documented dynamic path, and `.mcp.json` already exists as a scaffold artifact. ADR-0023 extends the principle rather than amending it.

## 4. Owner-gate questions (verbatim, each with recommendation)

**Q1′ (rewritten — replaces the plan's Q1, whose premise is false).** *Pi's measured behavior (verified in dist source, live machine): scaffolded ai-badger projects contain no pi-trust-requiring resources, so `ctx.isProjectTrusted()` is true in every mode including headless `-p`, and the fork's gate passes on day one — until someone adds `.pi/settings.json` or an ancestor `.agents/skills`, at which point headless arming silently stops (no trust.json, `defaultProjectTrust:"ask"`). Keep the `isProjectTrusted()`-only gate with this corrected semantics (recommended), add an adapter `project_trust` auto-trust for the now-narrow fragile case, or write `~/.pi/agent/trust.json` at scaffold time (schema now known from source — `{ "<canonicalPath>": true|false }` with nearest-parent lookup — but only effective for projects that carry trust-requiring resources, and unversioned)?* **Recommendation: keep (i) with corrected docs/tests; make the post-scaffold note informational, not a parity prerequisite; revisit only if the fragile-case UX bites.**

**Q2 (skills gating asymmetry — plan's Q2 stands, rationale must be rewritten).** *Should the adapter's `resources_discover` skills contribution be unconditional, or gated on `ctx.isProjectTrusted()` like pi gates its own `.pi/skills` and `.agents/skills`? Unconditional preserves headless behavior and claude parity but is a deliberate divergence from pi's own classification of project skills; the honest calibration is that the adapter already executes project-declared hook shell commands ungated, so gating skills would be security theater within the ai-badger stack.* **Recommendation: unconditional, with the ADR recording divergence-from-pi + hooks-precedent (not the subagent precedent, which matches pi's classification for `.pi/agents` and proves nothing about skills).**

**Q3a (migration end state — plan's Q3a stands with two new conditions).** *Repurpose `adjust_mcp.py`/`adjust_skills.py` as migration-only removers (removing exactly their own previously-written entries, `--no-install` printing the removal proposal), or delete outright with a documented manual cleanup? If repurposed: accept shape-aware removal (skip-and-warn on same-named entries that don't match the generated shape) and version-gating on the installed fork?* **Recommendation: repurpose, with both conditions; shape-awareness is what makes "atomic, idempotent, unknown-key-preserving" true for values, not just keys.**

**Q3b (`mcpDisabledTools` residual — plan's Q3b stands).** *Keep `mcpDisabledTools` global (toggles from project A apply in project B), and accept that the fork's `saveDisabledTools` is a non-atomic read-modify-write that can race a scaffold's atomic `os.replace`?* **Recommendation: accept the scoping; optionally have P1 make `saveDisabledTools` atomic as a drive-by (same temp+replace pattern), since the fork is already being restructured.**

**Q4 (new — forced by measured live state).** *Two scaffolded projects on this machine (`ai-raccoon`, `job-search-ai-assistant`) declare a remote `rider` server (`type:"http"` + `url`) in `.mcp.json`; claude arms it, and the fork already ships streamable-HTTP/SSE transports. Should the converter map `type:"http"/"sse" → type:"remote"` (full parity, small mapping), or skip remote shapes with a warning (plan's current choice, partial parity for those projects)?* **Recommendation: map it — the skip costs real parity in real projects for ~10 lines, and without it the support.json row cannot honestly say "same server set as Claude Code".**
