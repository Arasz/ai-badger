## Q2 — Are the P2 summary-field tests vacuous-pass-proof? What's missing

## Q3 — The wrap-guard test (C4/P2.2): the exact red-first scenario

**First, the honesty correction (QA-2):** `messages.id` is `INTEGER PRIMARY KEY AUTOINCREMENT` (`badger_store.py:58`, engine copy line 58 identical). SQLite's `AUTOINCREMENT` forbids rowid reuse for the lifetime of the DB file — after a full prune, the next insert takes `max_ever + 1`, never a reused low id. C4's stated motivation ("rowid reuse after full prune + tick-refreshed cursor ts → `id > cursor` silently skips reused ids") **cannot occur through the store's own writes**. The guard still earns its place, but for a different state: *cursor survives while the messages table is rebuilt below it* (DB replacement/partial restore — the api-engineer's own R2(a) recovery-runbook delete). The plan text must say that, or the test gets written against a mechanism that cannot happen and the real one goes unprobed.

**Can it be written without simulating rowid reuse by hand? Yes — it must be, and it can,** because the guard's observable is the invariant `cursor_id > COALESCE(MAX(id),0)`, not the mechanism that produced it. Concrete red-first scenario using the file's existing machinery (`frozen_clock`, `_seed_message`, `_cursor_row`):

1. Seed 3 messages; `deliver_for_session("S", "P")` → cursor lands at id 3 (normal caught-up state).
2. Simulate the *rebuilt-messages* state exactly: `DELETE FROM messages; DELETE FROM sqlite_sequence WHERE name='messages';` then insert 2 fresh rows — they take ids 1, 2. (Resetting the sequence is byte-equivalent to "the DB was replaced and the cursors row survived"; no hand-invented rowids, every id is one SQLite would really mint.)
3. **RED (pre-guard):** `deliver_for_session("S", "P")` returns `[]` — ids 1, 2 sit ≤ cursor 3 and are unreadable *forever* (the tick-refreshed cursor ts means the row never prunes). Post-guard: returns both rows, cursor lands at 2, and the summary counts the re-delivered batch.
4. **Boundary companion (strict `>`):** `cursor == MAX(id)` is the *healthy caught-up* state — already asserted at `tests/test_message_bus_store.py:741-742` — and must **not** reset. Mutation: guard flipped to `>=` → that existing test goes red. This is also the honest residual (see Q6): after a replacement, ids climbing back to exactly the cursor are indistinguishable from caught-up without an epoch — record it, don't claim it healed.
5. **Post-reset read path (needs a plan sentence — fold into this MUST):** the consolidated P2 dropped the architect's "the gate re-applies on that read." Specify: reset-to-0 routes the read through the *gated* path (30-min window + cap + leg-scoped landing), not a live `id > 0` — otherwise the reset can resurrect old mail, and B7 pins whichever the plan picks.
6. **Composition pin (SHOULD):** under the armed timer, C1's fail-open prefilter manufactures the healing spawn (MAX changed in the empty state ⇒ tick spawns ⇒ guard runs *before* new mail arrives). One test: empty-table state + timer tick ⇒ the guard ran (cursor reset observable in the seeded DB). Under wake=off the seams still heal the `cursor > MAX` case on their next spawn — same test, seam-driven variant.
