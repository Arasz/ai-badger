## Findings

### F1 — MUST — the helper's order contract is unspecified, and the only order any lane wrote down ("Sorted.") empirically breaks the guard on healthy trees

The architect's helper docstring (moe-architect §3.1) ends "**Sorted.**" and the plan's D1 describes the set with union/minus language only — no order. But the guard's re-scaffold argv becomes the **delivery order** (`offered = dict.fromkeys(argv + asked_for)`; under explicit argv every name is already present, so delivery order == argv order — scaffold.py L270, skill_delivery.py L255–267), and manifest skill rows are recorded in delivery order — V6 shows the committed manifest is in **block order**, not flat-sorted. `normalized()` preserves list order (V5, guard L182–203). Therefore a flat-sorted helper makes the re-scaffolded `.ai-badger/manifest.json` differ from the committed one in row order → `same_content` False → "content differs" finding (verdict: UNCLASSIFIED via `owning_entry`, guard L217/250) → **the guard FAILS a healthy tree**, and because the pre-commit hook is `always_run` (V14) it blocks this task's own Package 4–6 commits; re-scaffolding with default argv rewrites block order, so the mismatch is self-perpetuating, not a one-time regen.

**Required change (plan text):** D1 must pin the helper's return order to `Scaffolder`'s delivery order — `sorted(default_skills_in(common))` then `sorted(include-derived ∩ addable)` then stack-local appended in `resolve_stacks(config)` order (`stack_local_skills` sorted within each stack) — minus exclusions throughout; and must correct the architect doc's "Sorted." wording. The order is *observable contract*, not cosmetic.

### F2 — MUST — D1's "Scaffolder.__init__ refactored to call the same helper" does not specify the refactor shape, and the naive shape silently changes a consumer-visible contract that no named test catches

`__init__` receives the argv `skills` list; the helper is `(root, config)`-only. If the refactor computes the **full** expected set and does `offered = dict.fromkeys(list(skills) + expected)`, then an explicit narrow argv (`--skills task`) silently **gains the catalog defaults** (today: argv *replaces* the default — scaffold.py L774/L806; the usage doc L10 advertises `[--skills task,prompt-markers]`, and V10 shows a test exercising narrow argv). The plan's chosen net — full suite green — cannot catch this: `test_install_plugins.py:359–371` asserts printed plugin commands (stack-plugin derived, unchanged by extra skills), and `test_stack_skill_discovery.py` asserts stack-local delivery, not default-absence. Delivery-set order also changes for recovery runs (harmless only by the argv-first dedupe accident).

**Required change (plan text):** D1 must state the split: `Scaffolder.__init__` consumes **only the include-derived part** (aliases → expand groups → alias-map → sort → ∩ addable), keeping `offered = dict.fromkeys(list(skills) + asked_for)` verbatim (L268–270); the full expected set is for the guard. Add one pin test: narrow argv delivers no scope-default skill.

### F3 — SHOULD — D3's `manifested` pseudocode comment is factually wrong, and the extra manifest read it hides is unspecified

Architect §2.6: `manifested = scaffolded_skill_names(target manifest)  # already read for recovery`. False: the validation block runs exactly when `skills` is non-empty (artifacts/unknown checks precede or replace nothing of the recovery branch, which is `if not skills:` — scaffold.py L806–808), so the manifest has **not** been read on this path; `main()` must add a read of `target/.ai-badger/manifest.json` (L811 shows the derivation) with the same absent/corrupt tolerance the recovery branch has (L812–821). Semantics are fine — absent manifest ⇒ `manifested = []`, catalog covers fresh scaffolds; and for the guard's re-scaffold the target manifest is the throwaway copy's faithful copy of the audited one (V7), so the manifest-known escape hatch uses the right manifest. But the plan text should correct the comment and state the new read, or an implementer will "optimize" it into the recovery branch where it never executes.

### F4 — SHOULD — D2's fail-fast mechanism is underspecified where it meets the guard's exit-code model, and the config parse is a new failure mode

`collect()` communicates via return values (findings → `check()` prints → exit 1) and `Refusal` (→ exit 2, guard L275–301, L321–336, main). The plan's narrowing message ("records N of the M skills … lists missing + counts") is multi-line prose that does not fit `Finding.line()`'s one-row shape — so D2 needs either a distinct exception caught in `main()` returning 1, or synthetic findings. AC2 asserts `returncode == 1` **and** `!= 2` (test-engineer §1-AC2), so the mechanism must be pinned or the RED→GREEN gate is ambiguous. Related, same site: `collect()` today only checks `CONFIG` exists (guard L280–282) — D2 makes it *parse* config.json, and an unparseable config must become a Refusal (exit 2), not a traceback. Also in scope of the docstring rewrites (reviewer risk #13 names only builder L129 and `remediation()` L135–137): the **module docstring** (guard L1–17, "The check is a reproduction, not a comparison of recorded hashes … every resulting difference is a finding") is now inaccurate — a narrowing fails *before* any reproduction.

### F5 — SHOULD — the helper's composition, as described, omits three inputs that change the set on real configs

(a) **Stack list**: stack-local discovery iterates `resolve_stacks(config)` (badger_lib L958–968) where `commonStacks` is config-overridable, while the skip-set is the **constant** `DEFAULT_COMMON_STACKS = ["common"]` (L955; skill_delivery L261) — a config with `commonStacks: ["web"]` gets `features/web/skills/` discovered as stack-local. The architect's primitive list (§3.1) cites `stack_local_skills` but not `resolve_stacks`; an implementer who "fixes" the constant/config mismatch changes the set. (b) **Exclusions are alias-mapped** (`exclusions(config, aliases)`, badger_lib L98–101) and applied at two points (offered filter scaffold.py L279; stack-local append skill_delivery L266) — "− exclusions" must mean the alias-mapped set, everywhere. (c) **Expand-before-alias order is load-bearing** (scaffold.py L268): alias-mapping before `expand_skill_groups` would break a group name that is also an alias, and vice-versa for member names in groups. Pin all three in D1's composition sentence. (Verification note: on this repo today derived-set == manifest's 32 rows holds under the correct composition — my recomputation of defaults/asked_for/stack-local reproduced the manifest set exactly, V6.)

### F6 — SHOULD — the changelog's upgrade notes omit the scaffolder-side argv contract change, which is consumer-visible

The scaffolder ships to consumers as mirrors (`.ai-badger/skills/welcome-ai-badger/scripts/scaffold.py` and the host-level `skills/welcome-ai-badger/scripts/scaffold.py` both exist in-repo), so D3's exit-2-on-garbage/unknown is a **consumer CLI contract change**, not just framework hygiene. Today: garbage → silent skip note, exit 0; alias-named argv → silent skip (the alias hint path is live — V9, real gateways with absorbed members). Post-fix: exit 2 + named message. D8's changelog bullets cover the guard advice shape, the new "no longer writes it" findings, and the gotchas — add the scaffolder argv validation (consumers scripting narrow/alias argv must update), or 0.150.0's upgrade notes under-document the blast radius.

### F7 — SHOULD — the non-regression inventory misses `tests/test_every_check_can_fail.py`

The file carries its own guard provocation whose fixture `_self_scaffolded_repo` scaffolds with `--skills ""` (V12, L303–320) — it trusts manifest recovery exactly the way `_freshen` does, and it is the meta-suite's witness that this gate can fail. It stays green post-fix (fixture manifest is the healthy committed one), but the plan's untouched-green lists (Package 4; test-engineer §4) name only the guard file's 13 tests and `test_scaffold_empty_skills.py`. Name it — and note that D2 adds a *second* failure path to a gate whose meta-suite charter is per-gate failure witnessing; adding a narrowing provocation there is cheap symmetry, though AC2 already covers the behavior.

### F8 — MAY — the companion test doc's mechanism-tier snippets are stale against the decided signatures

Test-engineer §1-AC4 calls `rescaffold_argv(sys.executable, guard.SCAFFOLD, guard.CONFIG, ".", ".")` (5 args) and no-arg `guard.remediation()`; D1/Package 4 thread `expected` through the builder (6 args) and `remediation()` needs `expected` (or root) too — today's no-arg signature (guard L135–137) cannot render the new argv. Blast radius is contained (V8: guard-internal only; consumer_journey imports other helpers), and the implementation lane writes the tests, so nothing breaks — but the plan should state the new signatures so AC4's mechanism tier is written against them, and so `rescaffold(work)` keeps its harness-visible signature (computing `expected` from `work`'s own config — a faithful copy of root's, so the one-oracle property holds).

### F9 — MAY — D2's message overclaims delivery when index.json is stale

The helper's name-walks are filesystem-based (`default_skills_in`/`opt_in_skills_in`/`stack_local_skills`) but delivery resolves through **index.json** (`find_skill_in_stacks`, badger_lib L938–946). On an index-stale tree the fail-fast firing is *correct* (staleness is the guard's charter — the 0.147.0 incident was exactly this), but the message's "re-scaffolding would deliver the missing: …" is then false (delivery silently skips, skill_delivery L276–280). Hedge the wording or name the index as a possible cause.

### F10 — MAY — the superset story's finding shape is "content differs on manifest.json" more often than "no longer writes it"

For a config-include-dropped skill (not declined, source present, stack configured), SupersededPrune does **not** delete the mirror — its only reasons are declined / stack-left / source-gone, and declined dirs are explicitly kept (V13, superseded_prune.py L1–40). The re-scaffold therefore rewrites manifest.json without the row (finding: "content differs", UNCLASSIFIED verdict) while the mirror path itself is silent. For catalog-*dropped* skills (source gone) the promised per-path "no longer writes it" does occur. Changelog's "intended new findings" note (D8) should describe both shapes so the one-time diff is not misread.

### F11 — MAY — exit-code 2 collision with argparse is acceptable; close open question 2

Argparse exits 2 on unknown flags; D3's refusal also exits 2. Both are argv-contract errors with named output — the collision costs only that scripts must match on message, not code. The chain stays coherent: a scaffolder exit 2 inside the guard's re-scaffold surfaces as `SCAFFOLDER FAILED` Refusal → guard exit 2 (guard L156–159). Recommend answering G0 question 2 with "keep 2, document the collision".

### F12 — MAY — D5's ruling is sound but removes a tripwire; take the cheap replacement

D5 (keep fixture `_freshen` on `--skills ""`, D2 as the canary) is well-argued and correct on the healthy tree (fixture manifest == committed, expected == recorded). But it deletes the only structural check that the fixture is fresh-by-construction; the test-engineer's optional canary (assert the `reused N` note's N equals the manifest's skill-row count, scaffold L816) is two lines and restores the property D5 gives up. Recommend the implementation lane take it despite the wording-coupling caveat.

## Answers to the review brief's specific attacks

1. **Helper composition (D1)** — inputs enumerated in V1–V3, V11 and F5: aliases (gateway manifests across *all* stacks), alias-mapped exclusions, inclusions, opt-in addable gate, expand→alias order, argv-first dedupe, exclusion filter at ctx, config-overridable commonStacks vs constant skip-set, stack-local append conditions. The one input the plan's composition text misses outright: `resolve_stacks` (F5a) — plus the order contract (F1) and the argv-interplay split (F2). Behavior-neutrality of the `__init__` refactor is *achievable* but only under the F2 shape; the test that would catch a wrong shape is the narrow-argv pin (F2) — no existing test does.
2. **Argv contract (D3)** — `--skills 'documentation'`: `documentation` is itself a catalog gateway name (V9) → allowed; an absorbed *member* name → refused with alias hint (contract change from silent-skip, F6). Manifest provenance: `main()` reads the **target's** manifest (V7) — for the guard's throwaway copy that is the faithful copy of the audited manifest, so the manifest-known escape hatch keys off the right artifact. `prune_discovery` interplay: refusal paths return before `Scaffolder` is constructed, so no live path's prune behavior changes; only the manifest-absent case flips `bool(skills)` False→True inside the throwaway copy — reviewer risk #11 already names it. Exit 2 vs argparse: F11, acceptable.
3. **Fail-fast placement (D2)** — `collect()` is right (single funnel into `check()`, before the copy+re-scaffold spend). Superset manifests: no fail-fast; the re-scaffold's manifest rewrite surfaces as F10's content-differs finding — intended, needs accurate changelog wording. Manifest absent entirely: `manifest = {}` (guard L287–288) ⇒ recorded = ∅ ⊊ expected ⇒ fail-fast fires with N=0 — verdict (fail) matches what the re-scaffold would produce anyway ("the re-scaffold writes it" findings); message slightly odd for a wholly absent manifest, acceptable.
4. **Contract changes** — `rescaffold_argv`/`remediation` signature changes have no downstream callers beyond the guard and its tests (V8); the one stale artifact is the test doc's snippets (F8).
5. **Invariants** — #129 preserved (empty stays recovery; artifacts/unknown checks only on the non-empty path); consumer repos: `gates/` not shipped (verified `copy_engine_and_schemas`, scaffold.py L569–574) but the *scaffolder* ships (F6); stdlib-only holds (every helper primitive already lives in badger_lib — no new imports); same-commit mirror rule enforced in Packages 5/6; the invariant the plan doesn't name: the guard's own charter docstring (F4) and the meta-suite file (F7).
