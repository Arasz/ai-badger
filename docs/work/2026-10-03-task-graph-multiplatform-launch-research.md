# Research: a task-graph launch that starts from any subdirectory, on every OS, without sh or git

**Date:** 2026-10-03
**Question:** How can ai-badger declare the `task-graph` MCP server so that it starts correctly when the host session begins in any subdirectory of the project, on macOS, Linux and native Windows, with no dependency on `sh` or `git`, relying only on `uv`?

## Answer

Let `uv` supply a Python interpreter and put a stdlib walk-up in a `-c` string. Every host
then generates the same entry:

```json
{
  "command": "uv",
  "args": [
    "run", "--no-project", "python", "-c",
    "import os,sys,subprocess;from pathlib import Path;r='.ai-badger/skills/task-decomposition/scripts/task_graph_server.py';c=Path.cwd();f=next((d/r for d in (c,*c.parents) if (d/r).is_file()),None);f or sys.exit('task-graph: '+r+' not found at or above '+str(c));sys.exit(subprocess.call([os.environ.get('UV','uv'),'run','--script',str(f)]))"
  ]
}
```

The `-c` string contains no `"`, `\`, `%`, `^`, `&`, `|`, `<`, `>` or `!`. It survives JSON,
POSIX `execve`, the MSVCRT command-line rules, and even a `cmd.exe` pass. It uses no `os.exec*`,
so the macOS and Linux runs exercise the same code path Windows takes. A relative `cwd` field
does not work on any host (F3 to F5), and uv has no upward script lookup (F7), so this is the
only candidate that needs no new file, no per-machine install and no host feature.

Grade mix: 10 MEASURED, 5 READ, 4 INFERRED, 3 UNVERIFIED. Everything on macOS was measured.
Nothing on Windows was. The Windows claims rest on documented quoting rules and spawn code,
not on a run.

## Findings

### F1 — The baseline relative launch fails from any subdirectory, git or not [MEASURED]

`uv run --script .ai-badger/.../task_graph_server.py` resolves the path against the spawn cwd.
From `vcsproj/a/b` uv's Python reports `can't open file '$SP/vcsproj/a/b/.ai-badger/skills/task-decomposition/scripts/task_graph_server.py': [Errno 2] No such file or directory`
and exits 2. The MCP SDK client then reports `MCP error -32000: Connection closed`.

**Evidence:** macOS 27 (Darwin, arm64), uv 0.12.5, node 26.10, MCP TypeScript SDK 1.29.0
`StdioClientTransport` driven by `$SP/mcp_probe.mjs` (`Client.connect` + `listTools` + `close`),
run from `$SP/vcsproj` (a `git init` repo), `$SP/vcsproj/a/b` and `$SP/plainproj/a/b/c` (no git).
The baseline connected at root and failed in both subdirectories. `$SP` is this session's scratchpad.

### F2 — The walk-up `-c` launch connects from root, git subdirectories, non-git subdirectories, paths with spaces and non-ASCII, and a consumer Python project [MEASURED]

Through the SDK transport the winner connected from `vcsproj`, `vcsproj/a/b`, `plainproj/a/b/c`,
`pyproj2/src/pkg` (a directory under a consumer `pyproject.toml`) and `spaced dir ü/proj/a b`.
The stub logged the cwd as the session directory and `__file__` as the project-root script.
The real `task_graph_server.py`, copied into `$SP/realproj` with a `.ai-badger/config.json`
marker, answered from `realproj/deep/er` with `OK server=task-graph tools=12 ready_ms=480`.
From a directory with no project above it, the launcher prints
`task-graph: .ai-badger/skills/task-decomposition/scripts/task_graph_server.py not found at or above $SP/nowhere`
on stderr and exits 1, which the host reports as a failed server.

**Evidence:** same machine and harness as F1, servers `winner` and `walkup` in
`$SP/cand.json` generated by `$SP/make_configs.py`, runs via `$SP/run_probes.sh`.

### F3 — Claude Code 2.1.288 ignores `cwd` on stdio servers, relative or absolute [MEASURED]

The session ran in `vcsproj/a/b` and `.mcp.json` sat at the repo root. A server with
`"cwd": "."` failed. So did one with `"cwd": "<absolute vcsproj path>"`. Both stubs either
never started or started in `vcsproj/a/b`. The same held for a `--mcp-config` file with
`"cwd": ".."` and with an absolute `cwd`: the stub logged `cwd=$SP/vcsproj/a/b` both times. The
walk-up entry in the same file reported `connected`.

**Evidence:** `CLAUDE_CONFIG_DIR=$SP/claudecfg claude -p "/mcp" --output-format stream-json --verbose`
(`$SP/claude_probe.sh`), which reads the `system/init` event's `mcp_servers[].status`. The
`/mcp` command in print mode makes no model call. Output from `vcsproj/a/b`:
`baseline -> failed`, `walkup -> connected`, `cwd_dot -> failed`, `cwd_abs -> failed`.

### F4 — Claude Code finds the root `.mcp.json` from a subdirectory in a non-git tree too [MEASURED]

From `plainproj/a/b/c`, with no `.git` anywhere above it, Claude Code loaded
`plainproj/.mcp.json`. The winner reported `connected` and the stub's `file` was
`$SP/plainproj/.ai-badger/...`. So the subdirectory problem is real for Claude in both layouts,
and the walk-up fixes both.

**Evidence:** `$SP/claude_probe.sh plainproj/a/b/c`. Output: `server task-graph -> connected`,
`stub launched: cwd= $SP/plainproj/a/b/c file= $SP/plainproj/.ai-badger/skills/task-decomposition/scripts/task_graph_server.py`.

### F5 — Copilot CLI 1.0.91 honours an absolute `cwd`, resolves a relative one against the session directory, and finds `.mcp.json` upward only inside a git repo [MEASURED]

From `vcsproj/a/b`, `cwd_abs` connected with the stub at `cwd=$SP/vcsproj`. `cwd_dot` and the
baseline exited 2 (`MCP server process exited before completing the MCP initialize handshake (exit code 2)`).
The winner connected (`rmcp::service Service initialized as client`). From `plainproj/a/b/c`
the discovered server set was empty (`"signature":"{\"servers\":[],...}"`), so in a non-git
subdirectory Copilot declares nothing and the launch form cannot matter. An absolute `cwd`
cannot be committed portably (0.51.0 changelog), so it is no answer.

**Evidence:** `$SP/copilot_probe.sh`: `COPILOT_HOME=$SP/copilothome COPILOT_OFFLINE=true COPILOT_ALLOW_ALL=true COPILOT_PROVIDER_BASE_URL=http://127.0.0.1:9/v1 copilot -p hi --disable-builtin-mcps --log-level debug`,
killed after 25 s. The model endpoint is dead and offline mode is on, so no request was billed.
Server outcomes come from the `rust:copilot_runtime::mcp::native_connector` lines in the debug log.

### F6 — pi reads `.pi/mcp.json` only from the session directory, and resolves `cwd` against it [MEASURED]

`pi mcp list` from `vcsproj` connected all three servers (baseline, walk-up, `cwd: "."`). From
`vcsproj/a/b` it printed `No MCP servers configured`, although the trust entry covers
`vcsproj`. pi never sees the project config from a subdirectory, so the launch form does not
matter there. The source agrees: `loadMcpConfig` reads `join(options.cwd, ".pi", "mcp.json")`
with no walk, and the transport cwd is `resolve(cwd, expandHome(config.cwd ?? "."))`.

**Evidence:** `PI_CODING_AGENT_DIR=$SP/piagent pi mcp list` (`$SP/pi_probe.sh`), pi 1.0.0, with an
isolated `trust.json` that trusts the scratch projects. Source:
`~/.bun/install/global/node_modules/@earendil-works/pi-coding-agent/dist/extensions/mcp/config.js:79-81`
and `.../dist/extensions/mcp/runtime.js:65-67`.

### F7 — uv has no upward search for a script; `--directory` and `--project` take paths relative to cwd [READ]

`uv run --help` (0.12.5) lists `--directory <DIRECTORY>  Change to the given directory prior to running the command`
and `--project <PROJECT>  Discover a project in the given directory`. Project discovery walks
up for `pyproject.toml`, not for an arbitrary script. A consumer project need not have one,
and `.ai-badger/` is never an ancestor of a subdirectory. A relative `--directory ../..` would
hard-code the depth.

**Evidence:** `uv run --help`, lines 55-64 and 210-213 of its output on this machine.

### F8 — Without `--no-project` the outer `uv run` writes a `.venv` and `uv.lock` into a consumer Python project [MEASURED]

From `pyproj/src/pkg`, under a `pyproject.toml` declaring `dependencies = ["six"]`, the
variant without `--no-project` printed `Creating virtual environment at: $SP/pyproj/.venv` and
left `.venv/` and `uv.lock` in the consumer's root. With `--no-project`, a fresh copy
(`pyproj2`) gained neither. The inner `uv run --script` is isolated either way.

**Evidence:** `DIRS=pyproj/src/pkg $SP/run_probes.sh walkup walkup_noflag`, then `ls -a pyproj`.
`walkup` left `.ai-badger pyproject.toml src`. `walkup_noflag` added `.venv uv.lock`.

### F9 — The winner costs about 20 ms more than the baseline and leaves no orphans [MEASURED]

Ready times, five runs each, warm uv cache, through the SDK transport: the baseline at root
took 41, 39, 41, 41, 41 ms. The winner at root took 61, 65, 60, 61, 64 ms, and from `a/b`
64, 63, 61, 62, 64 ms. The real server from a deep subdirectory took 137, 112, 114 ms (three
runs). An earlier unwarmed batch ranged from 90 to 420 ms for both shapes, so the cold first
launch dominates any difference. After every SDK, Claude, Copilot and pi run,
`pgrep -f 'scratchpad/.*task_graph_server'` counted 0.

**Evidence:** `$SP/timing.sh vcsproj 5 baseline winner`, `$SP/timing.sh vcsproj/a/b 5 winner`,
`$SP/timing.sh realproj/deep/er 3 winner`, on the same Mac with other agent sessions running.

### F10 — The process tree is uv, python, uv, server (about 84 MB RSS), and closing stdin tears it down in about 18 ms [MEASURED]

`$SP/tree_rss.py winner-shape` (the `walkup_call` entry, identical code) showed four
processes: outer `uv` 19.2 MB, `python -c` 19.8 MB, inner `uv` 21.0 MB, server 24.5 MB. The
`os.execvp` variant drops the python layer, which leaves three processes and about 65 MB.
Closing stdin made the top process exit with code 0 after 18 ms (exec variant 17 ms). The
cost of the single code path is one idle 20 MB Python per session.

**Evidence:** `python3 $SP/tree_rss.py walkup` and `python3 $SP/tree_rss.py walkup_call`, `ps -axo pid=,ppid=,rss=,command=` three seconds after spawn.

### F11 — The winner connects in all three real hosts wherever the host loads the config [MEASURED]

Claude Code: `connected` from `vcsproj`, `vcsproj/a/b` and `plainproj/a/b/c`. Copilot CLI:
`Service initialized as client` from `vcsproj/a/b`. pi: `task-graph: connected` from
`vcsproj`. The generated files held only the winner entry (`.mcp.json`, `.github/mcp.json`,
`.pi/mcp.json`, written by `$SP/make_configs.py`).

**Evidence:** `$SP/claude_probe.sh` (three dirs), `$SP/copilot_probe.sh vcsproj/a/b win1`, `$SP/pi_probe.sh vcsproj`.

### F12 — The MCP SDK stdio transport spawns without a shell, resolves `cwd` with Node semantics and inherits a fixed env allowlist [READ]

`StdioClientTransport.start` calls `cross-spawn` with `shell: false`,
`windowsHide: process.platform === 'win32'` and `cwd: this._serverParams.cwd`. A relative
`cwd` therefore resolves against the host process directory. The default environment on
Windows is `APPDATA, HOMEDRIVE, HOMEPATH, LOCALAPPDATA, PATH, PROCESSOR_ARCHITECTURE, SYSTEMDRIVE, SYSTEMROOT, TEMP, USERNAME, USERPROFILE, PROGRAMFILES`.
`PATH` is inherited, so a bare `uv` resolves. `close()` ends stdin, waits 2 s, then sends
SIGTERM, then SIGKILL. The `UV` variable the launcher reads is set by the outer uv itself,
not inherited from the host.

**Evidence:** `@modelcontextprotocol/sdk` 1.29.0, `dist/esm/client/stdio.js:1,8-24,65-75,147-164`
(copy under `~/Library/Application Support/Code/agent-host/sdk-cache/claude/0.3.220/`).

### F13 — uv exports its own path as `UV` to every subprocess [READ]

"UV: added in 0.6.0. The path to the binary that was used to invoke uv. This is propagated
to all subprocesses spawned by uv." The probe confirmed it on this machine:
`"UV": "~/.local/bin/uv"` in every stub launch. So the inner call reuses the outer binary
even when the host found `uv` by an absolute or `${HOME}` path that is not on `PATH`.

**Evidence:** https://docs.astral.sh/uv/reference/environment/ (entry `UV`). The probe facts are in `$SP/probe.log`.

### F14 — The `-c` string round-trips the Windows command-line rules unchanged [INFERRED]

Under the MSVCRT rules only `"` and a backslash run before a `"` are special inside an
argument. A quoted argument without them parses back to itself. The string has neither, which
`make_configs.py` asserts. That holds for each hop: Node or Rust building the command line for
`uv.exe`, then uv (Rust `std::process::Command`) building one for `python.exe`. It also contains
none of cmd.exe's metacharacters, so it survives the case where cross-spawn routes through
`cmd.exe` because `uv` resolved to a `.cmd` shim. This reasons from the rules quoted in the
`subprocess` docs ("Converting an argument sequence to a string on Windows") and the
character assertion. It was not run on Windows.

### F15 — On Windows the child inherits the host's stdio pipes through `subprocess.call` [INFERRED]

`subprocess.call` with no `stdin`/`stdout`/`stderr` performs "no redirection", so the child
gets the parent's standard handles. That is the same mechanism `uv run` uses on Windows to hand
stdio to Python, and `uv run --script` MCP servers already work there. Avoiding `os.execvp`
matters because Windows has no in-place exec: the host would watch a process that exits while
a detached successor holds its pipes. That last point is UNVERIFIED here (see F21). The
winner sidesteps it by never calling exec.

### F16 — Windows teardown relies on stdin EOF, which the real server honours [INFERRED]

The SDK on Windows ends stdin and then `kill`s only the top process, while pi runs
`taskkill /pid <pid> /T /F` over the whole tree
(`@earendil-works/pi-mcp/dist/transports/stdio.js:15-22`). Once the host's write end closes,
the server's `for raw in source:` loop
(`.ai-badger/skills/task-decomposition/scripts/task_graph_server.py:1291-1310`) ends and the
chain unwinds: inner uv exits, `subprocess.call` returns, python exits. On POSIX this was
measured in about 18 ms (F10). On Windows it is reasoned from that code, not run.

### F17 — `pin_cwd` is dead because no portable `cwd` exists and Claude never honoured it [READ]

`.mcp.json` once pinned `cwd` to the checkout. That broke for clones and worktrees
(`docs/changelog/0.32.0-defects-found-by-a-real-refresh.md:31-40`,
`docs/changelog/0.51.0-mcp-json-stops-shipping.md:22-30`). Commit `2eada6a8` (#288) set
`pin_cwd=False` on every destination. The column and `_carry_live_cwd` remain
(`features/common/skills/welcome-ai-badger/scripts/mcp_tools.py:129,147-170,494-495,551-566,594`)
but never fire. F3 shows Claude Code would ignore the field anyway.

**Evidence:** `git log -S "pin_cwd=True" -- features/common/skills/welcome-ai-badger/scripts/mcp_tools.py` gives `2eada6a8` and `dec4844c`, plus the cited lines.

### F18 — The generator cannot emit the winner today without a schema change or four overrides [READ]

A top-level server declaration has `command` (split on whitespace) and no `args`
(`schemas/stack-mcp.schema.json:16-28`, `additionalProperties: false`). `split_on_whitespace`
would shred the `-c` string (`mcp_tools.py:108-118`). `_render_entry` already passes an `args`
array through unsplit when the resolved server carries one (`mcp_tools.py:486-493`), but only
`agentOverrides.<agent>` may supply `args` (`schema:57-80`). The smallest change is to allow
`args` on the server item. The alternative is one identical override each for `claude`,
`copilot` and `pi`, which would be the same list maintained three times.

**Evidence:** cited lines in this worktree at `60dfcbd8`.

### F19 — Rendered per host file, the winner differs only in how `command` is spelled [INFERRED]

`.mcp.json` (Claude + Copilot): `"command": "${HOME}/.local/bin/uv"` where the scaffolding
machine has uv in `~/.local/bin`, otherwise `"uv"`. `.github/mcp.json`: `"command": "uv"`
plus `"tools": ["*"]`. `.pi/mcp.json`: `"command": "~/.local/bin/uv"` or `"uv"`, plus
`"exposure": "direct"`. All three carry the identical `args`. Hermes `~/.hermes/config.yaml`
(operator-written) takes the same `command`/`args`. This comes from the `home_prefix`,
`all_tools` and `exposure` columns (`mcp_tools.py:147-170`) and `_home_relative_command`
(`mcp_tools.py:504-540`) applied to the F18 declaration. The generator was not run with
the new declaration.

### F20 — Windows execution of the winner was not run [UNVERIFIED]

No Windows machine was available, and a CI runner would need a push, which this task
forbids. A `windows-latest` job that runs `$SP/mcp_probe.mjs` against the winner from a
subdirectory would settle F14, F15 and F16 in one go.

### F21 — `os.execvp` on Windows breaks the host's process handle [UNVERIFIED]

This is the widely reported behaviour (the exec'd image runs as a new process and the caller
exits). It was not checked here, and the recommended launcher does not depend on it.

### F22 — Claude Code's own bundled transport matches the SDK file read in F12 [UNVERIFIED]

Claude Code ships as a compiled binary. F12 reads the SDK copy cached by the VS Code Claude
agent host, not the code inside `claude` 2.1.288. Its measured behaviour (F3, F4, F11) is
what this record relies on for Claude.

## Still open

- Windows (F20). One `windows-latest` CI job that spawns the winner through the MCP SDK from a
  subdirectory, then closes it and checks for leftover `python.exe`/`uv.exe`, settles F14 to F16.
- Linux was not run either. The POSIX path is the same code, so I expect it to behave as on
  macOS, but no Linux measurement exists.
- What should the scaffold do when the session starts in a subdirectory of a nested
  ai-badger project that has no `.mcp.json` of its own? The walk-up picks the nearest script
  while Claude used the outer `.mcp.json`. The server's own store walk (`project_above`) makes
  the same nearest-first choice, so the two agree. Nobody has decided that this is wanted.
- Should the generator's `${HOME}/.local/bin/uv` rewrite in a committed `.mcp.json` stay? It
  is per-machine (F19). A Windows teammate usually has no `HOME` set, and Claude would leave
  `${HOME}` literal. This predates task-graph and sits outside this question, but the winner
  inherits it.
- pi in a subdirectory and Copilot in a non-git subdirectory load no project config at all
  (F5, F6). No launch form fixes that. It needs a host change or an explicit user-scope entry.
- The cold first-launch cost (uv resolving two environments) was seen only as an
  unwarmed 90 to 420 ms spread and was not separated from machine load.

  run 37136797938 passed on the walk-up launch. That upgrades F14 and F15, and EOF teardown
