**Error envelope (RFC 7807 field set, adapted to stdio — no HTTP status line exists).** Tool-domain failure → `isError:true`, `structuredContent = {ok:false, error:{code,title,status,detail,instance,details?,retryable}}` with `status` the HTTP analogue (404, 409, 422, 500). Closed code set: `invalid-arguments` 422, `not-found` 404, `already-exists` 409, `conflict` 409, `invalid-transition` 409 (+`allowed_transitions`), `dependencies-incomplete` 409, `criteria-unmet` 422, `plan-in-progress` 409, `schema-version-unsupported` 422, `prerequisite-missing` 500 (+`remediation`), `config-error` 500, `store-error` 500 (`retryable:true` for `database is locked`). JSON-RPC errors are reserved for protocol failures only: parse −32700, invalid request −32600, method not found −32601, **unknown tool −32602**, internal −32603. Nothing raises through the loop; handlers return the envelope. No long-running operation exists (the Jev advisory is inlined, bounded, and fail-soft), so the `202`+operation-id contract is deliberately not used — stated in the server doc so a future async tool knows the rule.

**All mutations** take `expected_revision`; match → apply + `revision+=1` in one `BEGIN IMMEDIATE`; mismatch → `conflict` with the current revision (caller re-reads, retries once).

**Caller map.** `task-decomposition` (plan time): `plan_create` → `steps_ready` (waves; `advisory:"both"` only when the Jev flags allow) → `plan_export` (review artifact) → `plan_replace` (fold review findings). `task` (execution): `plan_get` on entry, `steps_ready` per wave, `step_start` before each lane dispatch, `step_complete`/`step_fail` after, `ac_check` during verification, `step_skip` for retired steps, `progress_checklist` at checkpoints, `plan_export` at finish. `quick-task`: **no calls** (escalates when >6 bullets). `status-report` caller: `progress_checklist` primary; `status_report.py` keeps its file-parsing fallback and its `packages/checked/total` keys untouched (P3 owns any rename). ## B3 — Forced choice: transport, stack, launch

**Decision: hand-rolled stdio JSON-RPC loop, stdlib-only protocol layer, pydantic as the single third-party runtime dep, `graphlib` for the DAG.** Shipping home: `features/common/skills/task-decomposition/scripts/task_graph_server.py` (a PEP 723 script: `requires-python = ">=3.10"`, `dependencies = ["pydantic>=2.12,<3"]`), launched by `uv run --script <path>`.

- **Counter-argument (SDK)**: the official `mcp` 2.2.0 already pins `pydantic`, gives protocol conformance for free, and has a documented stdio server helper. **Why rejected**: it drags ~15 direct deps (starlette/uvicorn/httpx2/pyjwt[crypto]/opentelemetry-api/python-multipart) — an HTTP stack a stdio server never executes — onto every consumer machine, and its 1.x→2.x churn would couple consumers to SDK versions we cannot test here. FastMCP 4.x is `fastmcp-slim`→`mcp` on top; same objection plus vendor release velocity. **Flip condition**: if a host rejects our `initialize`/`tools/list` handling in the smoke test and the failure is protocol-shape rather than framing, adopt `mcp` 2.x behind the same handler functions (the loop is one module; the handlers don't change).
- **Protocol surface to implement** (exact, testable): NDJSON framing on stdin/stdout (UTF-8, flushed; logs to **stderr only**), methods `initialize` (echo requested `protocolVersion` when ∈ {`2024-11-05`,`2025-03-26`,`2025-06-18`}, else reply the newest; result `{protocolVersion, capabilities:{tools:{listChanged:false}}, serverInfo:{name:"task-graph",version:<VERSION>}}`), `notifications/initialized` (no-op), `ping`, `tools/list` (pydantic-generated `inputSchema` per handler, `annotations{readOnlyHint,idempotentHint,openWorldHint}`: reads read-only, all writes idempotent, `openWorldHint` only for `steps_ready` when advisory enabled), `tools/call` (unknown tool → −32602; handler errors → envelope), and ignore `notifications/cancelled`.
- **Graph base**: stdlib `graphlib.TopologicalSorter` + adjacency in the pydantic model. Counter-argument: networkx 3.4.2 is zero-transitive, but copy-pins `>=3.4.2` picks 3.4.2 on 3.10, 3.6 on 3.11, 3.7 on 3.12+ — a second consumer prereq and a version-resolution surface for algorithms we don't use. **Flip condition**: first need for longest-path/critical-path or transitive reduction, or if P1's D1 owner makes networkx binding — then add `networkx>=3.4.2` to the PEP 723 header + `dependencies.json` and swap the facade internals only.
- **Store**: the server ships its own byte-identical `badger_store.py` copy and opens the project tracking store via `open_tracking()`; root resolved **at call time** from `AI_BADGER_TRACKING_ROOT`, else derived from `Path(__file__)` (`.ai-badger/skills/task-decomposition/scripts/…` → repo root, four parents) — never cwd, never import time. `SCHEMA_VERSION` 2→3, `_PLANS_DDL` via `UPGRADE_HOOKS[2]` (the `_BUS_DDL` pattern: fresh DBs replay it before stamping, stamped-2 DBs get it from the hook), `FAMILIES["task_plan"]` (born in SQLite, no legacy source), and `Store` accessors `plan_row/plan_upsert` next to `tasks_all` so no second module touches SQL.

## B4 — Jev advisory decision API

**Placement**: inside the server as `features/common/skills/task-decomposition/scripts/jev_client.py` + `jev_choice.py`, called only by `steps_ready` when `advisory != "off"`. Read-only: nothing about the plan is mutated or persisted; proposals are hints the dispatcher may ignore.

**Prompts — R4 §3 and §4 verbatim** (state = `{"step":{id,goal,instructions,acceptance_criteria[],declared_effort,files,verifier}}` for tier; `{"steps":[…],done[],edges[][]}` for wave pairs; one `choice` question per step named `tier` chained per ready step as `<id>_tier`, pairs named `<id_i>_<id_j>`), with these exact adaptations:
- tier instructions: `"Which model tier is sufficient to implement this step as specified? Judge the derivation the step demands, not its size."`; criteria = `{low:"Mechanical, single-file or rename-level change", medium:"Multi-file change needing judgement", high:"Design, debugging, architecture"}` (R4 §3 / `dr-client.ts:49-56`).
- wave instructions: `"Both steps are ready (their dependencies are done). May they run as concurrent lanes in this wave, each in its own worktree?"`; criteria = `{share-wave:"No shared writable external resource …", serialize:"Any shared writable external resource, ordered output contract, or race …"}` (R4 §4 verbatim).
- One fanned-out call when `advisory:"both"`: all tier questions + ≤45 pair questions (`PAIR_CAP=10` ready members; chunk above), `STATE_CHAR_CAP=32000` with deterministic truncation (instructions→1000 chars, then goals only; steps are never dropped), `BATCH_MAX` irrelevant to the endpoint — chunk questions, not options. `ATTEMPTS=2`, `ATTEMPT_SECONDS=8.0`, stage budget ≤15 s, no sleep, Retry-After ignored (parity with `qp.py:169-186`).
- **Gates/fail-safe direction**: tier — propose an **upgrade** only when `choice=="high"` ∧ `confidence ≥ 0.6`; never demote, never override a declared `level`/`model`; any failure → no proposal. Wave — `share-wave` at `confidence ≥ 0.7` adds no serialization; any failure or `serialize` → **serialize** (the safe direction: a wrong serialization costs time; a wrong parallel dispatch corrupts green runs).

**Env surface** (read from the server process only; key only in the `Authorization` header): `OPENROUTER_API_KEY`; master kill `AI_BADGER_JEV=0`; per-capability `AI_BADGER_JEV_TIER=0`, `AI_BADGER_JEV_WAVES=0`; `AI_BADGER_JEV_MODEL` (default `typesafe/jev-1.13`); `AI_BADGER_JEV_ENDPOINT` (default `https://openrouter.ai/api/alpha/decisions`); `AI_BADGER_JEV_TIMEOUT_MS`; test seam `AI_BADGER_JEV_TEST_OPENROUTER_BASE` with the `sk-test-` key + loopback-only rule copied from `client.api_base` (never a silent switch to production). ## B5 — Wire-versioning / compatibility

- `schema_version: 1` is part of the document and a **column** on the `plans` row, so scans need not parse payloads. **Policy: any shape change bumps it** (even additive-optional), because `extra="forbid"` already makes older servers refuse newer docs; the bump makes the refusal legible.
- **Loading a newer doc**: if row/doc `schema_version > SUPPORTED`, the server refuses **before** pydantic with `schema-version-unsupported` `{found, supported:[1], remediation:"upgrade ai-badger, or re-create the plan with this version"}`; the row is not mutated. This applies to `plan_get/export/steps_ready/progress_checklist/mutations` uniformly (the check is in the store adapter, once).
- **Older doc**: `PLAN_UPGRADES: dict[int, Callable[[dict], dict]]` in the model module, applied in memory oldest→newest inside the same read/write transaction; **empty today** (v1 is the first version); no hook for a found version → same `schema-version-unsupported` error, never silent coercion. `revision` (per-plan CAS token) and `schema_version` (format) are distinct and both documented.
- **Unknown fields in a v1 doc** → `invalid-arguments` with pydantic `loc` details (the `extra="forbid"` catch); the server never drops data to force a load.
- MCP tool schemas are **not** versioned — `tools/list` is the discovery contract each session; only the stored document is versioned.
