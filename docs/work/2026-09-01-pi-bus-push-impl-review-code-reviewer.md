## 2. State machine under the named interleavings

- **Generation races:** `busGeneration` increments on every `session_start` and in `disarmBus` (`index.ts:532-543`); `busTick` re-checks `busSession`/`gen` after **every** await (`:480-486, 490-492, 505-510`) and wraps everything in a catch (F7: an uncaught timer throw is fatal). A stale callback can neither touch a dead ctx nor advance the new session's watermark (it holds the old `state` object). A5/A6 tests cover fire-after-shutdown, double shutdown, and rebind.
- **In-flight tick across shutdown:** `session_shutdown` disarms **before** the cleanup spawn (`index.ts:646-649`), bounding the interleave to the already-spawned python process — the ADR records the residual (cursor-row recreation, gate-shaped read, 4-day TTL). Matches CR-N5i.
- **Flag expiry:** a missed `agent_end` cannot strand wake routing (`isIdle` is the authority); a missed compact-close defers ticks at most 10 minutes, and `agent_start` also clears the flag. Both halves tested.
- **Seam-decorator advance rules:** identical `decideTick` + `spawnAndSettle` path for both seams (CR-N4a); a seam spawn advances to **its own** tick capture on marker-free outcomes and never on marked ones (`adapter-bus.test.ts:546-563`); probe-error seam spawns carry no fingerprint ⇒ cannot advance.
- **CR-M3 soundness holds:** any row committed after the tick's probe has `id > watermark.maxId` ⇒ the next probe's MAX differs ⇒ spawn. The one over-approximation cost (an empty spawn for a send committed between probe and spawn-completion) is the accepted direction.
- **Timer/seam concurrency:** `inFlight` is checked before awaits and set only in `spawnAndSettle`, so a tick and a seam can both pass the check and both spawn (NOTE-3). The store's `BEGIN IMMEDIATE` exactly-once txn serializes them — the loser reads the advanced cursor and returns `{}` — so no duplication, no lost mail; worst case one wasted python spawn.
- **Wake-time race:** `sessionIdle` is evaluated **after** the spawn (up to 30 s later), which is the correct point — a session that started a turn mid-spawn gets steer-not-interrupt (C4-consistent), one that went idle gets the wake.

## 4. What the plan review missed (code-revealed)

### SHOULD-1 — ADR-0026 claims a mitigation that does not exist in the code

`docs/adr/0026-pi-bus-delivery-pushes-with-an-in-adapter-poll.md:143-145`: consume-then-lose is "Mitigated by the stale-ctx generation guard and a `nextTurn` compensation retry". There is **no** nextTurn retry: `index.ts:421-427` catches a non-stale `sendMessage` throw and only latches a notice; the watermark has already advanced (`spawnAndSettle`), so that mail is consumed and lost. The guard half is real; the retry half is not. This is the exact class of false ADR fact S1 flagged for the wrap guard. **Fix (2 lines):** either implement the retry (re-send with `{deliverAs:"nextTurn"}` in the catch, before notifying) or reword to "Mitigated only by the stale-ctx generation guard; a non-stale injection failure consumes the mail — residual, observability via the latched notice." Given the sub-millisecond window claimed, rewording is the honest cheap option — but then drop the unmeasured "sub-millisecond" figure too (no probe measured it).

### SHOULD-2 — the advance-side old-hook-copy residual is unrecorded, and C10's promised den-refresh note never landed

C10 implemented the **routing** fallback (missing summary ⇒ wake). But the **advance** rule has an unrecorded gap for the same population: on projects whose vendored `message_delivery_hook.py` predates this release (refreshed only by den-refresh), the old hook's fail-open net prints a bare `{}` — no marker exists in that copy — so `parseDeliveryStdout` reads it as a clean empty read and `advanceAllowed` is true. A persistent hook failure on such a project (the 44/day `OperationalError` class this task diagnoses) silently advances the watermark every ≥60 s and never delivers, with **no notice** (parseable `{}` never latches) — M1's stall, alive exactly where the marker cannot reach, until den-refresh runs. The plan (C10, second sentence) required recording "den-refresh coordination for hook copies alongside the project-id backfill note"; grep finds no such note in ADR-0026 or SKILL.full.md. **Fix:** one ADR residual bullet ("un-refreshed hook copies have no failure marker; a persistent failure there stalls silently — bounded retries every max-skip-staleness, no notice; den-refresh is the coordination") plus the SKILL.full.md coordination line.

### SHOULD-3 — merge-gate flake witnessed: the vendored byte-equality test

My first full-suite run on this exact tree: `1 failed, 5174 passed, 17 skipped` — `tests/test_p4_integration.py::test_scaffolded_consumer_carries_badger_store_copies_verbatim`. The same test passes in isolation (52 s) and my second full run reproduced the claimed `5175 passed, 17 skipped` exactly. Cause not identified (I captured only the tail of run 1, losing the assertion text); the fixture is module-scoped and looks hermetic (own HOME, tmp consumer), so the skew mechanism is unclear — possibly machine-load sensitivity in the scaffold subprocess. A gate that flakes ~1-in-2 local full runs will bite CI. **Fix:** re-run the gate immediately before push (done here: green on run 2); if it recurs, capture with `-x --tb=long` and triage; consider whether the 90 s `communicate` timeouts and the scaffold subprocess deserve a retry or a load-boundary comment.

### NOTE-1 — the probe fails open under bun on a quiescent (cleanly-closed, sidecar-less) DB; production runs Node

Live-verified both runtimes on the same store-created DB: **bun 1.4** `probeUserDb` → `{kind:"error"}` ("unable to open database file") on the cleanly-closed 0600 sidecar-less state; **Node 26.8.1** (the runtime pi actually loads extensions under) → `{kind:"ok"}` with the correct fingerprint, and a write attempt through the read-only open throws (`attempt to write a readonly database`). The A11 fixture cannot catch the bun case because its seed exits via `os._exit`, leaving sidecars present — the comment in `bus-store.ts:96-101` documents this accurately. Consequence is fail-open (always spawn), which is today's behavior; no action needed, but the "runtime note" is Node-specific and worth staying true in any future runtime switch.

### NOTE-2 — the read-only probe leaves `-wal`/`-shm` sidecars behind

Live-verified: after a Node probe of a quiescent DB, `ai-badger.db-wal`/`-shm` remain (a read-only connection cannot remove them on close). This is a directory-level side effect, not a DB write; SQLite recovers cleanly on next open, and the next writer's clean close removes them. QA-9's letter (no user-DB creation) holds; recording one ADR sentence would make the "read-only" claim precise ("read-only against the database file; transient wal-index sidecars").

### NOTE-3 — timer/seam double-spawn window

Both `busTick` and `gatedDelivery` check `state.inFlight` before awaits and set it only inside `spawnAndSettle` — two firings can interleave and both spawn. The store serializes them and the loser gets `{}` (exactly-once holds); cost is one wasted spawn per interleave. If the window ever matters, a second `inFlight` check inside `spawnAndSettle` (return a synthetic empty outcome) closes it.

### NOTE-4 — probes run on unwired projects before the script check

`gatedDelivery` probes (stat + read-only open + aggregates) on **every** seam firing, and the `existsSync` script check lives in `runDelivery` *after* the prefilter — so a project without `.ai-badger/hooks/message_delivery_hook.py` still pays one probe per LLM call (bounded to one probe per 60 s window after the first advance, since the spawn returns a marker-free `{kind:"empty"}`). An `existsSync` short-circuit at the top of `gatedDelivery` would make unwired projects zero-I/O. Not a correctness issue; a cheap follow-up.

### NOTE-5 — per-send cost of the machine scan

`_machine_project_ids` walks the scan root to depth 4 (pruned set, no symlink follow — correctly implemented) on every `--project-id` send; warm-cache cost is tens-to-low-hundreds of ms on a large home. Bounded, documented as a residual (depth misses), and the refusal lists what it found. Acceptable; worth a line in the SKILL if anyone complains about send latency.

## 5. Security / trust

- **The readOnly probe really cannot write:** live-verified — an `INSERT` through `openProbeDb`'s connection throws (`attempt to write a readonly database`); the connection is opened `{readOnly:true}`, used for one SELECT, closed within the probe; pinned by `bus-store.test.ts:180-209` and the A11 real-store contract (`:330-376`). ENOENT probes as `missing` (no DB creation — QA-9, live-verified).
- **No mail content reaches logs:** the hook's stderr prints type+location only; the log line carries the C8-sanitized message (live-verified with a corrupt DB — the message contained no payload substring). The TS side logs spawn errors (script stderr — the hook's own sanitized line) and at most 200 chars of non-JSON stdout into the **session's own UI** (the mail's intended recipient), never into a machine-wide log.
- **No new trust surface:** the probe reads the same user DB the hooks already read, under the user's own account; spawns still target `<cwd>/.ai-badger/hooks/message_delivery_hook.py` with the same env discipline as before; the timer adds no new command source; `AI_BADGER_PI_BUS_WAKE`/`AI_BADGER_PI_BUS_POLL_SECS` degrade safely with one-time notices (tested); the ADR's rejected-alternatives table correctly prices the daemon and TS-port options out.
