# Design review: ai-raccoon-memory skill + memory-grade hook (ai-badger framework)

Date: 2026-08-06 · Reviewer: design-review subagent (diagnose-and-review-hermes-integrations-in-ai-badger)
Scope: `features/common/skills/ai-raccoon-memory/` (SKILL.md, scripts/memory_grade.py, scripts/memory_grade_hook.py), `docs/plans/memory-grade-hook.md`, `features/common/hooks/hooks-manifest.json` + `ai_badger_hooks.py` wiring, the installed copies under `~/.hermes/skills/`, and the companion dogfooding skill `memory-quality-logging`. Operational ground truth (verified live 2026-08-06, see `docs/work/2026-08-06-hermes-integration-diagnosis.md`): the Hermes-side plugin deployment is broken (flat .py drops are invisible to Hermes' directory-plugin loader), the machine-wide quality log holds exactly one synthetic WP7 probe line after a week, and Claude Code is wired but has never invoked `memory_search`.
Review files read; evidence re-verified in this session: framework SKILL.md byte-identical to installed copy (diff clean), `~/.hermes/plugins/` has no `plugin.yaml` and no `__pycache__` for `ai_badger_hooks.py`/`memory_grade.py`, `~/.ai-badger/memory-grade/memory-quality.jsonl` = 1 line ("live probe wp7", usefulness 4), `pending.json` = `{}`, `ai_badger_hooks.py` framework copy = installed copy (diff clean), hooks.json carries the `memory_search` PostToolUse matcher.

## Verdict

The ai-raccoon-memory skill is a compact, well-sequenced agent procedure whose core bet — search the bank before the web, write durable facts with sources, watch the docs — is the right design for its purpose, and its first six sections are among the more actionable skill copy in the framework. The memory-grade hook, by contrast, is a well-engineered mechanism attached to a fundamentally weak measurement, deployed through a transport that never fires on the host that uses it most: after a week of machine-wide enablement it has produced exactly one synthetic line, and the skill's own §8 actively misleads the agent into believing telemetry is being collected. The design review verdict: the skill is 70% of the way there as a memory-usage procedure, and the grade hook is a dogfooding instrument whose cost (two scripts, six test files, three-agent wiring, duplicated documentation across two skills) is currently not repaid by anything it measures. The highest-value fixes are not more hook machinery but: (1) telling the truth in §8 about host coverage, (2) shipping the actual Hermes plugin (which resurrects all four dead Hermes hooks, not just this one), (3) adding host/session attribution to the log line so "no usage" vs "no capture" stops requiring external forensics, and (4) making the 1-5 grade legible as retrieval quality (query class, expected-source, per-source aggregation) instead of a scalar satisfaction score.

## Strengths

1. **Search-first-before-everything is the correct adoption lever, stated as a hard rule.** SKILL.md:33-35 ("Before web search, code search, or asking the user, run `memory_search(project_id, scope=all)`") puts the bank ahead of the two competing information sources an agent will naturally prefer. This is the single behavior that makes the whole feature pay, and it is unambiguous.
2. **Compact, numbered, agent-actionable structure.** 94 lines, eight sections, one ritual per section, a verification checklist (SKILL.md:90-94). No prose padding; every section is a procedure. The watch-on-docs ritual is correctly placed first — ingestion precedes retrieval, and the "only when the watch errors" CLI prerequisite (SKILL.md:25-29) is a good example of conditional-depth documentation.
3. **Write discipline is concrete and conservative.** "Durable facts only, one per entry, source included" (SKILL.md:45), `memory_share` "never automatically" (49), sweep exemption for shared entries (49-50) — these are the right guardrails, and they mirror the server's own `memory-usage-guide` prompt contract (verified in the AiRaccoon surface).
4. **The hook's defensive engineering is exemplary.** Env gate with exact-`"1"` semantics and zero IO when off (memory_grade.py:26-28, 134-135); matcher that normalizes every naming family and never matches other tools (memory_grade.py:31-40, plan:62-67); dual argument spellings read defensively (memory_grade.py:71-72, plan F4:102); grade validation as a guard (memory_grade.py:158-163); hook never raises and never blocks (memory_grade_hook.py:49-53); advisory-only `additionalContext` (memory_grade_hook.py:3-6). This is the commit-reminder discipline applied cleanly.
5. **The grade round-trip is honest by construction.** Line is written at call time with the full result payload; unanswered asks stay `usefulness: null` rather than being fabricated (memory_grade.py:74-75, plan:86); the result payload is never relayed through the prompt (plan:73, 138-139); grade-in-place keeps one-line-per-search (plan:88). The design correctly rejects grading via `memory_write` into the bank (plan:73).
6. **The plan documents its own failure modes and design trade-offs.** The env-vs-bank-settings decision (plan:24), the flood/ask-nag risk with the inject-once mitigation (plan:137), multi-agent transport differences (plan:141), and "measure only when it pays" log-growth deferral (plan:144) are the right risk-thinking. The TDD work-package structure with named gates (WP1-WP7, plan:90-133) is a strong execution scaffold, and the tests it produced (`test_memory_grade_{matching,config,log,roundtrip,helper,claude_hook}.py`) all exist.
7. **The machine-wide log placement is right.** `~/.ai-badger/memory-grade/memory-quality.jsonl` never pollutes a repo's `git status` (plan:69), and the line shape stays compatible with the session's manual log (plan:13) — a rare case of telemetry and working docs sharing a contract.

## Weaknesses

### W1 [SEVERE] SKILL.md §8 documents a hook that cannot fire on the primary host — the skill misleads the agent that telemetry is being collected

`ai-raccoon-memory/SKILL.md:69-88` instructs the agent to enable the hook ("When on, each search appends one line … and the very next turn asks the agent to rate it") with no caveat about host coverage. Verified reality: the Hermes deployment copies flat `.py` files into `~/.hermes/plugins/` (files present — `memory_grade.py`, `ai_badger_hooks.py`, both dated 2026-08-05 21:14), but Hermes' loader only accepts directory plugins (`plugin.yaml` + `__init__.py` with `register(ctx)`) that are additionally opt-in via `plugins.enabled`; there is no `plugin.yaml` anywhere under `~/.hermes/`, no `__pycache__` for either module (proof they were never imported), and `~/.hermes/config.yaml` `plugins:` lists only `disabled:` entries. A live organic `memory_search` in a Hermes session appends nothing to the log (diagnosis doc §3; independently re-verified: log still holds exactly the WP7 line). So on the host used for most sessions, every claim in §8 is false in operation. The companion skill knows this — `memory-quality-logging/SKILL.md:85-98` documents the gap in detail with a diagnostic recipe — which means the two skills **contradict each other** on a fact the agent cannot resolve without reading both. The framework's own changelog repeats the false claim ("All three agents wired", `docs/changelog/0.79.0-memory-grade-hook.md:18-21` — true as manifest declarations, false as runtime behavior). Evidence: SKILL.md:69-88 vs memory-quality-logging/SKILL.md:85-98; `~/.hermes/plugins/` listing; `find ~/.hermes -name plugin.yaml` → empty; diagnosis doc §2-3.

### W2 [SEVERE] The measurement the hook produces cannot drive retrieval improvements

The entire output is a scalar 1-5 "usefulness" per search, self-graded by the searcher in the immediate next turn. What that cannot do:

- **No query-class taxonomy.** Identifier vs path-shaped vs plain-NL queries retrieve through entirely different machinery in this bank (FTS5 `SourcePathQuery` vs vector vs hybrid — the ai-raccoon-pitfalls corpus shows FTS5 has no stemming, bm25 column weights saturate, and length normalization is document-level). A grade without the query class cannot say *which* retrieval path is failing.
- **No expected-source annotation.** A relevant hit at rank 1 and at rank 3 earn the same grade, so recall@k / MRR / rank-of-relevant are not derivable from the log even post-hoc. The `note` field is free text with no contract.
- **No per-source-file aggregation surface.** "docs/foo.md keeps failing to surface" is invisible in a stream of `{query, result, grade}` lines.
- **No host or session attribution in the line.** The line shape (memory_grade.py:67-76: ts, query, scope, projectId, workspaceId, result, usefulness, note) cannot answer "was this logged by Hermes or Claude?" — the exact question the empty-log forensics had to answer with a separate diagnostic document (memory-quality-logging `references/hook-coverage-diagnostics.md` exists precisely because the log can't). A telemetry format that can't distinguish "no usage" from "no capture" is missing its most important field.
- **Self-grading bias.** The grader is the searcher, one turn later, with no anchor; grades measure the agent's satisfaction with a turn, not retrieval quality. The single data point after a week (usefulness 4 on a synthetic probe) is a perfect illustration of the ceiling.

Evidence: memory_grade.py:65-76 (line shape), memory_grade.py:90-93 (ask text), plan:71-88 (round-trip), diagnosis doc §4 ("zero organic data points").

### W3 [SEVERE] Default-OFF gating + broken deployment + no self-verification in the skill = the feature cannot detect its own death

The plan's risk section (plan:135-144) enumerates flooding, prompt bloat, and log growth — but never the failure that actually occurred: the hook never firing. Contributing design facts: (a) the skill's verification checklist (SKILL.md:90-94) tests watch, search, and write-back — **not the grade hook**; the only hook check ever performed was WP7's one-time acceptance probe, which ran the helper directly and therefore verified the *helper pipeline*, not any live host (diagnosis doc §3, plan:130-133); (b) there is no recurring gate or heartbeat — a telemetry feature that has collected one line in a week has no mechanism to notice; (c) env-gated default OFF (defensible for privacy) means the *absence* of lines is the same signal as "off", so an off-by-default, never-self-checking telemetry system converges on permanent silence. The 0% organic capture rate after a week of enablement is the product of this design, not of bad luck. Evidence: SKILL.md:90-94, plan:130-133, diagnosis doc §3-4.

### W4 [MODERATE] `grade_line` rewrites the whole file without locking — unsafe under the feature's own machine-wide concurrency model

The log is explicitly machine-wide and multi-host (SKILL.md:81, plan:69, plan:141 "multi-agent wiring differences"). The append path is safe (O_APPEND, one line per call), but the grade fill reads the entire file and rewrites it (memory_grade.py:172-194: `read_text` → splice → `write_text`). Two sessions grading concurrently, or a grade racing a hook append from another host, silently drops lines. The plan's own risk list (plan:137-144) covers flooding and bloat but not lost updates. Also O(n) per grade with unbounded growth (deferred at plan:144 — acceptable, but the race is a correctness bug, not a scaling one). Evidence: memory_grade.py:172-194.

### W5 [MODERATE] The skill's pitfalls section omits every failure mode the field actually produces

SKILL.md:56-62 has four bullets (no path param, never pass `context`, embed_pending limit, delete_context access mode). The verified operational failure list — from the dogfooding record — is: stale embedding settings breaking search with a cwd-relative "Load model from <cwd>/<name> failed" (memory-quality-logging:99-104); the bundled ONNX model not shipping in the installed global tool, requiring manual provisioning (memory-quality-logging:105-109); silent FTS5-only degraded retrieval when the settings table is empty (no error at all — the degraded state looks like success); encrypted banks (SQLCipher via `AIRACCOON_DB_PASSPHRASE`/sidecar — the hook plan itself acknowledges the env-vs-bank distinction at plan:24, but the skill never tells the agent the bank may be encrypted); the MCP server dying mid-session with no auto-respawn; and wrong-bank risk via `--data-root` (the pitfalls skill's `memory_stats`-requires-projectId discovery recipe exists precisely because "which bank am I in?" is a real question). None of these appear in §6, and §3's escalation ladder (SKILL.md:37-41) has no branch for tool errors or degraded results — it covers only result-quality outcomes. The knowledge all exists in `~/.hermes/skills/ai-raccoon/ai-raccoon-pitfalls/SKILL.md`, but the memory skill's `related_skills` (SKILL.md:13) lists only `mcp-index` and `hermes-mcp-setup`, so the skill that gates every memory interaction does not reach the skill that documents how the server actually fails. Evidence: SKILL.md:13, 37-41, 56-62 vs ai-raccoon-pitfalls SKILL.md (SSE transport, context→custom scope, model provisioning, WAL-safe copies, degraded FTS-only state, encryption key sources) and memory-quality-logging:99-115.

### W6 [MODERATE] Three-way duplication of hook knowledge has already produced a contradiction and guarantees drift

The grade hook is described in three places: SKILL.md §8 (69-88), `memory-quality-logging/SKILL.md` (line shape 21-41, round-trip 43-56, config 58-71), and `docs/plans/memory-grade-hook.md` (full design). The watch setup is duplicated (SKILL.md:18-29 vs memory-quality-logging:75-77), and the memory_write/context pitfall is duplicated (SKILL.md:58-60 vs memory-quality-logging:113-115). The contradiction is live, not hypothetical: SKILL.md §8 says the ask arrives next turn; memory-quality-logging:85-98 says it never fires on Hermes. Duplication has already shipped an inconsistency; the next edit (e.g., fixing §8 per W1) will create silent drift in the other two copies. Note the installed copy of the memory skill is byte-identical to the framework source (diff clean) — the drift problem is *between sibling skills*, not between source and install. Evidence: diffs above; both SKILL.md files 4152 bytes, identical.

### W7 [MODERATE] The search-first ritual and escalation ladder lack stop conditions and failure branches

"2-3 formulations: exact phrase → keywords → plain-English restatement" (SKILL.md:34) is prescribed for every search with no budget: when is one formulation enough? When does the agent stop at two? (This mirrors the server's own `memory-usage-guide` prompt, so it is inherited rather than invented — but the skill is the place where it should gain agent-side judgment.) Exact-phrase-first is also the weakest first move against a hybrid scorer whose proven failure modes are lexical (no stemming, bm25 saturation — ai-raccoon-pitfalls Wave-2 findings); keywords/restatement are the formulations most likely to hit. The escalation ladder (SKILL.md:37-41) covers decisive/partial/no-hit but not: search errored, results obviously degraded (FTS-only thinness), or partial hit with conflicting sources ("reconcile" is one word for the hardest case). And the "No hit → search externally, then write the finding back" branch (line 41) has only "durable facts only" (45) as a guard against persisting unverified external claims — no instruction to mark provenance or uncertainty in the entry. Evidence: SKILL.md:31-41.

### W8 [MODERATE] Workspace sandboxing is presented as the default path for in-progress notes — over-engineered for the actual single-agent use

SKILL.md:45-49: "Plain writes land in committed project memory… For in-progress notes use workspace isolation: `memory_workspace_begin` → `memory_workspace_status` → `memory_workspace_consolidate(keep=[...])` (or `["all"]`…)". The workspace tier costs 3-4 tool calls plus a content-hash keep-list ceremony per note-taking episode, for a solo agent whose alternative — "one durable fact per entry" — already provides atomicity. The framework's own invariant ("an abstraction added before a real caller needs it is a cost with no buyer") applies to its own skill: the dogfooding record shows plain writes dominating, and the skill gives no decision rule for when the workspace pays (batch/uncertain writes where discard is plausible) vs when it is ceremony. It is defensible as an available tier; it is not defensible as the stated default for "in-progress notes" — which describes almost everything an agent does. Evidence: SKILL.md:45-49; ai-raccoon-pitfalls (workspace_consolidate `keep` required — the ceremony is mandatory, not optional).

### W9 [NIT] The skill never mentions Hermes' native memory surfaces, so its audience can't place the bank among them

Hermes-hosted agents always have `session_search` (conversation history) and the memories store available; the bank is project knowledge. The skill says "search the bank first" but never says what to do when the bank misses and the answer lives in prior sessions — an ordering the agent must invent. One comparison line in §2 would settle it (bank for project facts → session_search for "what did we do/say" → web for external). Evidence: SKILL.md:31-35.

### W10 [NIT] Minor precision issues

- SKILL.md:86 hardcodes `python3 ~/.hermes/plugins/memory_grade.py` in the framework source — correct only for the user-scope Hermes deployment; the framework checkout's own copy lives at `features/common/skills/ai-raccoon-memory/scripts/` and the helper's ask text self-reports its real path (`HELPER = Path(__file__).resolve()`, memory_grade.py:19), so the skill's hardcoded path is already inconsistent with its own mechanism.
- The skill's "healthy" definition (§1: watch settles to healthy) and the quality-logging skill's (pending==0 via `memory_stats`, memory-quality-logging:78-79) disagree on what a healthy bank is; both matter and neither skill mentions the other's check.
- `memory_search`'s `limit` param is never mentioned, so agents get whatever default the server applies and cannot trade breadth for latency.
- The verification checklist (SKILL.md:90-94) has no embed-completeness check (pending==0), the single most common cause of "search returns nothing" in the pitfalls record.

## Improvement opportunities

Ordered by impact/effort; each names the file and the change.

1. **Tell the truth in §8 and add the hook to the verification checklist** (framework `features/common/skills/ai-raccoon-memory/SKILL.md`, section 8 and Verification Checklist). [High impact, low effort] Add: "Host coverage: this fires on Claude Code/Copilot via PostToolUse; on Hermes only when the ai-badger plugin is installed as a directory plugin and enabled — verify with `memory_grade.py probe` plus one organic search before trusting the log; see `memory-quality-logging` skill for the diagnostic recipe." Add checklist items: "[ ] `AI_BADGER_MEMORY_GRADE=1` set in the host env" and "[ ] one organic `memory_search` appended a line to `~/.ai-badger/memory-grade/memory-quality.jsonl`". This converts the week-long silent failure into a five-second check and resolves the W1/W6 contradiction.

2. **Ship the real Hermes directory plugin** (per diagnosis doc §5: new `~/.hermes/plugins/ai-badger/` with `plugin.yaml` + `__init__.py` re-exporting `register`; change the destination in `features/hermes/adjustments/adjust_hooks.py`; extend `tests/test_hermes_plugin_install.py` to assert the plugin-dir shape; register via `plugins.enabled` with a scaffold-printed instruction; fix the temp-root `manifest.json` side effect of the freshness guard). [High impact, medium effort] This resurrects all four dead Hermes hooks — drift-notice, mcp-index context enrichment, commit-reminder, and memory-grade — not just the reviewed feature. It is the single change that makes §8 true.

3. **Add `host` (and optionally `sessionId`) to the log line** (`features/common/skills/ai-raccoon-memory/scripts/memory_grade.py`, `_build_line` at 65-76; the hook transports know their host — Hermes `post_tool_call` vs Claude `PostToolUse`). [High impact, low effort] The line then answers "no usage vs no capture" per host directly; `probe` can report organic line counts by host since a date. This is the cheapest way to make the feature self-diagnosing and kills the need for external forensics (W2/W3).

4. **Make grades legible as retrieval quality** — three small schema additions plus one aggregation recipe. (a) Add an optional `queryClass` field (identifier/path/NL/composite — the agent inflects it; the bank's own retrieval paths make these distinctions real, per ai-raccoon-pitfalls Wave-2). (b) Contract the `note` field: "if the relevant source is in the results, name it" so rank-of-relevant is recoverable post-hoc. (c) Document in `memory-quality-logging/SKILL.md` a monthly aggregation recipe (jq/awk over the JSONL): mean usefulness per (projectId, sourceFile), grade distribution per queryClass. [High impact, medium effort] This converts the log from satisfaction scores into the raw material for "which sources are stale, which query classes fail" — the only grades that can actually drive bank tuning (α sweeps, ingestion choices).

5. **Consolidate the duplicated hook knowledge into one owner** (`memory-quality-logging/SKILL.md` keeps the mechanics + verified pitfalls; `ai-raccoon-memory/SKILL.md` §8 shrinks to enable commands + pointer + the coverage caveat; delete the duplicated memory_write/context pitfalls from memory-quality-logging:113-115 in favor of a pointer to the memory skill §6). [Medium impact, low effort] Halves the drift surface and resolves the live contradiction (W6).

6. **Expand the memory skill's Pitfalls section with the five verified operational failures** (`ai-raccoon-memory/SKILL.md` §6: stale embedding settings → `ai-raccoon model set local`; ONNX not shipped → provision from a dev checkout; FTS5-only degraded state → check `ai-raccoon model show`/settings; encrypted bank → `AIRACCOON_DB_PASSPHRASE`/sidecar; server down → verify bank via `memory_stats`, restart). Add `ai-raccoon-pitfalls` to `related_skills` (SKILL.md:13). [Medium impact, low effort] The failure modes that actually cost sessions are currently documented only in a skill the memory skill never links (W5).

7. **Add failure branches to the escalation ladder** (`ai-raccoon-memory/SKILL.md` §3: "Search errored → verify server/bank (`memory_stats`), retry once, degrade to file grep + web"; "Suspiciously thin results → check embed state (pending==0) before concluding no knowledge exists"). [Medium impact, low effort] Closes the largest gap between the ladder and observed reality (W7).

8. **Make grade filling race-free** (`memory_grade.py` `grade_line` at 166-198): either file-lock around the rewrite, or switch to append-only grading (a second sidecar file of `{ts, usefulness, note}` merged at analysis time) so the log is strictly append-only under multi-host use. [Low impact, low effort] Removes the W4 lost-update class entirely.

9. **Add one-line decision rules to §2 and §4** (`ai-raccoon-memory/SKILL.md`): §2 — "one formulation suffices when the first hit is decisive; stop at two when the second adds nothing"; §4 — "use the workspace only when you expect to discard or revise before committing; otherwise write directly" — and add a `limit` note to `memory_search` usage. [Low impact, low effort] Plus (from W10) align the "healthy" definitions between the two skills (watch healthy vs pending==0 — both checks, one line each).

## Comparison notes

- **vs Hermes' native memory surfaces (`session_search`, memories store):** `session_search` is always-injected, zero-setup, FTS5 over the conversation store — the right tool for "what did we do/say", per-profile and per-session by nature. The ai-raccoon bank is project-scoped, durable across sessions by design, hybrid (semantic + FTS), watch-ingested from docs, and shared across projects via the promotion tier — but it costs an MCP server lifecycle, model provisioning, and settings fragility (all of W5's failure modes). They are complements, not rivals; the skill's omission (W9) leaves the ordering to the agent. The grade hook has no Hermes-native equivalent — which is exactly the argument for hosting the telemetry where the search actually happens (see next point).
- **vs hosting telemetry in the server instead of the agent host:** the hook-in-every-host approach multiplies deployment surface across three agent transports and has now failed on one of them for a week (W1). The bank's server is a single always-running process that sees every `memory_search`; it could write the query/result line natively (host-independent, no hooks at all) and expose a tiny "grade last search" MCP tool that returns the ts pointer — eliminating the shell helper, the ts copy-paste, the pending stash, and the entire Hermes/Claude transport split, while keeping the agent's grade as the only human/agent input. The current design chose the agent-side hook for good reasons in the plan (plan:24, 73 — bank-settings reads couple to schema; result payload only reliably available to the hook), but "the hook only reliably sees the result" is a Claude/hook-ABI fact, not an MCP fact — the server sees the result trivially. This alternative deserves a decision record, not just a footnote, before more hook surface is built.
- **vs plain docs (repo markdown + grep/IDE search):** the bank's value proposition is hybrid retrieval, cross-project shared tier, dedup, sweep, and watch-based freshness — real capabilities at multi-project scale. For a single project, plain docs plus the IDE's FTS5 may match retrieval quality at zero infrastructure cost; the bank's own pitfalls corpus (bm25 saturation, no stemming, degraded-mode silence) shows its retrieval is not uniformly better than grep for identifier queries. The skill's search-first mandate is a bet that the bank wins; the grade hook exists to test that bet and currently cannot (W2/W3). The honest interim position — already practiced in the dogfooding record — is the session-scoped manual JSONL (`docs/work/<date>-ai-raccoon-memory-quality.jsonl`), which yields the same line shape without any hook dependency; the skill should say so when the automated path is unverifiable.
