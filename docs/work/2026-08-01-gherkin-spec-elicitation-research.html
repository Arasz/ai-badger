Research & validation ai-badger 1 August 2026

The specification format as the interview script

An assessment of the proposal to add a create-task-spec skill that starts from a rough idea and interrogates its way to a structured specification — the agent extracting knowledge from the person rather than proposing content for them to nod at. The core idea holds, and has a sharper justification than expected: Gherkin's grammar is a question generator with an objective stopping condition.

Scope note: the format is for the agent. No BDD runner, no compiler, no editor plugin is in play — which removes every dependency question and leaves only the format itself.

Verdicts at a glance

C1 Strongly validated
The agent should actively extract knowledge — force the user to think by asking questions, with the structured format dictating what gets asked.

The strongest idea in the proposal, and it has a property generic questioning does not: because Gherkin's grammar has required slots, the question list is derived from the artifact rather than from a checklist, and it terminates when the artifact is structurally complete.

C2 Refuted
The skill should emit two documents: a .feature and a .specb.

.specb is not a format — it is an alternate file extension recognised by one Java tool, holding identical Gherkin. With that tool out of scope there is nothing left to decide: use .feature, the conventional extension. The instinct that one file is not enough is still right; the second document just isn't a spec file.

C3 Validated with caveat
With structured documents, we know what to build with exact meaning.

Structure buys precision about behaviour, and it buys a countable notion of completeness. It does not buy exactness on its own — the meaning is only as exact as the answers elicited, which is why the questioning discipline, not the file format, is what carries this claim.

C4 Validated
Use the owner gate review before emitting, if details need ironing out.

Fits, with a role change under the elicitation framing: the gate is not where the user approves the agent's proposals, it is where they rule on the gaps their own answers left behind. The existing result contract already separates a deliberate DEFER from silence.

C5 Redesign advised
A third skill, task-with-spec, whose only job is chaining the two.

The integration is right; the wrapper is not. This repo already chains skills without one — differential-feature-refactor calls owner-gate-review inline and reads its result back. A third skill buys one entry point at the cost of a scope declaration, a plugin sync, a docs row, and a permanent "which one do I invoke?" ambiguity.

C6 Reframed
"Brainstorming, but with more steps."

Related, but not the same axis. Brainstorming diverges then converges on what to build; this skill starts once that is settled and converges on exact meaning. It should sit downstream and not try to replace the existing brainstorming skill.

The thesis: grammar as a question generator

A structured interview usually means a fixed checklist of dimensions — problem, scope, data, auth, edge cases. That works, but the checklist is arbitrary: someone chose those headings, and nothing says when a dimension is finished.

Driving the interview from the target format is stronger, because Gherkin's grammar already specifies what a complete document contains. Every required slot that is empty is a question that must be asked. Every rule with no example is a hole you can point at. The interview stops when the document is well-formed — not when the conversation feels long enough.

Empty slotQuestion it forcesWhy it can't be skipped
Ability:What capability is this, as one noun phrase?One Feature per file — naming it forces a scope boundary
As a …Who specifically? Name a role, not "the user".A generic persona produces generic rules downstream
I want …What do they want to do — the capability, not the button?The first place imperative, UI-coupled phrasing creeps in
So that …What changes for them? How would you know it worked?An unanswerable benefit means the feature isn't justified yet
Rule:What must always be true? Name something that could be violated.Rules are the invariants; a spec with none is a wish list
Example: (under a rule)Give me a case where this holds. Now one that nearly violates it. Now one that fails.Three prompts per rule reach edges the user hadn't considered
GivenWhat must already be true before this happens?Surfaces unstated preconditions and setup dependencies
WhenWhat single event triggers it?A second When means it is really two scenarios
ThenHow would you know it worked, without opening the database?Forces an observable outcome instead of an internal state check
Examples:What are the real values? Where exactly is the boundary?Turns "it should validate the amount" into a testable threshold
@tagsWhat does this belong with? Who else is affected?Catches cross-cutting impact the user didn't volunteer

Slot names use the plain-English Gherkin keywords. Ability is a standard synonym for Feature, alongside Business Need — verified against the dialect file shipped with the Cucumber parser, which defines 80 spoken-language dialects.

Incompleteness you can count

This is what makes the format-driven approach mechanically checkable rather than a matter of judgement. A partially-elicited spec has holes with names: 

Ability: DiscountAppliesAtCheckout
  As a returning customer
  I want the loyalty discount applied before tax
  So that the total I am quoted is the total I pay

  Rule: a loyalty discount applies before tax is calculated

    Example: discount precedes tax on a single item
      Given my cart contains "Wireless Headphones" at "60.00"
      When I open the checkout summary
      Then the discounted subtotal is "54.00"

  Rule: an expired membership receives no discount
    ← hole: rule stated, no example given

    @deferred
    Example: expired membership pays list price
      ← hole: scenario titled, no steps

Three states, all detectable: a rule with no scenario, a scenario with no steps, and a scenario whose steps are complete. The first two are the outstanding question queue. The interview ends when the queue is empty or every remaining hole carries an explicit deferral — never because the agent decided it had enough.

Buildable without a dependency

Hole-counting is a property of the grammar, not of any tool. Gherkin is line-oriented and every non-blank line must start with a keyword, so the narrow question the skill asks — which rules have no examples, which examples have no steps — needs a scanner, not a parser.

That matters here: ai-badger is stdlib-only apart from jsonschema and an optional pyyaml. Pulling in a Gherkin parsing library to count holes would break that discipline for no gain. A small stdlib scanner keeps the skill dependency-free and makes the completeness check something tests can assert on.

The polarity problem

Two pieces of close prior art sit at opposite ends of the axis this proposal cares about. Picking the wrong one would quietly defeat the design.

Proposal-first

SpecBinder ships Claude Code commands covering these same stages. Their instructions read: "suggest 2–6 plausible business rules", "extrapolate scenarios", "extrapolate from the title and description".

The agent generates content; the human edits it. Under the elicitation framing this is the anti-pattern — a user shown six plausible rules stops generating a seventh and starts editing someone else's list.

Question-first

dotnet-claude-kit's /spec, already installed here and MIT-licensed. Its contract: "Never assume. Every gap in the idea becomes a question. If Claude catches itself thinking 'probably', 'presumably', or 'the usual way' — that thought is a question to ask, not a decision to make."

Questions come in rounds of 3–5. A dimension is finished when a follow-up round produces zero new questions. "I don't know" is legal and becomes a Deferred Decision with a fallback the developer picks now — silent deferral is forbidden.

The anchoring risk, stated plainly

Language models are strongly disposed to fill a blank rather than leave it open, and users are strongly disposed to accept a plausible list. Together those produce a spec that reads as agreed but encodes the model's guesses. Since the entire value of the artifact is that it captures what the person knows, this is not a rough edge — it is the failure mode that makes the skill worthless while appearing to work.

The calibrated middle

Pure interrogation is exhausting, and sometimes a person genuinely cannot answer until they see the shape of an option. The rule that resolves it — borrowed from the question-first pole — is to propose options to choose between, never content to accept. Offer two or three alternatives with trade-offs and a recommendation; the user picks, and a recommendation is never silently applied. That keeps them generating decisions instead of proofreading.

What a round actually looks like

Agent Here's what I understood: returning customers get a loyalty discount, and you want it applied before tax rather than after. Is that the idea — and what did I get wrong?
User Right, and it only applies to members in good standing.
Agent "Good standing" is doing a lot of work there, and it's now a rule I can't write. Three questions: 1. What makes a membership not in good standing — expired, suspended, unpaid, something else? 2. If it lapses mid-checkout, does the price they were quoted still hold? 3. You've given me one rule about tax ordering. Is there a second about which items the discount covers, or does it apply to the whole cart?
User Expired or unpaid. Not sure about the mid-checkout one.
Agent Recording "expired or unpaid" as the rule. The mid-checkout case goes to the decision gate rather than my guess — with two options for you to rule on: honour the quoted price for the session, or re-price on payment. Question 3 is still open: does the discount apply to every item?

Illustrative, not a transcript. Three moves carry the design: an unanswerable phrase is challenged rather than interpreted, "not sure" becomes a gate decision rather than a default, and the unanswered question is re-asked instead of dropped.

What Gherkin cannot be asked to say

The interview can only elicit what the format can hold. Gherkin describes observable behaviour and nothing else — which is exactly why a second document is needed, and what it should contain.

Elicitable into the spec file

  • Behaviour as Given / When / Then
  • Invariants as first-class Rule blocks
  • Shared setup via Background (one per Feature or Rule)
  • Parameterised cases via Scenario Outline + Examples
  • Structured arguments: data tables, doc strings
  • Cross-cutting grouping via @tags

Must go in the manifest instead

  • Non-functional requirements — latency, volume, cost
  • Architecture and layering constraints
  • Which files to touch; where new code belongs
  • Explicit out-of-scope boundaries
  • Security and compliance obligations
  • Decision provenance — who ruled what, what stayed deferred

Two hard constraints from the reference are worth enforcing during elicitation: only one Feature per file, and no two steps within a scenario may share identical text.

Recommended architecture

One new skill and a small change to an existing one.

1. create-task-spec — in features/common/skills/

An elicitation loop emitting two documents that are genuinely different from one another:

<Name>.feature

The behavioural contract, in standard Gherkin.

  • User story header
  • Rule blocks as elicited invariants
  • Scenarios with concrete steps
  • Deferred items left step-less and tagged
  • @spec-id linking back to the manifest

spec.json

Everything Gherkin structurally cannot hold — the manifest task consumes.

  • Scope and explicit out-of-scope
  • Non-functional requirements
  • Target paths and architecture constraints
  • Gate verdicts with provenance
  • Deferred decisions and their chosen fallbacks
  • Spec-file path and hole count at emit time

Neither of these can be derived from the other — which is what the original two-document instinct was reaching for.

2. The elicitation loop

01 Restate and confirmPlay the idea back in the agent's own words and ask what's wrong. Never start questioning the wrong idea.
02 Elicit the ability headerPersona, capability, benefit — three slots, three questions, no invented answers.
03 Elicit rules until dry"What else must always be true?" until the user produces nothing new — the until-dry test rather than a fixed count.
04 Elicit scenarios per ruleHolds / nearly violates / fails. Titles only — the queue of step-less scenarios is now visible to both sides.
05 Elicit steps, challenging phrasingReject UI verbs and internal-state assertions. A second When splits the scenario.
06 Owner gate on what's leftEvery "not sure", every contradiction, every remaining hole becomes one decision card: APPROVE / CHANGE / REJECT / DEFER. Nothing is emitted while a card is unanswered.
07 Emit both documentsSpec plus manifest, with verdicts and deferrals recorded as provenance.

Numbered because the stages are genuinely sequential — each one's output is the next one's input, and 06 is a hard stop. Stages 03 and 04 loop internally; 05 can send the user back to 04 when a step reveals a missing case.

3. Integration — extend task, don't wrap it

Teach task's Phase 1 to recognise a spec manifest path as its argument, and let create-task-spec end by handing one over. The plan Phase 1 delegates to the architect persona gets strictly better input — an elicited behavioural contract plus explicit constraints, instead of freeform text — and Phase 3's quality gate gains an exact pass condition.

4. scripts/render_spec.py — the spec as a readable page

The spec file is optimised for the agent, which leaves the human side underserved: plain Gherkin is legible but flat, and it does not show what is missing. A renderer closes that gap, and it comes almost free — the same stdlib scanner that counts holes for the completeness check is the parser the renderer needs. One scanner, two consumers: a gate that blocks emission and a page that makes the state of the spec obvious at a glance.

  • Show the holes, don't just count them — a rule with no examples and a scenario with no steps rendered as visible gaps, so an unfinished spec looks unfinished.
  • Separate elicited from deferred — deferred items carry their chosen fallback and the gate verdict that put them there.
  • Fold in the manifest — scope, out-of-scope and constraints beside the behaviour they bound, which is the one view neither file gives alone.

It belongs in the skill's scripts/ rather than behind an extension.json gate: the gate mechanism keys on config conditions like stack or platform, and there is no condition under which a project would want the renderer switched off. Keeping it a plain script also means it stays re-runnable against any spec, at any time, not only at emit.

Rendered specs have an obvious home. docs/work/ is already the canonical place for dated records and already holds generated HTML from the owner gate — so a rendered spec sits beside the review form that ruled on it.

5. What registration costs

Adding a catalog skill is more than a SKILL.md: scope must be declared in SKILL_SCOPES in engine/badger_lib.py — there is no fallback, and an undeclared skill ships to nobody, the documented failure that left code-review-checklist dark for its entire life — then the index rebuilt, validation passed, and a default-scope skill synced into skills/.

Recommendation

Proceed — the elicitation framing is what makes it worth building

A skill that proposes a spec for someone to approve is a convenience. A skill that interrogates someone into producing one is a different thing, and Gherkin is an unusually good instrument for it because its grammar supplies both the questions and the stopping condition. Build create-task-spec as an elicitation loop emitting a .feature file and a spec.json manifest. Integrate by teaching task to accept a manifest path rather than adding a wrapper skill.

With the toolchain out of scope, the only external artifact is the format itself — which is stable, widely understood, and costs nothing to adopt. What has to be built here is the questioning discipline and a small stdlib scanner that counts the holes.

Open choices worth a decision round before implementation: JSON or YAML for the manifest, whether the skill refuses to emit while any hole is unruled, how many rounds the loop tolerates before it must gate, and where emitted specs live in the tree.
