## Headline finding (changes the plan): Copilot cannot carry injected prompt context

- GitHub's Copilot hooks reference (fetched 2026-09-27, docs.github.com/en/copilot/reference/hooks-configuration)
  gives `userPromptSubmitted` the input `{sessionId, timestamp, cwd, prompt}` (or the VS Code
  spelling `{hook_event_name:"UserPromptSubmit", session_id, timestamp, cwd, prompt}`) and the
  output `{modifiedPrompt?}`. It says: *"modifiedPrompt is only honored by SDK programmatic hooks.
  Command and HTTP config-file userPromptSubmitted hooks have their output dropped, including
  modifiedPrompt."* The same page lists `additionalContext` only on `sessionStart`,
  `notification`, `postToolUse` and `subagentStart`. [READ, vendor docs]
- VS Code also reads `.github/hooks/*.json` (and maps Copilot-format files). Its hooks reference
  (code.visualstudio.com/docs/agents/reference/hooks-reference) says `UserPromptSubmit` supports
  only the common output (`continue`, `stopReason`, `systemMessage`, the last "shown to the
  user"). `additionalContext` is listed for SessionStart, SubagentStart, PreToolUse and
  PostToolUse, and not for UserPromptSubmit. [READ, vendor docs]
- So `.github/hooks/ai-badger-hooks.json` → `userPromptSubmitted` (generated by
  `features/copilot/adjustments/adjust_hooks.py:96-153`) is a seam that **runs the script and
  throws its stdout away**. Wiring the RAG hook there would cost up to the full ~1.3–5 s per
  prompt (S2) plus one search-log row (S10) and deliver nothing to the model.
- **Recommendation: no Copilot arm.** Record a `copilot` exemption on the new manifest row in
  `tooling/validate.py` `HOOKS_MANIFEST_AGENT_EXEMPTIONS` (`validate.py:186`), worded as a wall
  and not a gap, quoting the doc sentence. The Copilot CLI 1.0.88 is installed on this machine
  (`/opt/homebrew/bin/copilot`, MEASURED `copilot --version`), so a 15-minute fired-in-anger
  spike (P0) can move this from READ to MEASURED before the exemption text is committed.
- **Side-effect finding (out of scope, file an issue):** by the same doc, the existing Copilot
  `userPromptSubmitted` arms for `message-delivery-per-turn`, `context-enrichment` and
  `prompt-markers` (`hooks-manifest.json:62,156,174`) inject nothing either, and
  `docs/dictionary.md:22` ("Context injection … `userPromptSubmitted` event") is wrong. That is the
  "shipped is not running" defect again. The P0 spike covers this too.

## 1. Design

### 1.1 Feature placement

`features/common/skills/ai-raccoon-memory/scripts/` — the skill that already owns the
ai-raccoon hooks (`memory_first_gate*.py`, `memory_grade_hook.py`; wired from
`features/common/hooks/hooks.json:102,183,187,196`) and already has a `badger_store.py` sibling in
its scripts dir. Reasons:
- **Declining works as expected.** A project that lists `ai-raccoon-memory` in `config.exclude`
  loses this hook through the existing `drop_declined()` / `declined_skill()` path
  (`skills/welcome-ai-badger/scripts/hook_wiring.py:87-111`, and the check at `:317-324` in the
  rewrite loop). A new skill would need its own exclude semantics and its own twin rows in docs.
- **The Hermes delivery list already names this skill.** `SHARED_SKILL_MODULES` has
  `("ai-raccoon-memory", "memory_first_gate.py")` (`features/hermes/adjustments/adjust_hooks.py:39`).
  Adding a row there follows the existing pattern.
- `features/common/retrieval/` is the wrong home: it holds the BM25 matcher and has three
  per-agent copy sites (claude/copilot `adjust_retrieval.py`, hermes `RETRIEVAL_MODULES`,
  `adjust_hooks.py:53`). A fourth kind of retrieval there would mean three more twin lists.

`scope: default` (`features/common/skills/ai-raccoon-memory/SKILL.md:10`) means every scaffold
gets the wiring. The owner's "on when present" rule is therefore enforced **at runtime** (a
`.ai-badger/project-id` exists and `~/.ai-raccoon/mcp-token` is readable), not at scaffold time.
The cost for a project without ai-raccoon is one python spawn per prompt that returns in
milliseconds (INFERRED; the same cost `context_enrichment_hook.py` already pays).

### 1.2 Module split (three files, all stdlib-only, Python 3.10+)

| file | role | imports |
|---|---|---|
| `memory_context.py` | **Pure core.** `should_enrich(prompt) -> Decision` (port of `shouldEnrich` minus the `/skill:` rules, S6), `unique_long_words`, `NOISE_3CHAR_WORDS`, `CONTROL_WORDS`, `prune_hits(mem, code)`, `one_line`, `format_block(query, mem, code) -> str` (the verbatim default-mode block, lane B §1.10). Also the orchestrator `context_for(prompt, cwd, session_id, search) -> str or None`: kill switch → gate → project-id → `search(...)` → prune → both-empty → block. The transport is passed in as `search`, so the core does no I/O of its own. | stdlib only |
| `raccoon_search.py` | **Transport.** `read_token(home)`, `project_id(cwd)` (delegates to the sibling `badger_store.resolve_project_id`, `features/common/hooks/badger_store.py:2105-2119`, instead of a second walk; see §4), and `search(query, project_id, session_id, *, url, token, timeout) -> (mem, code) or None`: one JSON-RPC `tools/call` of `memory_search` `{projectId, sessionId, query, scope:"project", limit:5}` to `http://127.0.0.1:7721/mcp` with `X-AiRaccoon-Token`, parses the single SSE `data:` frame, and returns None on any error, `isError`, 401, refusal or timeout. | stdlib (`urllib.request`, `json`), sibling `badger_store` loaded by path |
| `memory_context_hook.py` | **Claude entry.** Reads stdin JSON (`prompt`, `session_id`/`sessionId`, `cwd`), loads the two siblings by path under distinctive `sys.modules` keys (the `_load_context_enrichment` pattern, `features/common/skills/mcp-index/scripts/context_enrichment_hook.py:41-68`), prints `{"hookSpecificOutput":{"hookEventName":"UserPromptSubmit","additionalContext":block}}` or nothing. `guarded_main()` always exits 0 (the pattern at `context_enrichment_hook.py:173-199`). | siblings by path |

Hermes does not use the entry script. It calls `memory_context.context_for(..., search=raccoon_search.search)` in-process (§1.3c).

**Mode:** ship **default mode only**. Expanded mode costs one `memory_get`/`code_get` per hit
(up to 10 calls) under the same deadline. The measured base search already takes 1.27–1.56 s
(S2), so expanded mode would not fit a 5 s budget without partial results. The default block
already tells the model to call `memory_get`/`code_get` by hash when it needs more (lane B
§1.10), so expanded mode only pre-fetches what the model can fetch on demand. Leave out the
mode env var and add it only if someone asks for it (ask-if-simpler).

**Kill switch:** `AI_BADGER_MEMORY_CONTEXT`. The literal `"0"` disables the hook; any other value,
or no value, leaves it on. This follows the exact-literal convention of `AI_BADGER_PI_AWAY`
(`hook-bridge.ts:698-699`). Read it on every call, not at import time, so a long-running Hermes
gateway picks up a change.

**Budget:** script deadline 5.0 s via `urlopen(timeout=5)`, plus an absolute deadline check
while reading the body. The Claude hook `timeout` is 8 s. On any timeout or error, inject
nothing.

### 1.3 Per-agent delivery

#### a) Claude Code — `.claude/settings.json` `UserPromptSubmit` via `hook_wiring.py`

Files to touch:
1. `features/common/hooks/hooks.json` → `hooks.UserPromptSubmit` (currently two entries,
   `hooks.json:3-20`): append
   `{"hooks":[{"type":"command","command":"python3 \"${CLAUDE_PLUGIN_ROOT}/features/common/skills/ai-raccoon-memory/scripts/memory_context_hook.py\"","timeout":8}]}`.
   The `timeout` survives the rewrite because `hook_wiring` copies each hook dict with
   `new_h = dict(h)` and changes only `command` (`hook_wiring.py:308-330`) [READ]. Existing
   entries already carry `"timeout": 10` (`hooks.json:46,103`).
2. `features/common/hooks/hooks-manifest.json`: add a new row `memory-context` with the claude
   arm `{"type":"hooks-json","entry":"hooks.json","event":"UserPromptSubmit","script":"memory_context_hook.py"}`.
   `HookWiring.wire()` selects the hooks.json command by script-suffix match (`select_hooks()`,
   `hook_wiring.py:153-169`), rewrites `${CLAUDE_PLUGIN_ROOT}/features/common/skills/` →
   `${CLAUDE_PROJECT_DIR}/.ai-badger/skills/` (`:301-312`), wraps it in `guarded()` (`:61-75`),
   and merges it into `.claude/settings.json` with dedupe by (matcher, skill-relative script id)
   (`merge_hooks()`, `:114-205`).
3. Payload keys: Claude sends `prompt`, `session_id`, `cwd`. Read them duck-typed like
   `context_enrichment_hook.py:125-140`. `sessionId` is **required**: without it the result
   is `isError` (S5).
4. Latency: Claude runs all matching `UserPromptSubmit` hooks for one event in parallel
   (UNVERIFIED this session; it is the documented Claude Code behaviour), so the ~1.3 s search
   overlaps `context_enrichment_hook.py` and `message_delivery_hook.py` instead of adding to them.

Plugin-only installs (repo-root `hooks/hooks.json`, which carries only `drift_notice_hook.py`,
READ) do not get the hook. That matches `context-enrichment`, whose hook only reaches
scaffolded projects.

#### b) Copilot — no arm (a wall, see the headline)

Files to touch: `tooling/validate.py` `HOOKS_MANIFEST_AGENT_EXEMPTIONS` gets
`"memory-context": {"copilot": "<wall reason quoting the vendor doc>"}`.
`tests/test_hooks_manifest_agent_coverage.py` asserts that the reason is non-trivial.
`features/copilot/adjustments/adjust_hooks.py` needs **no change**: it skips a row with no
`copilot` arm (`:100-103`).

If P0 unexpectedly shows that Copilot does honour `additionalContext` on `userPromptSubmitted`,
the change is a single manifest arm (`event:"userPromptSubmitted"`, `script:"memory_context_hook.py"`).
The generator then emits `timeoutSec: 10` (`adjust_hooks.py:148`), which is above the 5 s script
budget, and the entry script already accepts `sessionId`. The scaffold-time exemption comes out
at the same time.

#### c) Hermes — in-process `pre_llm_call` in `ai_badger_hooks.py`

Files to touch:
1. `features/common/hooks/ai_badger_hooks.py`:
   - Add `_load_memory_context()` and `_load_raccoon_search()` through the existing
     `_load_sibling_module(module_name, filename, label)` (`ai_badger_hooks.py:63-98`). A
     missing file then logs "missing" **once** and the feature goes inert, which is the right
     behaviour for a stale plugin dir.
   - In `pre_llm_inject_context()` (`:634-729`), append the memory block **last** (after the MCP
     tool hint, before `if not parts`, `:727`). Wrap it in its own `try/except` and
     `logger.warning`, like the bus arm (`:664-669`). Inputs: `prompt = message or user_message`
     (`:652`), `project = _project_cwd(cwd)` (`:651`; there is no `cwd` in the real payload, so it
     falls back to `os.getcwd()`, `tests/test_hermes_plugin_payloads.py:7-12`), and
     `session_id = kwargs.get("session_id")` (the real payload carries it, `:7`).
   - **Per-turn dedupe.** The repo disagrees with itself on how often `pre_llm_call` fires: the
     docstring says "once per turn, before the tool-calling loop" (`ai_badger_hooks.py:640`),
     while the validator's exemption text says "before every LLM call including tool-loop
     continuations" (`validate.py:199`) [READ, conflicting; UNVERIFIED which is true]. Make the
     code correct under both readings. Keep an in-process `dict[session_id] -> sha1(prompt)` and
     skip the search when the same session sends the same `user_message` again. Otherwise one
     agent turn with N tool calls could pay N × 1.3 s. Clear it in `on_session_start`, next to
     `reset_gate_state()` (`:331-334`).
2. `features/hermes/adjustments/adjust_hooks.py:35-43` `SHARED_SKILL_MODULES`: add
   `("ai-raccoon-memory", "memory_context.py")` and `("ai-raccoon-memory", "raccoon_search.py")`.
   Both destinations (project `.ai-badger/hooks/`, `:214-219`, and user-global
   `~/.hermes/plugins/ai-badger/`, `:158-163`) are covered by that one tuple.
   `LEGACY_FLAT_FILES` is derived from it (`:56-58`). `badger_store.py` already ships
   (`USER_PLUGINS`, `:26`).
3. `tests/test_hermes_plugin_install.py` `SHARED_SKILL_FILES`: add the same two rows. The
   derive-or-delete test at `:205-208` fails until the rows match.
4. Manifest: the `memory-context` row gets `"hermes": {"type":"plugin","entry":"ai_badger_hooks.py","method":"pre_llm_call"}`,
   the same shape as `context-enrichment`.

Hermes-specific delivery facts:
- The call blocks the Hermes turn serially, and nothing in Hermes enforces a timeout on it
  (INFERRED from the in-process call). The transport's own deadline is the **only** bound, so
  P2 must prove that the deadline is total and not just per socket operation.
- On a gateway (Telegram/Discord/etc.), the process cwd is usually not a scaffolded project.
  `project_id()` then finds no `.ai-badger/project-id` and the hook stays silent, which is
  the correct result (INFERRED).
- The user-global plugin dir holds whichever version the **last** scaffolded project installed.
  All inputs (project-id, token) must be resolved per call from cwd and `$HOME`, never frozen
  at install time.

#### d) pi — stays excluded, and what proves it

Nothing is added for pi, and three structural facts keep it that way:
1. `hooks-manifest.json` has no `pi` arm on any row (research Lane A §2, MEASURED by
   extraction), and `HOOK_CAPABLE_AGENTS = ("claude","hermes","copilot")` (`validate.py:180`).
2. pi's `before_agent_start` spawns only `DELIVERY_SCRIPT = .ai-badger/hooks/message_delivery_hook.py`
   (`features/pi/adjustments/adapter/index.ts:68,324,729-733`). It does not replay the
   `UserPromptSubmit` array. `loadGates()` (`index.ts:101`) reads `.ai-badger/hooks/hooks.json`,
   but only for Pre/PostToolUse (`:249,294`).
3. pi's own copy list (`features/pi/adjustments/adjust_hooks.py:83-91`) is fixed and does not
   include the new modules.

**Proof (integration test, P5):** scaffold `agents: [claude, hermes, copilot, pi]` into tmp with
`--no-install`. Assert that no file written by the pi adjustment, and neither `index.ts` nor
`hook-bridge.ts`, names `memory_context`. Also assert that the `before_agent_start` spawn target
is still only `message_delivery_hook.py`. That last assertion is a grep on TS source: it is
brittle, but it is exactly the tripwire needed. If someone later adds a generic replay, the test
goes red and forces an explicit decision.

**No in-script `PI_SESSION_ID` guard.** With no seam that calls the hook under pi, such a guard
could never be seen to fire (prove-the-check-fails). It would also wrongly silence a Claude
session launched from inside a pi shell, because the child inherits pi's env (INFERRED). Add it
only if generic replay ever lands.

## 5. Risks and open questions

1. **Copilot delivery is impossible via config-file hooks** (READ, vendor docs). *Rec:* exempt it
   as a wall and run P0 to move this to MEASURED. File a separate issue for the three existing
   Copilot `userPromptSubmitted` arms that are probably inert, and for `docs/dictionary.md:22`.
   Do not fix them in this task.
2. **Hermes `pre_llm_call` frequency is contradicted in-repo** (`ai_badger_hooks.py:640` vs
   `validate.py:199`). *Rec:* add the (session, prompt) memo either way. It costs a dict, and
   under the "every LLM call" reading it prevents N × 1.3 s per turn.
3. **Latency on every gated prompt** (1.27–1.56 s, S2; the owner accepts the full wait). On
   Hermes it is serial, and the transport deadline is the only bound. *Rec:* make the deadline
   total (a slow-drip test) and do not add retries. On Claude the hooks run in parallel
   (UNVERIFIED), so the added wall-clock ≈ max(hooks), not the sum.
4. **`scope:"project"` suppressing shared-tier hits for an unknown id is UNVERIFIED.** S5 measured
   leakage for an unknown id but does not say whether `scope:"project"` stops it. *Rec:* before P2
   merges, run a one-off manual probe with a random uuid and `scope:"project"` against the live
   serve (not in the suite), and record it MEASURED. If it still leaks, the missing-project-id skip
   is the only guard, and it already exists.
5. **Stale user-global Hermes plugin across projects.** One `~/.hermes/plugins/ai-badger/` serves
   all projects, holding the last installer's version. *Rec:* resolve everything per call. The
   missing-sibling path is already inert and logged once.
6. **Removing the Hermes modules on exclude is UNVERIFIED.** `adjust_hooks` copies
   `SHARED_SKILL_MODULES` without reading `config.exclude`. *Rec:* document the kill switch as the
   off-switch and do not widen scope; raise an issue if it is confirmed.
7. **Search-log growth**: one row per enriched prompt per surface (S10). *Rec:* accept it and
   mention it in the SKILL.md.
8. **Stale-worktree noise on Claude**: when the script is missing, `guarded()` prints a
   `systemMessage` on every prompt. *Rec:* accept it; existing hooks behave the same, and
   den-refresh fixes it.
9. **Open: expanded mode and the mode env var.** *Rec:* cut both (see §1.2) and reopen only if a
   user asks.
10. **Open: debug telemetry** (`debug_log` terminal states: skip reason, no-hits, error, hit, the
    `docs/retrieval.md:457-497` discipline). *Rec:* include one `_debug` call per terminal state in
    `context_for`. It costs almost nothing when disabled and answers "did it even run?" for
    call-behaviorist. It is the first thing to cut if the reviewer wants a smaller change.

## 6. Simpler shape?

The smallest version that meets every ruling:
- **Two files instead of three:** `memory_context.py` (gate + format + transport + `context_for`)
  and `memory_context_hook.py` (the Claude entry). Hermes loads one sibling instead of two, and
  there is one `SHARED_SKILL_MODULES` row. The pure-core boundary is kept by convention and a
  test (`context_for` takes `search` as a parameter), not by a file boundary.
- **Two agents:** Claude and Hermes. Copilot is an exemption row, which the evidence already
  forces.
- **Default mode only, one env var** (`AI_BADGER_MEMORY_CONTEXT=0`).
- **No `PI_SESSION_ID` guard, no badger_store session state, no telemetry.** The Hermes memo stays
  an in-process dict.
- **Packages:** P1+P2 merge into one "core" package, P3 and P4 run in parallel, and P5 is
  integration. P0 stays; it is 15 minutes and settles the Copilot row.

What that cuts: the separate transport module (only a test seam), expanded mode (a 10-call fan-out
that does not fit the budget), the mode env var, per-surface telemetry, and a defensive pi guard
that could never fire. What it keeps is everything the rulings require: every-prompt gating, the
one HTTP call with `scope:"project"`/limit 5, the 5 s budget with a silent fail, on-when-present,
the `"0"` kill switch, stdlib-only code, tests that never touch the live serve or `$HOME`, and pi
excluded with a test proving it.

My recommendation is the simpler shape plus the one-line telemetry (risk 10). The three-file
split is fine if the architect lane prefers a hard I/O boundary, but it buys a boundary, not a
behaviour.
