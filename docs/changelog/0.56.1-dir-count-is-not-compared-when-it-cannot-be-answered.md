# 0.56.1 — `dir_count` is not compared when it cannot be answered

Closes [#230](https://github.com/Arasz/ai-badger/issues/230). Net −8 lines of logic.

0.54.2 fixed #224 by pruning directories that exist only to carry a path another
entry owns. That reconstruction was wrong in the other direction.

## The case it got wrong

`scaffold.py` copies a source skill with `_test_ignore`, so a directory whose only
content is a `tests/` subtree lands in the target **empty** — and is counted into
`dirMeta` at record time, before any adjustment runs. When an adjustment later
writes beneath it, the prune removes it again:

```
pre-adjustment  (what dirMeta records):  file_count=1  dir_count=1
post-adjustment (what drift computes):   file_count=1  dir_count=0
file_count and content_hash agree
```

A false `locallyModified` — #224's verdict with the opposite sign.

## The fix is a deletion

`dir_count` is simply **unanswerable** once another entry owns part of the tree:
the recorded number described the tree before that entry wrote, so the two count
different things. Rather than reconstruct it, drift stops comparing it —
`_differs` takes `compare_dir_count`, false exactly when `exclude_rel` is
non-empty, and the pruning branch in `dir_content_hash` is gone.

Nothing is lost. A genuinely added directory that holds a file moves `file_count`
and `content_hash` anyway, and git cannot deliver an empty one — only a person
can create it, and an empty directory is not an edit to any file.

## Rewritten test worth naming

`test_dir_content_hash_exclude_rel_prunes_ancestors_owned_only_by_nested_entry`
asserted the pruning this removes, so it is replaced by
`test_dir_content_hash_still_counts_a_directory_a_nested_entry_created`, which
pins the opposite: `dir_count` describes the tree on disk, and the caller decides
when it is comparable. The rest of #224's coverage is untouched — editing a
skill's own file is still reported, and a file another entry owns still is not.
