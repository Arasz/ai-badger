# 0.53.0 — the index row stops being hand-written

**Date:** 2026-07-30

Closes [#160](https://github.com/Arasz/ai-badger/issues/160).

## What was wrong

The per-file changelog convention exists to avoid merge conflicts on one growing file, and the
entry files delivered that. **The index row in `docs/changelog/README.md` did not.** Every PR
riding one unreleased version edited the same table line, so N concurrent PRs cost N−1
hand-resolved conflicts on it — five in a single session (#179, #199, #200/#201, #204), every
one on that line.

Worse, a careless resolution was invisible. `gates/docs_guard.py` checked that the README's
links pointed at real files, not that every file had a row, so a resolution that took one side
and lost an entry passed every gate and shipped.

## Added

- **`tooling/changelog_index.py`** — generates the release table from the entry files, and
  `--check` fails when the committed table is not the one the files imply. Modelled on
  `index_build.py` and `version_sync.py`: mechanical, offline, one concern.

  Everything it needs is already on disk. The version comes from the `{version}-{slug}.md`
  filename; the title from the entry's first `# ` heading with a leading `{version} —`
  stripped (the Version column already carries it). Only the region between
  `<!-- changelog-index:start -->` and `<!-- changelog-index:end -->` is written — the README's
  prose about the convention is left alone.

- **A stated ordering rule.** Versions sort semver-descending on `(major, minor, patch)` as
  integers: `0.10.0` above `0.9.4`, which a text sort inverts. Entries at one version join with
  ` · ` in **filename** order — not commit order, so a row is a function of the tree alone and
  two branches that each add an entry regenerate the same row whichever lands first.

- **`<!-- index-note: … -->`** — an optional line in an entry, rendered after that entry's link
  as ` — *…*`. It is how 0.7.1's row keeps saying that its mechanism was later reverted; that
  annotation was the one fact the table carried which no entry file did. The marker must be a
  line of its own: this very entry writes it inside a code span, and the first run against the
  real tree indexed that prose as a note — anchoring it was the fix.

## Changed

- Regenerating rewrote **45 of the 83 rows** and dropped none. The version set and every link
  are unchanged; 8 rows changed cell order under the filename rule, and the rest now carry the
  entry's own H1 where the hand-written cell had been re-edited — lower-cased, shortened, or
  given hyphens and backticks the heading never had. Every differing row is enumerated in
  [PR #207](https://github.com/Arasz/ai-badger/pull/207).
- `--check` runs in `.pre-commit-config.yaml`, the lefthook `docs` lane and CI — the three
  places `index_build --check` runs.
- `RELEASING.md`, `CONTRIBUTING.md`, `docs/scripts.md` and the changelog README's own
  Convention section now say "run the generator" instead of "add a row".
- `gates/docs_guard.py` keeps its "every entry has a row" assertion, now the weaker of two
  overlapping checks. Its docstring says so, and says the generator wins if they disagree —
  the gate still runs against trees the generator is not pointed at, and the "VERSION has an
  entry" half has no other owner.

## Behaviour changes worth knowing

- **Do not hand-edit the table.** Run `python3 tooling/changelog_index.py` and commit the
  result; a stale table now fails pre-commit, the pre-push `docs` lane and CI.
- **An entry needs a `# ` heading.** The generator refuses (exit 1, naming the file) rather
  than indexing a blank title — as it does for a file not named `{version}-{slug}.md`.
- **A conflict on the table line is still possible** and no longer resolved by hand: take
  either side, re-run the generator, and `--check` proves the result. This entry's own row was
  added that way, resolving a real rebase against `0.52.1`.
