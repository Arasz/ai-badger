# 0.87.2 — the catalog carries no real vault identifiers

`features/dotnet/skills/dotnet-sqlcipher-encryption/references/bitwarden-bws-integration.md` shipped
a real Bitwarden Secrets Manager project id and secret id, together with a description of what the
secret's value was. They arrived with the 0.86.0 learned-skills harvest and were public for the
length of one afternoon.

They are identifiers, not credentials — reading them grants no access without a `BWS_ACCESS_TOKEN`.
What they grant is reconnaissance: they name which vault entry holds the key and what it protects.
That is enough to breach `no-hardcoded-secrets`, which asks for sample values that are obviously
fake, not merely non-exploitable. Both are now all-same-digit placeholders, and the line describing
the secret's contents is generic.

`tests/test_catalog_carries_no_real_identifiers.py` stops the class rather than the instance. It
walks every tracked file under `features/` and rejects any UUID that is not an obviously-fake
placeholder, plus credential-shaped strings (GitHub, OpenAI, AWS, Slack). Its own could-fail tests
use the two identifiers 0.86.0 actually shipped, so the check is known to catch the thing it was
written for.

The rotation this calls for happens outside the repository.
