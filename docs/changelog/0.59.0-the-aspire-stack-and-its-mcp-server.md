# 0.59.0 — the aspire stack, and the MCP server the CLI already ships

A project running under an Aspire AppHost now detects as its own stack, and gets
the Aspire CLI's agent surface wired up with it.

## The stack

`features/aspire/` — detected by the files that mark an AppHost:

```
apphost.cs            single-file AppHost (Aspire 13+)
AppHost.cs            the 13.0 project template
AppHost.csproj
*.AppHost.csproj      the classic <Solution>.AppHost naming
```

It `requires` `dotnet`, because an AppHost is a .NET project and scaffolding
aspire alone would miss it.

**Detection is by filename only, deliberately.** The marker that identifies an
AppHost most precisely is the `Aspire.AppHost.Sdk` reference — and that lives
*inside* the csproj. `stack.schema.json` is explicit that content facts belong in
`detect.py`'s dependency pass rather than in a glob signal, so adding it there is
a follow-up rather than something smuggled in as a glob that would never fire.

A test pins the boundary: a `.csproj` with no AppHost detects `dotnet` and **not**
`aspire`, so the MCP prose does not reach every .NET repository.

## The server

`aspire agent mcp`, declared — the Aspire CLI ships it, so a project on this
stack should have it wired rather than described:

```json
{
  "mcpServers": {
    "aspire": { "command": "aspire", "args": ["agent", "mcp"] }
  }
}
```

Thirteen tools are indexed with curated intents, in three groups: read the
running system (`list_resources`, the console/structured logs, the traces), act
on it (`execute_resource_command`, `select_apphost`), and answer authoring
questions from aspire.dev (`search_docs`, `get_doc`, `list_integrations`,
`get_integration_docs`). `doctor` covers the case where a command fails for
reasons that are not the code.

The injected prose says the thing worth saying: **when the question is about the
running system, ask the AppHost rather than reading code and inferring.** The
tools need a running AppHost (`aspire start`); without one they report no
connection rather than an empty system.

`execute_resource_command` is the only write in the set and is called out as
such.

## Sourced, not recalled

Config and tool list taken from
<https://aspire.dev/get-started/aspire-mcp-server/>; the AppHost file names from
Microsoft Learn's Aspire 13.0 upgrade guide. Nothing here is from memory — an
invented tool name in a curated index is worse than an absent one, because the
matcher will happily return it.
