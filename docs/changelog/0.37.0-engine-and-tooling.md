# 0.37.0 — `scripts/` becomes `engine/` and `tooling/`

**Breaking.** Listed in `BREAKING_VERSIONS`. Read "Upgrading" before refreshing.

[ADR-0011](../adr/0011-engine-and-tooling-directories.md), phase 2.
[0.36.2](0.36.2-the-gates-move-out-of-scripts.md) moved the four repo gates to `gates/`; this
finishes the split.

| New home | Files |
|---|---|
| **`engine/`** | `badger_lib.py`, `unsafe_literals.py`, `requirements.txt`, `requirements-dev.txt` |
| **`tooling/`** | `index_build.py`, `validate.py`, `sync_plugin_skills.py`, `version_sync.py`, `install_plugins.py` |

`scripts/` no longer exists. `is_framework_root` now anchors on **`engine/badger_lib.py`**, in
`badger_lib` and verbatim in all 18 bootstrap-shim copies — this changes the string, not the rule
`test_every_bootstrap_shim_is_the_same_predicate` enforces.

The directory was a file-type bucket holding three unrelated concerns: the library every shim
imports, maintainer catalog tooling, and gates a consumer never runs. The names divide on what
actually matters — **what a consumer's code imports** versus **what a maintainer runs**.
`catalog/`, `distribution/` and `release/` were rejected: each names one of the five tooling
scripts' jobs and misnames the other four.

## Upgrading — one command, and it must come from outside your project

```bash
python3 "$AI_BADGER/features/common/skills/den-refresh/scripts/refresh.py" --target . --root "$AI_BADGER"
```

That is the invocation `den-refresh/SKILL.md` has always documented, and it is why this ships as
a single breaking release rather than behind a compatibility window.

> **There is no escape hatch from inside your project, and this is by design.** Your
> `.ai-badger/` carries vendored copies of the bootstrap shim that only know
> `scripts/badger_lib.py`. Against this release they answer "not a framework root" about a
> framework root. `--root`, `$AI_BADGER`, the ancestor walk, the recorded root, the cache and
> `PYTHONPATH` **all fail** — the first two because an operator's declaration is validated with
> that same stale predicate, so ADR-0009's "refuse rather than fall through" turns the escape
> hatch into a second wall.
>
> The fix must come from the framework, not from the project. It already exists.

Verified against a project scaffolded by 0.36.2 and then pointed at this release:

```
before: vendored shims still on the scripts/ predicate: 9 / 9

$ "$FW/features/common/skills/den-refresh/scripts/refresh.py" --target . --root "$FW"
rc: 0   reScaffolded: True   backup: .ai-badger.bckp

after:  vendored shims still on the scripts/ predicate: 0 / 9
        all nine import cleanly
        ~/.hermes/plugins/ re-copied and repointed
```

Only two deployment shapes carry stale shims — a `.ai-badger/` scaffold (9 files) and
`~/.hermes/plugins/` (2). A framework checkout resolves by ancestor walk and the Claude plugin
cache updates wholesale, so both self-heal. `drift_notice_hook.py` keeps running from the cache,
so it keeps telling you to refresh: the recovery loop closes itself.

## Three constraints, each of which silently breaks something

Found by running the split, not by reading it:

1. **`unsafe_literals.py` moved with `badger_lib.py`.** Left behind, `learned_skills_sync.py`
   raises `ModuleNotFoundError` — and that import sits *after* the `try/except RuntimeError`
   ADR-0009 relies on, so the Hermes plugin would **fail to load** rather than degrade to
   silence. That is the exact defect [0.34.1](0.34.1-a-hook-never-breaks-a-session.md) fixed.
2. **Every shim inserts both directories.** `scaffold.py` bare-imports `install_plugins`, which
   lives in `tooling/`.
3. **The five tooling scripts resolve `parent.parent / "engine"`.**

A test now fails any shim that omits either directory or still names `"scripts"`, and a
parametrised test runs each tooling script and fails on an `ImportError`.

## Also

`requirements.txt` and `requirements-dev.txt` moved to `engine/`, alongside the only modules that
declare third-party imports. `deps_guard`, `dependabot.yml` and `pyproject.toml` follow.

`docs/getting-started.md` gains a troubleshooting entry with the exact recovery command and the
plain statement that `--root` does not work here.

`test_a_cloned_repo_cannot_steer_a_session_start_hook`'s decoy now plants
`vendor/engine/badger_lib.py`. Left on `scripts/`, it would have passed for the wrong reason —
the decoy rejected as not-a-root rather than ignored as a working-directory input.
