# 0.34.0 — skills that arrive, and one definition of "framework root"

Forty-five commits. Two of them fix bugs that made ai-badger's most visible promise false: the
plugin advertised skills it did not ship, and `den-refresh` could not deliver a skill added to
the catalog after a project was scaffolded.

## Claude Code can see the skills again

Two independent causes, either sufficient on its own ([#103](https://github.com/Arasz/ai-badger/issues/103)).

**The plugin shipped its skills where nothing reads them.** Claude Code loads plugin skills from
`<plugin-root>/skills/`; ours lived in `.claude/skills/`, which is a *project* path. The loader
said so itself — `Checking plugin ai-badger: skillsPath=none, skillsPaths=0 paths`. The plugin
description promised "welcome-ai-badger, feed-badger, task, …" and delivered none of them, for
roughly twenty releases: cache versions 0.1.0–0.5.0 shipped 6–8 skills at that path, 0.10.2
onward shipped zero.

Skills now live at `skills/` in the repo root ([ADR-0008](../adr/0008-plugin-skills-live-at-the-plugin-skill-path.md)),
and a test asserts the plugin exposes the skills its own description claims — the check whose
absence let this survive.

**Scaffolded projects had no Claude discovery path at all.** `features/copilot/` has three
adjustments; `features/claude/` had none. Copilot and Hermes got working skill discovery from
the same scaffold; Claude got nothing. `features/claude/adjustments/adjust_skills.py` now
symlinks `.ai-badger/skills/<name>` into `.claude/skills/`.

**A skill you hand-committed is never replaced.** A destination is overwritten only when
ai-badger demonstrably placed it — our own symlink resolving inside `.ai-badger/skills/`, or a
path recorded in `manifest.json`. Anything else is left byte-for-byte and named in a note telling
you what to do about it. Third-party skills already in `.claude/skills/` are never touched.

## `den-refresh` can deliver a new skill

[#104](https://github.com/Arasz/ai-badger/issues/104). Three defects, each sufficient alone:
detection never looked at the `common` stack — where **every** framework skill lives — so the
whole catalog was discarded before comparison; `newItems` was computed to gate the re-scaffold
and then dropped from the report; and the re-scaffold took its skill list from `manifest.json`,
a closed loop in which a skill absent from the manifest could never be added to it.

> **The first refresh after upgrading will report — and install — every default-scope framework
> skill your project never received.** For most projects that is one or two; for one scaffolded
> several versions ago it may be several. They install once and the report is clean from the next
> run onward.

> **A skill deleted from a project comes back on the next refresh.** Manifest absence meant both
> "not wanted" and "not yet known", and nothing could tell them apart. `welcome-ai-badger`
> already restored deleted default skills on every run — so removal-by-absence only ever
> "worked" in `den-refresh`, and the divergence between the two entry points *was* the bug.
> **There is currently no supported way for a project to decline a framework artifact.** That is
> a real gap, not a workaround waiting to be documented; the design is recorded in
> [`docs/research/2026-07-27-skill-removal-semantics.md`](../research/2026-07-27-skill-removal-semantics.md)
> and will ship separately.

## One definition of "framework root"

Wave 7. `_bootstrap_lib()` was copied into ten entry points and **five** independent predicates
answered "is this a framework root?" — they disagreed, and two of the four deployment shapes
(a `.ai-badger/` scaffold, `~/.hermes/plugins/`) raised `RuntimeError` at *module import*, which
made the error's own advice to "run with `--root`" unreachable because argparse never ran.

Resolution order is now `--root` → ancestor walk → `$AI_BADGER` → a root recorded in
`manifest.json` **above the script** → the cache ([ADR-0009](../adr/0009-one-framework-root-resolution.md)),
with a four-shape integration test.

Two decisions came out of an independent review that found reproduced regressions in the first
attempt, and both are worth stating because the wrong choice looked reasonable:

- **The recorded root is read above the *script*, never above the working directory.** A manifest
  above the script belongs to whoever installed it; a manifest above `cwd` belongs to whatever
  repository you happened to open. With the latter, a repo containing a crafted
  `.ai-badger/manifest.json` could point at its own vendored directory and get code executed by a
  hook that runs on session start. Re-validating the target proves it *is* a framework tree; it
  cannot prove *whose*.
- **The ancestor walk outranks `$AI_BADGER`.** A script living inside a framework tree is
  unambiguous about its engine; an environment variable is a guess — and a stale one silently
  loaded a different framework's engine against this catalog.

## Drift stops crying wolf

Three permanent false positives, each one a report that appeared on every run regardless of what
you did:

- **Adjustments reported as changed, forever.** The manifest recorded the hash of the file an
  adjustment *wrote* while naming the adjustment *script* as its source, so drift compared two
  different things. In this repository that was 22 entries every run. `feed-badger` stops
  proposing your skill symlinks as contributions for the same reason.
- **Templates and adjustments would have reported as new, forever**, once `common` began being
  scanned — their manifest entries are keyed by output path and can never match an index name.
- The last refresh before upgrading still shows the old entries; they are read from the manifest
  you already have. That same refresh rewrites it, and they do not return.

## `call-behaviorist analyze` measures what it claims to

It audited `.ai-badger/hooks/hooks.json` — what ai-badger *intended* to wire — rather than
`.claude/settings.json`, where hooks are actually registered, so wired hooks were invisible to
it. It keyed components by **basename**, so two different `user_prompt_hook.py` collapsed into
one and an instrumented hook's silence was explained away by its uninstrumented twin. Its own
`enabled`/`cleared` events counted as evidence, so `health: unknown` — documented as meaning
*nobody looked* — was unreachable, and a single bookkeeping line produced a high-severity alarm.

And a fourth, with an uncomfortable provenance: `is_instrumented()` read a command string
containing the literal `${CLAUDE_PROJECT_DIR}`, so the read always failed and **every** hook was
reported as uninstrumented. Hook commands only became placeholder-relative in 0.32.0 — the fix
that repaired duplicate hook registration silently blinded the tool built to detect hook
problems, and nothing caught it because "everything is uninstrumented" looks like a plausible
report.

## Also in this release

- **The statusline capture is wired**, opt-in via `statusLineCapture.enabled` (default off,
  because a project-level `statusLine` overrides your own). It shipped inert: `poll_limit.py`'s
  rate-limit fast path never fired, so every check spent a probe. Disabling restores the renderer
  it displaced.
- **`support.json` said Junie reads `.junie/guidelines.md`**; the scaffolder writes
  `.junie/AGENTS.md`, which is Junie's highest-precedence path. The doc was wrong, and a test now
  asserts every `scaffoldedFile` matches what that agent's `scaffolding.json` actually writes.
- **`$schema` is permitted** by the two schemas that set `additionalProperties: false` without
  it, so adding the editor hint no longer invalidates the file.
- **Secret scanning covers every branch**, not just `main` — a topic branch pushed with no PR
  open was never scanned.
- **`deps_guard.py`** fails the build on a third-party import `requirements.txt` does not
  declare.

## Upgrading

Re-scaffold. The first refresh does more than usual: it installs skills you never received,
rewrites manifest hashes so drift goes quiet, and adds `.claude/skills/` symlinks. Review the
diff — particularly any note about a path left untouched, which means something there is not
ours to replace.
