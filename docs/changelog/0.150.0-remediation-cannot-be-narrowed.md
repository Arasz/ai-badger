# 0.150.0 — the freshness guard cannot be blinded by its own remediation

The scaffold freshness guard's core promise — re-scaffolding ai-badger against itself changes
0 paths — had two holes, both witnessed in production (d-16 finding F2; the 0.140.0 merge
shipped a narrowed manifest at `ea17ae60`). This release closes both, and the scaffolder's
skill-selection contract is now validated instead of silently forgiving.

## What changed

- **R1 — scaffolder argv validation.** `scaffold.py --skills` now refuses quoting-artifact
  values (literal `''`/`""` arriving through non-shell transports, backslashes, untrimmed
  names) with exit 2 and a named message, and refuses names unknown to both the catalog and
  the target manifest (typo protection, with a gateway-alias hint). Previously such a run
  silently skipped the bogus "skill", delivered only config-include + stack-local skills
  (11 of 32 on this repo), and exited 0 — the under-production behind the d-16
  "nondeterministic" freshness failures. `--skills ""` (empty = reuse the scaffolded set,
  #129) and `--skills ","` are unchanged.
- **R2 — the guard detects narrowing.** The guard now derives the expected skill set
  independently of the manifest (`expected_skill_names(root, config)` in `engine/badger_lib.py`
  — scope-default catalog, then include-derived, then stack-local, in delivery block order,
  alias-mapped exclusions at every stage) and **fails fast with a named message** when the
  manifest records a strict subset of it, listing the lost mirrors by path. Previously a
  manifest that under-reported the managed set made every later guard run blind to those
  mirrors — hand edits and upstream staleness included.
- **R3 — the remediation cannot re-narrow.** The guard's re-scaffold and its printed
  remediation now carry the explicit expected set instead of `--skills ''` (one argv builder,
  so the printed advice is still exactly what the guard ran). The old advice recovered the
  skill list *from the manifest being audited* — on a narrowed manifest it regenerated the
  same narrowed set and the guard went green over the defect it had just reported.
- **R4 — determinism pinned.** The scaffolder is pinned idempotent (two consecutive runs,
  byte-identical modulo stamp fields) and the two `--skills` transports are pinned to the
  same managed set. The 0.148.0-era 42-path manifest loss is confirmed already repaired at
  0.149.1 (AC0 double-scaffold: 32/32 skills, 212 entries, run-2 diff empty).

## Upgrade notes

- **Scripts that embedded the old remediation command** (it printed `--skills ''`) keep
  running and keep working on healthy manifests — but stay blind on narrowed ones. Re-read
  the command from the fixed guard's output instead.
- **The scaffolder argv change is consumer-visible** (the scaffolder ships as a mirror):
  garbage or alias-absorbed `--skills` values now exit 2 with a message instead of
  silently scaffolding a narrowed set. If you scripted `--skills` values that only worked
  by accident, they will now refuse loudly — the refusal names the fix (alias hint).
- **Intended new guard findings on superset manifests:** a skill removed from
  `config.include` (but not excluded) surfaces as `manifest.json content differs` when its
  manifest rows drop on re-scaffold; a skill removed from the catalog surfaces as
  "the re-scaffold no longer writes it". Both are the freshness contract working, not
  defects — commit the re-scaffolded manifest in the same change.
- **Gotcha, now documented where you will hit it:** never remediate a freshness-guard
  failure with `--skills ''` — it recovers the skill list from the manifest being audited,
  so on a narrowed manifest it regenerates the same narrowed set and the guard goes green
  over the very defect it reported. Regenerated mirrors ride in the same commit as the
  source edit that made them stale.

Consumer-repo action: none required; re-run `den-refresh` to pick up the fixed scaffolder
mirror.
