# 0.16.2 — factual corrections to the Claude model lanes

Follow-up to #59, which merged before its review round finished. The lane *recommendations* hold;
several of the claims used to justify them did not survive checking against the sources, and one
of them was doing real work in the argument.

## Fixed

- **The Sonnet-only weekly limit is no longer described as bonus capacity.** #59 said Sonnet had
  "headroom nothing else can reach" and that work sent there is "paid for out of an allowance the
  other lanes cannot spend". The source supports neither. It says only: *"Max plans also have two
  weekly usage limits: one that applies across all models and another for Sonnet models only."*
  A model-scoped limit alongside an all-model limit reads at least as naturally as a **second
  constraint** on that model than as a second allowance for it, and nothing on the page says
  Sonnet usage is exempt from the all-model limit. Since this was the stated rationale for the
  largest lane in the document, it mattered. The Sonnet lane is now justified on per-token price
  and task fit, which needs no unsupported premise.

- **The 50% figure is a billing threshold, not a ceiling.** #59 called it a cap you cannot exceed.
  The page actually says: *"once you use up to 50% of your weekly usage limits on Fable 5, you can
  continue in one of two ways: keep using Fable 5 with usage credits, or switch to another Claude
  model."* You are not stopped — you are moved from plan-funded to credit-funded. The plan list
  was also incomplete: it is Max plans, premium seats on Team plans, **and premium seats on
  seat-based Enterprise plans**.

- **The recommendation is now plan-conditional, because it inverts on Pro.** #59 stated "same
  pool, faster burn, 50% ceiling" unconditionally, while separately noting that on Pro and
  standard Team seats Fable bills from usage credits instead. Those two cannot both be applied at
  once: where Fable is not in the plan pool, dispatching it *preserves* the pool that the whole
  argument is trying to conserve, and Opus is the one spending it. `config.json` carries no
  plan-tier signal, so the extension now states both shapes and tells the reader to check
  Settings → Usage rather than assuming a plan.

- **"One weekly pool covers every model" is scoped.** As written it contradicted the same
  document's own Sonnet-limit and Pro carve-outs. It now applies to plan-included models on Max
  and premium seats.

- **The "robust either way" argument about Opus is corrected.** #59 argued that if Opus has its
  own reset it is "strictly better". That repeats the allowance-versus-cap error: a model-scoped
  limit constrains rather than grants, so that branch would make Opus *worse*, not better. The
  underlying ambiguity is real and still flagged — the Max-plan article calls the second limit
  Sonnet-only while the usage-limit best-practices article still refers to a reset "for Opus only
  and all other models" — but it is no longer resolved in the recommendation's own favour.

- **The Fable lane now names its dispatch alias** (`model: "fable"`). Every other lane gave a
  concrete `model` string; Fable did not, leaving the fourth lane with no executable form.

## Added

- `test_real_scaffold_with_retained_extensions_has_no_drift` — a round-trip guard over
  `scaffold.record()` and `drift.compare()`. The existing dir-entry drift tests hand-build their
  manifest, so they cannot catch the two sides diverging on which directory they hash or which
  patterns they exclude. #59 introduced exactly that divergence and the suite stayed green; #62
  has since fixed it, and this test keeps it fixed. Verified to fail when the exclusion sets are
  pulled apart again.

## Known, not fixed

- With `extensions/` excluded from the skill directory hash on all three sides *and*
  `under_dir_target()` suppressing the per-file walk beneath a directory entry, no local edit to
  a file under `skills/<skill>/extensions/**` is detectable by `feed-badger` — such an edit is
  silently discarded on the next re-scaffold, having never been offered upstream. Tracked
  separately.

- `VERSION` went `0.17.0` → `0.16.1` on main after #59 merged, so the `0.17.0` changelog entry
  now sits above a lower version number. This entry continues from the current `0.16.1` rather
  than guessing at the intent.
