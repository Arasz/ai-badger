# 0.219.0 — A re-scaffold removes what ai-badger wrote for a retired catalog entry

**Minor** · **Date:** 2026-11-12

A re-scaffold now removes the config entries that ai-badger wrote for an MCP server or a hook that
the catalog retired. It removes an entry only when it can prove that ai-badger wrote it. ADR-0049
records why (`docs/adr/0049-scaffold-prunes-catalog-retired-entries.md`). The research is in
`docs/work/2026-11-11-prune-retired-catalog-scaffold-entries-research.md`. This closes the prune
follow-up of ADR-0048.

## Added

- **Retired servers in the catalog.** `stack-mcp.json` has a new `retired` array. It keeps every
  launch that ai-badger ever shipped for a retired server. `features/common/stack-mcp.json` retires
  the four semantica launches. The schema shares one server definition (`$defs`) between `servers`
  and `retired`. A framework test reads git history and fails when a launch is deleted from
  `servers` without a `retired` item. That test needs a full clone.
- **MCP prune.** A refresh removes an entry from `.mcp.json`, `.github/mcp.json` and `.pi/mcp.json`
  when its launch matches a retired launch. It reads `retired` from every catalog stack, and it
  never treats a name that any stack still declares as retired. A file that holds a retired entry
  is cleaned even when its agent is no longer selected. A note names each removal.
- **Hook prune.** A refresh removes a hook entry from `.claude/settings.json` only when ai-badger
  owns it, its skill has no catalog source, and the script that the command runs is missing from
  the target. It checks every event. A note names each removed script.
- **Notes.** The Claude adjustment writes a note for each retired server that is still in
  `enabledMcpjsonServers` or `permissions.allow`. It names the exact strings. Hermes projects get a
  note when a retired entry was removed, because the scaffold does not write `~/.hermes`.

## What a refresh never removes

- A permission rule. `mcp__<name>__*` in `permissions.allow` is a plain string. ai-badger cannot
  tell its own rule from a user's rule for a server they installed themselves.
- A name in `enabledMcpjsonServers`, an entry in `permissions.deny` or `disabledMcpjsonServers`.
- An entry whose launch differs from every retired launch. This is how you keep a retired server:
  **change any launch field** (`command`, `args` or `env`), and the refresh keeps the entry and
  writes a "kept" note.
- An entry of a server that is unavailable on this machine, declined in `config.exclude`, or
  user-scoped.
- Anything in `~/.hermes/config.yaml`.

## How to retire a server

Move every launch that ai-badger shipped for the server from `servers` to `retired`. Never delete
a launch. `CONTRIBUTING.md` describes the step.

## Upgrade notes

The first refresh at 0.219.0 removes the semantica entries that ADR-0048 told you to remove by
hand. You still remove these by hand:

- **Claude Code** — the `semantica` name in `enabledMcpjsonServers` and the `mcp__semantica__*`
  rule in `permissions.allow`. The refresh prints a note that lists them.
- **Hermes** — the `semantica` entry under `mcp_servers` in `~/.hermes/config.yaml`.

If you want to keep a server that the catalog retired, change one of its launch fields before you
refresh.

This version is not in `BREAKING_VERSIONS`. A refresh needs no extra step.
