# 0.63.0 — `optIn` becomes a scope a project can choose, and six skills use it

ADR-0005 gave every catalog skill a scope: `default` ships everywhere, `optIn` is "catalogued,
installed only when named". Nothing could name one.

`config.json` had no key that selects a skill. `skillScope` is install scope — plugin or project
— not selection. `exclude.skills` only declines. The single way in was `scaffold.py --skills`,
which no ordinary `welcome-ai-badger` run passes, and which `den-refresh` cannot reach at all
because it recovers the skill list from `manifest.json`: a skill absent from the last scaffold
stayed absent forever.

Every common-stack skill was `default`, so nothing had ever tested the other branch. `optIn` was
a scope that existed in the type and not in the product.

Nothing told anyone an `optIn` skill existed, either — no listing, no description, no instruction
for adding one. A skill could be catalogued, correct, and unchoosable. That is the shape of the
failure ADR-0005 was written about: `code-review-checklist` shipped to nobody for its entire life
and nothing failed.

## What changed

**`include.skills`.** A new top-level `include` object in `config.json`, symmetric with
`exclude`:

```json
"include": { "skills": ["update-documentation"] }
```

It is resolved at `Scaffolder.__init__` — the same single enforcement point that already carried
`exclude`, so `welcome-ai-badger` and `den-refresh` cannot disagree about what a project asked
for any more than they can about what it declined. The effective set is the passed-in skills,
plus `include.skills`, minus `exclude.skills`. **`exclude` wins** when a name is in both.

A name that matches no `optIn` skill — or matches a `default` one, already installed — is a note
and never fatal, following `_note_exclusions`: a refresh refuses on an invalid config, so a fatal
one would turn an upstream rename into a broken upgrade.

The path that mattered was `den-refresh`, because it re-derives skills from the manifest and is
where a silent no-op would have hidden. Adding `include.skills` to a config is already
`drift.configChanged`, so the re-scaffold that delivers the skill is self-executing. There is a
test that walks exactly that.

**`availableOptIn`.** Both the scaffold result and the refresh report now list every `optIn`
skill the project has not installed: its name, a one-line description, and the literal config
edit that adds it.

The description is read from the skill's own `SKILL.md` frontmatter so it cannot drift from the
skill. ADR-0005 rejected frontmatter parsing for *scope* because no script here parses YAML and
`pyyaml` is a guarded optional import — that reasoning is about behaviour, and it still holds.
`skill_description()` is therefore a dependency-free reader of one scalar, used only for
reporting, degrading to `None` on every miss: absent file, no frontmatter, unterminated
frontmatter, missing key, empty block, binary. The degradation is what the tests are about.

`drift.detect_new_items` now skips `optIn` skills. Without that, every `optIn` catalog skill is
an unscaffolded index item, so drift reports it as new on every refresh, forces a re-scaffold
that by definition cannot deliver it, and never quiets.

## Six new skills, all `optIn`

Three documentation skills, contributed from a repository that had used them through a full
documentation migration:

| Skill | Answers |
|---|---|
| `scaffold-documentation` | The tree does not exist yet, or is missing its directory READMEs. |
| `update-documentation` | The hot path: one documentation change, placed, evidence-backed, recorded. |
| `migrate-documentation` | A wholesale reorganisation, resumable across days and compactions. |

Each base skill is usable in a project with **no documentation tooling at all** — every gate that
was a script call is stated as a postcondition the agent verifies by hand, and none was softened
into a suggestion. The tool-bound half is an `extensions/ledger/` fragment gated on `docs.tool`,
which reuses the existing free-form `docs` map, so no schema or engine change was needed for it.
`update-documentation` and `migrate-documentation` link into `scaffold-documentation`'s
`references/` rather than a shared sibling package: `index_build.py` only indexes a directory
containing a `SKILL.md`, so a package beside the skills would never be catalogued and never
delivered.

Three code-navigation skills:

| Skill | Answers |
|---|---|
| `review-changes` | Where does the risk concentrate in this diff, and is it tested? |
| `debug-issue` | Trace the call chain from symptom to entry point before hypothesising. |
| `refactor-safely` | Preview every affected location before changing one; bracket the apply with tests. |

These derive from the skill templates the `code-review-graph` project auto-installs (MIT,
© 2026 Tirth Kanani) and are rewritten so every step carries a baseline path — `git diff`,
`git log -S`, find-references, the project's own configured test command — that needs no graph
server. Each names the graph call as an accelerator and instructs the agent to discover real tool
names from the server's listing rather than assuming them. The rewrite is what makes them worth a
listing slot in a project with no MCP servers at all.

`optIn` is the honest scope for that second group for a second reason: a project that has
`code-review-graph` installed already receives those three from it. Shipping them `default` would
put this framework's plugin mirror and its `.claude/skills/` symlinks in contention with files
another tool owns. `tooling/sync_plugin_skills.MANAGED_EXTERNALLY` existed to prevent exactly
that, and `optIn` reaches the same outcome without ai-badger having to claim the names.

## Consequences

A project that wants any of the six adds them to `include.skills` and refreshes. A project that
does not, gains nothing in its skill listing — which is the point: the listing budget is finite,
and a skill nobody invokes crowds out one somebody does.

`docs/skills.md` now carries a scope column. A reader who cannot tell which skills arrive unasked
cannot use that page.

`docs/authoring-a-feature.md`'s PR checklist gained the line it was missing: a new common-stack
skill must be declared in `badger_lib.SKILL_SCOPES`, or it ships to nobody.
