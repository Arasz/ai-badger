# 0.185.0 — third-party egress is opt-in, and a project can lock it

**Minor** (default flip) · 2026-10-02

ai-badger can now be used in corporate repositories that hold client data. By default, project
data reaches only the agent host's own model provider. See
[ADR-0034](../adr/0034-third-party-egress-is-opt-in-and-lockable.md) and the new
[data access reference](../reference/data-access.md).

## What changed

- **The memory-context pipeline no longer turns on just because `OPENROUTER_API_KEY` is set.**
  Before this release, having the key was enough to send each gated prompt, plus up to 48
  memory and source-code excerpts, to OpenRouter. The pipeline now runs only when all three of
  these hold:
  - `AI_BADGER_ALLOW_THIRD_PARTY=1` is set;
  - the key is present;
  - no `.ai-badger/config.json` in any ancestor directory declares `dataPolicy`.

  In every other case the hook runs one local ai-raccoon search.
- **One egress rule in `openrouter_client.post_json`.** A non-loopback destination needs the
  opt-in, and the project must be unlocked. Loopback is always allowed: the exact hostname
  `127.0.0.1`, `localhost` or `::1`, with no userinfo. A caller that passes no environment is
  refused by default. A request with no key sends no `Authorization` header.
- **`dataPolicy: "local-only"` in `.ai-badger/config.json`** (new schema key) locks third-party
  egress for that directory tree, whatever a developer's shell sets. The check fails closed:
  the tree is also locked if a config file in it is unreachable, unreadable, over 1 MiB,
  malformed, not a JSON object, or not a regular file. The walk covers the resolved path and
  `$PWD`, so a symlinked checkout stays locked. Re-running `welcome-ai-badger` keeps an
  existing `dataPolicy`.
- **Refusals you opted out of are visible.** With the opt-in set and a lock in force, the
  memory hook writes one `hook-errors.log` line naming the locking config (never the prompt).
  `jev_choice.py`'s off envelope gains a `refusal` code and a reason naming the actual cause.
  A notice outside an exception no longer reads "hook failed: Unknown at unknown".
- **The Jev advisory never forwards `OPENROUTER_API_KEY` to a custom endpoint.**
  - `AI_BADGER_JEV_ENDPOINT` must be `https://` or loopback `http://`.
  - It authenticates with the new `AI_BADGER_JEV_ENDPOINT_KEY`, or sends no header when that
    is unset or empty.
  - The unused `jev_choice.endpoint()` helper is removed.
  - A loopback endpoint, for example a local `Mapika/decider` classifier, works even in a
    locked project.
- **New docs:**
  - `docs/reference/data-access.md`, which lists every egress surface and also names what the
    opt-in does *not* govern;
  - the research record behind it, `docs/work/2026-10-02-aib-local-only-data-access-hardening-research.md`.
    It covers the egress inventory and Hugging Face research into local and company-cloud
    stand-ins for Jev.

## Upgrade notes

- **To keep the OpenRouter pipeline**, set `AI_BADGER_ALLOW_THIRD_PARTY=1`. Without it the hook
  silently runs a single local search.
- **Jev advisory users.** With `AI_BADGER_JEV=1` and OpenRouter's default endpoint, the advisory
  now reports `status: off` until `AI_BADGER_ALLOW_THIRD_PARTY=1` is set.
- **The flip takes effect on refresh.** A consumer project keeps the old key-presence behaviour
  until `den-refresh` re-scaffolds its `.ai-badger/` copies. Hermes picks the change up when any
  project refreshes, because it shares one user plugin.
- **Old scaffolders reject `dataPolicy`.** Versions older than 0.185.0 refuse a config that
  contains it (`additionalProperties: false`), so upgrade before committing the lock.
- **Change in `AI_BADGER_JEV_ENDPOINT`.** If you pointed it at a host that relied on receiving
  your OpenRouter key, set `AI_BADGER_JEV_ENDPOINT_KEY` instead.
