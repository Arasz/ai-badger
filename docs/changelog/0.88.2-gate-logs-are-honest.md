# 0.88.2 — the gate's logs record pushes, not test runs

`verify.sh` keyed `LOG_DIR` by checkout so a nested run could not overwrite the log a failing push
cites, and then wrote its one-line summary to a hardcoded `logs/lefthook.log`. The pytest lane runs
`verify.sh`, so the suite appended rows like

```
2026-08-07 14:05:57 | lane | release | FAIL | 0s | failed: release
```

to the repository's own summary. No push produced them, and nothing distinguishes them from rows
that did.

`LOG_SUMMARY` now honours `VERIFY_LOG_SUMMARY`, for the same reason `LOG_DIR` honours
`VERIFY_LOG_DIR`, and the test harness sets it alongside the directory so every gate invocation
from the suite lands in a temp file.

`tests/test_verify_gate.py` also wrote a sentinel into the **real** cited log directory and never
put it back, so a developer whose release lane failed and who followed the `logs:` path in the
failure block read a test fixture. A `_preserved` context manager now restores the prior bytes —
or the file's absence — in a `finally`.

Two existing tests move with it. `test_summary_log_is_appended_on_run` and
`test_summary_log_records_failed_lanes` asserted against `REPO / "logs" / "lefthook.log"`; they now
read the redirected path. Their intent is unchanged — both are about the summary's append behaviour
and pipe-delimited format, not about where it lives — and both were the tests writing the phantom
rows above.

This is small and it comes first because everything else is measured with these logs. A gate whose
own record cannot be trusted makes every timing and lane claim downstream unfalsifiable.
