# 0.147.0 — status-report skill: mid-task status without waiting for the task

A new default-scope common skill that answers "where are we?" in seconds while a task is
still running — current task, progress as a checklist, what is next, and sub-agent/
delegation status — without deferring the answer to task end. Its defining contract is
importance: a status request is handled at the first natural boundary, never queued behind
the work it is asking about.

## What changed

- `features/common/skills/status-report/` — SKILL.md + `scripts/status_report.py`.
  The script is stdlib-only (it ships into scaffolded projects where `badger_lib` does not
  exist) and exits 0 on every reporting path: each tracking source degrades independently
  to its section's placeholder ("(no task in progress)", "(no plan file)", "(not found)",
  "(no live lanes)") instead of failing the report.
- Four sections, each from an existing source the `/task` pipeline already writes:
  **current task** (latest IN_PROGRESS in `executed-tasks.json` wins; other open tasks stay
  visible), **progress checklist** (plan-file package headings + `- [x]` counts, with an
  explicit newest-file-fallback marker when no plan filename carries the task id),
  **what's next** (`state.json`'s `next`, verbatim), **sub-agents & delegation** (recorded
  subagent entries from `token-usage.json`, live lane worktrees matched to open task ids
  including `-lane-*` prefixes, live sessions from `current-session.json`).
- Honest-by-construction rules the SKILL.md pins: an empty recorded-subagent list does not
  mean no delegation is running (records land on completion only); stale IN_PROGRESS
  entries from dead sessions are reported, not hidden; loop-step positioning is the
  agent's inference and must be phrased as such; the agent adds one live-session line from
  its own context, kept visually apart from the script-derived records.
- The skill is `scope: default` (ADR-0018) — it arrives in every scaffolded project
  without being asked for.

## Discovered en route (operational)

Skill delivery resolves skills through `index.json`
(`skill_delivery.scaffold_skills` → `find_skill_in_stacks`), so a brand-new skill must be
indexed **before** the self-scaffold run that delivers it — index-then-scaffold, not the
other way round. With the stale index the scaffold silently skipped the new skill ("not
in any configured stack") while still passing the freshness guard, because the guard
re-scaffolds with `--skills ""` (reuse-manifest) and cannot notice a skill the manifest
never gained.
