# 0.44.0 — Shape D refuses to run stale plugin copies

[0.35.6](0.35.6-the-cache-reports-its-own-skew.md) taught the framework cache to report its own
skew and recorded, under "Not covered", that Shape D — the two hook modules copied into
`~/.hermes/plugins/` — stayed unjudged. This closes that gap, though not in the way the note
predicted.

## The gap was not where it was recorded

The note said the installer's record carries no `frameworkVersion`, so `warn_on_cache_skew` reads
`None` and stays quiet. True, and nearly worthless: that check returns before it consults the
manifest unless the resolved root **is** the cache, which in a normal Shape D install it is not.
Adding the key would have bought a warning for one unusual install choice.

Investigating it surfaced the failure that actually bites.

## Copy skew

The modules in `~/.hermes/plugins/` are **snapshots taken at install time**. The framework root
they resolve keeps moving. A user who installed at 0.30.0 and has since pulled their checkout to
0.43.0 runs 0.30.0 hook code against a 0.43.0 engine — the engine/catalog skew
[ADR-0007](../adr/0007-no-python-distribution.md) exists to eliminate, arriving through the one
door nothing inspected. It needs no unusual choice, only the passage of time.

`adjust_hooks._record_framework_root` now stamps the copies with `copiedFromVersion`, and both
plugin modules compare it against the root's current `VERSION` at import.

**The key is deliberately not called `frameworkVersion`.** Everywhere else in the tree that name
means *the version that scaffolded this project*; Shape D has no project, and the only knowable
value is *the version that produced these copies*. Same shape, different question.

## Warn, refuse, or say nothing

| Comparison | Behaviour |
|---|---|
| Equal | Silent. The common case costs one `.get()` and one string compare. |
| Differs, no `BREAKING_VERSIONS` entry between them | One stderr line; the hook runs. |
| Differs, a boundary between them | **Refuse.** |

Materiality reuses the project's existing answer to "does this difference require action" rather
than inventing a second severity rule: `BREAKING_VERSIONS` already means *a full re-scaffold is
required*, `den-refresh` already reads it that way, and `badger_lib.is_breaking_transition` already
implements the predicate. A docs-only patch bump must never disable anyone's hooks.

**Direction is normalised.** `is_breaking_transition` is asymmetric by design — `from < breaking <=
to` cannot hold when `to < from` — but a *downgrade* across a boundary is exactly as dangerous:
newer copies against an older engine. The check orders the pair before asking, so a boundary
between the two versions is material whichever way the skew runs.

## Refusing without breaking the session

Refusal never raises, never changes an exit code, and never ends a session. Each module declines in
its own idiom:

- `ai_badger_hooks.register()` registers none of its three callbacks and says why on stderr. **The
  plugin still loads** — the agent runs with ai-badger's hooks absent rather than wrong.
- `learned_skills_sync` entry points return `_refused(...)`, exactly as they already do when the
  engine is unreachable.

Absence is never treated as evidence: a record written before this release, an unreadable
`VERSION`, an unparseable manifest, or a version string that cannot be ordered all leave the copies
unjudged and running. Any deployment that is not Shape D has no record beside the module at all, so
the check costs one missing-file stat and returns.

## Where the check does *not* live

Not in the bootstrap shim. `test_every_bootstrap_shim_is_the_same_predicate` pins all ten shim
copies byte-identical, and copy skew is Shape-D-specific while the shim serves ten call sites that
mostly are not. Putting it in the two plugin modules' own startup leaves the shared predicate
untouched — that test still passes, and it was the safety net for this change.

## Not covered

**Copies edited by hand are still undetectable.** The record describes what the installer wrote,
not what is on disk; a content hash would close it and is deferred until someone reports it
mattering. **There is no override.** Re-running `welcome-ai-badger` is the remedy, and an escape
hatch waits for a user genuinely blocked without one.

**A rolled-back root cannot report boundaries added after it.** `BREAKING_VERSIONS` is read from
the resolved root, the only tree the check has. On an upgrade that root is current and lists every
boundary; on a downgrade it is the older tree, and a boundary introduced later is missing from its
own list — so the same version pair refuses one way and warns the other. Closing it needs a
boundary list trustworthy independently of the root, which does not exist today. The behaviour is
pinned by a test rather than left to be rediscovered.

## Upgrading

Nothing required. Existing installs carry no `copiedFromVersion` and keep running exactly as
before; the stamp appears the next time the Hermes plugins are installed or refreshed.
