# 0.107.0 — the edit guard allows the files a project is told to own

0.101.0 made `generated_file_guard.py` agree with `scaffold_freshness_guard` for *templates*, by
recording `seedOnce` on the manifest entry the scaffolder writes. Two files inside the skills
tree were still on the wrong side of that agreement. Probed against the live guard at 0.104.0:

```
DENY  .ai-badger/skills/prompt-markers/markers-context.json
DENY  .ai-badger/skills/task/project-local.md
```

Both are files `skill_delivery` deliberately preserves. It stashes them before the `rmtree` +
`copytree` and writes them back afterwards, which is exactly why the push-time gate is happy for
a project to edit them — they are the two documented ways a project customises a delivered skill.
The guard refused them anyway.

## Why `seedOnce` could not be reused

`seedOnce` is a boolean on the entry for one file. Neither of these files *has* an entry: a skill
is recorded as a single directory entry (`.ai-badger/skills/task`), and everything under it
inherits that entry's verdict. `project-local.md` cannot be given one — a manifest entry requires
a `source`, and no catalog ships a `project-local.md` for the guard to point an author at.

So the entry that exists has to say which of its contents are not the framework's:

```json
{ "feature": "skills", "target": ".ai-badger/skills/prompt-markers",
  "projectOwned": ["project-local.md", "markers-context.json"] }
```

## One list, written by the code that preserves

The two kinds of preserved file — `project-local.md` and `SEED_ONCE_SKILL_FILES` — were already
one concept in `SkillDelivery.project_owned_files`, which `superseded_prune` consults before
deleting a skill tree. That concatenation is now the module-level `project_owned_names`, and it
has two readers: the preservation itself, and the `projectOwned` value the scaffolder records.

The guard reads the manifest and nothing else. **Adding a name to `SEED_ONCE_SKILL_FILES` needs
no change to `generated_file_guard.py`** — the next scaffold puts it in the manifest, and the
guard allows it. That acceptance is pinned by a test that injects a name and probes the guard:
`test_a_newly_preserved_skill_file_is_allowed_without_touching_the_guard`.

`Scaffolder.record` grew a `**extra` that is merged into the entry verbatim, so a collaborator
can record what it knows and the entry alone cannot say. `scaffold.py` is 849 lines against its
850 budget.

## Allowing the edit was half of it

Exempting the file at edit time and stopping there would have moved the refusal, not removed it.
A skill's `hash` covers the written directory, so editing a preserved file inside one moved the
manifest, and the push gate rejected what the edit gate had just allowed:

```
SCAFFOLD FRESHNESS GUARD FAILED: re-scaffolding this repo against itself would change 1 of 1402 path(s):
    .ai-badger/manifest.json  (content differs, regenerates differently)
```

`seedOnce` never had this problem because `templates` is `hashes_source` — the recorded hash is
the catalog's, so editing `state.json` cannot move it. A skill's is not. So the recorded `hash`
now drops the `projectOwned` paths via `dir_content_hash`'s existing `exclude_rel`, the same
mechanism that already keeps an adjustment's file out of the skill it wrote into (#224). Both
readers of that hash drop them too, or every skill would read as edited forever:

| Reader | Question it answers | Change |
| --- | --- | --- |
| `drift._dir_entry_verdict` | did the project edit its copy? | `exclude_rel` gains the entry's `projectOwned` |
| `detect_additions` (feed-badger) | is this skill a contribution? | same |

`dir_count` comparison is still keyed on nested entries alone — a preserved file is a file, and
skipping the structural check for every skill would have cost more than it bought.

Measured after the change, with `markers-context.json` hand-edited in this repo: the edit guard
says `ALLOW`, and `scaffold_freshness_guard` reports `1402 path(s) compared … only version stamps
differ — PASS`. Adding a `project-local.md` is allowed too and passes the gate once re-scaffolded
— `SKILL.md` is appended from it, so that file is genuinely stale until the scaffold runs.

## What is still refused

Only the listed names, and only inside the entry that lists them:

- `SKILL.md` and `scripts/*` in the same skill directory — still denied, pointing at the catalog.
- A name absent from that skill's list — denied. The guard reads the list; it does not assume
  `project-local.md`.
- One skill's list does not reach a sibling skill's copy of the same filename.
- A more specific entry still wins: `.ai-badger/skills/task/scripts/claude_session_source.py` is
  written by `features/claude/adjustments/adjust_task.py`, which has its own entry, so naming it
  on the directory entry would not exempt it.
- An empty string in the list does not exempt the skill directory itself.
- A malformed `projectOwned` (a string where a list belongs) exempts nothing, and does not throw
  — a `PreToolUse` hook that dies blocks the tool it gates.

A manifest written before 0.107.0 carries no `projectOwned` and every file inside a skill reads
as generated, which is the same self-healing refusal `seedOnce` chose: loud, overridable with
`AI_BADGER_ALLOW_GENERATED_EDITS=1`, and fixed by one re-scaffold.

`schemas/manifest.schema.json` gains `projectOwned` (`entries` items are
`additionalProperties: false`, so an unlisted key would have failed `validate.py`).
