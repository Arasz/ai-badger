# 0.35.3 — an untagged release fails the guard instead of mentioning it

`release_guard` already detected releases that shipped without a tag. It printed
`UNTAGGED RELEASES: …` and then returned **0**, with a test asserting that on purpose:

```python
assert rc == 0  # informational: the bump itself is correct
```

The reasoning was narrowly true — the bump under inspection *was* correct — and it made the
check unable to do the one thing it existed for. **0.35.0, 0.35.1 and 0.35.2 all shipped
untagged**, which is what the detector was written to prevent after the incident recorded in
[`docs/incidents/2026-07-27-untagged-releases.md`](../incidents/2026-07-27-untagged-releases.md).
A warning on a passing gate is read by nobody; the gate was green, so the push went out.

The consequence is not cosmetic. `release_guard` compares the shipped surface against the last
release tag, so three untagged releases left every later run comparing against **0.34.1** — a
baseline nine commits stale, silently widening the diff it was supposed to police.

## What changed

**An untagged release now returns 1.** The message is unchanged; the exit code is not.

**The check runs before the diff, and independently of it.** It used to sit on one narrow
path — shipped surface changed *and* VERSION bumped — so the pushes that actually followed
0.35.0 never reached it: they were docs-only, took the early `no shipped-surface changes —
PASS` return, and never looked at tags at all. An untagged release is a fact about the
repository, not about what a particular push happened to touch, so it is now checked on every
run that finds a tag.

**The failure prints the fix**, one `git tag -a` line per missing version, because the remedy
is the non-obvious part: the tag belongs on the commit that carried that VERSION, not on HEAD.

Unchanged: the version in `VERSION` is still exempt. One release in flight is the model
(`RELEASING.md`, "Several PRs, one release"), and a test pins that boundary.

### The limit worth knowing

The guard resolves the last tag by highest semver, so it only ever sees versions **above** it.
A version left untagged below the highest tag is invisible and stays that way. This catches the
release you just shipped — not archaeology.

## Upgrading

Nothing required, but the first run after upgrading fails if you have untagged releases, and
lists them. Tag them at the commit carrying each `VERSION` and push the tags. In this
repository that was 0.35.0, 0.35.1 and 0.35.2, now tagged at `97999a2`, `bea9c85` and
`d26db3f`.
