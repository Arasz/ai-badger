# 0.38.0 — an upgrade is not version skew

[#108](https://github.com/Arasz/ai-badger/issues/108).

`call-behaviorist analyze` aggregated the set of versions a component ran at **across the whole
window** and emitted `version_skew` at severity `high` whenever that set had more than one member.

During a window in which the framework itself shipped seven releases — `0.35.1 → 0.36.0`, which is
exactly what this repository did on 2026-07-27 — every component legitimately ran at several
versions *in sequence*. `analyze` reported all seven as high severity and returned
`health: degraded`. **Six were artefacts of upgrading. Exactly one was real**, and finding it meant
reconstructing the timeline by hand.

That is the failure mode the tool exists to prevent: a `high` finding that fires on every ordinary
upgrade teaches the reader to skip it, so the one real instance is buried among six false ones.
The same shape as [0.35.4](0.35.4-behaviorist-stops-inventing-failures.md), one layer up.

## The rule is now temporal, not set-based

Each version a component ran at carries the range it was observed in — `{from, to, records}`,
exposed as `observed[component].version_ranges`.

- **Ranges disjoint** → an upgrade. Reported as **`version_progression`** at a new **`info`**
  severity, which is excluded from the health verdict entirely. A severity that fires on every
  ordinary upgrade is the disease, not the cure.
- **Ranges overlap** → two copies were live at once. Still `high`, and now naming each competing
  version with its observed range:

```
[high] version_skew: drift_notice_hook
    two copies were live at once — their observed ranges overlap:
    0.35.2 [2026-07-27T22:55:42+00:00 → 2026-07-28T06:41:21+00:00];
    0.36.0 [2026-07-28T06:25:49+00:00 → 2026-07-28T06:48:09+00:00]
```

**A range whose timestamps cannot be parsed counts as overlapping.** Unreadable evidence must not
silently drop a real finding — the same reasoning that makes `release_guard` fail rather than pass
when a git command errors.

Replaying the issue's exact window — six hooks upgrading in sequence plus the one genuine overlap
— now yields **one** high finding where it used to yield seven.

## `unknown` was being counted as a version

429 of 2,291 records in that window carried `version=unknown`. It is `VERSION_UNKNOWN`, the
documented sentinel for *"no VERSION file and no manifest above the code that ran"* — an absent
number, not a version. Counting it as one manufactured skew.

It is excluded from the version set for both skew and progression, and **not discarded**: a new
`version_unresolvable` finding (severity `low`) reports how many records could not name a version
and the span they cover. Records carrying `unknown` are evidence of a scaffold copy predating
0.35.4, which is precisely the signal
[#109](https://github.com/Arasz/ai-badger/issues/109) is about.

## Why minor rather than patch

Two new finding kinds and a new `info` severity are additive changes to the report schema. Anything
parsing `findings` will see them.

**Consequence worth knowing:** because `version_unresolvable` is `low`, a project whose scaffold
predates 0.35.4 now reports `health: warn` rather than `ok` until it is refreshed. That is honest —
there really is a stale copy — but it is a change in what a clean report looks like.

## Not done

The issue's alternative suggestion — compare versions within a single session id — is not
implemented. Range overlap covers the case without depending on a session field that most records
lack.

Timestamps are second-granularity, so two versions whose switchover lands inside the same second
read as an overlap. Deliberate: a same-instant disagreement is the concurrency case.

## Note

No existing test was rewritten or deleted; all 43 prior assertions pass unchanged. That is the
evidence against overshoot — the risk in this change was making `version_skew` never fire at all,
and the two tests that assert it fires on same-instant records still do.
