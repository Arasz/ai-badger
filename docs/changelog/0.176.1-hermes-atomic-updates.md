# 0.176.1 — the Hermes plugin's two counters stop losing updates

**Patch** — `features/common/hooks/ai_badger_hooks.py` (the Hermes plugin) now routes both
its test-economy and commit-reminder call sites through the sibling modules' own atomic
`update_entry`, closing the same class of race P02 and P03 already closed on the Claude
side. 2026-09-24.

## What was wrong

- The test-economy call site ran `test_economy.get_entry`, then `advance_session`, then
  `set_entry` as three separate store round trips. A second plugin invocation landing
  between the read and the write computed from the same stale entry, so one of the two
  full-suite counts was lost.
- The commit-reminder call site ran the same three-step shape:
  `commit_reminder.get_entry`, `advance`, `set_entry`. Two edits landing close together
  could lose one crossing the same way.
- P02 and P03 already fixed this exact race on the Claude-side hooks by adding
  `suite_economy.update_entry` and `commit_reminder.update_entry`, each one atomic
  `kv_update` transaction. The Hermes plugin kept calling the older three-step sequence.

## What changed

- `_maybe_count_test_run` now calls `test_economy.update_entry(project, session, is_full,
  now=...)` directly; the hook no longer calls `get_entry`/`advance_session`/`set_entry`
  itself.
- `_maybe_remind_commit` now calls `commit_reminder.update_entry(project, count, threshold,
  escalate_after, now=...)` directly, in place of `get_entry`/`advance`/`set_entry`.
- Both sites' output is unchanged: the same `fires`, `escalated`/`at_risk` and message text,
  since `update_entry` computes them through the same `advance_session`/`advance` logic —
  only the store round trip collapses from three calls to one transaction.
- No new store API: this only swaps the call sites to the atomic helpers P02 and P03
  already built.
