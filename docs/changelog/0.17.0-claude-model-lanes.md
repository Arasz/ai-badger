# 0.17.0 — Claude model lanes for the `task` skill

## Added

- **`task` extension: `claude`** (`features/common/skills/task/extensions/claude/`), gated on
  `agents=claude` in `.ai-badger/config.json`. It binds the base skill's delegation *roles* to
  concrete Claude models — Opus for planning and the Phase 3 quality gate, Sonnet for
  implementation by default, Haiku for trivial mechanical work — and documents the subscription
  metering that makes those the cheap choices.

  The reasoning that drives the lanes, verified 2026-07-26 against `support.claude.com`: a
  single weekly pool covers every model, so a higher tier is not extra capacity. Fable draws
  from that same pool, spends it faster, and is separately capped at 50% of it, which makes it
  strictly worse value than Opus for the same reasoning work. Sonnet is the one lane with an
  additional Sonnet-only weekly limit, so pushing work there spends an allowance nothing else
  can reach. The extension carries a re-verification note, since limits change.

  > **Superseded — see `0.17.4-claude-lanes-factual-corrections.md`.** Several claims in the
  > paragraph above did not survive review against the sources: the Sonnet-only weekly limit is
  > not documented as bonus capacity, the 50% figure is a billing threshold rather than a
  > ceiling, and the comparison inverts on Pro and standard Team seats. The shipped extension
  > text has been corrected; this entry is left in place as the historical record.

## Fixed

- **A scaffolded skill that keeps a config-gated extension no longer reads as permanently
  "changed".** `scaffold.record()` hashed the skill directory *including* `extensions/`, while
  `feed-badger`'s `detect_additions` hashed it *excluding* `extensions/`. The two could never
  agree for any project whose config retained an extension, so `feed-badger` reported the skill
  as locally modified forever and offered to contribute framework content back upstream. Both
  sides now exclude `extensions/`: gating keeps or prunes it per project, so it is not part of
  the skill's own identity.

  This was latent rather than new — it was invisible only because every existing extension is
  pruned under the test suite's minimal config, and the first extension that survives by default
  exposed it. Verified against a real scaffolded repo, where `.ai-badger/skills/task` and
  `.github/skills/task` were both being reported as changed. Existing projects clear the false
  positive on their next re-scaffold, which rewrites the manifest hash.

  Not addressed here: `drift.py` hashes the framework *source* directory against the same
  manifest field that `scaffold.record()` writes from the *target*, so those two disagree for
  any skill with extensions as well. Fixing it means deciding what the manifest hash should
  mean for extension content, which deserves its own change rather than a ride-along.

## Changed

- The base `task` skill's **Model & delegation policy** now says explicitly that its bullets are
  roles rather than models, and points at the agent-specific extension for the binding. The base
  stays model-neutral.
- The **Extensions** footer now covers agent-specific model lanes alongside source control.
- The **`hermes`** extension no longer claims the base skill contains Claude model names — it
  never did after the base was made neutral, and the stale sentence sent readers looking for
  text that was not there. It now frames itself as the Hermes-side binding of the same roles,
  parallel to the new `claude` extension.
