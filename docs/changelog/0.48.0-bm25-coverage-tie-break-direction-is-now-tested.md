# 0.48.0 — the BM25 coverage tie-break's direction is now tested

## The gap

`features/common/retrieval/bm25.py`, `Bm25Corpus.rank`, sorts results by
`(-r.score, -r.coverage, r.doc_id)`. The mutation-testing pass in #151 found a survivor:
flipping `-r.coverage` to `+r.coverage` changed nothing the existing suite could see, because no
test constructed two documents whose scores land on the *exact same float* while their coverage
differs — the only condition under which the second sort key ever decides anything. Filed as
#154 rather than blocking #151, since a clean test needed a hand-tuned corpus rather than an
obvious addition.

## The test

`tests/test_retrieval_bm25.py::test_coverage_breaks_an_exact_score_tie_toward_higher_coverage`
drives the real `Bm25Corpus.rank` (not hand-built `ScoredDoc`s, which would exercise Python's
`sorted` rather than this code) with an analytically solved tie: two documents of equal weighted
length so `length_norm` cancels, matching disjoint query terms of unequal document frequency so
their coverage differs, and one document's term frequency solved so its BM25 score equals the
other's bit-for-bit. The test asserts that equality with `==`, not `pytest.approx` — an
approximate tie would let the primary `-r.score` key decide the order and never exercise the
coverage tie-break, making the test theatre.

Verified by hand: flipping `-r.coverage` to `+r.coverage` in `bm25.py` fails the new test (the
order assertion, specifically — the score-tie and coverage-difference assertions still hold);
reverting restores green. #151's mutmut lane was not yet on `main` at the time this landed, so
the mutation-testing confirmation step was skipped rather than run against a tool that isn't
there yet.

## Not covered

No production code changed — the tie-break's behaviour was already correct, only untested.
