# 0.53.0 — one frontmatter block, and the configured stacks' personas

[Issue #210](https://github.com/Arasz/ai-badger/issues/210). The Copilot agents adjustment had two
defects, both visible in this repository's own `.github/agents/`.

**It emitted two frontmatter blocks.** The converter wrote its own `---` header and then appended
the persona file whole — including the persona's own `---` block. `architect.agent.md` carried one
at lines 1-10 and a second at 12-26. Whatever the Copilot CLI does with the second block, it is not
what was intended.

**It delivered personas from stacks the project does not use.** It iterated every stack in the
whole index rather than the configured ones, and never consulted `config.exclude.personas`. This
Python/JS repository was shipped `dotnet-engineer`, `angular-engineer`, `cloud-infra-engineer` and
`frontend-engineer` — four personas for stacks it does not have. `.ai-badger/agents/` held the
right five files the whole time, because `scaffold_personas` applies the correct rule.

## One rule, read by both deliveries

The correct rule is extracted to `badger_lib.applicable_feature_items(index, config, feature)` —
resolved stacks (including `commonStacks`) minus `config.exclude[feature]`, as `(stack, item)`
pairs. `scaffold_personas` now reads it instead of open-coding it, and the scaffolder passes its
result to every adjustment as `context["personas"]`.

The adjustment does **not** re-derive a set of its own. That is deliberate and it is why the fix
holds: an adjustment is loaded by path from the framework root, and the convention already in
`run_adjustments` is that what an adjustment cannot resolve itself travels in the context — as
`skills`, `mcp_declarations` and `mcp_declined` already do. A second copy of the stack rule inside
the adjuster is exactly the divergence this issue is about, and resolving `engine/badger_lib.py`
from an adjustment would also plant a second root predicate, which
`test_no_root_predicate_lives_outside_a_bootstrap_shim` forbids (ADR-0007).

## What an emitted agent file looks like now

The persona's frontmatter is parsed off, merged, and re-emitted once. Precedence is
**defaults < the persona's own frontmatter < `PERSONA_MAP`**, so an unmapped persona keeps its own
description and tools instead of getting `AI agent persona: <name>`, while the three deliberate
Copilot mappings (`architect`, `code-reviewer`, `test-engineer`) still win. A `tools:` value
written as one comma-separated string — how the persona files spell it — is normalised to a list.
A persona with no frontmatter at all still converts, on the defaults.

## Stale files from earlier runs are removed

Fixing the rule is not enough on an existing project: the four wrong-stack files were already on
disk. `prune_superseded` does not reach them — their manifest entries carry feature `adjustments`
under the still-configured `copilot` stack, so nothing but the adjuster knows which of its own
outputs this run no longer asks for. The adjustment now reads the prior manifest and deletes the
`.github/agents/*.agent.md` files attributed to it that this run did not write, and names them in
its note. A hand-authored `.agent.md` has no manifest entry and is never touched.

## On this repository

`.github/agents/` goes from nine files to five, and matches `.ai-badger/agents/` exactly:
`api-engineer`, `architect`, `code-reviewer`, `hermes-agent-author`, `test-engineer`.

## Tests

`tests/test_adjust_agents_copilot.py`, ten cases. Four cover the frontmatter contract, two the
pruning behaviour (including the hand-authored file that must survive), one asserts the adjuster
delivers exactly what the context carries and re-derives nothing, one pins
`applicable_feature_items`, and two run the real adjustment through `Scaffolder.run_adjustments`
over a fake framework — the end-to-end check that a dotnet persona and a declined persona both
stay out of `.github/agents/`.

No test was rewritten: the file is new in this change.
