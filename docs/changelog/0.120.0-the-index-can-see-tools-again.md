# 0.120.0 — the index can see tools again

Since #188, `mcp-index` has had no way to learn what tools a server exposes. `hermes mcp list
--json` was the only listing that carried tool names, and it does not exist on the installed
hermes. #187 removed the data-loss hazard that created — a text-mode listing yields
`status: unknown` and touches no tools — but nothing restored discovery, and the closed issue
said so.

Measured on a project scaffolded at 0.119.0: `mcp-index update` listed 19 servers and added
`semantica` with **zero** tools, while `features/common/mcp/semantica/tools.json` describes
eleven of them. Fifteen live, connected servers held nothing. The recommendation hook offered
`ai-raccoon:get_prompt`, a tool that is not in that server's surface, because nothing could tell
the index it had gone.

Two mechanisms here, and they compose. Against the installed hermes, a listing that carried no
tools at all now yields **133 tools across 11 servers**: 128 enumerated directly, and 5 for
`code-review-graph`, which could not be tested and fell back to the catalog.

## `hermes mcp test <server>` enumerates tools, so ask it

#188 listed this as a candidate and nobody had checked. It works — twelve tools for `semantica`,
one server per invocation. `--discover` on `init` and `update` asks it for every server the
listing left unenumerated.

The trap is the exit code. `hermes mcp test` exits **0 whether it connected or not**:

```
$ hermes mcp test plugin:github:github
  ✗ Server 'plugin:github:github' not found in config.
  Available: dotnet-sdk, glider, code-review-graph, ai-raccoon, rider, semantica
$ echo $?
0
```

A parser that trusted that would read "not found" as "this server exposes nothing" and mark a
whole source empty — the exact shape of the 98-tool wipe #187 was written to prevent. So
`parse_hermes_test_tools` returns `None`, not `[]`, unless it sees the printed
`✓ Tools discovered:` block, and `enrich_with_hermes_test` leaves a server it could not test at
`tools_known: False` so absence stays non-evidence. Three tests pin the distinction.

It is opt-in because it costs one connection per server — roughly 20s for eleven. A server
hermes does not have in its own config, which is every plugin- and connector-provided one,
cannot be tested at all and falls through to the catalog.

## The catalog could not reach a project that had no listing

`_redescribe_from_catalog` iterates `source["tools"]` — the tools already in the index. It
re-describes; it never adds. Populating a source had only ever come from the host listing, so
once no listing carried tools, a server the framework fully describes landed as `tools: {}` and
stayed there. Curation shipped in `features/<stack>/mcp/<server>/tools.json` was unreachable for
every server except the ones `hermes mcp list --json` used to enumerate.

`_seed_from_catalog` fills a source when, and only when, the host declined to enumerate
(`tools_known` False). It is a floor, never an override, and each clause has a test:

- a listing that carries tool detail is authoritative, **including when it reports none**
- an entry already in the index wins, whatever its `origin` — `manual` curation is untouched
- a tool marked `status: removed` stays removed; the seed does not resurrect a retirement
- a server the catalog does not know stays empty; seeding invents nothing
- run twice, the index is byte-identical

## Plugin-decorated server references in `tag` and `intent`

Carried in from the branch opened alongside this work, unchanged, with its own tests.

## A note on the design that did not ship

The first version of `--discover` threaded a third parameter through `_fetch_mcp_tools`. That
broke four existing stubs in `tests/test_mcp_index_server_status.py`, which patch the function
with a two-argument lambda. Rewriting those four tests to accept the new arity would have been
the obvious repair and the wrong one: the enrichment does not belong in the fetch, it belongs
after it. Moving it up to the command level left the signature alone and deleted the diff. The
regression was the design review.
