# 0.139.0 — Git owns its own storage

**Minor.** 2026-08-28. New PreToolUse guard and SessionStart check; no breaking changes.

## The incident

An agent hand-edited a repository's `.git/config`, truncating it to 296 bytes and losing
`remote.origin.fetch` along with nearly every `[branch]` tracking section.

The consequence was measured in throwaway repos rather than reasoned about. With the refspec gone:

```
$ git fetch origin
 * branch            HEAD       -> FETCH_HEAD
$ git for-each-ref refs/remotes/
  refs/remotes/origin/main 0d62ff9      <-- STALE; the remote was at 33e309f
```

Fetch reports success and exits 0. `refs/remotes/origin/*` silently stops moving, so
`origin/main` freezes at whatever commit it held when the file broke, and every later comparison
against it — diff, log, merge-base, a rebase target — answers about a snapshot instead of the
remote. That silence is why this is refused at edit time rather than detected downstream.

The `[branch]` loss is the louder half: without `branch.<name>.merge`, `git pull` fails outright
with "There is no tracking information for the current branch."

## `git-internals-guard` (PreToolUse)

`features/common/skills/git-work/scripts/git_internals_guard.py` refuses a hand write to a git
dir. The rule is path-shaped, not program-shaped: a path is protected when any component is
`.git`, when the final component is `.git` (the pointer file a linked worktree or submodule
uses — truncating it detaches the worktree), when it is one of git's user-level configs
(`~/.gitconfig`, `$XDG_CONFIG_HOME/git/config`), or when a bounded ancestor walk finds a
directory holding `HEAD`, `objects` and `refs` — which is what keeps bare repos and
`git init --separate-git-dir` in scope, where no component is literally `.git`.

Edit-shaped tools hand their target path to that predicate. Bash commands are lexed into ordered
write/run events, tracking `cd`, and checked for a redirect target, a mutating program with a
protected path in its arguments (`sed -i`, `tee`, `truncate`, `dd`, `cp`, `mv`, `rm`, …), an
interpreter one-liner whose code names one, and a nested `sh -c` to recurse into.

`git ...` is allowed unconditionally and every read is allowed. `git config`, `git remote` and
`git branch --set-upstream-to` write through git's own lock file and touch only the key they are
given; they are the repair route the refusal names.

**This is a guard against accident, not an authorization boundary.** It fails open on a lexer
error, an oversized command and any exception, because a PreToolUse hook that dies blocks the
tool it gates. An unlisted command passes, in keeping with the philosophy
`blast_radius_kill_guard.py` already states for `STACK_HAZARDS`. Known holes, probed against the
finished guard rather than reasoned about: `p=.git/config; rm "$p"` (variable indirection),
`echo .git/config | xargs rm`, `find .git -name config -delete`, an editor (`ed`, `vi`), `patch`,
and a throwaway script file instead of a `-c` string. `AI_BADGER_ALLOW_GIT_DIR_EDITS=1` disarms
it; that variable is read from the hook's own process, which an agent's inline `VAR=1 <cmd>`
prefix cannot reach, so it is a human-only escape hatch.

Wired for **claude** and **hermes**. The Hermes arm translates that runtime's tool names and
argument keys (`write_file`/`patch` → `path`, `execute_code` → `code`, `terminal` → `command`,
`workdir` as cwd) onto the same rule; the guard module stays the single source of truth. Copilot
is exempted: it fires `preToolUse` but its hook protocol has no block-with-reason channel, and a
refusal naming the transactional route is this guard's entire output.

One registration detail worth recording: the guard is **one** `hooks.json` entry with a combined
`Edit|Write|MultiEdit|NotebookEdit|Bash` matcher, not two blocks. `hook_wiring.merge_hooks()`
dedupes by script identity alone, so a second matcher block naming the same script is silently
dropped — two blocks would have shipped a guard whose Bash half never fired, with every test green.

## `git-config-health` (SessionStart)

`features/common/skills/git-work/scripts/git_config_health_hook.py` warns once per session when
a repo has an `origin` remote but no `remote.origin.fetch`, or when the checked-out branch has no
`branch.<name>.merge`. It names the repair in the notice. Silent when healthy, when there is no
remote at all, outside a repo, and when git is unavailable; always exits 0.

It resolves cwd from the hook payload, never from `CLAUDE_PROJECT_DIR`, which names the main
checkout even in a worktree session. Config is shared across worktrees but HEAD is not, so the
wrong precedence made the hook report the main checkout's branch — and go silent in exactly the
worktree session it exists to protect. Wired for claude and copilot; hermes is an acknowledged gap.
