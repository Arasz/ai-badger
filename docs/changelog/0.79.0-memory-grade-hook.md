# 0.79.0 — memory-grade hook grades every memory_search

A new framework hook logs every `ai-raccoon` `memory_search` call to a machine-wide quality
log and asks the agent to rate the retrieval's usefulness, so memory quality can be correlated
per project and workspace across sessions (dogfooding the memory store).

- **Default off**: `AI_BADGER_MEMORY_GRADE=1` is the single knob. Absent/unset/`0`/garbage
  makes the hook fully inert — no reads, no writes, no prompt injection.
- **One JSONL line per search** lands in `~/.ai-badger/memory-grade/memory-quality.jsonl` at
  call time with `ts, query, scope, projectId, workspaceId (null when none), result,
  usefulness: null, note: null` — the same shape as the session's manual quality log
  (`docs/work/2026-08-05-ai-raccoon-memory-quality.jsonl`) plus `workspaceId`, so the two
  stay comparable.
- **Grade round-trip**: the next LLM turn carries a one-line ask; the agent fills the grade in
  place with `memory_grade.py grade <ts> <1-5> [note]`. Unanswered asks stay `null` — honest
  data, and the full line is never lost. `memory_grade.py probe` prints config state, the log
  path and the last 3 lines.
- **All three agents wired**: Hermes stashes/pops the ask (`post_tool_call` →
  `pre_llm_call`), Claude and Copilot emit it as `additionalContext` from a PostToolUse hook
  matched on `memory_search`; all logic lives in one shared `memory_grade.py`, deployed beside
  `ai_badger_hooks.py` in both scaffold destinations.
- The helper's tool-name matcher accepts every naming spelling (`mcp__ai_raccoon__memory_search`,
  `ai-raccoon:memory_search`, bare `memory_search`) and never matches other memory tools.

**What a consumer must know:** the hook is inert until `AI_BADGER_MEMORY_GRADE=1` is set
machine-wide (`~/.zshrc` + `launchctl setenv`, then restart the agent host). The memory-grade
log lives in the user's home, never in a project's working tree.
