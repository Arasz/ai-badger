# 0.126.1 — derive-facts Stopped Counting Its Own Doc Comment

**Type:** PATCH
**Date:** 2026-08-16

## The defect

`derive-facts.sh` (the `ai-raccoon-manual-checklist` skill's fact-derivation script) counted the
MCP tool surface with a loose `grep -rho "\[McpServerTool"`. Against AiRaccoon v1.20.0 that
returned 28; the real count, and what the live server reports, is 27.

The 28th match was not an attribute use. `src/AiRaccoon/Tools/McpToolInventory.cs:7` is a doc
comment that names the attribute in prose, because that file *is* the reflection-based tool
inventory:

```
///     The MCP tool surface, derived by reflection over this assembly's own `[McpServerTool]`
```

A file documenting the attribute it reflects over is exactly the shape this script exists to
support, so the overcount was not a one-off — any future file doing the same would inflate the
count again. In the run that caught this, the bad count manufactured a phantom "two new tools
since 1.19.1" (only `memory_performance` was added), sending a checklist lane looking for a tool
that does not exist. A derived number that is wrong is worse than a hand-typed one, because it
carries the authority of having been measured.

## The fix

`count_attribute` now matches whole lines first, drops any line whose trimmed content opens with
`///`, `//` or `*`, and only then counts the attribute occurrences that remain. Filtering by
comment-line shape survives a bare `[McpServerTool]` with no `(Name = ...)` argument, which
matching only `[McpServerTool(Name` would not.

## Regression test

`tests/test_ai_raccoon_stack.py::TestTheDerivationScriptFailsLoudly::test_a_doc_comment_mentioning_the_attribute_does_not_inflate_the_count`
builds a fixture with a `///` line mentioning `[McpServerTool]` plus two real attribute uses and
asserts the count comes back 2, not 3. It fails against the unfixed script.

The script's existing "fails loudly on zero" contract (`gates` under `derive-facts:`) is
unchanged and still covered by the two tests next to it.
