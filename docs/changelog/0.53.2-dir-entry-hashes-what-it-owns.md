# 0.53.2 — a directory entry is hashed over the files it owns

Closes [#224](https://github.com/Arasz/ai-badger/issues/224).

A fresh clone of this repository accused itself of editing its own scaffold:

```console
$ python3 features/common/skills/welcome-ai-badger/scripts/drift.py --target . --root .
locally modified: this project edited its own copy — a re-scaffold overwrites these; move anything worth keeping into project-local.md first
  local    features/common/skills/mcp-index
```

Nothing had been edited. The same verdict appeared on every downstream project
that configures the `claude` or `copilot` stack, and it could not be cleared —
the only way to make it go away was to delete files the scaffolder itself had
written.

## What was wrong

`adjust_retrieval.py` copies four `features/common/retrieval/` modules into
`.ai-badger/skills/mcp-index/scripts/`. They are framework output and carry
their own manifest entries under `adjustments`, which is source-hashed.

The skill's own entry, meanwhile, records the skill: `dirMeta {file_count: 7}`.
`drift.py` then answered "did the project edit its copy?" by re-hashing the
whole destination directory — all eleven files, four of them placed by the
scaffolder a moment after it wrote the hash. The two numbers could never agree.

`gates/scaffold_freshness_guard.py` already documented the underlying hazard and
routed around it. `drift.py`'s local-modification branch and `feed-badger`'s
`detect_additions.py` did not.

## What changed

A directory entry is now hashed over the files *that entry* owns. The set to
skip comes from the manifest itself — any other entry whose `target` is nested
inside this one, which is the general case that the hardcoded `extensions`
exclusion was a special case of.

- `badger_lib.nested_entry_targets(entries, target)` derives that set.
- `badger_lib.dir_content_hash` gained `exclude_rel`, which skips exact relative
  paths and their subtrees. The existing `exclude` matches path *segments*, so it
  could only have excluded every `bm25.py` in the tree, not the one file another
  entry owns.
- `drift.py` and `detect_additions.py` pass it. Only the *local* question
  excludes those paths; the framework-drift question still hashes the source
  exactly as before, because the source never received them.

Editing a skill's own files is still reported. The exclusion is scoped to the
adjustment's path, not to the directory containing it.

## Two smaller fixes in the same area

`detect_additions.py` applied no exclusions at all when scanning managed
directories for new files, so `feed-badger` opened with `.DS_Store` as a
contribution candidate, complete with an invitation to review it for
project-specific tokens.

`.DS_Store` also joins `SKILL_EXCLUDE_PATTERNS`. One dropped inside a skill
directory used to produce the same false "locally modified" verdict — a report
that a project had edited a file its author could not see.

## No re-scaffold required

Recorded hashes keep their meaning; nothing in the manifest format changed, and
already-scaffolded projects get the correct verdict from the new code against
their existing manifests.
