# 0.70.1 — a bump is upward

`main` read `VERSION` 0.69.3 while `ai-badger--v0.70.0` was already tagged. A release below its own
highest tag has nowhere to go: the next version is either a duplicate or another step backwards.

## How it happened

Two PRs merged out of order on 2026-08-01. #274 carried 0.70.0 and merged first; #275 carried
0.69.3 and merged seventeen minutes later, writing `VERSION` backwards. Both changes are in main —
nothing was lost — but the recorded version stopped describing the tree.

The ordering requirement was known and stated in #275's own description. It was not re-checked
before merging, which is the part worth recording: a stated precondition that nobody verifies at
the moment of action is a comment, not a control.

## Why nothing caught it

`release_guard` asked whether `VERSION` **differed** from the last released tag:

```python
if current_version != released_version:
    print(f"... VERSION was bumped ({released_version} -> {current_version}) — PASS")
```

Inequality is not ordering. It reported `0.70.0 -> 0.69.3` as a bump and passed — on every push,
on both branches, and on main afterwards. The gate that exists to protect the release sequence
was blind to the one direction that breaks it.

## What changed

`VERSION` is 0.70.1, above the highest tag.

`release_guard` now compares semver order. A version *above* the released tag passes as before; a
version *below* it fails with what to do:

```
VERSION went backwards: 0.70.0 is already released as ai-badger--v0.70.0,
but VERSION now reads 0.69.3.
    set VERSION above 0.70.0 — a release below its own tag has nowhere to go
```

An unparseable version on either side falls through to the existing "still {version}" branch
rather than being treated as ordered — a version the guard cannot read is not a version it should
rule on.

## Tests

Two added to `tests/test_release_guard.py`, both red before the change:

- `test_fails_when_version_goes_backwards` — releases 0.2.0, tags it, then changes a shipped path
  and sets `VERSION` to 0.1.9. Was PASS, now fails and names both versions.
- `test_fails_when_version_equals_an_older_released_tag` — the same defect at equality rather than
  below, which the original code did catch; pinned so the ordering rewrite cannot lose it.

Pointed at the real repository, the rewritten guard reports the actual defect on main, which is
how this entry's numbers were obtained rather than reasoned about.

## The tag

`ai-badger--v0.69.3` points at `981212c`, which contains **all of 0.70.0's shipped surface** —
`evidence-first-research` included. It labels a superset of what it claims, and a checkout of it
gets more than 0.69.3 ever was. No coherent 0.69.3 release exists to point at: the content merged
on top of 0.70.0, not before it.

So that tag is deleted, and its content is re-released here as 0.70.1. `ai-badger--v0.70.0` is
correct and stays where it is.

**Order matters:** the tag is removed *after* 0.70.1 is tagged, never before, so there is no window
in which main's content has no tag at all. `.claude-plugin/plugin.json` and `marketplace.json` read
0.69.3 today and are regenerated to 0.70.1 by this change, so nothing is left pointing at a tag
that stopped existing.
