# 0.42.1 — an agent is a catalog stack too

A regression in [0.42.0](0.42.0-drift-sees-a-subtraction.md), caught by re-scaffolding this repo
against it before the release went any further.

0.42.0 taught drift to notice a stack removed from `config.stacks`. It decided orphanhood with
`resolve_stacks(config)` — and `config.agents` is a *different axis*. `scaffold.py` reads
`features/<agent>/` directly for every name in `config.agents`, with no entry in `config.stacks`:

```python
for agent_name in self.config.get("agents", []):
    adj_path = self.root / "features" / agent_name / "adjustments" / "adjustment.json"
```

So every agent-delivered entry looked orphaned. On this repo — `agents: [claude, copilot, hermes]`,
with `copilot` deliberately absent from `stacks` — that was 21 manifest entries and 11 files:

```
orphaned : ['features/copilot/adjustments/adjust_agents.py', ...]
   .github/copilot-instructions.md was edited here — left in place (stack 'copilot' is no longer in config.stacks)
   .github/agents/architect.agent.md   was edited here — left in place (...)
   ... 9 more
```

## What it cost, and what it did not

No file was deleted. Adjustment-written entries record the hash of the *source script*, not of
the generated output, so the ownership check could never match and the pruner always fell through
to "left in place". That is luck rather than design, and it is exactly the safety net
`prune_superseded` was built to have — but it is not a reason to be relaxed about the predicate
that feeds it.

The visible damage was worse than it looks:

- Eleven false `was edited here — left in place` notes on **every** refresh, training the reader
  to skim the one that matters.
- `drift.orphaned` was permanently non-empty, so `has_drift` was permanently true and
  **den-refresh re-scaffolded on every run and could never report a project up to date** — for any
  project configuring an agent that is not also a stack, which is the ordinary case for `copilot`
  and `junie`.

## The fix

`badger_lib.delivering_stacks(config)` names the real set — `resolve_stacks(config)` plus
`config.agents`, deduplicated — and `is_orphaned` takes that instead. Its docstring says what
passing the wrong one does, because the failure is silent.

`compare()` gained a `delivering` parameter rather than widening `stacks`. The two answer
different questions: `stacks` drives new-item detection, where an agent's catalog items must not
appear, and `delivering` drives orphan detection, where they must. Folding them together would
have traded this bug for its mirror image.

## Verified

On this repo, second consecutive refresh:

| | 0.42.0 | 0.42.1 |
|---|---|---|
| `reScaffolded` | `True`, every run | `False` |
| `orphaned` | 4 sources, 21 entries | `[]` |
| false prune notes | 11 | 0 |

The #116 reproduction still converges: a genuinely dropped stack is still detected and its file
still pruned.
