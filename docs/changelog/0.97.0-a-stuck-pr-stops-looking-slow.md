# 0.97.0 — a stuck PR stops looking slow

`gitleaks` became a required status check in 0.91.0, which closed review finding A6: before
that the job could be red and a PR still merged. This release closes the shape A6 turns into
once the check is required — a required check that **never runs at all**, and looks exactly
like one that is merely slow.

## The measured case

PR #341's branch conflicted with `main` between 17:37 and 18:14 UTC on 2026-08-07. Over that
window, queried from the Actions API:

```
push-triggered runs on fix/pre-push-chain-honest
  Lint and test | d26de0a7 | 18:10:27Z | failure      <- reported
  Lint and test | bc536058 | 18:33:34Z | success
  Lint and test | 51ca7144 | 19:18:37Z | success

pull_request-triggered runs on the same branch
  Secret scan   | bc536058 | 18:33:38Z | success      <- first run is AFTER the merge commit
  CodeQL        | bc536058 | 18:33:38Z | success
  Secret scan   | 51ca7144 | 19:18:40Z | success
  CodeQL        | 51ca7144 | 19:18:40Z | success
```

Commits `c5b7a891` and `d26de0a7` — the conflicting ones — produced **zero** `pull_request`
runs. Not queued runs, not cancelled runs; none were dispatched. GitHub documents this
plainly: *"Workflows will not run on `pull_request` activity if the pull request has a merge
conflict."* There is no merge ref to check out.

So the required `gitleaks` context reported nothing, and the mergebox renders "has not
reported" the same way it renders "still running". `build (3.10)` kept reporting throughout,
because `Lint and test` triggers on `push` and a conflict does not affect a push. That
asymmetry is the whole trap: one check moving is what makes the other look slow rather than
absent.

## `Stuck PR watch`

`.github/workflows/stuck-pr-watch.yml` runs every six hours and on `workflow_dispatch`. It
asks GraphQL for every open pull request's `mergeable` state and posts one notice on each
`CONFLICTING` one, naming the trigger that will never fire, the check that will never report,
and the fix (merge the base branch; this repo merges, never rebases).

`.github/scripts/conflicting_pr_report.py` does the filtering — stdlib only, no network — so
the behaviour is unit-testable and no attacker-controlled pull request text ever reaches a
shell. Only integers cross that boundary. The script and the workflow share one marker
constant, so the string the dedup searches for is the string the notice carries; a drift there
would mean either a notice re-posted every six hours or one never posted while the run
reported success.

`MERGEABLE`, `CONFLICTING` and `UNKNOWN` are the only three values GitHub's `MergeableState`
enum has, and it computes the answer lazily. `UNKNOWN` is reported as unknown rather than
folded into "clean" — a detector that answers "all clear" when it does not know is the failure
mode it exists to catch. The same applies to a malformed payload, to GraphQL `errors`, and to
a truncated page: the query asks for the first 100 open pull requests and also for
`totalCount`, and the script refuses outright rather than report on 100 of 101 and leave the
101st quietly clean.

The dedup answers the same way. It reads the last 100 comments, and seeing the marker settles
the question — but *not* seeing it settles nothing once a pull request has more comments than
that, because the notice may simply have scrolled out of the window. Those are reported as
`history_truncated` and left alone, so a stuck pull request that attracted a long discussion
gets checked by hand rather than re-notified every six hours.

The comment loop is a `for` over the numbers rather than `jq | while read`. The pipeline form
runs in a subshell, so one pull request closing between the query and the comment would abort
under `set -e` and leave every later pull request silently uncommented; each is now attempted
and the step still fails at the end if any did not land.

## What was rejected, and why

- **`pull_request_target`.** It does run on a conflicting PR, but it runs in the base
  repository's default-branch context with that repository's secrets, and `actions/checkout`
  with no `ref` takes the base branch rather than the PR. `gitleaks` would scan `main`, pass,
  and report green about code it never read: a required check turned into a rubber stamp,
  bought with the fork attack surface `.ai-badger/invariants/pin-actions-to-sha.md` exists to
  keep closed. Strictly worse than the gap.
- **`merge_group`.** Fires only when a pull request enters a merge queue, and a conflict with
  the base is a removal condition for the queue. It cannot reach a PR in this state.
- **Documenting alone.** Done as well, not instead — `CONTRIBUTING.md` step 7 now covers it,
  including the one-line `gh pr view <n> --json mergeable` check for the window before the
  scheduled run fires. But the failure mode's defining property is that it looks like normal
  waiting, so it has to come and find you.

## Permissions

`contents: read` and `pull-requests: write` — the least that reads a checkout and writes a
comment. No `contents: write`, no `security-events`, no `actions` scope. `persist-credentials:
false` on the checkout, a `concurrency` group, and `timeout-minutes: 10`.

## The pinning invariant now holds in every instance

0.92.0 added `features/github/invariants/pin-actions-to-sha.md` — *"Every third-party GitHub
Action referenced in a workflow is pinned to a full commit SHA, never a tag or branch"* — and
scaffolded it into `CLAUDE.md`. At that moment the repository violated it in **all nine**
`uses:` references it had. A rule the project ships and does not honour is worse than no rule:
it teaches every reader that the invariants are decorative. Fixed here rather than deferred,
since this release already owns `.github/`.

| Workflow | Action | Pinned to |
|---|---|---|
| `codeql.yml` | `actions/checkout` | `3d3c42e5…` (v7.0.1) |
| `codeql.yml` | `github/codeql-action/init` | `5595ccaf…` (v4.37.6) |
| `codeql.yml` | `github/codeql-action/analyze` | `5595ccaf…` (v4.37.6) |
| `labeler.yml` | `actions/labeler` | `bf12e9b0…` (v7.0.0) |
| `pylint.yml` | `actions/checkout` | `3d3c42e5…` (v7.0.1) |
| `pylint.yml` | `actions/setup-python` | `5fda3b95…` (v7.0.0) |
| `release-tag.yml` | `actions/checkout` | `3d3c42e5…` (v7.0.1) |
| `secret-scan.yml` | `actions/checkout` | `3d3c42e5…` (v7.0.1) |
| `secret-scan.yml` | `gitleaks/gitleaks-action` | `e0c47f4f…` (v3.0.0) |

Each carries a trailing `# vX.Y.Z` so the readable version survives, resolved to the precise
release tag sharing that commit rather than the floating major.

Every SHA was resolved from the API and then re-checked in the other direction: ask what the
commented tag points at today, and demand it equals the SHA in the file. That check is not
ceremony. `github/codeql-action@v4` is an **annotated** tag, so its ref resolves to a tag
object (`24c7eb38…`), not a commit; pinning that value would have named something that is not
a commit at all. Dereferencing gives `5595ccaf…`. The other four are lightweight tags pointing
straight at commits. All ten references — the nine above plus this release's own — verify, and
all five upstream commits carry a verified signature.

**Not done here, and deliberately: there is still no lint.** Nothing in `gates/` or `tooling/`
checks this, which is exactly why the invariant could ship violated nine times over and go
unnoticed. A guard belongs beside the others in `gates/`, held by another lane this wave. The
rule it should enforce: every `uses:` in `.github/workflows/*.yml` matches
`<owner>/<repo>[/<path>]@[0-9a-f]{40}`, and every workflow or job declares a `permissions:`
block. Both halves of the invariant, checked, or it will drift again.
