# 0.172.13 — the commit-reminder report fails closed, the hook stays fail-open

**Patch** — `ensure_committed.py`'s at-risk report can no longer say "Nothing is at risk"
when it does not actually know that, and the Claude-side hook's persisted counter no
longer loses an update when two tool calls race it. 2026-09-24.

## What was wrong

- **A broken user store read as "nothing is at risk."** `load_state()` caught every
  exception, including a store that failed to open at all, and fell back to the (usually
  absent) legacy file. `ensure_committed.py`'s report then rendered an empty `atRisk` list
  through `format_report`, which always prints "No project has unanswered commit commands.
  Nothing is at risk." — indistinguishable from a genuinely clean run.
- **A `git status` failure or timeout silently dropped an at-risk project.**
  `uncommitted_files` returns `[]` on any failure, and the report used that same emptiness
  to mean "work has since been committed," filtering the project out of `atRisk` instead of
  flagging that its status could not be determined.
- **Two concurrent hook invocations for the same project could lose one's update.** The
  hook ran `get_entry`, `advance`, `set_entry` as three separate store round trips; a second
  invocation between the read and the write computed from the same stale entry, and the
  last write won.

## What changed

- `commit_reminder.load_state(strict=True)` propagates instead of falling back to the
  legacy file. Only `ensure_committed`'s report asks for it; every other reader (the hook,
  `get_entry`, the Hermes side) keeps the fail-open default.
- `ensure_committed.py`'s report reads state strictly. When the store cannot be read at all
  it prints "state unreadable" (never "Nothing is at risk") and exits 1; a normal run keeps
  exiting 0 whether or not work is at risk.
- `commit_reminder.git_status` returns a `GIT_UNKNOWN` sentinel on failure or timeout,
  distinct from an empty, clean result. The report lists such a project as
  `"uncommitted": "unknown"` instead of dropping it. `uncommitted_files` (the hook's fail-
  open view) is unchanged.
- The hook's read-modify-write now runs through `commit_reminder.update_entry`, one atomic
  `Store.kv_update` transaction, instead of separate `get_entry`/`set_entry` calls: a
  concurrent second invocation serializes on the write lock and sees the first's result
  before computing its own.

## Upgrade notes

- Re-scaffold to pick up the updated scripts. No state migration is needed.
- A parent that runs `ensure_committed.py` and checks only the human-readable summary
  should also check the exit code: 1 now means the report itself is unreliable, not that
  no project is at risk.
