# 0.64.4 — The remote-tag guard stops blocking its own tag push

0.64.3 taught `release_guard` to refuse a release tag that exists locally and not on `origin`.
It then refused the push that would have fixed that — because pushing a tag runs the same
pre-push hook, and at that moment the tag is, by definition, local-only.

Circular, and found immediately: the very next release could not be tagged.

## The rule is about the sequence, not about VERSION

A local-only tag is reported **only when the remote already has a higher release tag**. That
means the published order skipped it, which is the actual defect. A tag above everything on the
remote is indistinguishable from one being pushed this second, so it is never reported.

The original failure stays caught, and in the shape it actually had: `ai-badger--v0.61.3` was
lost, then `0.62.0` shipped without it — at which point the remote had moved past it and it
started failing other people's pull requests.

## Two wrong fixes first, both from the same mistake

The first attempt reported every local-only tag, and blocked its own push. The second exempted
the tag matching `VERSION` — which held until `VERSION` was bumped ahead of the untagged
release, at which point it failed again, one step further along.

Both were written from the failure rather than from the sequence the failure sat in. The
symmetry with `skipped_versions` — which reasons about the *range* between the last tag and
`VERSION` rather than about any single version — was there to copy from the start.
