# 0.48.0 — the Claude hook wiring stops adopting a neighbour's script

## The defects

Both in `features/common/skills/welcome-ai-badger/scripts/hook_wiring.py`, the same class
#150 fixed on the Copilot side (`adjust_hooks.py`), in the branch #150 did not touch.

**1. `select_hooks(source_event_hooks, script)` took the whole event when unnamed.**

```python
def select_hooks(source_event_hooks, script):
    if not script:
        return list(source_event_hooks)   # every command registered for the event
```

A manifest entry naming no `script` adopted every command registered for its event in
`features/common/hooks/hooks.json` — not just its own.

**2. The fallback picked whichever glob match sorted first.**

```python
hook_scripts = list(skill_hook_script.glob("*_hook.py"))
...
script_path = hook_scripts[0]
```

When a manifest entry had no command in `hooks.json`, this globbed the skill's `scripts/`
directory and took an arbitrary match — ignoring `claude_entry["script"]` even when the
manifest named one.

## Why neither fired today

`prompt-markers` is the one manifest entry whose `claude` block names no `script`. It worked
only because `hooks.json` has no `UserPromptSubmit` key at all (so defect 1 returned nothing
by accident) and its `scripts/` directory holds exactly one `*_hook.py` (so defect 2 had only
one candidate to arbitrarily pick). Issue #147, which wires `context-enrichment` onto
`UserPromptSubmit`, would have broken both accidents at once: `prompt-markers` would have been
wired to `context-enrichment`'s script, and `user_prompt_hook.py` would never have been wired
at all — silently, since `merge_hooks` deduplicates by script identity and the deletion showed
no error, no note, no test failure. Issue #152 files this ahead of #147 landing.

## The fix

- `select_hooks(..., None)` now returns nothing. A script-less entry cannot tell which
  registered command in `hooks.json` is its own, so it always falls through to resolving its
  own script by filesystem convention instead of guessing from the event's contents.
- The glob fallback honours `claude_entry["script"]` when the manifest names one, resolving
  the exact file rather than globbing. When it does not, the glob is sorted and, if more than
  one `*_hook.py` candidate remains, the hook is skipped with a note naming every candidate
  rather than picking one — mirroring `adjust_hooks.py`'s refusal, but as a note rather than a
  raised exception (see below).
- `features/common/hooks/hooks-manifest.json`'s `prompt-markers` entries (`claude` and
  `copilot`) now name `"script": "user_prompt_hook.py"` explicitly, matching every other entry
  in the manifest. Verified byte-identical scaffold output (`.claude/settings.json` and
  `.ai-badger/hooks/hooks.json`) for a project scaffolding `prompt-markers` before and after.

## Note, not raise

Unlike the Copilot side, `HookWiring.wire()` is called directly from `Scaffolder.run()` with no
surrounding `try`/`except` — `run_adjustments()`'s broad `except Exception` is a different call
site that never reaches hook wiring. A raised exception here would abort the whole scaffold run
after several steps had already written files, with no manifest recorded. Every existing
refusal in this module (declined skills, missing scripts, unscaffoded targets) already
degrades to `self.ctx.notes.append(...)` and continues; the new ambiguous-glob refusal does the
same, for consistency and because there is no net to catch it otherwise.

## Was the manifest change necessary, or would the code guard alone suffice?

Necessary, not just insurance. `select_hooks(..., None)` returning nothing prevents *ambiguous*
adoption, but the #147 regression scenario is not ambiguous — `hooks.json` would carry exactly
one command for `UserPromptSubmit`, and it isn't `prompt-markers`'. A guard that only fires on
"more than one candidate" cannot detect "the one candidate belongs to someone else"; only a
named script lets `select_hooks` see it does not match. The regression test below is built on
exactly that single-wrong-candidate shape and fails without the manifest change even with the
code fix in place.

## Tests

`tests/test_hook_wiring_claude.py` (new), all written red-first:

1. A four-script skill directory, manifest names one — that one is wired, not glob order.
2. `hooks.json` grows a second `UserPromptSubmit` command belonging to another hook —
   `prompt-markers` still wires `user_prompt_hook.py`, never the newcomer. This is the #147
   regression, written before #147 exists.
3. An ambiguous glob with no named script refuses, naming every candidate.
4. Every claude `hooks-json` manifest entry names its script (the belt, guarding the manifest
   invariant directly).

Mutation-checked by hand: reverting the `select_hooks` fix fails test 2 only; reverting the
glob-fallback fix fails tests 1 and 3; reverting the manifest `script` addition fails test 4
only. Restoring each fix returns the suite to green — each test protects exactly one fix.

## Not covered

`context-enrichment` and `task-checkpoint` remain unwired for Claude; issues #147 and #141 land
those separately, now onto a wiring path that can no longer silently misattribute a command.

## Migration

None for existing projects: `select_hooks` and the glob fallback already resolved to today's
one correct answer for every current manifest entry, and the `prompt-markers` manifest addition
was verified to produce byte-identical scaffold output.
