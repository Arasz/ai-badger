# 0.93.0 — jsonschema on first use, one finding shape, one guarded VERSION reader

Three architecture items from the full-project review (D1, D5, D7). The first is the one the
review called the best value-to-cost in the whole audit; the other two are small and were kept
small on purpose.

## `jsonschema` is imported when something validates, not when something imports (D1)

`engine/badger_lib.py` imported `jsonschema` at module scope. Thirteen entry points import
`badger_lib`; two of them ever validate. The other eleven — `changelog_index`,
`install_plugins`, `retrieval_eval`, `sync_plugin_skills`, `version_sync` and all six gates —
paid for the validator on every pre-push run and never used it.

The three validation functions (`validate`, `validate_file`, `check_schemas_selfvalid`) now
resolve the module through one deferred helper.

**It stays required.** The `ImportError` propagates. A machine without the wheel gets a refusal
from validation, never an empty error list — the invariant the project's own summary states.
What changes is that such a machine can now *run* the eleven scripts that never validate; before
this, `import badger_lib` itself died on them.

### Measured

Interleaved A/B in one process, 40 alternating samples per arm, so the machine's load hits both
arms equally. The eager arm is HEAD's exact shape (the two top-level imports restored into a
copy of the new file):

| arm | min | median |
|---|---|---|
| eager (0.89.0) | 224.8 ms | 761.4 ms |
| lazy (this release) | 111.9 ms | 226.4 ms |
| interpreter floor (`python3 -c pass`) | 52.7 ms | 67.5 ms |

Import cost above the floor: **172.1 ms → 59.2 ms**. **113 ms saved per process, 66% of
`badger_lib`'s import cost.** The medians are inflated and unstable — three other lanes were
running on this machine — so the minimum is the figure to read; the median is reported only
because suppressing it would be picking the flattering statistic.

The review quoted ~470 ms on a different machine. That number was not reused; these were
re-measured here.

## One `Problem`, one failure report — for the three gates that have one (D5)

`deps_guard`, `docs_guard` and `shipped_paths_guard` each carried a private copy of
`Problem(path, line, message)` and its `location()`, and the copies had already drifted:
deps_guard's dropped the line-less fallback, so a missing `engine/requirements.txt` was reported
as `engine/requirements.txt:0` — a line that cannot exist. They now share
`gates/gate_report.py`, a sibling rather than an `engine/` module: `engine/` is enumerated by
`tests/test_engine_tooling_layout.py` as the library every shim imports, and this is not that.

**The other three gates were deliberately left alone.** D5 was written as "one `Problem` and
`report()` for the gates", plural and unqualified. Read against the source, only three of the six
report `path:line: message` at all: `release_guard` and `tdd_guard` print lists of paths with
their own remediation, and `scaffold_freshness_guard` has `Finding(path, change, verdict)`, a
genuinely different shape. Retrofitting them onto a common type would have been an abstraction
with no buyer, which this project's own invariant tells you not to build. The shared piece is
about 15 lines and has three real callers and a real defect behind it; that is the whole case
for it. `tests/test_gate_report.py` pins the boundary in both directions — the three share one
type, and the other three have no `Problem` at all.

## One guarded reader for `<root>/VERSION` (D7)

`tooling/version_sync.py` and `gates/release_guard.py` both read `VERSION` with a bare
`read_text()`, so a tree without one produced a `FileNotFoundError` traceback out of a gate.
Both now call `bl.read_version(root)`, which raises `bl.MissingVersion` naming the file — and
both callers turn that into a printed refusal and exit 1.

**The two `read_version` implementations stay two.** `engine/framework_copies.py` has its own,
returning `Optional[str]`, and it should: it answers a different question. `bl.read_version` asks
"what version does this root declare?" of a tree that must have one; `framework_copies` asks
"does that tree over there report a version?" while walking arbitrary directories on the machine,
where *no* is a normal answer, and it is deliberately free of `badger_lib` because a SessionStart
hook imports it. Merging them would mean one function with two contracts.

That module's docstring did give `badger_lib`'s unguarded `jsonschema` import as the reason for
staying separate. D1 retires that reason, so the docstring now states the one that survives: a
per-session hook should not import 1000 lines it never calls.

## Proof

`tests/test_dependency_honesty.py` gained three behavioural tests that block `jsonschema` in a
child interpreter with a `sys.meta_path` finder and assert that all three validation entry
points raise, plus one asserting `badger_lib` does not load the module at all.

**One test was rewritten:** `test_jsonschema_is_imported_unguarded` asserted
`"\nimport jsonschema" in badger_lib.py` — a text match on the source, satisfiable only by a
top-level import and blind to whether validation actually refuses. It is replaced by
`test_validation_refuses_when_jsonschema_is_absent`, which asserts the contract rather than the
syntax.

Every gate was broken on purpose and watched go red — see the pull request for the seeded
defect and exit code per gate.

## One regression the lazy import caused, found in review

`mcp_index.py` relied on `import badger_lib` *itself* raising when `jsonschema` was absent:
`_try_import_badger_lib` returned `None`, and `_write_index` degraded to a printed note
(`tag`/`intent`) or refused cleanly (`init`). After the lazy import the module imports fine and
the `ImportError` fires inside `bl.validate`, at a call site with no handler — so a consumer
project without `jsonschema` got a traceback instead of the documented note. That is exactly the
scenario the script's local `atomic_write_text` copy exists to survive.

`_validate_against_schema` now catches it and returns `None`, which is what "validation
unavailable" already meant there. `tests/test_mcp_index.py` gained
`test_a_reachable_framework_without_jsonschema_still_degrades` and
`test_init_still_refuses_when_jsonschema_is_absent` — both go red without the catch, and the
second pins that `init` still refuses rather than writing unvalidated.

Two smaller consequences of the same change: `CONTRIBUTING.md` and `SECURITY.md` both stated
that `badger_lib` imports `jsonschema` unguarded, which is no longer true, and `docs_guard`
cannot see prose. And the meta-gate discovers every `gates/*.py` as a check, so
`gate_report.py` — a helper with no verdict — had no provocation; discovery is now narrowed to
files defining a top-level `main()`, with `test_discovery_still_finds_every_runnable_gate` so
the narrowing cannot quietly hide a real gate.
