# 0.52.0 — discovery comes back, from the host that still answers

`mcp-index init` and `update` had one tool-listing source, `hermes mcp list --json`, and it is
gone. On the installed hermes:

```
$ hermes mcp list --json
usage: hermes [-h] [--version] [-z PROMPT] [--usage-file PATH] [-m MODEL]
              …
hermes: error: unrecognized arguments: --json
```

[0.51.0](0.51.0-the-index-records-curation-and-status.md) removed the data-loss hazard that
followed from it — a text-mode listing yields `status: unknown` and touches no tools — but left
discovery dead: `init` produced sources with no tools and nothing else.
[Issue #188](https://github.com/Arasz/ai-badger/issues/188).

## A second verified surface: `claude mcp list`

`claude mcp list` lists every server and, unlike any `hermes mcp list` mode, says *why* a server
is not answering. Captured on a 2026-07 install (usernames replaced):

```
Checking MCP server health…

claude.ai Google Drive: https://drivemcp.googleapis.com/mcp/v1 - ✔ Connected
claude.ai Microsoft 365: https://microsoft365.mcp.claude.com/mcp - ! Needs authentication
plugin:github:github: https://api.githubcopilot.com/mcp/ (HTTP) - ✘ Failed to connect — HTTP 400: …
plugin:playwright:playwright: npx @playwright/mcp@latest - ✔ Connected
rider: http://127.0.0.1:64482/stream (HTTP) - ✔ Connected
```

It never prints tool names — neither `claude mcp list` nor `claude mcp get <server>` does, and
`hermes mcp list` has no `--tools` mode either. So this release restores **server** discovery and
honest per-server status, not tool discovery. That is the whole of what the two CLIs support, and
saying so is the point: the index claims nothing its input cannot carry.

## Three sources, asked in order

`features/common/skills/mcp-index/scripts/host_listings.py` is new and owns the chain:

| order | source | what it carries |
|---|---|---|
| 1 | `hermes mcp list --json` | server names **and their tools** — the only source that can |
| 2 | `claude mcp list` | every server plus a reachability phrase; no tools (~14s for 17 servers) |
| 3 | `hermes mcp list` | server names and an enabled flag from the text table; no tools |

The first source that lists a server wins. `--host hermes` / `--host claude` restricts the chain to
one CLI; `--from-json` still skips the hosts entirely. Every source that did not answer is named:

```
$ mcp_index.py init --target demo
Listed 16 server(s) via `claude mcp list`.
  (skipped hermes mcp list --json: exit 2 (hermes: error: unrecognized arguments: --json))
Indexed 0 tools across 16 server(s).
  16 server(s) reporting no tools: claude.ai Microsoft 365 (unauthenticated), …
  plugin:github:github (unreachable), rider (unknown).
```

Before this release the same command on the same machine produced no source at all. When **no**
source answers, both commands refuse and print what each one said, rather than raising
`FileNotFoundError` at a user — the previous behaviour when hermes was not installed at all.

## Three new statuses, and no fourth

The `status` enum in `schemas/mcp-tools.schema.json` was designed additive
([ADR-0014](../adr/0014-mcp-support-is-configuration-not-retrieval.md) decision 7). It gains:

| `status` | the phrase that produces it | remedy |
|---|---|---|
| `unauthenticated` | `! Needs authentication` | `claude mcp login <server>` |
| `unreachable` | `✘ Failed to connect` | fix the endpoint or credentials it names |
| `pending_approval` | `⏸ Pending approval` | approve the `.mcp.json` server in the host |

A server that is merely `✔ Connected` stays `unknown`: connected is not a tool list. The first two
phrases were measured; the third is quoted verbatim in `claude mcp list --help`. Claude Code's other
documented phrases — `Connection error`, `Rejected`, `not configured` — are **not** mapped, because
nobody here has seen one; an unrecognised phrase reads as `unknown`. A status nothing can set is not
a status, and a status set from a phrase nobody captured is a guess.

## The hazard the second source would otherwise have reintroduced

The two hosts name the same server differently — `code-review-graph` under hermes,
`plugin:ai-badger:code-review-graph` under Claude Code. An `update` that switched source would
therefore have found every previously-indexed server missing from the new listing and marked it
`absent`, with every one of its tools `removed`. That is the #145 data-loss shape again, one source
change later.

0.51.0's rule was per-server: a server listed without tool detail is left alone. This release
extends it to the listing: **when a listing carries no tool detail at all, a source it does not name
is left untouched** — same status, same tools — and named in the output.

```
  1 source(s) left untouched — this listing carries no tool detail, so a server it does not
  name is not evidence of removal: rider.
```

Only `hermes mcp list --json`, the one source that carries tools, can still move a source to
`absent`. `manual` curation survives either way, as before.

## Known limitation

The mcp catalog is keyed on the bare server name, so it does not reach a Claude-Code-listed plugin
server (`plugin:ai-badger:code-review-graph`). Indexing from `claude mcp list` therefore gets no
curated entries for it — the overlay and `origin` semantics are unchanged, and reconciling the two
naming schemes is its own decision, not a side effect of restoring discovery.
