# 0.53.0 — one declaration per server, per host

[Issue #193](https://github.com/Arasz/ai-badger/issues/193). The Copilot CLI reads **both**
project MCP files — `.github/mcp.json` and `.mcp.json`, looked up from the cwd upward — and the
documentation settles neither their precedence nor whether the `tools` allowlist 0.51.0 started
writing ever takes effect. A consumer repo that keeps a `.mcp.json` therefore declared
`code-review-graph` twice, with different content, and nobody could say which declaration ran.

Measuring the precedence needs an interactive `/mcp show` session on a real Copilot install. That
is still not done here. Instead **the answer stops mattering**: the two files now describe the
same server identically, `cwd` aside, and a server whose two renderings cannot be reconciled is
declared once and named in a note.

## What a project with both hosts gets

`config.agents: ["claude", "copilot", …]`, one declared server, one re-scaffold:

`.mcp.json` (untracked here per #173; written all the same)

```json
{
  "mcpServers": {
    "code-review-graph": {
      "args": ["-m", "code_review_graph", "serve"],
      "command": "python3",
      "cwd": "/absolute/path/to/the/project",
      "tools": ["*"]
    }
  }
}
```

`.github/mcp.json`

```json
{
  "mcpServers": {
    "code-review-graph": {
      "args": ["-m", "code_review_graph", "serve"],
      "command": "python3",
      "tools": ["*"]
    }
  }
}
```

Same executable, same arguments, same environment, same allowlist. Whichever file the Copilot CLI
prefers, it registers the same server with the same tools — which is what "the answer stops
mattering" means, and it is checkable without an interactive session.

## The three divergences, and what happened to each

**1. The `tools` allowlist — moved into the file both hosts read.** `tools` is Copilot's field and
Claude Code's `.mcp.json` schema has no counterpart. Writing it there anyway rests on a claim that
had to be verified before anything could depend on it: *Claude Code ignores an unknown per-server
key rather than rejecting the entry.* Measured on Claude Code 2.1.220, with a negative control
first — the validator has to be proven live before its silence means anything:

```
$ cat .mcp.json          # control: a key of the wrong type
{"mcpServers": {"probe": {"command": 17, "args": ["-m", "code_review_graph", "serve"]}}}
$ claude mcp list
 └ [Warning] [probe] mcpServers.probe: Skipped — invalid MCP server config for "probe":
   command: expected string, received number

$ cat .mcp.json          # the same entry, valid, plus an unknown key
{"mcpServers": {"probe": {"command": "python3", "args": ["-m", "code_review_graph", "serve"],
                          "cwd": "…", "tools": ["*"]}}}
$ claude mcp list
probe: python3 -m code_review_graph serve - ⏸ Pending approval (run `claude` to approve)
```

No warning, and the entry loads exactly as it does without the key: the per-entry validator runs
and reports, and it does not reject extra keys. Had it been strict this whole approach would have
been dead, and this file would say so instead.

**2. The two command splitters — collapsed into one.** `.mcp.json` used to keep a command whole
unless an argument looked package-shaped (`-`, `@`, `/`), so `hermes mcp serve` was one string
there and `{"command": "hermes", "args": ["mcp", "serve"]}` everywhere else. Two files that split a
command differently declare two different executables, which is the contradiction this issue is
about, so `split_package_args` is gone and `split_on_whitespace` is the only splitter left. Both
hosts document an executable plus an `args` array, and a declaration that spells out `args`
is still never split at all — that is the escape hatch for a command with a space in its path.

**3. `cwd` — the one deliberate, documented difference.** It stays in `.mcp.json` only. Claude Code
documents nothing about it either (0.32.0 measured it), and Copilot documents no `cwd` at all;
adding it to `.github/mcp.json` would trade an unknown precedence for an unknown schema, and if
Copilot's parser were strict the server would vanish from both files instead of one. It is also the
key that cannot change the outcome: it selects a working directory, not a server and not a tool
set — and the Copilot CLI only finds these files by walking up from a cwd already inside the
project.

## What cannot be reconciled is declared once, and said out loud

Two constructs still make the two renderings genuinely different, and neither is a rendering bug:

- a `${HOME}`-relative command (0.28.0's fix for user-installed tools that are absent from a
  non-login PATH) — documented for `.mcp.json`, documented nowhere Copilot reads;
- an `agentOverrides` entry that resolves `claude` and `copilot` to different commands.

For those, `.github/mcp.json` gets no entry at all, `.mcp.json` is the single declaration, and the
run says which server and which keys:

```
MCP server 'fs' is declared only in .mcp.json: the entry .github/mcp.json would carry differs
from it (command), and Copilot CLI reads both files with no documented precedence (issue #193)
```

An entry an earlier run already wrote is **removed** from `.github/mcp.json` in that case, with the
usual `.bak-*` copy beside it — merge-only would have left the contradiction in place on upgrade.

This is a real loss for one case: a per-agent MCP override between Claude and Copilot can no longer
be delivered. It never could. A file Copilot also reads cannot hand Copilot a different command
from the one it hands Claude; before this release the two files simply disagreed and the outcome
was whatever the undocumented precedence decided. A deterministic single declaration plus a note
beats a coin flip.

## `.mcp.json`'s readers are Claude Code *and* the Copilot CLI

`McpDestination.owner` becomes `readers`, a tuple in priority order, and `.mcp.json`'s is
`("claude", "copilot")`. Its `agentOverrides` resolve for the first configured reader, so a
**Copilot-only** project — no `claude` in `config.agents` — now gets Copilot's overrides in
`.mcp.json` instead of no overrides at all. That was the last way the two files could contradict
each other on a project that never configured Claude.

A project configuring neither host still gets `.mcp.json` (its arrival routes do not consult
`config.agents`), rendered without overrides and noted, exactly as before.

## Rewritten tests

A rewritten test is where a regression hides, so each is named:

- `test_stack_mcp_servers.py`: `test_the_two_command_splitters_agree_or_are_documented_to_differ`
  (6 cases) → `test_one_splitter_renders_the_same_executable_everywhere`, and its two divergent
  cases (`echo v2`, `hermes mcp serve`) now assert one shared entry instead of two shapes.
  `_render_everywhere` drops the `tools` key from `.mcp.json` as well as from `.github/mcp.json`.
- `test_stack_mcp_servers.py`: `test_mcp_json_applies_no_override_when_claude_is_not_configured` →
  `test_mcp_json_uses_copilot_overrides_when_claude_is_not_configured`, which asserts the opposite
  outcome. The case it used to cover — no reader configured at all — is kept as the new
  `test_mcp_json_applies_no_override_when_neither_reader_is_configured` on a Hermes-only project.
- `test_stack_mcp_servers.py`: `test_copilot_mcp_json_uses_copilot_overrides` keeps its name and
  drops `claude` from `config.agents`; with both hosts configured the entry is no longer written.
- `test_stack_mcp_servers.py`: `test_two_declarations_in_one_stack_both_reach_mcp_json` and
  `test_mcp_json_no_duplicate_from_two_stacks` assert on `args` rather than on a whole-string
  `command`, which the single splitter no longer produces. Same for
  `test_mcp_declared_servers.py`'s `test_a_later_stack_wins_over_an_earlier_one`.
- `test_copilot_mcp_json.py`: `test_no_other_destination_grows_a_tools_array` →
  `test_the_claude_user_proposal_grows_no_tools_array` — `.mcp.json` grows one now; the
  `~/.claude/settings.json` proposal, which no Copilot surface reads, does not.
- `test_copilot_mcp_json.py`: `test_the_copilot_overrides_are_the_ones_applied` keeps its name and
  its assertion, on a Copilot-only project.
- `test_mcp_user_tool_paths.py`: `test_the_copilot_mcp_json_keeps_the_bare_command` →
  `test_a_rewritten_command_leaves_the_copilot_file_undeclared`. The bare command it asserted was
  the divergence; the file is now not written for that server.
- `test_mcp_catalog_instructions.py`: `test_the_generated_mcp_json_still_carries_the_one_declared_server`
  keeps its name and gains `"tools": ["*"]` in the frozen entry.

New: `tests/test_one_declaration_per_server.py`, nine cases, from "the two files agree byte for
byte apart from `cwd`" to "an earlier run's divergent entry is removed".

## Behaviour changes worth knowing

- **`.mcp.json` entries gain `"tools": ["*"]`**, unconditionally — a re-scaffold rewrites every
  generated entry. The key is inert for Claude Code (verified above) and is there for the Copilot
  CLI, which reads the file whether or not the project lists `copilot` in `config.agents`.
- **A command with spaces is split** in `.mcp.json` now. `{"command": "hermes mcp serve"}` becomes
  `{"command": "hermes", "args": ["mcp", "serve"]}`. Declare `args` explicitly to opt out.
- `.github/mcp.json` loses entries whose two renderings diverge, with a backup and a note.
- `.mcp.json.example` carries the allowlist too, so the file it stands in for still matches.
