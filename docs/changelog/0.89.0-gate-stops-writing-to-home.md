# 0.89.0 — the read-only freshness gate stops writing into `$HOME`

`gates/scaffold_freshness_guard.py` documents itself as read-only: "the tree under `--root` is
only ever read". It is not, and was not. The gate copies the repo into
`tempfile.mkdtemp(prefix="scaffold-freshness-")` and re-runs the scaffolder there, and the
Hermes adjustment resolved its install root as `Path.home() / ".hermes" / "plugins"` — not
derived from `--target`, and not gated on `--no-install`. So every run overwrote the operator's
installed Hermes plugin with copies from a directory it was about to delete, and recorded that
directory as `frameworkRoot`:

```
frameworkRoot: /private/var/folders/.../T/scaffold-freshness-lbe6oeam/work
exists: False
```

That record was read off a live machine. The `scaffold-freshness-` prefix is the gate's own
fingerprint, and the gate runs on pre-commit, pre-push and CI — so every local commit did this.
The skill-namespace relink wrote into the same user scope for the same reason, leaving
`~/.hermes/skills/<project>/*` pointing into deleted temp trees.

A framework plugin whose recorded root does not exist cannot bootstrap, and
`ai_badger_hooks.py` caught that failure, discarded the `RuntimeError`'s fully actionable
message, and set `FRAMEWORK_ROOT = None` with **no output at all** — while lesser problems
twenty lines away print to stderr. The plugin loaded, registered all four hooks, and did
nothing. Two hours of "the drift notice never fires" looks exactly like a plugin that is
switched off.

## What changed

**The install is confined.** `_install_user_plugins` is a no-op under `--no-install`, which now
reaches the adjustments through the context `scaffold.py` already builds — no second flag.

The two user-scope writes are fixed by different mechanisms, because they had different defects.
The plugin install derived its destination from **nothing** — not `--target`, not a flag — so it
wrote into the real home no matter what the caller asked for; that one needed the `--no-install`
gate. The skill-namespace relink is already `--target`-derived and writes links pointing back at
the project being scaffolded, which is correct behaviour for a real target; it only became
dangerous when the target was a throwaway directory. So `--no-install` does **not** suppress it,
and a normal `--no-install` scaffold of a real repo still maintains that repo's namespace.

What covers both is the root: the plugin directory and the namespace now resolve through
`$HERMES_HOME`, the variable Hermes itself defines and that `ai_badger_hooks.hermes_skills_root`
and `hermes_session_source` already honoured; `~/.hermes` is the fallback, not the hardcoded
answer. `rescaffold()` points `$HERMES_HOME` at a directory inside its own throwaway holder, so
neither write can reach the operator's Hermes home — and that holds for the plugin install too,
independently of `--no-install`.

One consequence worth stating: `den-refresh` builds its Scaffolder with `install=False`
(`refresh.py:230`), so it no longer refreshes `~/.hermes/plugins/ai-badger` as a side effect. It
still maintains the namespace, which it calls explicitly and reports as `hermesSkillLinks`. The
documented remedy for stale plugin copies is unchanged and unaffected: `badger_lib.copy_skew`
already says *"re-run welcome-ai-badger to refresh them"*, and a welcome-ai-badger run still does.

**The silence is broken.** The bootstrap `RuntimeError`'s message is printed once to stderr
before `FRAMEWORK_ROOT = None`, in the `ai-badger: <message>` style the copy-skew warning
already uses. It names every place the shim looked and what to do about it.

**The remediation is the command the gate runs.** The gate printed

```
python3 features/common/skills/welcome-ai-badger/scripts/scaffold.py \
    --config .ai-badger/config.json --target . --root . --no-install --skills ''
```

and ran that *plus* `AI_BADGER_MCP_AVAILABILITY=all`, which it sets so its verdict does not
depend on what the host has on `PATH`. Following the printed form verbatim on a machine without
`hermes` installed dropped `hermes` and `ai-raccoon` from `.github/mcp.json`, `.hermes.md` and
three agent-discovery files — and the gate then rejected the tree its own message produced, nine
paths at a time. `remediation()` and `rescaffold()` now share one argv builder and the printed
command carries the environment.

## Proof

`tests/test_scaffold_freshness_guard.py` seeds a fake `$HOME` with an installed plugin *and* a
skill namespace, runs the gate, and compares a hash-per-path snapshot of the whole `~/.hermes`
tree before and after — so it covers both write paths, not just the one named in the report. A second test takes
the command the gate prints out of its own stdout, runs it on a minimal `PATH` — the machine the
forced availability exists for — and re-runs the gate against the result. Both were red before
this change; the second reproduced the exact nine-path failure quoted above.

`tests/test_hermes_plugin_install.py` pins the `--no-install` no-op and the `$HERMES_HOME`
override at the adjustment, and end-to-end through `Scaffolder`, so the flag cannot quietly stop
being passed. `tests/test_hook_bootstrap_diagnostic.py` strands a copy of the plugin with no
framework above it and asserts it says so.

Two existing tests were rewritten and one fixture changed shape, because `--no-install` now
means something they relied on it not meaning:
`test_scaffold_installs_hermes_plugin_as_directory_plugin`,
`test_scaffold_refreshes_stale_hermes_plugin` and
`test_the_installer_records_the_version_the_copies_came_from` pass `install=True`
(`make_scaffolder` defaults to `install=False`), and the session `shapes` fixture in
`tests/test_deployment_shapes.py` drops `--no-install` — the `hermes-plugins` shape *is* the
user-scope install, so the fixture that builds it has to ask for one.

The suite's session `$HOME` redirect now also clears `$HERMES_HOME`, which outranks `$HOME`
wherever the Hermes user scope is resolved.
