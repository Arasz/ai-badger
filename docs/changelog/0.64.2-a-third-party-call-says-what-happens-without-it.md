# 0.64.2 — A third-party skill call says what happens without it

`differential-feature-refactor` steps 6 and 7 read *invoke `superpowers:brainstorming`* and
*invoke `superpowers:writing-plans`* — bare imperatives with no presence check and no fallback.
On a machine where that plugin was never installed, the middle of the workflow is a hole and
nothing notices.

The same file already carried the shape that works, in its *Relationship to a spec skill*
section: name the **capability**, condition on presence, state the fallback inline. Steps 6-7 now
follow it, and a project without the plugin is told what to write instead.

## A convention with a test, not a mechanism

Gating third-party references at scaffold time was considered and rejected: a scaffolded
`SKILL.md` is committed and shared, while plugin presence is per-machine and mutable, so the
output cannot depend on the condition. `tests/test_third_party_skill_references.py` pins the
convention instead — every catalog `SKILL.md` is scanned, and a `plugin:skill` reference with no
fallback in its own block fails.

## Two ways it was wrong first, both caught by running it

**The plugin set is derived, not listed.** The first pattern flagged `node:fs`, `path:line`,
`name:score`, `server:tool` and `trust:untrusted` — ordinary prose, none of them a skill. A
denylist of non-plugin prefixes would grow forever, so the set now comes from
`features/*/skills.json`: only a name this catalog actually installs can be a reference, and the
set maintains itself as sources are added.

**The unit is the step, not the paragraph.** With blank-line splitting the guard passed on the
very file it was written for. That workflow is one unbroken numbered list, so step 1's *"fall
back"* excused the bare reference in step 6 — a check that could not fail, in a change about
holes that nothing notices. Splitting on list-item boundaries as well fixes it, and a regression
test pins that specific arrangement.
