# 0.53.0 — fixtures people actually typed

Issue #140's last open item. The three MCP eval fixture sets are author-written, and the issue
named the bias without flinching: the queries were invented by the person who also wrote the
descriptions being matched, which lifts recall for a reason that has nothing to do with the
matcher. `tooling/fixture_harvest.py` reads the retrieval telemetry the hooks already write and
proposes the other kind — queries somebody really typed — without dragging user content into a
public repository.

```
$ tooling/fixture_harvest.py --log ~/.ai-badger/debug/audit.jsonl --out candidates.jsonl
records=1269  retrieval=74  tool_checks=0
not harvestable: redacted=0  clipped=57  machine=0
harvestable: 12 distinct queries from 17 records
```

Every record lands in a named bucket: another component's, a tool check (`known` / `unknown` /
`server_unindexed` — about a call, not a query), redacted at write time, clipped by the 200-char
field cap, tag-shaped harness turn, or harvestable. Duplicates collapse with a `seen` count.

## A candidate is not an answer

A candidate carries the **observed** outcome — `hit` or `gate`, and what was returned — and never
an `expect` field. Telemetry records what happened; what *should* have happened is a judgement a
human makes, and that review is also the privacy gate. Nothing reaches a fixture file without
someone reading it first.

Redaction, strongest first:

| Level | What is written |
|---|---|
| `AI_BADGER_DEBUG_REDACT` at write time | The query was never on disk; the harvester says so and says how to change it |
| default output | The query is replaced by its SHA-256 — runs join and count, the text never leaves the machine |
| `--include-queries` | The text, for the reviewer, with a warning printed next to the path |

`project` is always a 12-character digest of the project path, never the path: a path names a
client.

## Fired in anger, and what it found

Against a real 1269-record log: 74 retrieval records, **0 redacted, 0 machine-shaped, 57
clipped**. Seventy-seven percent of real retrieval traffic is longer than the 200-char field cap,
so the obstacle to harvesting is not the redaction switch anyone worried about — it is that real
messages are long and the log stores only a prefix of them. Twelve distinct queries survived, and
the checked-in output carried no query text, no path, and no project name.

That also answers, honestly, what proportion of the corpus should be observed rather than
authored: a proportion is the wrong target. The longest authored set averages 15.3 tokens; the
traffic that gets clipped is several times that, and it is exactly the regime where issue #165's
coverage-gate defect did its damage. Until the observed subset reaches that regime at all, no
percentage makes the distribution right. Raising the query cap — the record budget is `PIPE_BUF`
at 4096 bytes, and one 200-char field is nowhere near it — is the prerequisite, and it is a change
to `debug_log.py` in every deployment shape, not to the harvester.
