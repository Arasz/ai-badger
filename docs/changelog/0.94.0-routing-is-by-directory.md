# 0.94.0 — routing by directory is ruled, and two drift documents catch up

Documents only. No production code changes in this release, and the one question ADR-0018 leaves
open changes nothing in the tree until it is ruled on.

## ADR-0005's revisit condition fired, and the owner ruled on what it exposed

ADR-0005 rejected declaring a skill's routing scope in `SKILL.md` frontmatter on exactly one cost,
and named its own trigger for reopening: *"Worth revisiting if anything else ever needs frontmatter
at build time."*

Seven readers now do. `skills_lint` rule 10 requires eight frontmatter keys on every catalog
`SKILL.md` and refuses a block it cannot parse deterministically; the scaffolder reads persona
`model:` lanes; the dispatch gate reads `model:` to deny an undeclared `Agent` call. The premise is
dead, and so is the specific fear behind it — a parse miss is now a reported violation, never a
silent pass.

Re-examining it surfaced a conflict neither existing record admitted: ADR-0005 rejected deriving
routing from directory layout, and ADR-0010 did exactly that a day later.

**Ruled: the project routes skills by stack directory.** ADR-0005's rejection of directory-derived
routing is superseded outright, and ADR-0010 is restated rather than merely tolerated. The ruling
ratifies what the code already does and already argues —
`badger_lib.catalog_skills_for_stack`'s own docstring says *"Membership here is the directory, not
the scope, because that is what 'this stack owns it' actually means"*, added after filtering by
scope delivered an `optIn` skill to `.ai-badger/skills/` and linked it into no discovery directory
(#261). Scope is the wrong key for ownership.

One framing is retired with it. The fifteen stack-local skills (claude 1, dotnet 11, hermes 2,
mcp 1) are routed by **presence in a stack directory**, not by absence from `SKILL_SCOPES`.
`stack_local_skills`' `not in SKILL_SCOPES` clause is a guard against routing a universal skill
twice — measured at 0.93.1 it excludes nothing — and calling it the routing rule made a deliberate
design read like a bug.

`SKILL_SCOPES` is therefore restated as what it actually is: a **scope declaration for the
universal set**, answering `default` vs `optIn` for the 36 skills under `features/common/skills/`.
Not a routing table.

[ADR-0018](../adr/0018-where-the-skill-routing-declaration-lives.md) records the ruling and leaves
one question open — where that scope declaration lives — recommending the constant stays, narrowly.

## Three of the review's figures did not survive checking

The ADR records the measurements rather than the claims:

- `SKILL_SCOPES` holds **36** entries, not 39 — 14 `default`, 22 `optIn`.
- Removing the dict entirely takes `engine/badger_lib.py` from 1032 lines to 991, against pylint's
  default limit of 1000. The `too-many-lines` disable buys **nine lines of headroom**, so it
  belongs to the module's size, not to ADR-0005 — measured with pylint, not estimated.
- `skill_scope()` and `default_skill_names()` have **no production callers**. The property that an
  undeclared skill is an error is held by
  `test_every_catalog_skill_is_reachable_by_a_declared_route`, not by `UnknownSkillScope`.

A fourth measurement went against the ADR's own recommendation and is recorded as plainly:
`default_skills_in` already calls `iterdir()` and stats a `SKILL.md` per entry, so `SKILL_SCOPES`
never avoided filesystem I/O — it filters a directory walk. The draft's strongest argument for
keeping the constant was withdrawn on that basis, and the recommendation now stands on one
property (the ship-unasked set stays reviewable in one hunk) plus migration cost.

## Two documents still described the old drift behaviour

0.91.0 changed what Tier 1 drift detection counts as drift. Two documents went on describing the
behaviour it replaced; both are corrected against the code at 0.93.1.

**[ADR-0001](../adr/0001-versioning-and-release-model.md) decision 5** said the check "prints one
line on mismatch and is silent otherwise". A new amendment records what is true now:

- The comparison is `versions_diverge`, which reads `(major, minor)` off each side and ignores the
  patch slot. `0.93.0` against `0.93.1` is silent; `0.93.1` against `0.94.0` still speaks. An
  unparseable version on either side falls back to string inequality.
- The hook can speak with **no version drift at all** — `competing_copies_notice` is emitted on its
  own when the idle `~/.ai-badger/framework` cache disagrees with the tree the session is running
  from.

What has not changed, and the amendment says so: two local reads, no network, silence on every
failure path.

**[hermes-claude-compatibility.md](../hermes-claude-compatibility.md)** carried the same stale
prose plus a working sample that got it wrong. Its `inject_drift_notice` example compared
`scaffold_ver != fw_version`, which is the behaviour 0.91.0 removed — anyone porting it would have
built a hook that nags on every patch release. The sample now carries the `(major, minor)`
comparison, duplicated inline the way the shipped Hermes hook duplicates it and for the reason that
hook's own comment gives, with a pointer to the test that pins the two spellings against each
other. The Option B cron prompt was fixed for the same reason.
