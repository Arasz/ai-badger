# 0.47.0 — retrieval tells you what it did, and a redact switch for the query

Phase 0 of the skill-index spike (`docs/adr/0004-mcp-tool-index.md`'s reopening question):
before anything about a matcher gets rebuilt, measure whether it misses. Measurement needs
a record of what the retrieval path actually did — and that record did not exist.

## The defect

`ai_badger_hooks.py`'s only MCP-index observation point was:

```python
logger.debug("mcp_index_hit=%s tool=%s", known, tool_name)
```

on a bare `logging.getLogger("ai_badger_hooks")` with no configured handler in any shipped
deployment shape (Claude, Copilot, Hermes). `docs/adr/0004-mcp-tool-index.md` lists this under
"Consequences → Positive: Observability" — it was the appearance of observability, and nobody
had ever read one of those lines. It is now routed through the existing `debug_log` facility
(`_debug(...)`), the same off-by-default, `call-behaviorist`-managed sink every other hook uses.

## `hit` / `gate` / `absent`

The retrieval path (`_find_relevant_tools`, consumed by `pre_llm_inject_context`) previously
produced one observable outcome — nothing appended to context — for two different reasons: no
tags were extracted from the query (measured: 8 of 11 realistic purposes), or tags were
extracted but every scored tool fell below the match threshold. A "no match" that reads
identically to "no index" is a bug that hides itself; distinguishing them is the entire point
of this phase:

- **`hit`** — at least one candidate cleared the bar; something was returned.
- **`gate`** — candidates were scored and all fell below the bar. A correct, frequent outcome,
  not a failure — but previously indistinguishable from `absent`.
- **`absent`** — no `.ai-badger/mcp-tools.yaml` to search.

Each record carries the extracted terms, how many tools were considered, the top three scored
candidates as `name:score`, what was actually returned, and the match threshold in force — so a
later threshold change is attributable to a jump in the record rather than inferred.

## The query field, and `AI_BADGER_DEBUG_REDACT`

The query text is the one field carrying user content, and it is indispensable: a retrieval
record without it can neither diagnose a miss nor become a fixture for the eval harness a later
phase depends on. It is recorded by default, alongside `AI_BADGER_DEBUG` / `AI_BADGER_DEBUG_DIR`'s
existing opt-out convention: setting `AI_BADGER_DEBUG_REDACT` drops the query field only, leaving
every other field intact so the log stays useful for counting. The drop happens inside
`debug_log.log_event` itself, at the point of writing — a redacted record never contains the
text, which rules out a post-processing scrubber that could be bypassed or lag behind a write.

## `behaviorist.py`'s two constraints

- **No new component.** The new events log under the existing `ai_badger_hooks/mcp_retrieval`
  phase of the already-established `ai_badger_hooks` component — the same pattern
  `ai_badger_hooks/session_start` and `ai_badger_hooks/commit_reminder` already use. A novel
  top-level component would be reported as an orphaned wiring fault by the tool whose entire
  job is finding those.
- **`KEY_NAMES` is the record's real schema.** Seven new keys (`query`, `terms`, `candidates`,
  `top`, `returned`, `threshold`, `tool`) are added to `debug_log.KEY_NAMES` in the same commit
  that introduces them, so `call-behaviorist`'s `tail` expands them by name instead of printing
  a raw letter. A new completeness test (`tests/test_mcp_retrieval_telemetry.py`) asserts
  `set(record.keys()) <= set(KEY_NAMES)` for every record this component emits — a check on the
  writer, since that is the failure that actually happens.

## Migration

Nothing required. `debug_log` is off by default; nothing is written until `call-behaviorist`
switches it on.

## Not covered

The skill index itself, the BM25 matcher, the eval harness, a `why` command, and any change to
what the MCP matcher *returns* — all explicitly out of scope for this phase. The matcher's own
zero-tag gap (8 of 11 realistic purposes) is now something this telemetry can count; whether it
justifies replacing the matcher is Phase 3's question, gated on the D7 measurement this makes
possible.
