# 0.102.0 — the meta-gate proves gates run, and the workflow pins are enforced

Three holes of one shape: a list nobody compares against the list it must match. A check that
exists and a check nobody runs look identical from inside the test suite, and so do two
enumerations that have quietly drifted apart.

## The meta-gate never read verify.sh

`tests/test_every_check_can_fail.py` globs `gates/`, finds every runnable script, and demands a
registered provocation for each — a known-bad state it builds and runs, proving the gate can
fail. It never opened `.lefthook/pre-push/verify.sh`. Lane membership was asserted only by
`test_every_advertised_lane_is_dispatchable`, whose lane list is a hardcoded `parametrize`
checking LANES → dispatch table; `tests/test_gates_layout.py` carried a third hardcoded list.
None of the three asked the question in the other direction: does a lane run this gate?

So a gate could live in `gates/`, be named in both hardcoded lists, be documented in
`docs/scripts.md`, carry a provably-correct provocation — and be dispatched by nothing.

Measured: a runnable `gates/probe_lint.py` wired to no lane was planted, and every coverage test
stayed green. `test_every_gate_is_dispatched_by_a_lane` now walks `$LANES` through the `lane_cmd`
case arms and the `lane_*` helpers those arms call, and fails on exactly that plant.

Two properties the walk had to have, both pinned by their own test:

- It reads `$LANES`, not the file. `mutation` has a `lane_cmd` arm and is deliberately outside
  `$LANES`, so a gate only `mutation` ran would never run on a push.
- It takes one hop through the tooling scripts a lane runs. `gates/skills_lint.py` runs on every
  push as an `import` inside `tooling/validate.py --all`, and its filename appears nowhere in
  `verify.sh` — the first draft of this test reported it as an orphan.

## Nine pinned actions, and nothing keeping them pinned

0.97.0 pinned all nine GitHub Actions references to commit SHAs, honouring
`features/github/invariants/pin-actions-to-sha.md`. Nothing enforced it. The pins were correct
by inspection only — which is how that invariant came to ship violated nine times over within
hours of being written.

`gates/workflow_lint.py` enforces both halves: every `uses:` in `.github/workflows/*.yml` is a
40-character commit SHA (a `./` local action is exempt — there is no remote code to re-fetch),
and every workflow, or each of its jobs, declares an explicit `permissions:` block. It is
line-oriented, so pyyaml stays optional (ADR-0005), and a file whose `jobs:` block it cannot
read is a violation rather than a skip.

It found a live one on its first run: `.github/workflows/pylint.yml` — the workflow that runs
every other gate in CI — declared no `permissions:` anywhere and ran on the repository's default
token scope. Fixed here to `contents: read`.

The lint runs in the new `workflows` lane of `verify.sh` and as a step in `pylint.yml`, and it
carries two provocations in the meta-gate's REGISTRY: a tag-only `uses:` and a workflow with no
`permissions:` block. Both were also proven against the real workflow tree by mutation —
unpinning `actions/labeler` produced `labeler.yml:15: actions/labeler@v7 is not pinned`, and
restoring it returned `ok  workflow lint — 6 workflow(s) checked`.

## The hook's `unset` and `badger_lib`'s list had drifted

`verify.sh` drops git's hook environment in shell; `badger_lib.git_env()` drops it in Python
from `GIT_LOCATION_ENV`. Two hand-maintained enumerations that must agree, and nothing compared
them. Five of the nine names in `GIT_LOCATION_ENV` were missing from the shell list:
`GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_NAMESPACE`
and `GIT_CEILING_DIRECTORIES`. All five are added here.

What that costs was measured with `GIT_COMMON_DIR` set: `risk_mode.py` printed nothing, so a
`--risk` task silently reverts to the full gate; `commit_reminder.uncommitted_files` returned
`[]`; `memory_first_gate` reported the other repository's basename. **The divergence between
the two lists is demonstrated; the live break is conditional** — nothing here showed that a
real hook run ever meets a set `GIT_COMMON_DIR`, only what happens when one does.

`test_the_hook_unsets_every_variable_badger_lib_calls_a_location_variable` reads
`GIT_LOCATION_ENV` from `badger_lib` and the `unset` line out of `verify.sh` and requires the
shell list to be a superset — not equality, because `verify.sh` legitimately also drops
`GIT_QUARANTINE_PATH`, `GIT_REFLOG_ACTION`, `GIT_AUTHOR_DATE`, `GIT_COMMITTER_DATE` and
`GIT_EDITOR`, which pin git's behaviour rather than its location. It went red on exactly the
five names above before the fix, and red on `['GIT_COMMON_DIR']` when that one name was deleted
again afterwards. Two more tests pin the reader itself, so a parse that quietly returned
everything cannot stand in for the comparison.

That makes three instances of this defect class found on the same day: three gate-name lists,
three path-containment predicates, and these two environment lists.
