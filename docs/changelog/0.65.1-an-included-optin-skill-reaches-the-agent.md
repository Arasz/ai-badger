# 0.65.1 — An included `optIn` skill reaches the agent

A skill named in `config.include.skills` was written to `.ai-badger/skills/<name>/` and reported
as included — and no discovery link was placed into `.claude/skills/`, which is the only place
Claude Code looks. The run reported success while the skill was unreachable.

Placing the link by hand did not survive: the next refresh deleted it and reported it as *"no
longer delivered to this project"*, in the same run that delivered it. One report said both
things about the same three skills.

## Cause

`scaffold.py` filtered the **delivered** set through `skills_for_stack`, which answers *what
does this stack ship by default*. That is the right question when deciding what to deliver and
the wrong one when deciding which already-delivered skills belong to an agent: an `optIn` skill
the project asked for is in the delivered set and, by definition, not in that answer.

`catalog_skills_for_stack` answers by **directory membership**, whatever the scope, because that
is what "this stack owns it" means. One change fixes both halves — the link is placed, and
`adjust_skills._prune` stops removing it, because it is now in the delivered list it checks
against.

## Why it shipped

The tests asserted delivery to `.ai-badger/skills/` and stopped there. Delivered and
discoverable are different claims, and only the first was being checked.

Four tests added: the link exists and resolves to a real `SKILL.md`; a `default` skill still
reaches the agent (the fix must widen the filter, not shift it); an `optIn` skill nobody asked
for still does not; and a second run does not prune the link the first one placed.

Reported as #261.
