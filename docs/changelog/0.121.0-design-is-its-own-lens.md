# 0.121.0 — design is its own lens

A `ux` stack, and a design lane in `complete-project-scope-code-review`. Both come from running
that skill over a real project and finding a whole class of defect that no lane in the roster was
asking about.

## What the gap looked like

The recurring-lenses table had a **Consumer surface** row — "CLI/API/UI contracts, error text,
exit codes". That is an interface-correctness lens. Nothing in the table asked whether the product
was any good to use: how long a flow ran, what a screen said when it had nothing to show, whether
a component followed the design document the project had already written.

On that campaign a design lane was added late, deliberately **separate** from the existing
frontend-code lane rather than folded into it. Over the same files, the code lane's findings and
the design lane's findings barely intersected — the code lane asked "is this correct" (wiring,
data fetching, type honesty), the design lane asked "is this good to use", and the design lane
returned several times as many findings. Merged into one lane, the second question would have
lost: correctness is the easier question and it arrives with evidence attached.

## `features/ux/`

A stack in the shape of `github` — a `stack.json`, two invariants, one instruction file:

- **Design every state a user can reach.** Empty, loading, partial, error and success are states
  of the surface, not accidents of the data.
- **Record the design choice that looks like a defect.** Design intent leaves no trace in the code
  that expresses it, so an unrecorded deliberate choice is indistinguishable from an oversight.
- `ux.instructions.md` — flow length, state coverage, microcopy, reuse of the project's own design
  language, destructive-action affordances, and not restyling a surface before checking what feeds
  it.

Detection is from UI component files (`*.tsx`, `*.jsx`, `*.vue`, `*.svelte`, `*.razor`), which is
a proposal and not the scope: the lens applies to a command line and a terminal UI as much as to a
rendered view, and no file extension announces those, so a CLI project adds `ux` to `stacks` by
hand. Because the review skill derives its lane roster from the project's configured stacks, a
project carrying `ux` gets the design lane derived rather than remembered.

## The calibration, which matters more than the recommendation

The design lane was the least reliable lane on that campaign as well as the most productive, and
the skill now carries both halves.

- **Check for a ratified decision before filing taste as a defect.** The adversarial pass refuted
  that lane's single highest-severity finding outright: it had flagged a product-wide default as a
  defect, and the default was an owner-approved decision recorded in a plan document the lane never
  opened. A design lane needs this check more than a code lane does, because design choices are
  deliberate more often and the ruling that made them deliberate lives in a document, not in the
  code. Every design finding now names where it looked for a prior ruling; "nowhere" is an answer,
  and it turns the finding into a question for the owner.
- **A design lane that only reads source produces opinions.** Its most valuable findings came from
  running the product and taking screenshots. The same instrument cuts both ways — two findings
  turned out to be artifacts of the lane's own mock rather than defects in the product, and it
  caught and withdrew both itself — so a finding now says which it looked at.
- **A cosmetic finding can be sitting on a correctness bug.** One finding filed as cosmetic turned
  out to rest on a status that never rendered at all, because the producer and the consumer parsed
  it differently. Design review lands on exactly the surfaces where a silent defect shows up as
  something that merely looks off.
