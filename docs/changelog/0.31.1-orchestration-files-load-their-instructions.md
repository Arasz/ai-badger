# 0.31.1 — orchestration files load their instructions

## The bug

`features/azure/instructions/azure-functions.instructions.md` scoped itself with:

```
**/*Orchestrator*.cs
```

Durable Functions code is conventionally named **both** ways — `OrderOrchestrator.cs` *and*
`OrderOrchestration.cs` — and `*Orchestrator*` matches only the first. Files named
`*Orchestration.cs` silently never loaded these instructions. Reported from a real project
where three of 91 routed files were affected.

Silently is the operative word: a path-scoped instruction file that never matches produces no
error. It simply is not there.

## The fix

The stem both spellings share is `Orchestrat`:

```
**/*Orchestrat*.cs        (was **/*Orchestrator*.cs)
**/*[Oo]rchestrat*.ts     (was **/*[Oo]rchestrator*.ts)
**/*[Oo]rchestrat*.js     (was **/*[Oo]rchestrator*.js)
```

Verified with `fnmatch`: `OrderOrchestration.cs` went from unmatched to matched, and
`OrderOrchestrator.cs` still matches.

## Also checked, not changed

The other `applyTo` stems in the catalog — `*Function*`, `*Activity*`, `*Cosmos*`, `*Mcp*` —
already cover their plural and derived forms.

`*Repository*` has the same theoretical gap (it would miss `Repositories.cs`), but the
repository convention names files `CustomerRepository.cs` inside a `Repositories/` directory,
and the glob matches on the filename, so the realistic case is already covered. Left alone
rather than widened speculatively.

## Upgrading

Re-scaffold. If your project has `*Orchestration.cs` files, they will start loading the Azure
Functions instructions — which is the point.
