# 0.50.0 — the checkpoint hook users had to wire themselves

`features/common/skills/task/scripts/stop_hook.py` has shipped since the skills moved into
`features/common/`, tested and scaffolded into every project, and `features/common/hooks/
hooks-manifest.json` never carried an entry for it — `git log -S "stop_hook" --
features/common/hooks/hooks-manifest.json` is empty. Not a decision recorded anywhere; an
omission.

## What the evidence actually said

Issue #141 argued the case from dormancy: an unwired script, `checkpoints.latest` zero for the
framework's entire life. Both premises are wrong, and the truth is a stronger argument.

`checkpoints.latest` is populated downstream with real numbers, e.g.
`{"contextTokens": 276168, "assistantMessages": 896, "cumulative": {…}}`. The debug log holds
31 `stop_hook` records across three sessions and three framework versions (0.36.0, 0.37.0,
0.40.0) with no errors. Three sibling repos register the script on `Stop` by hand, and the
commit that first did it is titled *"chore: sync with ai-badger — catalog refresh + wire the
missing runtime"*. A user hit the gap and patched around it, in three repos, and said so in the
commit message.

So this release is not shipping an untried idea. It is adopting upstream what people already
run in production.

(The same issue also reported that `stop_hook`'s debug records name no project. They don't —
but only in the log's oldest entries: attribution shipped in #114/0.41.0 and every unattributed
record predates it. Nothing to fix, and no test added for it.)

## Wired on two events, for two different reasons

| Manifest entry | Event | What it is for |
|---|---|---|
| `task-checkpoint` | `Stop` | Per-turn. Refresh `latest`, promote STARTED → IN_PROGRESS, and block once when a finished task left `state.json` or the agent docs unattended. |
| `task-checkpoint-session-end` | `SessionEnd` | Once, at the end. Flush the checkpoint for a final turn `Stop` never saw. |

`Stop` is not a session-end event — it fires when the assistant finishes a turn, and **not at
all** when the turn was interrupted. The file's old docstring claimed `token-usage.json` stays
fresh "even if the session dies abruptly", which `Stop` alone cannot deliver: the tokens of an
interrupted final turn are never checkpointed. `SessionEnd` is what closes that, so it is wired
too, and the docstring now says which event delivers which property.

The two events have opposite capabilities and the script honours the difference. A `Stop`
hook's stdout reaches the model as `{"decision": "block", "reason": …}` and by no other route,
which is why the enforcement half stays `decision: "block"` — an "advisory" Stop hook is not a
gentler feature, it is a silent deletion. `SessionEnd` has no decision control at all and its
JSON output is ignored, so on that event the script checkpoints and never blocks; a test pins
that it also spends none of the per-task one-shot reminder flags there.

## Three guards on the block

- `stop_hook_active` — the documented loop-breaker, unchanged.
- Per-task one-shot flags (`stateJsonReminderSent`, `compactionReminderSent`) — unchanged.
- **New: a per-session block budget.** Claude Code stops honouring a Stop hook's block after
  eight in one session; a ninth costs a turn and changes nothing. The hook counts its own in
  `executed-tasks.json` under `stopBlocks` and, once the budget is spent, returns *before*
  touching any reminder flag — spending a reminder's single shot on a block the platform will
  ignore throws the message away.

## Three defects fixed on the way in

**The transcript scan was unconditional and repeated.** `parse_transcript_usage` reads the
whole JSONL. On a hook that now runs every turn, that is paid per turn — and it was paid once
*per matching task*. The hook now returns before scanning anything when no tracked task owns
the session, and parses at most once when several do.

**Payload fields were indexed by one spelling.** Sources disagree (`session_id`/`sessionId`,
`transcript_path`/`transcriptPath`, `tool_use_count`/`turn_count`,
`session_end_reason`/`exit_reason`). Every read now goes through a `field()` helper that tries
each known spelling and falls back, with tests for the camelCase payload; an unrecognised
`hook_event_name` is treated as a turn stop, because losing the block channel silently is the
worse of the two failures.

**A zero checkpoint could overwrite a real one.** `make_checkpoint` drops
`parse_transcript_usage`'s `transcriptFound` flag, so a missing or unreadable transcript
produced an all-zero checkpoint indistinguishable from a session that spent nothing — and wrote
it over the last good measurement. This is still live code, not history: the degenerate
`contextTokens: 0, assistantMessages: 3` records in the downstream projects predate 0.41.0, but
nothing since then closed the path that produces them. An empty checkpoint is now refused over
a populated one, and still written when there is none yet.

## Agent coverage

Claude only, with recorded exemptions for Hermes and Copilot in
`tooling/validate.py`'s `HOOKS_MANIFEST_AGENT_EXEMPTIONS` — the shape #147 made mandatory. Both
exemptions rest on the same fact rather than on convenience: the tracked-task record this hook
refreshes exists only because `session-start-tracking` (itself Claude-only by design) wrote a
Claude session id onto it, and the numbers come from parsing that session's Claude transcript
JSONL. Hermes' `on_session_end` carries `completed`/`interrupted` booleans and neither a session
id nor a transcript path; Copilot has `agentStop` and `sessionEnd` but keeps its usage in
`~/.copilot/session-store.db`. Wired on either, the script would match no task and measure
nothing. Junie is excluded at the platform level and is not re-litigated here.

## Also corrected

The `task` skill's `SKILL.md` and `compute_usage()`'s comment both claimed a per-subagent cache
split "isn't available" because the completion notification exposes only `total_tokens`. Half
right. `parse_transcript_usage` already reads `cache_read_input_tokens` per message and branches
on `isSidechain`, so a **main-vs-sidechain** aggregate is cheap. It is the **per-subagent**
split that is out of reach: attributing a sidechain message to the dispatch that produced it
needs `parentUuid` chasing, which nothing here implements. Both places now say that precisely.

## Tests

`tests/test_stop_hook.py` gained fifteen cases in four classes — transcript-scan avoidance,
payload-spelling fallbacks, `SessionEnd` being checkpoint-only, and the block budget. Nine of
them fail against the previous implementation; the rest are characterisation guards.
`tests/test_task_checkpoint_wiring_end_to_end.py` is new and loads the *real* manifest and
`hooks.json`, the same philosophy as the context-enrichment wiring test: a synthetic fixture
passing proves nothing about a catalog that never registered the hook.

**Two tests were rewritten, and a rewritten test is where a regression hides:**

- `test_scaffold_hook_wiring.py::test_wiring_from_a_second_checkout_does_not_append_a_duplicate`
  asserted that no command string appears twice anywhere in `settings.json`. Wiring one script
  on two events makes that false by design, so it now asserts uniqueness **per event** and
  compares the whole event→commands mapping between the two checkouts — a strictly stronger
  assertion than the old length comparison.
- `test_stop_hook.py::test_debug_logging_records_checkpoint_event` and
  `test_the_checkpoint_record_names_the_project` ran with no tracked task at all, so under the
  new skip-early path they would have recorded a `skip`. Both now seed the IN_PROGRESS task
  whose checkpoint they claim to be about, and a new sibling test pins that the no-task case
  records `skip` rather than a `checkpoint` that checkpointed nothing.

## Migration

None for consumers already wiring the script by hand: `hook_wiring.py` dedupes on script
identity, so the next `welcome-ai-badger`/`den-refresh` collapses a hand-written `Stop` entry
into the generated one instead of appending a second. Projects that never wired it gain a
`Stop` and a `SessionEnd` hook on their next re-scaffold.
