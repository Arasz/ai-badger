# 0.173.0 — grounded feedback reaches Claude's PostToolUseFailure

**Minor** — a second, Claude-only hooks-manifest entry wires `grounded_feedback_hook.py` onto
`PostToolUseFailure`. 2026-09-24.

## What was wrong

Claude's `PostToolUse` "Runs immediately after a tool completes successfully" (hooks.md) — it
never fires for a failed Bash call. Every other host this hook already covers (Copilot, Hermes,
pi) runs its own post-tool hook regardless of outcome, so `grounded-feedback`'s single
`PostToolUse` arm reached them but silently missed every Claude Bash failure, the exact case
Rule 3C exists for.

## What changed

- A new manifest entry, `grounded-feedback-failure` (claude arm only, `PostToolUseFailure`),
  sits beside the existing `grounded-feedback` entry, whose `PostToolUse` arm is untouched. pi
  reads the generated `.ai-badger/hooks/hooks.json`, and its `PostToolUse` group still lists
  grounded-feedback there, unmoved.
- `grounded_feedback_hook.py` now branches on the incoming `hook_event_name`: `PostToolUse`
  keeps reading `tool_response`/`exit_code` as before; `PostToolUseFailure` reads `error`
  instead — the exit code from a leading `Exit code N` line when present, `?` otherwise, with
  any trailing truncation marker preserved verbatim — and treats `is_interrupt: true` as nothing
  to report.
- The hook now echoes back whatever `hook_event_name` it was actually called with (defaulting to
  `PostToolUse` when absent, matching every existing caller) instead of hard-coding
  `"PostToolUse"`.
- `tooling/validate.py`'s `HOOKS_MANIFEST_AGENT_EXEMPTIONS` records why `grounded-feedback-
  failure` names no `hermes`/`copilot` arm: both already reach every failure through the
  sibling `grounded-feedback` entry's single post-tool hook, which fires regardless of outcome.
