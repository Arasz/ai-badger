# 0.64.0 — The `dotnet` and `aspire` stacks declare their upstream skill sources

`features/python/` has declared its external skills since the source mechanism existed. `dotnet`
and `aspire` never did, so every project on those stacks added the same marketplaces by hand or
went without.

Both upstreams are first-party and were verified installable before being catalogued:

| Stack | Source | Plugins |
|---|---|---|
| `dotnet` | [`dotnet/skills`](https://github.com/dotnet/skills), which resolves as marketplace **`dotnet-agent-skills`** | `dotnet-diag`, `dotnet-test`, `dotnet-msbuild` |
| `aspire` | [`microsoft/aspire-skills`](https://github.com/microsoft/aspire-skills) | `aspire` |

The marketplace name is worth stating out loud because it is not derivable from the repository
name: `dotnet/skills` declares itself `dotnet-agent-skills`, and `claude plugin install
…@dotnet-skills` fails.

What each brings, in one line:

- **`dotnet-diag`** — performance investigation: an anti-pattern catalogue with detection recipes,
  trace collection, dump collection, BenchmarkDotNet.
- **`dotnet-test`** — CRAP scoring and coverage analysis, static untested-source discovery, the
  testability chain (detect static dependencies → generate wrappers → migrate call sites), and
  test-quality audits.
- **`dotnet-msbuild`** — binlog failure and performance analysis, incremental-build correctness,
  MSBuild anti-patterns.
- **`aspire`** — AppHost lifecycle and observability, including the rules that keep concurrent
  checkouts from fighting each other: one isolated AppHost per worktree, stop before rebuilding,
  never kill the runtime by process name.

Note `aspire` declares `requires: ["dotnet"]`, so an aspire project receives the three dotnet
plugins as well.

## `support` is `["claude"]`, and that is a fact about the installer

Not a hedge. `install_plugins._source_supports_agent` gates on the source's `support`, then looks
for an instruction keyed by the source *type* in `features/<agent>/plugins-instructions.json`.
Only claude's has a `marketplace` key. `copilot` and `junie` ship `{"instructions": {}}`; hermes
has `hub`, `tap`, `url` and `well-known`, and no `marketplace`. Declaring `"common"` would have
produced three warnings per plugin and installed nothing — a declared agent that silently
delivers nothing being exactly the failure this catalog is meant to prevent.

Making these reachable from Copilot or Hermes is not a `support` edit. A marketplace URL is the
wrong shape for either: Copilot reads `.github/skills/<name>/SKILL.md`, Hermes reads its own hub
or tap. Both would need a new source type that fetches a repository and copies its `skills/`
into place — nothing here copies files from an external source today; every installer path shells
out to an agent CLI. The upstream repositories would cooperate (they ship Cursor, Gemini and APM
manifests beside the Claude one, and their `skills/` are plain `SKILL.md` directories), but that
is a schema change and belongs in its own decision.

## Tests

`tests/test_stack_skill_sources.py` checks the real `features/` tree rather than a fixture: every
`skills.json` entry names a source declared in its sibling `skills-source.json`; a stack that
declares skills declares sources; a source in use never claims an agent whose
`plugins-instructions.json` has no instruction for its type; `marketplace` appears only in
claude's; and `install_skills` over the real catalog emits the marketplace add plus one install
per plugin, with zero warnings.

`tests/test_install_plugins.py`'s existing deliberate-act allowlist gained the four new entries —
the test that fails when a third-party plugin is added without someone choosing to.
