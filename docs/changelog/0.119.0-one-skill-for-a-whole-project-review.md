# 0.119.0 — One Skill For A Whole-Project Review

**Type:** MINOR
**Date:** 2026-08-14

## What Changed

- **Added** `features/common/skills/complete-project-scope-code-review/` (opt-in) with
  `references/` and three config-gated extensions: `dotnet`, `claude`, `github`.
- **Removed** `features/common/skills/parallel-expert-review/`. Its job is the new skill's

## Why a new skill rather than a bigger `parallel-expert-review`

The distilled workflow is a campaign, not a review pass: ground-truth baseline → derived lane
roster → parallel read-only lanes → integration → an adversarial pass that publishes what it
refuted → severity calibrated against the live system → a twice-reviewed plan → waved
implementation → a join review on every merge. Six of those nine stages have no counterpart in
`parallel-expert-review`, and the two that do — dispatch and integrate — are the two it does.

Keeping both would have put two skills in front of the same request ("MoE review", "review the
whole codebase") with one holding half the methodology. Everything `parallel-expert-review`
carried that the new skill did not is folded in: ground-truthing the plan before dispatch,
wave-gated dispatch under a concurrency cap, reconciling lane disputes from source rather than by
lane count, the mid-review merge hazard (now in the `github` extension), before/after architecture
diagrams as a plan deliverable, and `references/owner-gate-form-lifecycle.md`, which moved across
intact.

## Why it did not absorb the skills it composes with

`evidence-first-research` owns the grade vocabulary; `multi-lane-report-assembly` owns the
assembly mechanics; `research-record-audit` owns adversarial re-derivation; `owner-gate-review`
owns per-decision rulings; `design-gate-audit` owns gate honesty; `task` owns one work package.
Each does one job well and is used outside this workflow. The new skill names them and hands off
rather than reimplementing them — a skill that does everything is a skill nobody can reason about.

## Neutrality is asserted, not claimed

`tests/test_complete_project_scope_code_review.py` scaffolds two projects: a dotnet/claude/github
one, where all three extension fragments must land in the merged `SKILL.md`, and a python/copilot
one with no source-control platform, where none of them may. The second was watched go red (it
fails when handed the first's config) before being trusted; a fourth test greps the catalog source
for the tokens that belong in an extension — `dotnet build`, `pytest`, `gh pr`, `C#`, `Opus` — and
it caught one leak in the base skill's own prose on its first run.

## The eight failure modes are the payload

`references/failure-modes.md` carries the cases the workflow exists to catch, each with its
control: circular benchmarks (held-out evaluation by family, required rather than advised),
vacuous gates, specifications that encode the defect, join defects, in-sample metrics,
findings that turn out to be refutations, silent ratchets, and expectations pinned where they
should be derived.
