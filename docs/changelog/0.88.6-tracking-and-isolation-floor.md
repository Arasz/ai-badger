# 0.88.6 — the tracking store, the memory bank and the cwd all follow the checkout

Four fixes with one root: something resolved a project by looking at where it happened to be
standing, and worktree-per-task moved the ground under it.

## Token tracking had been dead for eleven consecutive tasks

`tracker_lib.resolve_project_root` walked up from the cwd to the nearest `.ai-badger/config.json`.
A task worktree carries its own copy of that marker, and the `/task` skill's Phase 1 says every
command for the rest of the task runs in the worktree — so `finish` checkpointed against an empty
store. Measured: the identical command printed `No tracked tasks` from
`.ai-badger/worktrees/full-project-review` and the full list from the checkout, and
`task_tracker.py subagent <id> …` refused with `Unknown task <id>. Run start first.`

The fingerprint was in the tracker's own data — every task from `memory-grade-hook` (2026-08-05)
through `skills-shape` (2026-08-07) reported `tokens=0`, eleven in a row, including all five of
that week's release tasks, while a task deliberately run from the checkout recorded
`tokens=326441893 cacheEff=0.958 mix=sonnet-5:54%`. Tasks predating the worktree default carry
counts (`gherkin-specbinder` 12.5M), which places the regression at 0.69.0 (#272).

`collapse_worktree()` asks git for `--show-toplevel` and `--git-common-dir` in one `rev-parse`: a
linked worktree is a working-tree root whose shared `.git` lives elsewhere, and that `.git`'s
parent is the checkout that owns the store. The collapse applies only when the resolved checkout is
itself an ai-badger project, so a vendored project nested inside an unrelated repo stays where it
is, and only to the cwd walk — `CLAUDE_PROJECT_DIR` stays the authoritative override the test
suite's own isolation depends on.

**The eleven zero-token records are left as they are.** Nine of them have no surviving transcript
to recompute from, and a number that was never measured must not be written as if it were. They
read as zero because the measurement was broken, and the changelog is where that is recorded.

`skills/task/scripts/` and `.ai-badger/skills/task/scripts/` carry a header declaring lockstep with
an upstream `job-search-ai-assistant` copy of this skill. **This change diverges from it**, and it
is deliberate: the fix stays stdlib-only and free of `badger_lib` coupling, because these files run
from the Claude Code plugin cache with no framework on `sys.path`.

## The memory gate pointed every worktree session at an empty bank

`memory_first_gate.project_id`'s docstring said "repo basename"; the code was `Path(cwd).name`, the
*directory* basename. Measured, from a worktree the gate blocked `Grep` and named
`project_id=full-project-review`, against which `memory_search` returns `{"results":[]}`; from the
checkout it named `ai-badger`. The gate fired, cost a tool call, and sent the agent to external
search — it enforced nothing.

Now derived from `git rev-parse --path-format=absolute --git-common-dir`, whose parent is the main
checkout. `--show-toplevel` returns the worktree's own path and would not have fixed it. Any git
failure falls back to the directory basename and then `unknown`, and `AI_RACCOON_PROJECT_ID` still
wins outright.

## The cwd joins the isolation floor

`tests/conftest.py` redirected `$HOME`, the debug sink and `CLAUDE_PROJECT_DIR`, but never the cwd —
so any script resolving a project root by walking up from bare `os.getcwd()` found the real
checkout, and the fix above made that walk reach *further*, from a worktree all the way to the main
checkout. With the new fixture disabled, `resolve_project_root(env={})` returns
`/Users/arasz/RiderProjects/ai-badger` from inside the suite.

A session-autouse `chdir` to a scratch directory closes it. The blanket change was viable: the full
suite is 3326 passed / 18 skipped with it in place, so no test was silently depending on the repo
being the cwd.

## Two silent failure modes stop being silent

`~/.ai-badger/hook-errors.log` held **241** swallowed hook exceptions (227 `OSError`, 14
`AttributeError`) that nothing read; several name test files. The suite now prints the standing
count at teardown and fails the run if it grows, so the backlog is bounded from here even though
the existing entries are the operator's state and are left untouched.

The six sibling-module loaders in `ai_badger_hooks.py` were reported as failing open silently on a
corrupt module. **That was inaccurate** — they already logged a warning. What they did not do was
say the feature was *off*, or stop re-logging: the failed module is popped from `sys.modules`, so
the next call retried and warned again. One shared `_load_sibling_module` now keeps absent silent
(an older scaffold legitimately lacks it) and reports broken exactly once per process as
`<label> disabled` — `memory-first gate disabled` for the enforcement gate — through both
`logger.warning` and the call-behaviorist debug log. Six near-identical 20-line copies become one,
which is how five of them came to drift in the first place.

## Six stale tracker entries closed

`ai-badger-issues-drain-session`, `pr-254-takeover`, `pr-257-takeover`, `f2-third-party-fallback`,
`enrich-last-article-about-skills` and `issue-286` had sat `IN_PROGRESS` since 1–5 August with no
worktree and no open issue behind them, so `status` reported six live work streams that did not
exist. All six ran through `finish`; none had a worktree to release (`keptBecause` empty in every
case), and `issue-286` recovered a real 2,642,415-token record from its surviving transcript.

One finding fell out of doing it: **`finish` overwrites a recorded usage with zero when the session
transcript has been deleted.** `ai-badger-issues-drain-session`'s measured 247,290,612 tokens
became 0 because `~/.claude/projects/…/76822bdc-….jsonl` no longer exists and `compute_usage`
clamps the delta at zero. The record was restored from the pre-sweep state and annotated; the
underlying refusal — `finish` should not replace a measurement with a fabricated zero — is not
fixed here.
