# 0.92.0 — the catalog's claims are checked, not just written down

Wave 2 lane L7 of the full-project review (`docs/work/2026-08-07-full-project-review-plan.md`,
item W6). Four things the catalog asserted in prose while nothing verified them.

## A config could name a stack that does not exist

`schemas/config.schema.json` said stacks must come from the catalog — in a `description` string,
which no validator reads as a constraint. So `features/github`, a directory holding one
`{"skills": []}` and nothing else, stayed selected by this repo's own `config.json` and
advertised in its `CLAUDE.md` while being absent from `index.json.stacks` entirely.

Two checks now close it:

- `catalog_stack_gaps` rejects any `features/<dir>` that ships neither a `stack.json` nor a
  feature directory — exactly the shape `features/github` had. It mirrors `index_build`'s own
  membership rule, so it needs no built index to compare against.
- `config_stack_gaps` rejects a config naming a stack **or an agent** the catalog cannot ship.
  `agents` names catalog directories as much as `stacks` does (`badger_lib.delivering_stacks`),
  so both are checked.

The second runs on every `validate.py --kind config`, which is the command `welcome-ai-badger`
tells an operator to run against a proposed config before scaffolding. A schema-valid config
selecting `kubernetes` now exits 1 and names the stack.

`features/github` was populated rather than deleted: it detects `.github/workflows/*.yml`, and
ships a pinned-SHA / least-privilege-`permissions` invariant plus a path-scoped instruction file
for workflow authoring. The catalog is 19 stacks now, and this repo's own scaffold is truthful.

## 21 JSON files under `features/` matched no schema

`SCHEMA_INSTANCES` only ever proved that a *schema* had instances. Nothing proved an *instance*
had a schema, so a new catalog file simply went unvalidated — including
`features/common/hooks/hooks.json`, which feeds `.claude/settings.json`.

`unschemad_feature_json` walks `features/` from the other end: every `*.json` under it must match
a `SCHEMA_INSTANCES` glob or a `FEATURE_JSON_WITHOUT_SCHEMA` entry that states why not. Three new
schemas cover the families the review named:

| Schema | Covers |
|---|---|
| `hooks.schema.json` | `features/*/hooks/hooks.json` — the command shapes rewritten into an agent's config |
| `mcp-tags.schema.json` | `features/*/mcp-tags.json` — the closed MCP tag vocabulary |
| `skill-extension.schema.json` | the 13 `extensions/*/extension.json` activation descriptors |

`mcp-tags.json` had declared `$schema` and `$id` as though it were a schema, so it validated as
neither. It now points at its own schema.

Five families are exempt by glob with a stated reason (settings snippets, prompt-marker context,
eval fixtures, the shipped agent-instructions schema template, the state seed). A mis-keyed
exemption is itself a violation — the pattern must match a file that exists.

## A stack could point at another stack's artifacts

`features/dotnet` declares `"requires": []`, so a dotnet-only scaffold contains no
`cloud-infra-engineer` — and its persona sent readers to one anyway. `cross_stack_reference_gaps`
now holds every stack to its declared `requires` closure. It found three dangling pointers:

- `dotnet`'s persona → `cloud-infra-engineer` (ships only with `azure`)
- `angular`'s persona → `client-never-writes-directly` (ships only with `react`)
- `mcp`'s skill → `dotnet-mcp-server` in `related_skills`

All three are fixed. `features/common` is exempt by name and with a stated reason: it ships in
every scaffold and has no `requires` closure of its own to violate.

The dotnet Cosmos/Durable Functions content is now conditional in its own prose — every section
that assumed Azure says so up front, and the store-agnostic rule is stated before Cosmos is given
as the worked example. Nothing was deleted; it just stopped presenting one cloud as the default.

## `clean-architecture-layering` was not actionable

Three lines telling an agent to keep the domain layer pure, without saying which project that is,
what counts as "framework", or what to do in a repo with no ADR process. It now names the domain
layer by shape (the assembly others reference and which references none of them, no
`PackageReference` on a web/data/cloud SDK), defines "framework" by forbidden namespace, says to
record the decision wherever the project already records decisions and to say so in the PR when it
records none — and links the ArchUnitNET test in `dotnet-domain-modeling` that turns the rule from
a convention into a red build.

## Evidence

Each new rule was broken on purpose and confirmed red, because a green gate here is a weak signal:

| Break | Result |
|---|---|
| a config selecting `kubernetes` | `INVALID config stack membership`, exit 1 |
| `features/ghost/` holding only a `skills.json` | `INVALID catalog stack membership` |
| a new `features/python/surprise.json` | `INVALID feature json schema coverage` |
| the dotnet persona pointed back at `cloud-infra-engineer` | `INVALID cross-stack references` |
| `hooks.schema.json`'s glob repointed at a path that does not exist | the glob test goes red **and** `hooks.json` immediately reappears as unschema'd |
| an exemption glob mis-keyed to `templates/stat.json` | the exemption test goes red **and** `state.json` reappears as unschema'd |

The last two matter most: an inert glob in `validate.py` had already silently disabled a schema
once (the review's A10). Coverage that is only declared is not coverage.
