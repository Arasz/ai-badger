# 0.77.0 — Hermes task tracking gathers real token data

The `/task` skill's tracker recorded all-zero checkpoints under Hermes: it resolved sessions
only from `CLAUDE_CODE_SESSION_ID`, parsed only Claude JSONL transcripts, and recorded subagent
tokens only by hand. Hermes stores the same numbers in `~/.hermes/state.db`, so the tracker now
reads them.

- `resolve_own_session()` gains a `HERMES_SESSION_ID` branch (Claude's env var still wins when
  both are set; Claude shapes are untouched).
- New `parse_hermes_session_usage` / `make_hermes_checkpoint` map the Hermes store onto the
  existing checkpoint shape: `sessions` → cumulative tokens, `session_model_usage` → per-model
  breakdown, `messages` → assistant-message count, `async_delegations` → dispatch count.
  `contextTokens` stays 0 — Hermes stores no per-message tokens (`messages.token_count` is NULL
  on every row) and no context-window snapshot; an honest zero beats a fabricated estimate.
- `task_tracker.py start` records `trackingSource` so `finish`/`reattach` (later processes)
  pick the same checkpoint maker; `resumeCommand` becomes `hermes --resume <id>` under Hermes.
- `subagent --delegation <id>` reads a completed delegation's real tokens from
  `async_delegations.result_json` instead of a hand-typed count — the live `delegate_task`
  return exposes no token count. Mutually exclusive with the manual `<total_tokens>` argument.
- Reads are read-only (`sqlite3` `mode=ro`): the tracker never writes, locks, or creates the
  Hermes store, and degrades to zeroed checkpoints when Hermes is absent — it never crashes a
  session over missing data.

Fixes the premise behind the `tooling/validate.py` exemptions (which claimed Hermes produces no
session data the tracker could parse). A Hermes plugin hook for automatic per-turn checkpoints
remains an optional future extension; the in-session CLI path is what the `/task` skill drives.
