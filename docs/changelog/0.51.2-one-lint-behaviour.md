# 0.51.2 — one lint behaviour, not two

Issue #183. `CLAUDE.md` documented `lint` as `python3 -m pylint engine tooling features gates`.
CI (`.github/workflows/pylint.yml`) and the lefthook `pylint` lane both run something else —
every tracked non-test file, enumerated:

```bash
pylint $(git ls-files '*.py' | grep -v '^tests/')
```

Two invocations, two verdicts. The one an agent reads before pushing was the weaker one: it
reported 10.00/10 while the push failed on `C0302 too-many-lines` in `scaffold.py`.

## What the two commands actually covered

Measured on this checkout, at `220cf9d`:

| | Files linted |
|---|---|
| `pylint engine tooling features gates` | 78 |
| `pylint $(git ls-files '*.py' \| grep -v '^tests/')` | 177 |

The 99-file difference is entirely `.ai-badger/` (55) and `skills/` (44) — the two mirror trees
the scaffolder and `tooling/sync_plugin_skills.py` regenerate from `features/`. Naming four
directories can only ever lint the directories named, and `scaffold.py` exists in three trees:
the old command linted one copy of it, CI lints all three. A mirror is *supposed* to be
byte-identical to its source, which is exactly why nobody notices the gap until it is stale —
the moment a lint difference matters is the moment only CI can see it.

The precise symptom the issue reports (a 1001-line `features/.../scaffold.py` rated 10.00) does
not reproduce under pylint 4.0.6, which recurses into a directory argument that is not a package.
The divergence is real regardless, and the fix removes the class rather than the instance.

## The fix

`commands.lint` in `.ai-badger/config.json` is now the enumerating invocation, so re-scaffolding
propagates it into `CLAUDE.md`, `HERMES.md`, `.hermes.md` and `.github/copilot-instructions.md`.
The selection string — `git ls-files '*.py' | grep -v '^tests/'` — is now literally the same text
in three places: the config, the CI workflow, and `lane_pylint` in `.lefthook/pre-push/verify.sh`.
It is portable to macOS and Linux (POSIX command substitution, `git ls-files` relative to the
repo root, no GNU-only `grep` flags) and matches CI byte for byte.

`tests/test_gates_layout.py` pins the parity. `test_every_gate_is_a_pylint_target` — which
asserted that the command *named* every directory holding our Python — is gone, because
enumeration makes the question meaningless; three tests replace it:

- `test_documented_lint_command_enumerates_files_like_ci` — the documented command wraps the
  shared selection in a command substitution.
- `test_ci_and_lefthook_select_the_same_files_as_the_documented_command` — the same selection
  string appears in the workflow and the lefthook lane.
- `test_lint_selection_covers_every_directory_holding_our_python` — runs the selection under
  `/bin/sh` and asserts no directory we author is missing from the result, and that `tests/`
  is not in it.

Option 2 from the issue — keep the package invocation and document lefthook as authoritative —
was rejected: the command in `CLAUDE.md` is the one agents run, so it is the one that has to be
true.
