# 0.69.2 — The merge tags itself

Tagging a release was a manual step after every merge, and the step was skipped often enough to
have its own signature failure: `release_guard` fails *every later push* until the missing tag
exists, so the next unrelated PR's CI breaks on a gate nobody touched. 0.61.1, 0.64.2 and 0.68.0
each did this, and each cost a round of confused diagnosis before someone pushed a tag by hand.

A push to `main` now tags itself.

## What it does, and what it refuses to do

The workflow reads `VERSION`, and:

- **Refuses a non-semver `VERSION`** — that is a broken tree, not a release.
- **Skips a version with no `docs/changelog/<version>-*.md` entry.** This repo's invariant is
  that every release records what changed; a merge that did not bump has nothing to tag, rather
  than earning a tag with an empty story behind it.
- **Skips a version already tagged**, so re-runs and docs-only pushes are no-ops.
- **Tolerates losing a race** with a concurrent merge: if the push fails but the tag then exists,
  that is success — the tag existing is the only outcome the workflow cares about.

The annotation is the changelog entry's title, so `git tag -n` reads as a release list.

## Only the remote counts

The first draft of the failure branch asked `git rev-parse refs/tags/<name>` to decide whether a
concurrent run had already pushed the tag. That check cannot fail: `git tag -a` had created the
local ref moments earlier. A push rejected for any real reason — tag protection, a token without
`contents: write` — would have printed "nothing to do" and exited 0, leaving the remote untagged
and `release_guard` failing on the next push for reasons the green workflow run denied.

This is the same lesson as D3, which taught `release_guard` to read remote tags rather than local
ones. Both existence checks now ask `git ls-remote`, and losing a genuine race stays the only
tolerated push failure. Caught in review on #273.

## The coupling worth a test

Creating tags and creating tags the guard *recognises* are different achievements. If the
workflow's name ever drifted from `release_guard.TAG_PATTERN`, tags would keep appearing and the
guard would keep reporting none — the silently-permissive path its own docstring warns about.

`tests/test_release_tag_workflow.py` renders the workflow's actual tag expression and asserts the
guard parses the result, rather than restating the format in the test where the two could agree
with each other and disagree with reality.
