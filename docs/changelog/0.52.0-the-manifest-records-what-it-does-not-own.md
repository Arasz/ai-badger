# 0.52.0 — the manifest records what it does not own

Issue #194 part 2. `.mcp.json`, `.github/mcp.json` and `.claude/settings.json` are files
ai-badger *merges into* and never claims: they have no manifest entry, by design, because the
project owns them. That left one question unanswerable. When step 7 (PR #192) retired
`.github/copilot/mcp-config.json` — a path no Copilot surface reads — "did ai-badger write this
file, or did someone else?" could only be *inferred*, from a key-shape heuristic
(`mcp_tools.only_generated_entries`: a top level of `mcpServers` alone, entries carrying only
`command`/`args`/`cwd`/`env`/`tools` ⇒ ai-badger wrote it). It was the right call for one
migration. It is not a record.

The manifest now carries one:

```jsonc
"generatedConfig": [
  { "path": ".claude/settings.json", "destination": ".claude/settings.json", "frameworkVersion": "0.52.0" },
  { "path": ".github/mcp.json",      "destination": ".github/mcp.json",      "frameworkVersion": "0.52.0" },
  { "path": ".mcp.json",             "destination": ".mcp.json",             "frameworkVersion": "0.52.0" }
]
```

Every config file a scaffold run actually wrote or merged into, the destination label it was
written for (`mcp_tools.McpDestination.label` for the MCP configs), and the version that last
wrote it. The next retirement reads the record instead of guessing at key shapes;
`only_generated_entries` stays for the one migration that shipped before the record existed, and
its docstring now says so.

## It is bookkeeping, not ownership

The distinction is the whole design, and each half of it is a test:

- **Drift never reports these paths.** `drift.compare` reads `entries`; a `generatedConfig`
  record is invisible to it.
- **A record licenses no write.** Nothing reads the section back. A re-scaffold merges into
  `.mcp.json` exactly as it did before — hand-added servers and hand-added top-level keys
  survive — because the record changed no code path that writes.
- **A hand-edited file is still the project's.** The record says "ai-badger wrote here, at this
  version", and nothing more. It is not a hash, so it cannot claim the content is still ours.
- **A refused write records nothing.** A `.mcp.json` whose `mcpServers` is not a mapping is
  protected, not written — and so not recorded.
- **A proposal is not a write.** `~/.claude/settings.json` is proposed and never written
  (ADR-0014 decision 6), so it never appears.
- **Tracking is irrelevant.** `.mcp.json` is gitignored in this repository (0.51.0 stopped
  shipping it) and is recorded anyway: the record is of writes, not of version control.

A record outlives the run that wrote it while its file is on disk, and dies with the file. That
is what makes it evidence: a path last written by 0.40.0 keeps saying `0.40.0` through every
later run that leaves the file alone — exactly the state #192 had to reason about — and the run
that retires the file drops the record with it.

## Also

`scaffold.py` was 999 lines when #194 was filed and 850 after part 1, which put a line budget on
it. This feature's bookkeeping therefore landed as its own module,
`generated_config.py` (`GeneratedConfigRecords`), rather than as thirty more lines in the
orchestrator — the budget doing the job it was added for.

Adjustment scripts run out-of-process and cannot reach the run's context, so files they write
(`.github/hooks/ai-badger-hooks.json`, the Claude MCP approvals) are not recorded yet. The
section is the scaffold's own destinations.
