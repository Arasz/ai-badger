# 0.139.0 — Hermes cannot be gated per dispatch, and its isolation switch is off by default

0.138.0 gated Claude's `Agent` dispatches on worktree isolation and left Hermes open, with
two `strict=True` xfails recording the gap and a note that closing it needed an observed
`delegate_task` payload. This is that observation, and it redirects the fix.

## What the schema settles

`delegate_task` cannot express isolation. AST-parsed from Hermes 0.20.6's own
`DELEGATE_TASK_SCHEMA` (`tools/delegate_tool.py`), the per-task properties are exactly:

```
goal            string
context         string
output_schema   object
```

No `worktree`, `cwd`, `workdir`, `sandbox`, `branch` or `isolation`. So the `dispatch-gate`
exemption's **conclusion** was right — there is nothing per-dispatch for a `pre_tool_call`
hook to find missing — even though its stated **reason** was not.

That reason claimed "Hermes has no custom-agent files (support.json customAgents
supported=false)". `support.json` records that same flag for **claude**, where this gate
ships and resolves the `.claude/agents/*.md` lanes the framework itself scaffolds. A premise
both agents satisfy explains neither. The exemption now cites the schema.

## What the source turned up instead

Hermes *does* isolate subagents — `delegation.worktree_isolation` in `~/.hermes/config.yaml`
(`tools/delegate_tool.py:887`), which gives each delegated child its own git worktree from
the parent's commit. It is session-wide configuration, not a dispatch argument, and it
**defaults to false**. With it off, `delegate_tool.py:2727` seeds every child's cwd from the
parent's and all lanes share one checkout.

Measured on the reporting machine 2026-08-28: the `delegation:` block set only
`max_iterations: 250`, so the default applied and every Hermes subagent was sharing the
working copy. That is the reported symptom — "no worktree isolation unless I mention it" —
in its Hermes form, where mentioning it in the prompt could not have helped either.

## The fix is a notice, not a gate

`ai_badger_hooks.subagents_share_one_tree()` reads the config on session start and warns when
the key is unset or false, naming the file and the line to add. It never writes: ai-badger
does not own user-global Hermes config, and a "read-only" gate that wrote to `$HOME` bricked
this plugin once already (0.89.0).

Parsed by a targeted scan of the `delegation:` block rather than pyyaml — `ai_badger_hooks`
deliberately keeps `import yaml` off the hook path. The scan stops at the next top-level key,
so `worktree_isolation` under some other mapping is not read as this one.

## Verification

Ten mutants against the scan, all caught. One survivor on the first pass — dropping the
comment guard in the block scan — turned out to be an equivalent mutant (no comment can start
with the key being matched), and chasing it found a real defect the tests had missed: an
inline comment. `worktree_isolation: true  # keep them apart` parsed as the value
`"true  # keep them apart"`, so a correctly-configured user was warned anyway — the false
alarm that teaches people to ignore the notice. Fixed, tested both directions, and the
unreachable guard removed rather than left as a branch no test can exercise.

The two Hermes tests in `test_dispatch_isolation_gap.py` are no longer xfails. They assert
the resolved behaviour: the exemption reason stands on its own evidence, and the plugin
surfaces the setting.
