# 0.126.0 — A Stack's Skills Reach The Agent

**Type:** MINOR
**Date:** 2026-08-16

Every skill a configured stack ships now gets a discovery link, the same way a `common` skill
always has. Scaffold output shape changes for any project configuring a stack that carries
skills, hence MINOR.

## The defect

`Scaffolder._run_adjustments` filtered the delivered skill list before handing it to the
adjustment that writes `.claude/skills/`:

```python
agent_stacks = [s for s in self.stacks if s in ("common", agent_name)]
```

`resolve_stacks(config)` returns `commonStacks + config.stacks`, and an agent name appears in
neither — `config.agents` is a separate key. So the second clause never matched anything and
the literal resolved to `["common"]` on every run. A skill from any other stack was copied into
`.ai-badger/skills/`, recorded in `manifest.json`, named in `index.json`, and linked into no
directory an agent reads.

Delivery was never the problem. `SkillDelivery.discover_stack_local` walks every configured
stack and appends its skills, and `scaffold_skills` copies them. They arrived; nothing pointed
at them.

This is [#261](https://github.com/Arasz/ai-badger/issues/261) one stack over — the same failure
(delivered, unregistered, unreachable for its whole life) reached through a different
hand-maintained list. `derive-or-delete-the-list` is explicit about why: a literal that must
mirror what is on disk drifts the moment someone adds to one side, and nothing compares them.

## The fix

`badger_lib.discovery_stacks_for_agent(config, agent)` derives the qualifying stacks: every
stack the project draws from, minus the stacks that *are* the other configured agents. Nothing
is named in a literal, so a stack added to `features/` needs no edit here.

The one exclusion is deliberate and unchanged: an agent's own catalog stays its own. A
`features/copilot/skills/` skill does not land in `.claude/skills/`, and a project that
configures `hermes` as both stack and agent still routes those skills through the Hermes
namespace linker rather than the Claude one.

## What appears in an existing project

A re-scaffold adds discovery links for skills already on disk. Nothing new is downloaded and no
file content changes — only the links. For a project configuring `dotnet`, `mcp` and
`ai-raccoon`, that is thirteen: `dotnet-bdd-testing`, `dotnet-domain-modeling`,
`dotnet-flaky-test-diagnosis`, `dotnet-hosted-service-review`, `dotnet-hosted-service-testing`,
`dotnet-logger-message-design`, `dotnet-mcp-server`, `dotnet-sqlcipher-encryption`,
`dotnet-system-commandline`, `dotnet-tool-publishing`, `observability-contract-review`,
`mcp-tool-surface-testing`, `ai-raccoon-manual-checklist`.

They were always meant to be reachable, and they consume the host's skill-listing budget. A
project that wants fewer has `config.exclude.skills`.

## The prune signal the widening exposed

`adjust_skills` read "we do not know what was delivered" off the skill list being empty — an
empty `--skills` means "unchanged", not "none"
([#129](https://github.com/Arasz/ai-badger/issues/129)). But `discover_stack_local` appends
every configured stack's skills, so once a stack ships any, that list is never empty and the
guard stopped firing. A run whose `manifest.json` could not be read would then have deleted the
links it could not account for.

The scaffolder now says so explicitly: `Scaffolder.prune_discovery` reaches the adjustments as
`context["prune"]`, and a run that cannot vouch for its list prunes nothing and says why.
