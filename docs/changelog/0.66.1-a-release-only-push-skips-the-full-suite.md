# 0.66.1 — A release-only push skips the full suite

## First, a correction

The case for this change was put as "every `git push` runs the whole suite — three to five
minutes". That figure was wrong. Measured on this machine, 2026-08-01:

| | |
|---|---:|
| twelve non-pytest lanes, combined | **14s** |
| pylint | 12s |
| pytest | 49s |
| **whole gate** | **~75s** |

The three-to-five-minute number came from watching pushes that also waited on CI and, in one
case, a different repository's end-to-end suite. Fifteen pushes cost roughly nineteen minutes,
not an hour.

The gate was also **already selective** — `_lanes_for` has routed by changed path since it was
written, and a docs-only push has always skipped pytest and pylint. The premise that it ran
everything unconditionally was simply not true.

## What was actually true

A release commit reaches the full suite through the `*.json|VERSION` route. `VERSION`, the three
version literals, `index.json` and the regenerated changelog index are all that changes — and
every one of them is produced by a generator that already has a lane of its own: `version-sync`,
`index`, `docs`, `release`.

Running 2813 tests to re-prove what those four just proved is the one narrowing worth making.

## What changed

When **every** changed path is a regenerated release artifact — `VERSION`, `index.json`,
`.claude-plugin/*.json`, `docs/changelog/*.md` — the `pytest` and `pylint` lanes are skipped. The
twelve whole-tree guards still run, and they are 14 seconds.

One non-exempt path anywhere in the push restores the full suite. A schema edit is not exempt. A
`.ai-badger/` scaffold stamp is not exempt, because it mirrors sources that must still be tested.

This is deliberately the only narrowing. Everything else still routes to everything, because a
gate that quietly stops verifying is invisible until the day it matters.

## Worth saying

With corrected numbers the saving is 49 seconds on release-only pushes, perhaps a handful a day.
That is a much smaller prize than the one this was approved for. It is safe, it is bounded, and
`lanes-for` now makes the routing assertable against a path list rather than only against
whatever happens to be in recent history — but if it were being proposed fresh against the real
measurement, it would be a harder sell.
