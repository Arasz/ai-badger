# 0.128.1 — derive-facts Reads the VERSION File

**Type:** PATCH
**Date:** 2026-08-16

PATCH because the shipped file keeps its name and its contract: same three facts, same output
shape, same loud non-zero failure. Only the set of places it looks for one of them grew.

## The defect

ai-raccoon moved its version out of the csproj into a plain `VERSION` file at the repo root
(`7cfaefca`, *"publish reads VERSION, not the csproj element"*). `derive-facts.py` still read
`<PackageVersion>`, so on the very tree it ships for it printed:

```
derive-facts: no literal <PackageVersion> in .../src/AiRaccoon/AiRaccoon.csproj
derive-facts: the tree layout moved; fix this script rather than typing the fact by hand.
```

That is the script behaving exactly as designed — refusing to invent a fact. But it blocked every
checklist run, and the pressure at that moment is to type the version by hand, which is the
precise rot `derive-facts` exists to prevent. A guard that cannot be satisfied gets bypassed.

## The fix

The csproj element is still read first — a tree carrying both is stating the local one
deliberately — and the root `VERSION` file is the fallback. A blank or whitespace-only file is
still not a version. The failure message now names both sources.

## Evidence

Watched red before the fix: 4 new tests failing, 33 passing. Green after: 37 passing.

Two existing tests asserted the old `no literal <PackageVersion> in` wording. The message now
names two sources, so those assertions moved with it; they still assert the same property, a loud
non-zero failure with a reason.

Verified against the real tree that produced the defect — `ai-raccoon` at
`1.21.0-integration.1` — which now derives `version=1.20.1`, `mcp-tool-count=27`,
`mcp-prompt-count=2`, exit 0.
