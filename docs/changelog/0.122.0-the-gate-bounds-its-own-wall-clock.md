# 0.122.0 — The Gate Bounds Its Own Wall Clock

**Type:** MINOR
**Date:** 2026-08-15

## What Changed

`.lefthook/pre-push/verify.sh` now enforces one whole-gate deadline, `VERIFY_DEADLINE`
(default 90s, env-overridable). A run that outlives it exits **124**, records a `TIMEOUT` row,
and takes down the lane's entire process group.

The script's contract comment changes with it: `exit 0 = pass, 124 = the whole-gate deadline
killed the lane in flight, any other non-zero = a lane failed`.

## The defect

On 2026-08-15 a pre-push run started around 10:30, reached the pytest lane around 10:32, and was
still sitting at 60% with no output at 10:55. Its process had **PPID 1**: `git push`, lefthook
and `verify.sh` had all exited, and the lane outlived every one of them on a machine already at
load 59-104.

`logs/lefthook.log` has no trace of that run. It holds 225 pre-push rows and **every one is a
survivor** — `_log_summary` was only reached after `run_lanes` returned, so a run that hung or
was killed was invisible by construction.

## One number, not fifteen

The deadline bounds the push, not the lane. Fifteen hand-tuned per-lane thresholds would be a
hand-maintained list nothing ever compares against reality — the failure
[derive-or-delete-the-list](../../.ai-badger/invariants/derive-or-delete-the-list.md) names. The
lane in flight is still reported, but it is *derived*: `run_lanes` writes the current lane name
to `$LOG_DIR/current-lane` before each `run_lane`, and the watchdog reads it.

## The group, never the child

Killing the direct child is what produced the orphan. Reproduced incidentally while capturing
the red runs for this change: killing the three pytest processes left their `sleep 600`
grandchildren behind at PPID 1.

Pre-fix, `ps -o pid,ppid,pgid` showed the invoking shell, the gate, the lane and the
grandchild **all in one process group** — so a group kill without job control would have taken
down the caller, which in a real push is `git push` itself. Hence:

```bash
set -m                       # the background job gets a process group of its own
lane_cmd "$lane" >"$log" 2>&1 &
lane_pid=$!
set +m
```

`_signal_group` refuses a malformed group id and refuses this shell's own group, so the
mechanism cannot signal the push it is guarding.

## A timeout is not a lane failure

Exit **124** is GNU `timeout`'s convention, reserved here for a deadline kill. It is read off a
marker file the watchdog touches before signalling — never inferred from the lane's 143, which a
lane can exit on its own. 124 is non-zero, so lefthook still refuses the push.

## The row is written before the kill

This is the survivorship fix, and the reason the **watchdog** writes it rather than the main
shell: if the shell dies with the group, the row must already be on disk.

```
2026-08-15 11:20:44 | lane       | release | TIMEOUT | 2s | timeout:release
```

A `trap` on INT/TERM covers the other way a run ends with no row — an operator's Ctrl-C — and
lands an `ABORT` row naming the lane in flight. Every invocation now produces exactly one row,
which is what makes the log usable as evidence rather than a list of the runs that happened to
finish.

`_log_summary`'s fifth field is now a verbatim note rather than a hardcoded `failed:` prefix, so
`failed:pytest` and `timeout:pytest` are distinguishable by a reader.

## Proven to fail

Each of the four new cases in `tests/test_verify_gate.py` was run red before the fix existed and
green after, and each was then mutated individually and re-run:

| Case | Red before the fix | Mutation applied after | Result |
|---|---|---|---|
| `test_a_lane_past_the_deadline_is_killed` | `a 1s deadline let the gate run 601s` | (the pre-fix state *is* "no watchdog") | — |
| `test_a_timed_out_run_still_writes_a_summary_row` | row said `PASS`, not `TIMEOUT` | watchdog stops writing the row | red |
| `test_the_deadline_kills_the_whole_process_group` | `the deadline never fired (601s)` | `kill -TERM -$pgid` → `kill -TERM $pgid` | red, **and only this case** |
| `test_an_operator_interrupt_still_writes_a_summary_row` | hung: the trap never cancelled the watchdog | trap stops writing the row | red |

The third mutation is the one that matters: with the group kill reduced to a single-process
kill, the grandchild survived and **only** the process-group case went red — the other two
stayed green, which is what makes it a real check rather than a duplicate of them.

The fourth case found a genuine defect in the first draft of this change: the interrupt trap
killed the lane but left the watchdog armed, holding the run's stdout open for the rest of the
deadline and set to fire later against a process group that no longer existed. The trap now
takes the watchdog down first.

Timing is not load-sensitive: a 1s deadline against a 600s sleep. Red cost 601s per case; green
costs 19s for all three.

## Not Changed

`$LANES`, `_lanes_for`, `--risk` and lane selection are untouched — a separate work package owns
them.

## Unknown, and stated as such

The deadline must fire *below* whatever already SIGKILLs this hook on wall clock, or the row
never gets written. That ceiling could not be established: `lefthook.yml` declares no job
timeout (lefthook 2.1.10 supports the key; it is absent here), no `BASH_DEFAULT_TIMEOUT_MS` or
`BASH_MAX_TIMEOUT_MS` is set in any settings file, `ulimit -t` is unlimited, `TMOUT` is unset,
and no matching launchd job exists. The prior investigation reached the same conclusion.

**90s is therefore a guess, not a measurement**, and it is recorded as one in the script. The
15-second figure that appears in 0.91.0's entry is a different, measured mechanism — a ReDoS
guard inside the `.mjs` validators — and is not this ceiling.
