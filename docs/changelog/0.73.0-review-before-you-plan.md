# 0.73.0 — review before you plan, and check every join

Phase 1 went straight from "read the referenced docs" to "delegate decomposition". Nothing said to
establish what was true first, so a plan could be — and was — written from what the task *sounded*
like rather than from what the repository actually contained.

Twice on 2026-08-01 that cost real work. A rule proposed for the catalog turned out to be already
implemented in `features/common/skills/task/extensions/claude/extension.md`; a package scoped
against three assumed gaps shrank to one when the code was read. Both were caught by reviewing
before planning. Neither would have been caught by planning harder.

## What changed in the lifecycle

**Phase 1 gains a review step before the planning step.** Write down what has to be checked to
answer the task — every point in the request, and which need research rather than a guess — then
run that review and gather the evidence. *A plan written before the review is a guess with a table
around it.*

**Plans are split for parallelism and carry proof obligations.** Sections that can be worked
independently are named as such, along with which ones share a file and therefore serialise.
**Every point carries acceptance criteria and a quality gate** — what must be true, and the run
that proves it. A point without them is a wish. A point needing a specification or design gets
one, and the skill says to look for an installed skill that formalises that shape before writing a
bespoke document.

**Phase 3 gains "review every join, not just every part".** Each time separate work is combined —
findings into a plan, sections into a change, branches into a PR — the combination gets checked.
Parts that each passed alone routinely fail together: two branches pick the same version, one
renames what another calls, a guard passes on each half and fails on the whole. All three happened
this week.

## The part that pulls the other way

The same section says to **stop checking**. Execute the plan rather than re-reading it for
reassurance; a third pass over your own reasoning finds much less than the first and costs the
same. Re-verify after an integration when there is a reason to — something changed underneath, a
claim is load bearing, a check has never been seen to fail.

**Facts are the exception, and it is not a small one.** Anything from documentation, an earlier
run, or someone else's research is re-checked against its source every time. That is what goes
stale while your own reasoning stays put. This session shipped a cost figure four times the
measured value into two published places, and it survived because nobody re-derived it.

## Delegation

Three additions to the policy, none of them new ideas — all of them things that were being done
without being written down.

**Split work so it *can* run in parallel.** A large item worked through in sequence by one agent
is usually several items that could have run at once. The split happens while planning.

**Two levels of dispatch, no more.** You dispatch; those agents may dispatch once; nothing deeper.
The cap is about hardware, not design: every live agent costs memory and CPU share, and a tree
that widens without bound starves the work already running.

**Reach for whatever tool makes the work smaller** — a code graph, an MCP server, an installed
skill, a script the repo already has. The expensive path is often the one nobody checked for a
shortcut.

## Not added, deliberately

**"Prefer sonnet for implementation" already exists.** `features/common/skills/task/extensions/claude/extension.md` binds it:
*"Sonnet — implementation, by default … pass `model: "sonnet"` explicitly rather than relying on
the default."* Adding it to the base skill would have created two places to disagree, and the base
skill is deliberately model-neutral — the concrete lanes live in the agent extension.

That was found by reading the file rather than assuming the gap, which is the discipline this
release also writes into Phase 1.
