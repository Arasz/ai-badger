# 0.68.0 — A spec is elicited, not drafted

`create-task-spec` turns a rough idea into an exact specification by asking the person what they
know, rather than proposing a plausible one for them to approve.

## Why the polarity matters

A skill that drafts a spec for review produces a document that reads as agreed but encodes the
model's guesses. Two dispositions combine: models fill blanks rather than leave them open, and
people accept a plausible list rather than generate a competing one. Shown six candidate rules, a
person edits those six — they do not produce a seventh, and the knowledge that was supposed to be
extracted stays in their head. The artifact still looks complete, which is what makes the failure
silent.

So the contract is inverted. Never assume; a "probably" is a question to ask, not a decision to
make. Propose options to choose between, never content to accept. "I don't know" is legal and
becomes a recorded deferral with a fallback chosen at the time — silent deferral is forbidden.

## Why Gherkin, with no BDD toolchain in sight

Nothing here runs Cucumber, and no editor plugin is assumed. The format earns its place on three
properties that hold with no tool attached:

- **Its grammar is a question schema.** The interview script is derived from the artifact rather
  than chosen by whoever wrote the checklist. An empty required slot is a question.
- **Incompleteness is structural.** A `Rule` with no example and an example with no steps are
  facts about the file. `spec_holes.py` counts them, so "are we done?" has an answer that does not
  depend on the agent's opinion.
- **It is unambiguous for the reader that matters** — the implementation agent downstream.

`.specb` was considered and dropped: it is not a second format, only an alternate extension one
Java tool recognises, holding identical Gherkin. Emitting both would have emitted the file twice.

## What ships

- `create-task-spec` at default scope — a seven-stage loop from restatement through rules,
  scenarios and steps to an owner gate, emitting a `.feature` contract plus a `spec.json`
  manifest. Invoked with no idea, it explains the process and asks whether you are ready first.
- `scripts/spec_holes.py` — the completeness scanner. Stdlib only: Gherkin is line-oriented, so
  this needs a scanner rather than a parser, and the dependency floor stays where it is. Exits
  non-zero while any hole is still open.
- `scripts/render_spec.py` — renders a spec as a self-contained page with its gaps shown rather
  than merely counted. Shares the scanner, so the page and the gate cannot disagree.
- `task` Phase 1 now accepts a `spec.json` path in place of freeform text, so planning starts from
  an agreed contract and Phase 3 gains an exact pass condition.

No wrapper skill. This repository already chains skills without one — `differential-feature-refactor`
invokes `owner-gate-review` and reads its result back — so a third entry point would have bought
one memorable name at the cost of a permanent "which do I invoke?" ambiguity.
