# 0.182.1 — the pi MCP instruction catches up with pi's built-in MCP

**Patch** (instruction content) · 2026-09-30

`features/pi/instructions/pi.instructions.md` still asserted that pi core has no MCP support and
that the settings `mcp` key is read solely by the `pi-mcp-tools` fork. That was true of pi 0.84.3;
pi 0.99.1 ships MCP as a built-in extension (`builtin:mcp`), and every consumer project refreshed
against this framework got the stale claim written into its agent files — overwriting a consumer
that had already measured pi 0.99.1 and corrected the bullet by hand.

## What changed

- The MCP bullet states the native contract: config in `~/.pi/agent/mcp.json` (global) and
  `.pi/mcp.json` (project, trust-gated, overrides by name), not the settings `mcp` key; tools named
  `mcp__<server>__<tool>`; the `codemode` / `codemode-deferred` / `deferred` / `direct` / `hidden`
  exposure model with per-tool `toolExposure`; `/mcp` and `pi mcp add|remove|list|login|logout`;
  OAuth for HTTP servers without an `Authorization` header; the resource tools; `~/.pi/agent/mcp.log`;
  and `pi.registerMcpServer(name, config)` for extensions.
- The provenance line now reads "Measured against pi 0.99.1 for the MCP bullet and pi 0.84.3
  elsewhere" — only the bullet's claims were re-verified against pi's own `docs/mcp.md`.

## Behaviour changes worth knowing

- **No re-scaffold is required**, but the next `den-refresh` writes the corrected bullet into agent
  files, replacing the "pi core has no MCP support" claim wherever a project still carries it.
- `features/pi/adjustments/adjust_mcp.py` and its capability-marker gating still name the
  `pi-mcp-tools` fork; that machinery is untouched here and is a separate retirement.
