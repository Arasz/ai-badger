# 0.35.6 — the framework cache reports its own version skew

`~/.ai-badger/framework` is the **last** entry in the framework-root resolution order
([ADR-0009](../adr/0009-one-framework-root-resolution.md)). Wave 7 demoted it to that position
but did not discharge what makes it hazardous: it is **never updated in place**, so when it is
what answers, a caller runs a stale engine against a current catalog and nothing says so. On the
maintainer's machine it sits at **0.13.0** against a 0.35.x catalog — twenty-two releases behind,
silently.

That is precisely the engine/catalog skew ADR-0007 exists to eliminate, reintroduced at the one
point in the order nobody looks at.

## What changed

When the cache is the resolved root **and** its `VERSION` disagrees with the `frameworkVersion`
recorded in the nearest manifest above the script, it now names both versions on stderr:

```
ai-badger: /Users/you/.ai-badger/framework is version 0.13.0, but this project was
scaffolded by 0.35.6. The cache is never updated in place — remove it, or pass
--root <framework checkout>.
```

Silent when the versions match, when the cache has no `VERSION`, when the caller records no
version, and whenever the cache was not what answered. A correct cache prints nothing.

## A warning, not a refusal

The check sits inside `_bootstrap_lib()`, which ADR-0009 decision 5 requires to be **one text
shared verbatim by CLIs and by hooks that load on session start**. One text cannot refuse in one
context and stay quiet in the other, and the standing hook contract is that *a hook degrades to
silence; it never breaks a session*.

The order already draws this line: refusal belongs to **operator declarations** — `--root` and
`$AI_BADGER` were typed by somebody, so a wrong one must be reported rather than fallen through.
The cache is **discovery**, and discovery degrades. Refusing would re-break the deployment shapes
Wave 7 existed to fix on any machine where the cache is the only answer, trading a silently stale
engine for no engine at all.

stderr is the correct channel for both callers: it never contaminates a hook's stdout JSON
protocol, and it leaves the exit code untouched.

## Mirrored into all ten shims, deliberately

A stale cache imports **its own** copy of `badger_lib` — so a fix confined to `badger_lib` would
be inert for exactly the 0.13.0 case this addresses. The statement therefore lives in both
places, which is the duplication ADR-0009 decision 5 already accepts for the same reason. It
cannot drift: `test_every_bootstrap_shim_is_the_same_predicate` pins all ten shim copies
byte-identical, and a new `test_the_shim_and_badger_lib_state_one_cache_skew_warning` asserts the
warning text matches between the shim and `badger_lib`.

**Resolution order is unchanged**, including the security property that the recorded root is read
above the *script* and never above the working directory.

## Also

The shim's manifest walk was factored into one `manifests()` generator, so root and version come
from a single traversal, and it now skips non-dict JSON instead of calling `.get()` on whatever
`json.loads` returned.

## Not covered

**Shape D (`~/.hermes/plugins/`) stays unjudged.** `adjust_hooks._record_framework_root` writes
only `frameworkRoot` and no `frameworkVersion`, so there is nothing there to compare against and
those hooks stay silent. Adding the key is small but widens the change to the installer and its
manifest shape; it is recorded here rather than done.

One claim in the plan turned out to be stale: the real-home cache was **not** masking any test
failure. Running the full suite against a `$HOME` mirrored without `.ai-badger` gives a
byte-identical result. Wave 7 already closed that hole — `test_deployment_shapes.py` pins `HOME`
to an empty tree and `test_badger_lib.py` monkeypatches `FRAMEWORK_CACHE` in every resolution
test.
