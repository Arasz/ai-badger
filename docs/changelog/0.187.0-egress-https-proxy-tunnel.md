# 0.187.0 — opted-in egress goes through the corporate `HTTPS_PROXY`

**Minor** · 2026-10-03

T1b of the data-access plan; ADR-0035 D8. See [data access](../reference/data-access.md).

## What changed

- A non-loopback `https` request from the OpenRouter client (memory pipeline, Jev advisory) now
  tunnels through the proxy in `https_proxy` / `HTTPS_PROXY` via `CONNECT`, minus
  `no_proxy` / `NO_PROXY`. Before, it ignored the proxy, failing on proxy-only networks and
  bypassing DLP where direct egress existed.
- The deadline covers the `CONNECT`; only the proxy's name is resolved; the target's TLS name is
  verified; the API key and payload stay inside the tunnel and the tunnelled request carries the
  target's `Host`.
- The proxy value is `http://host:port` or a bare `host:port` (read as http, like curl).
  Credentials, another scheme, a path or no port fail as `transport` with nothing dialled.
  Loopback is never proxied.
- Proxy problems are diagnosable without leaking the value: when opted in, one
  `memory_context.proxy-refused: malformed|unsupported|connect-<status>|tls-verify` line per
  process in `~/.ai-badger/hook-errors.log`; the Jev advisory reports `proxy-malformed` /
  `proxy-unsupported` without retrying and lists runtime faults under `proxy_faults`.

## Upgrade notes

- No configuration change: the standard proxy variables are read. `HTTP_PROXY`, `ALL_PROXY`, system
  or PAC proxies and proxy authentication are not used.
