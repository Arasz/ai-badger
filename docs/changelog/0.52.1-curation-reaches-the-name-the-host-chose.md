# 0.52.1 — curation reaches the name the host chose

The mcp catalog is keyed on a server's own name (`code-review-graph`). `claude mcp list` does not
print that name for a plugin-provided server; it prints where it routes it from. On this machine,
run inside the ai-badger checkout and then outside it:

```
$ claude mcp list          # in the repo, whose .mcp.json declares the server
code-review-graph: python3 -m code_review_graph serve - ✔ Connected
hermes: /Users/…/hermes mcp serve - ✔ Connected

$ claude mcp list          # anywhere else, where only the plugin provides it
plugin:ai-badger:code-review-graph: python3 -m code_review_graph serve - ✔ Connected
plugin:ai-badger:hermes: /Users/…/hermes mcp serve - ✔ Connected
```

Same server, two names — and since `.mcp.json` stopped shipping in 0.51.0, the decorated one is
what **every plugin installer** sees. So an index built from the Claude listing got no curated
entries for exactly the server ai-badger ships: the overlay's flagship case, missed.
[Issue #203](https://github.com/Arasz/ai-badger/issues/203), documented as the known limitation of
[0.52.0](0.52.0-discovery-comes-back-from-the-host-that-answers.md).

## The listing name widens; it is never rewritten

`tool_descriptions.catalog_keys` turns one host listing name into the catalog keys it may match,
most specific first:

| listed as | keys tried, in order |
|---|---|
| `code-review-graph` | `code-review-graph` |
| `plugin:ai-badger:code-review-graph` | `plugin:ai-badger:code-review-graph`, `code-review-graph` |
| `claude.ai Google Drive` | `claude.ai Google Drive`, `Google Drive`, `google-drive` |

`catalog_tools` returns the first key the catalog holds, and `describe_tool` and `update`'s
re-description both go through it. The recorded source `name` stays whatever the host called it, so
the next `update` against that host still matches its own listing — curation reaches the source
without renaming it.

**The prefix was not collapsed at parse time**, which the issue floated as the likely fix, because
the same-name question answers against it. Two providers *can* ship one server name: the ai-badger
plugin declares `code-review-graph`, this repo's `.mcp.json` declares `code-review-graph`, and both
are live on the same install — the listings above are the host resolving that collision by scope,
and the decoration is the only thing that tells the two apart. Plugin and server names are
independent (`plugin:microsoft-docs:microsoft-learn`,
`plugin:dotnet-claude-kit:cwm-roslyn-navigator`) and no registry coordinates them, so two plugins
can collide the same way. A decorated key therefore stays addressable: set
`"server": "plugin:<plugin>:<server>"` in a `tools.json` and its exact match outranks the bare
entry. Matching widens the listing name only — a bare `foo` never borrows `plugin:a:foo`'s
curation. No schema change: `mcp-server-tools.schema.json` never constrained `server`'s shape.

## Measured on this machine's 16 real servers

`mcp-index init` over the names from both captures above, with the code-review-graph tool list the
live server exposes:

| listing | source name recorded | tools with `origin: catalog` |
|---|---|---|
| in-repo (bare) | `code-review-graph` | 5/6 before, 5/6 after |
| plugin-provided | `plugin:ai-badger:code-review-graph` | **0/6 before, 5/6 after** |

The sixth tool is `build_or_update_graph_tool`, which the catalog does not curate — it stays
`heuristic`, as it should. The bare case is unchanged, which is the point: this adds a fallback, it
does not move the first key.
