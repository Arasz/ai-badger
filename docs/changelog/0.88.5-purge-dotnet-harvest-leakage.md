# 0.88.5 — the dotnet catalog stops shipping one private project

`features/dotnet/` is not architecture this repository uses. It is guidance ai-badger ships to
every consumer .NET project: `index.json` registers all eleven dotnet skills, and
`features/dotnet/stack.json` detects on `*.csproj` / `*.sln` / `Directory.Build.props` with no
opt-in. The 0.86.0 learned-skills harvest filled it with a copy of one private application — not a
generalisation of it — so a stranger's namespaces, business rules and machine paths reached
everyone who has a `.csproj`. PR #326 removed that harvest's live vault identifiers. This removes
the rest.

## The always-on instruction file

`instructions/csharp.instructions.md` carries `applyTo: '**/*.cs'`, so its every line is loaded in
every consumer .NET repo — the largest blast radius in the stack. Three of those lines were one
application's contract, not C# convention:

- a rule routing state transitions through "the state machine" and keeping a "needs human
  attention" signal as a flag — the source app's workflow engine;
- an HTTP contract (`409` with the allowed transitions, `202` plus an operation id) imposed on
  every consumer's API;
- a multi-tenancy mandate that every persisted entity carry a tenant/owner key, which also
  duplicated `features/cosmos/invariants/partition-by-userid.md` — correctly gated behind the
  `cosmos` stack — into the ungated dotnet layer.

All three are gone. The surviving problem-details line now cites
[RFC 9457](https://www.rfc-editor.org/rfc/rfc9457), which obsoleted RFC 7807 in July 2023 and is
what [current ASP.NET Core guidance links](https://learn.microsoft.com/aspnet/core/fundamentals/error-handling-api?view=aspnetcore-10.0#problem-details).
The guard-clause line no longer says "where applicable", which softened the framework's own
`guard-clauses` invariant into a suggestion.

## Someone else's source tree

`dotnet-domain-modeling/references/cosmos-persistence-implementation.md` opened with "When adding a
new Cosmos-backed entity to **this project**, follow this **exact** sequence" and told the reader
to create files under `src/JobSearchAiAssistant.Domain/`. Namespaces are now `MyApp`, "this
project" is gone, and the recruiting-domain vocabulary is neutral. `financial-domain-modeling.md`
keeps what was genuinely general — a versioned rate table keyed by effective period, no fallback
when the table is missing, provenance travelling with the data — and drops the Polish payroll
statute it was written against. Four references whose only content was the source app's business
logic are deleted rather than paraphrased into claims nobody can support.

## A find/replace that produced code which cannot compile

The harvest's redaction pass replaced the project name inside identifiers, shipping
`internal static partial class the config dispatcher` and
`public interface the encryption command interface` as C# samples. Nineteen such artifacts across
eight files are repaired: identifiers renamed from their members, doubled articles fixed, a private
machine path removed, and every `ai-raccon` typo either corrected or replaced by a placeholder
where it was provenance the reader cannot have. Three skill cross-references named skills that do
not exist (`ai-badger-project-ops`, `grounded-citations`, `git-worktree-isolation`) and no rule
caught them.

## Three claims that were wrong

- **FluentAssertions 6 → 8** was recorded as an exemplary upgrade with no licence note. v8 moved
  from Apache-2.0 to the [Xceed Community License](https://www.nuget.org/packages/FluentAssertions/8.0.0/License),
  free only for non-commercial use; commercial use needs a paid per-developer licence. v7 is the
  last Apache-2.0 release. Version-bump automation set to "latest stable" walks a repository into
  the paid licence silently. FluentValidation is a different package by a different author and is
  still Apache-2.0 — the note says so, because the two get conflated.
- **"With NRT + DI, ctor null-checks are dead code — delete them"** appeared in two skills and
  contradicted `invariants/guard-clauses.md` without citing it. The premise is false: nullable
  reference types are compile-time only and
  [the runtime adds no null checks](https://learn.microsoft.com/dotnet/csharp/language-reference/builtin-types/nullable-reference-types#nullable-references-and-static-analysis),
  so null still arrives by deserialization, reflection, or a nullable-context boundary. Both are
  scoped to internal DI-only types; public API boundaries keep the guard.
- **`BackgroundServiceExceptionBehavior.StopHost` is the default** — still true, but as of .NET 11
  Preview 3 `RunAsync`/`StopAsync`/`WaitForShutdownAsync`
  [fault instead of completing](https://learn.microsoft.com/dotnet/core/compatibility/extensions/11/ihost-runasync-stopasync-throw-backgroundservice-failure),
  so the process exits non-zero.

## The gate

`tests/test_catalog_has_no_harvest_artifacts.py` holds both contracts: no harvest string survives
anywhere under `features/`, and no `references/` file is unreachable from its own `SKILL.md`. Its
could-fail tests seed a scratch tree with the literal text 0.86.0 shipped — the mangled class
declaration, the machine path, the `JobSearchAiAssistant` namespace, the "to this project"
sentence — so the check is known to catch what it was written for rather than merely asserted to.
A companion test proves the scanner still allows "this project" where it is the framework
addressing the consumer's own repository.

Seven `references/` files were on disk and named by no `SKILL.md`. Three were deleted (one of them
opened by declaring itself superseded and telling the reader not to follow it), two were the
harvest's business logic, and two were wired into their skill instead.
