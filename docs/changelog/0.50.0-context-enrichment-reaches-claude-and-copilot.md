# 0.50.0 — context-enrichment reaches Claude and Copilot, unconditionally

Closes issue #147: the MCP tool recommender (`context-enrichment`) reached only Hermes.
`hooks-manifest.json`'s entry named a `hermes` agent and nothing else, so the BM25 matcher
rebuilt in #144 ranked a corpus nothing on Claude Code or Copilot ever queried.

## The decision that was open, now made

The issue closed on one question: whether a recommender firing on every turn is worth the
context cost on Claude, given `UserPromptSubmit` already carries `prompt-markers`. **Decided:
wire it, for both agents, unconditionally — no config flag.**

- A gated turn injects zero tokens. The hint is emitted only when a candidate clears the
  coverage gate (docs/retrieval.md §4), so the cost is per-hit, not per-turn.
- The measured false-fire rate is 0.267 (docs/retrieval.md §5), bounded at ~300 chars per
  spurious hint — trivial against the full MCP tool listing Claude already loads every turn
  regardless.
- A config knob defaulting to off would reproduce the inert-by-default failure this issue exists
  to fix, for the third time in this repository's history.

## What shipped

- **`features/common/skills/mcp-index/scripts/context_enrichment_hook.py`** — the Claude/Copilot
  `UserPromptSubmit` adapter. Same telemetry component (`ai_badger_hooks/mcp_retrieval`) and event
  names (`hit`/`gate`/`no_terms`/`absent`/`legacy`) as the Hermes path, so an audit record reads
  identically regardless of which agent produced it.
- **`features/common/retrieval/context_enrichment.py`** — the logic the new hook calls: index
  loading, near-miss scoring, hint formatting. Factored out so the new hook does not duplicate
  what `ai_badger_hooks.py` already does inline for Hermes.
- **`features/claude/adjustments/adjust_retrieval.py`** and its Copilot twin
  (`features/copilot/adjustments/adjust_retrieval.py`) — deliver `tokenizer.py`, `bm25.py`,
  `mcp_matcher.py` and `context_enrichment.py` beside the scaffolded hook, in
  `.ai-badger/skills/mcp-index/scripts/`. This is the Claude/Copilot equivalent of the copy
  `features/hermes/adjustments/adjust_hooks.py` already does for Hermes — into a different
  destination, since Claude's and Copilot's own hook wiring never reads `.ai-badger/hooks/`.
- **`hooks-manifest.json`**: `context-enrichment` now names `claude` (`hooks-json`,
  `UserPromptSubmit`, script `context_enrichment_hook.py`) and `copilot`
  (`userPromptSubmitted`), alongside the existing `hermes` entry. The command itself is
  registered in `features/common/hooks/hooks.json` so `hook_wiring.py`'s `select_hooks` resolves
  it through the primary (`hooks.json`-lookup) path, the same one `session-start-tracking` and
  `commit-reminder` already take — not the script-less generate-default fallback #158 just
  hardened.
- **`commit-reminder`** gained a `hermes` entry in the manifest: `ai_badger_hooks.py`'s
  `post_tool_observer` already implements the equivalent behavior (`_maybe_remind_commit`,
  surfaced through `pre_llm_inject_context`'s pending-reminder mechanism) — the manifest simply
  never recorded it. Pure documentation; no behavior change.

## The structural test the issue asked for

> A test asserting every entry in `hooks-manifest.json` names every agent capable of that event
> — or explicitly records why it does not — would have caught all three occurrences.

`tooling/validate.py` gained `HOOK_CAPABLE_AGENTS`, `HOOKS_MANIFEST_AGENT_EXEMPTIONS`, and
`hooks_manifest_agent_gaps()`, wired into `validate.py --all`.
`tests/test_hooks_manifest_agent_coverage.py` asserts the real manifest has no gap, that an
unexplained gap fails, and — per #145's review finding that an untested reason string is not a
reason — that every exemption's text says something, not merely that a key exists.

The exemptions this forced to become explicit:

- **`session-start-tracking` on hermes/copilot** — Claude-only by design: transcript path,
  unfinished-task surfacing and the usage-limit poller are Claude Code concepts with no
  analogue elsewhere.
- **`prompt-markers` on hermes** — an acknowledged gap, not a design limit: marker detection has
  no Hermes-side implementation yet. Recorded honestly as a known TODO rather than dressed up as
  permanent, unlike the exemption above.
- **Junie, blanket** — `JUNIE_HOOK_EXEMPTION` records that Junie's own configuration ignores
  project-local hooks entirely, a platform limit rather than a per-hook one, which is why it
  never appears in `HOOK_CAPABLE_AGENTS` at all.

## A second, adjacent defect this exposed

Verifying the Copilot wiring by actually running the generated `.github/hooks/ai-badger-hooks.json`
command (not just asserting on it) surfaced a pre-existing bug in
`features/copilot/adjustments/adjust_hooks.py`, unrelated to this issue but blocking its own
verification requirement: `cmd.strip('"')` was applied to the *whole* rewritten command
(`python3 "<path>"`), not a matched pair — since the string starts with `p`, not `"`, this
stripped only the trailing quote, leaving every primary-path Copilot command (this repository's
own committed `.github/hooks/ai-badger-hooks.json` included, unchanged since before this issue)
with an unterminated quote that would fail at shell execution. No existing test caught it because
every assertion checked the trailing filename (`.rsplit("/", 1)[-1]`), which a stray leading
quote doesn't affect.

Fixed by deleting the stripping line entirely — the quotes around the path are correct shell
quoting, not something to remove — and pinned with a new test asserting the exact, balanced
command string, not just its trailing filename
(`tests/test_adjust_hooks_copilot.py::test_a_quoted_source_command_keeps_balanced_quotes_not_a_dangling_one`).
Three pre-existing tests asserted only the mangled filename shape and needed their basename
extraction updated to `.rstrip('"').rsplit("/", 1)[-1]` (the convention `hook_wiring.py`'s own
`select_hooks` already uses) to keep passing against the corrected, balanced output:
`test_copilot_session_start_wires_drift_notice_not_session_tracking`,
`test_two_source_hooks_json_entries_on_one_event_both_survive` (both in
`tests/test_adjust_hooks_copilot.py`), and
`test_copilot_wires_commit_reminder_with_matcher` (`tests/test_commit_reminder_wiring.py`).

## Claims in issue #147 that #155/#158 had already changed

The issue predates two PRs that landed since it was filed, and reasoning from the issue text
alone would have been wrong on both:

- **"This repo's own Claude scaffold contains ... No `mcp_matcher.py`."** True when written, but
  by the time this landed, this repository's own `.ai-badger/hooks/` *did* contain
  `bm25.py`/`mcp_matcher.py`/`tokenizer.py` — a side effect of #155's re-scaffold, not evidence
  the Claude path was fixed. Scaffolding a fresh Claude-only project (not reasoning from this
  repository's tree, which configures both Claude and Hermes) confirmed the modules were absent
  everywhere a Claude-only project would look, and remain a Hermes-only deliverable
  (`features/hermes/adjustments/adjust_hooks.py`, gated on `"hermes" in config.agents`, writing
  to `.ai-badger/hooks/` — a directory Claude's own hook wiring never reads).
- **Wiring `context-enrichment` naively would have deleted `prompt-markers` on Copilot.** #150
  fixed the Copilot adjuster's "second entry on one event overwrites the first" bug before this
  landed; `tests/test_adjust_hooks_copilot.py` (from #150) already had a passing regression test
  naming this exact collision by name. Verified rather than assumed: the suite passes with both
  `context-enrichment` and `prompt-markers` wired onto `userPromptSubmitted`.
- **The Claude-side wiring risk `hook_wiring.py`'s `select_hooks`/`wire()` fallback posed**
  (adopting a neighbour's command, or guessing via an ambiguous glob) was fixed by #158 before
  this landed. This entry's `claude` block names its own script
  (`context_enrichment_hook.py`) and resolves through the primary `hooks.json`-lookup path, so
  neither of #158's failure modes applies here.

## Verified by running

- Scaffolded a throwaway Claude-only project with the real `scaffold.py`: before this change,
  `.claude/settings.json` had no `UserPromptSubmit` entry beyond `prompt-markers`, and
  `.ai-badger/skills/mcp-index/scripts/` held only `mcp_index.py` and `legacy_yaml_subset.py` —
  confirming the issue's core claim was still accurate. After, the same scaffold wires
  `context_enrichment_hook.py` and delivers all four retrieval modules beside it.
- Invoked the hook directly with a query that clears the coverage gate and confirmed the
  recommendation in `additionalContext`, then re-ran with `AI_BADGER_DEBUG=1` and confirmed an
  `ai_badger_hooks/mcp_retrieval` record with event `hit` in `~/.ai-badger/debug/audit.jsonl` —
  the record this issue said had never existed on Claude Code.
- Repeated for the Copilot wiring path (`adjust_hooks.py` + `adjust_retrieval.py`), invoking the
  same hook script the way Copilot's `.github/hooks/ai-badger-hooks.json` wiring would.

## Behaviour changes worth knowing

`context-enrichment` now fires on every `UserPromptSubmit`/`userPromptSubmitted` turn for a
project with Claude or Copilot configured and the `mcp-index` skill scaffolded, the same as it
already did for Hermes. There is no opt-out flag by design (see "The decision" above); a project
that wants it off can decline the `mcp-index` skill via `config.exclude`.
