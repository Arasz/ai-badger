# 0.163.1 — pi skills discovery skips the learned/ subtree

**Patch** (behavior fix, no shape change) · 2026-09-06

## What changed

The pi adapter's ungated `resources_discover` contribution pointed at the
`.ai-badger/skills` tree root. Pi scans contributed paths recursively and pools
skills by frontmatter `name:`, while `learned/` is ai-badger's separate
per-session namespace that reuses canonical skill names — so every duplicated
name warned a collision and the stale copy was skipped (35 in ai-raccoon:
canonical-vs-learned and categorized-vs-`uncategorized` pairs).

The handler now contributes the tree's immediate child entries except `learned/`
instead of the root. Gateway containers (e.g. `dotnet-workload/`) stay
contributed so pi still discovers their `references/` members; fail-open falls
back to the root when the directory cannot be listed. Absent-skills-dir behavior
is unchanged (`{ skillPaths: [] }`).

## Wiring

- `features/pi/adjustments/adapter/index.ts` — enumerate children, skip `learned/`.
- `features/pi/tests/adapter-skills.test.ts` — new: canonical contributed,
  `learned/` never contributed, absent dir stays empty (TDD, RED recorded before
  the fix; `pi-ts` lane green: 162 pass, `tsc` clean).
- Projects that already deleted their stale `learned/` duplicates see no change
  beyond one fewer warning; projects that still carry them stop warning without
  any file change — the canonical entry wins by construction now.

## Residual

One structural pair remains by design: top-level `dotnet-mcp-server` vs the
`dotnet-workload/references/` gateway member (byte-identical `SKILL.md`, the
member is manifest-wired). Collapsing that pair is catalog curation, not
discovery — left for a catalog PR.
