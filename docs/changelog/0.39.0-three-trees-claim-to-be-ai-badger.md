# 0.39.0 — three trees claim to be ai-badger, and only one is ours to delete

**Issue:** [#109](https://github.com/Arasz/ai-badger/issues/109)

A consumer machine can carry three trees that each claim to be ai-badger, each with its own copy
of every hook script:

| Tree | Observed |
|---|---|
| `~/.ai-badger/framework/` | 0.13.0 — 23 releases behind |
| `~/.claude/plugins/cache/ai-badger/ai-badger/` | 23 versions, 0.1.0 … 0.36.2, 76 MB |
| `<repo>/.ai-badger/` | 0.36.1 |

`drift_notice_hook` fires once per tree, each comparing the project's scaffold against *its own*
`VERSION`, so a session opened two contradictory notices at two different versions. That reads as
a versioning bug in the framework. The actual message is **"you have two installs"** — which
nothing said, and nothing offered to fix.

0.35.6 made the cache *report* its own skew and deliberately stopped there. This discharges it.

## What changed

**`engine/framework_copies.py`** enumerates every tree that claims to be ai-badger, records who
owns each, and prunes the one ai-badger created. Stdlib only and deliberately free of
`badger_lib`, which imports `jsonschema` unguarded — a SessionStart hook cannot depend on that.
The root predicate is restated there rather than imported, and pinned to
`badger_lib.is_framework_root` by `test_the_copy_predicate_agrees_with_badger_lib`.

**The drift notice names the competing copies.** Whenever it fires it now appends the path,
version and owner of every tree it can see, and it fires on its own when an idle
`~/.ai-badger/framework` disagrees with the tree that is running — the 0.13.0 case, which
produced no drift of its own:

```
[ai-badger] 3 trees on this machine claim to be ai-badger, so this notice can appear once per
tree. The versions below differ because the copies do, not because the framework does:
  - 0.39.0  /Users/you/dev/ai-badger  — a framework checkout; this session is running from it
  - 0.13.0  /Users/you/.ai-badger/framework  — ai-badger's own cache, which nothing updates in
    place; ai-badger created it and can remove it: den-refresh --prune-cache
  - 0.36.2  /Users/you/.claude/plugins/cache/ai-badger/ai-badger/0.36.2  — Claude Code's plugin
    cache, which ai-badger only ever reads
```

Claude Code keeping several versions in its own cache is not nagged about; that is its business.
The copy scan is wrapped and degrades to silence — a hook never breaks a session — and a root
older than this release simply ships no scanner, which is not an error.

**`den-refresh --prune-cache`.** The refresh reports a `frameworkCopies` block unconditionally
(`competing`: path, version, owner, prunable; `cache`: what happened to `~/.ai-badger/framework`)
and deletes only under the explicit flag. Deleting from a home directory during an ordinary
refresh is surprising and hard to reverse, so the default detects and reports the path, the
version, and the command.

**`welcome-ai-badger` reports the same roster and deletes nothing.** Onboarding a repository is
not the moment to remove something from `$HOME`, and one deletion surface is easier to reason
about than two.

## What the prune refuses

`~/.ai-badger/framework` is ours — `badger_lib._clone_pinned` writes it — so 0.19.0's invariant
permits removing it. Being permitted is not being careless; the prune refuses anything not
demonstrably that cache:

- a path that does not **resolve to exactly** `<home>/.ai-badger/framework`
- a directory that is not a framework root (no `schemas/` + `features/` + `engine/badger_lib.py`)
- the path itself being a **symlink** — the link is never followed out
- a tree holding a symlink whose target **leaves** it (F-05's rule: refusal beats resolution)
- the root **the run itself is using**

A failed removal is reported, never raised.

## Not fixed, deliberately

**The Claude Code plugin cache is not trimmed** — the issue's suggestion 2. ai-badger only ever
*reads* `~/.claude/plugins/cache/`; no write, `mkdir` or `rmtree` anywhere in `engine/`,
`tooling/`, `gates/` or `features/` touches it. Claude Code creates and populates it, so deleting
76 MB of another tool's state would violate the 0.19.0 invariant that no command destroys state
it did not create. It is named in the notice, with its owner, and left alone.

## Tests

1467 → 1503 passing. New: `tests/test_framework_copies.py` (26 tests: discovery, ownership, the
notice, and every prune refusal). `tests/test_drift_version_notice.py`,
`tests/test_den_refresh.py` and `tests/test_scaffold.py` gained cases for the notice, the flag
and the report. Two tests in `tests/test_engine_tooling_layout.py` were widened to the engine's
third module. No test in the suite is allowed near a real `$HOME`: every fixture builds its own.
