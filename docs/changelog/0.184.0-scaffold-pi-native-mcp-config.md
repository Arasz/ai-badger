# 0.184.0 — the scaffold writes pi's native `.pi/mcp.json`, union-merged; `.mcp.json` is Claude's and Copilot's again

**Minor** (scaffold-affecting) · 2026-09-30

A pi-configured project now gets pi's native project MCP config, `.pi/mcp.json`, written by
the scaffold. The destination is pi's own: pi 0.99.1 reads `~/.pi/agent/mcp.json` globally
and `.pi/mcp.json` per project (project entries override global by name, tools are
`mcp__<server>__<tool>`). The write is a union, not a re-render of the declaration set — an
entry already in the file survives re-scaffold entry-identical with its
`exposure`/`toolExposure` tuning, new declarations are appended in the template shape, and a
server the scaffold does not know is never dropped. That is the sibling-reported motivation
in one number: their tuned consumer had cut **55 of 106** declarations from every prompt by
moving two servers to `deferred`; a flattening scaffold would have restored all 55.

The same change retires the fork-era pi reader of `.mcp.json`: `pi` leaves
`MCP_JSON.readers` and the `EXPANDS_HOME_ONLY` carve-out is deleted. With Claude and pi
configured, `.mcp.json` goes back to Claude's `${CLAUDE_PROJECT_DIR}` anchor and the
fork-era "dropped for pi" note is gone. The Copilot CLI reads `.mcp.json` too (cwd-upward
lookup), so its visible entries carry the anchored form again exactly as they did before
0.180.0.

## What changed

- **New pi destination (`.pi/mcp.json`).** Written only when `pi` is in `config.agents`,
  project-scoped servers only, and every write is recorded through
  `ctx.record_generated_config` (#194). New-entry template: a shell-string command is split
  into executable + `args` (`split_on_whitespace`); a user-tool-dir executable renders in
  `~`-form (pi expands `~` in `command`/`args`/`cwd` only — `${HOME}` stays literal and is
  never emitted); no fork `tools` allowlist; `"exposure": "direct"` stamped on every new
  entry; Claude's `${CLAUDE_PROJECT_DIR}` anchor is never inherited (the destination
  resolves `agentOverrides` for its own reader).
- **Union merge (F10/F11/F11a).** An existing entry survives re-scaffold entry-level
  byte-identical — deep-equal, the writer's re-serialization aside — with
  `exposure`/`toolExposure`/`enabled` and unknown keys preserved whole; a template that
  would render differently emits a template-drift note, never a rewrite; new declared
  servers are appended; user-added servers survive untouched; `config.mcp.decline` still
  removes its named servers with a note (#186); an unavailable server is removed only when
  its launch (`command`/`args`/`cwd`/`env`) is template-identical — decorations neither
  shield it from removal nor count as identity; a hand-edited launch is kept with a
  warn-and-leave note, never destroyed.
- **`.mcp.json` back to Claude's anchor.** `.mcp.json`'s readers are `claude` and `copilot`
  again; the 0.180.0 pi-reader floor is gone with the fork it served. A Claude+pi project
  carries Claude's `${CLAUDE_PROJECT_DIR}` launch as before 0.180.0, and the "written
  anchor-free for pi / dropped for pi" machinery and notes are removed. Claude-only and
  Copilot-only projects see no change.
- **Trust gate, named once per run.** `.pi/mcp.json` is on pi's trust-requiring project
  resource list (`dist/core/trust-manager.js`, `TRUST_REQUIRING_PROJECT_CONFIG_RESOURCES`).
  An untrusted project run headless (`-p`/json/rpc with `defaultProjectTrust` `ask` or
  `never`) skips project resources until it is trusted or pi is launched with `--approve`.
  That is pi's security model — the file declares stdio servers, and starting one runs a
  command — so the scaffold does not bypass it: it writes the file and names the gate in a
  per-run note. `tests/test_pi_adjustments.py` was amended to pin the new contract: the old
  "write nothing trust-requiring into `.pi/`" pin split into `.pi/mcp.json` written + noted,
  while the guard keeps its teeth for every other trust-requiring resource (`.pi/agents/` is
  not on pi's list).

## Upgrade notes

- **Minimum pi for the native path:** the built-in `builtin:mcp` extension (measured on
  0.99.1). The framework still ships the fork-migration adjustment code, so an old
  pi + `pi-mcp-tools` consumer keeps reading the now-anchored `.mcp.json` — and its
  converter expands `${HOME}` and nothing else, so it drops the anchored entries
  (`skipped:unexpanded-var` in the merge ledger). Moving that consumer to native pi is the
  fix; the full fork-machinery retirement is a separate change.
- **Re-scaffold:** `.pi/mcp.json` is materialized in every pi-configured project. Existing
  entries — including hand-tuned `exposure`/`toolExposure` and unknown keys — survive
  untouched; only newly declared servers are appended with the template.
- **Headless in an untrusted project:** the servers are written but skipped at read time
  until the project is trusted (or pi is launched with `--approve`); the scaffold's note
  names the gate.
