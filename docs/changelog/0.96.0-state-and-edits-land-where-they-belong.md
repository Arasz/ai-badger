# 0.96.0 — state and edits land where they belong

Two ways a write went to the wrong place. One was tracking state resolving a directory it had
no business owning; the other was a hand edit landing in a tree the scaffolder rewrites.

## The catalog is not a project root (N3)

A checkout carried `features/.ai-badger/task-tracking/poll_limit.pid` and `poll_limit.log` —
untracked, unignored, and enough to turn `validate.py --all` red. 0.93.1 stopped that from
failing validation and left the path resolution open. This is the resolution.

`collapse_worktree()` (0.88.6) did not prevent it, and could not have: it runs on the **cwd
walk**, and the leak comes from the fallback that walk falls through to. `resolve_project_root`
ended in `script_dir.parents[3]`, a fixed depth chosen for `<repo>/.claude/skills/task/scripts`.
For the catalog copy at `features/common/skills/task/scripts`, the same depth is `features/`.
Any process that started outside a project — a hook re-resolving in a child interpreter is the
common one — adopted the catalog and wrote there.

Reproduced against a `tmp_path` replica, which is the only safe way to exercise this:

```
FAILED test_a_cwd_with_no_marker_above_it_does_not_make_the_catalog_the_project
  AssertionError: the catalog copy adopted .../repo/features as the project root
FAILED test_writing_a_poller_pid_from_an_unmarked_cwd_leaves_the_catalog_untouched
  AssertionError: the poller wrote into the catalog:
    ['features/.ai-badger/task-tracking/poll_limit.log',
     'features/.ai-badger/task-tracking/poll_limit.pid']
```

The fix inserts the same marker walk, run from `script_dir` and stopping at `$HOME`, ahead of
the fixed depth. Every in-repo copy of these scripts — `features/common/skills/`,
`.ai-badger/skills/`, `.claude/skills/`, `skills/` — sits under the marker, so each now answers
with its own checkout regardless of where the process was started. The plugin cache copy sits
under `$HOME`, finds nothing, and falls through exactly as before.

One test was rewritten rather than added, because it asserted the defect as the contract:
`test_module_level_constants_fall_back_to_parents_index_by_default` demanded
`PROJECT_ROOT == SCRIPT_DIR.parents[3]`. It is now
`test_module_level_constants_resolve_the_checkout_not_the_catalog`, and it pins the mis-root it
replaced (`parents[3].name == "features"`) so the rename cannot quietly become vacuous.

## A hand edit to a generated file is refused at edit time (D8)

`.ai-badger/`, `.claude/` and the plugin's `skills/` tree are written by the scaffolder from the
`features/` catalog. Editing one by hand works, survives until the next scaffold, and is then
reverted. `gates/scaffold_freshness_guard.py` catches it at push time — after the work.

`generated_file_guard.py` is a PreToolUse gate on `Edit|Write|MultiEdit|NotebookEdit`. Its
oracle is `.ai-badger/manifest.json`, which the scaffolder already writes: every generated file
is recorded there against the source it came from, so the refusal names the exact `features/`
file to edit instead rather than inferring a path shape. The plugin's `skills/` tree carries no
manifest, so it gets the one extra rule — and only when the catalog directory it was copied from
is still on disk to prove the copy.

Deliberately out of scope: `templates`. `.ai-badger/state.json` and `CLAUDE.md` are seeded once
and then belong to the project; refusing to edit them would refuse the intended use.

It fails open on a corrupt manifest, on a path under no project, and on any internal error, and
the scaffolded command keeps the `[ -f ] … else systemMessage` shape so a missing script skips
rather than blocking the tool it gates. The project root is derived from the **edited file**,
not from the cwd or `$CLAUDE_PROJECT_DIR`: in a worktree session those name the main checkout
while the edit lands in the worktree.

### Fired in anger

Not a unit test asserting `False`. A real headless Claude Code session, in a project carrying
the wiring the scaffolder produces, told to edit a generated file:

```
TOOL USE  Edit -> .../anger-demo/.ai-badger/skills/task/SKILL.md
TOOL RESULT: .ai-badger/skills/task/SKILL.md is generated by ai-badger; the next scaffold
overwrites it, so this edit is lost. Edit features/common/skills/task/SKILL.md instead, then
re-run welcome-ai-badger (or den-refresh). Set AI_BADGER_ALLOW_GENERATED_EDITS=1 for a
deliberate one-off hand patch.
```

The file was unchanged afterwards. The same session, pointed at the catalog source the refusal
named, edited it successfully. And the scaffolder itself is untouched by the guard: its writes
are a subprocess, not an edit-shaped tool call — deleting
`.ai-badger/skills/welcome-ai-badger/scripts/generated_file_guard.py` and re-scaffolding with
the guard wired restored it byte-identical to its catalog source.

Eleven deliberate mutations of the guard were run and every one was killed. Two survived a first
pass and forced tests the suite did not have: a shortest-match-wins mutation of the manifest
lookup (nothing exercised two overlapping entries), and a plugin-tree rule that stops requiring
the catalog directory as proof of a copy — which would have made the guard refuse edits to a
consumer's own `skills/` tree.

### Claude only, and the reasons are recorded

`hermes` is an acknowledged gap — it fires `pre_tool_call` and can refuse, and the manifest the
guard reads is agent-independent, so the arm is possible and simply has not been written. Adding
it unexercised is the defect this item was written to avoid. `copilot` is a wall: its hook
protocol has no block-with-reason channel, and a refusal naming the file to edit instead is this
guard's entire output.
