# 0.51.1 — the observer emits when the index never heard of the server

Issue #170. `post_tool_observer` checked every tool call against `.ai-badger/mcp-tools.json` and
recorded `known` or `unknown` — but only from inside the loop that found the tool's server:

```python
for server in index.get("sources", []):
    if server["name"] == sname:
        known = tname in server.get("tools", {}) if tname else False
        _debug(_MCP_RETRIEVAL_COMPONENT, "known" if known else "unknown",
               project=project, **{_KEY_TOOL: tool_name})
        break
```

When no source named the server, the loop ran to the end and wrote nothing. So the check answered
"was this a tool the index knows about?" for tools whose *server* was already indexed, and stayed
silent for the case that matters most: a whole MCP server the index has never heard of — added
after the index was built, or never indexed at all. That is the strongest "the index is stale"
signal there is, and it was the one that left no record. As
[`call-behaviorist`](../../features/common/skills/call-behaviorist/SKILL.md) documents the
component, an absent record is indistinguishable from "the hook did not run".

## Its own event, not folded into `unknown`

`server_unindexed` is new, because the two silences want different repairs:

| Event | What happened | Remedy |
|---|---|---|
| `unknown` | The server is in the index; this tool is not in its `tools` | `mcp-index update` — the source is behind the server |
| `server_unindexed` | No source in the index names this server at all | Index the server; there is no source to update |

A server recorded with `status: empty` or `status: unknown` (ADR-0014 decision 7 keeps zero-tool
servers rather than dropping them) is **present**, and answers `unknown`. Only a missing source
entry is the new case.

This is the same rule that produced `gate`, `no_terms` and `legacy` in
[`docs/retrieval.md`](../retrieval.md): a silence with two meanings gets a second name.

## Two smaller things in the same check

- `server["name"]` was direct indexing. A source without a `name` key — which the schema forbids,
  but nothing validates at hook read time — raised `KeyError` inside a hook. It is now
  `server.get("name")`, so a malformed index skips the source instead of raising.
- The old code fell back to `sname = tool_name` for an unqualified name, so a built-in like
  `write_file` was checked against the sources as though it were a server. It emitted nothing
  then, and deliberately emits nothing now: a built-in is not an MCP tool, and counting every
  `write_file` call as an unindexed server would make the new event's count meaningless. Only
  `server:tool` names are checked.

## Tests

Three red before the fix, in `tests/test_mcp_retrieval_telemetry.py`:

- `test_a_call_to_a_server_absent_from_the_index_produces_a_record` — no record at all before.
- `test_a_source_missing_its_name_does_not_raise_in_the_hook` — `KeyError: 'name'` before.
- `test_every_key_this_component_writes_is_registered` — extended with a `server_unindexed` call,
  so the new event's fields are held to the same legend check as every other record.

Two more guard the unchanged behaviour: a server present with `status: empty` still answers
`unknown`, and an unqualified tool name still writes nothing.

## Behaviour changes worth knowing

- Debug logs gain a `server_unindexed` event under `ai_badger_hooks/mcp_retrieval`. Nothing reads
  the event vocabulary as a closed set — `behaviorist.py` counts events by name — so no reader
  needs updating, but a tail of an existing log will show a name it has not seen before.
- Only telemetry changed. No recommendation, no hint and no scaffold output moves.
