# 0.59.1 — the banner yields line 1 to frontmatter

Closes [#241](https://github.com/Arasz/ai-badger/issues/241).

Every generated `.github/instructions/*.instructions.md` carried the managed banner
on line 1, which pushed the file's `---` fence to line 3. VS Code and Copilot parse
an instruction file's frontmatter **only** when `---` is the literal first line, so
`applyTo` never resolved, `description` went with it, and the file was dropped from
the automatic-instruction set.

Nothing said so. The file existed, read correctly, and was listed in the manifest —
it just never attached to a request. In the repo where this was found, all 11
generated instruction files had been inert since the day they were first scaffolded.

## The two halves

The banner and the fence both claimed line 1, and they are mutually exclusive by
construction — which is why this is not a one-line fix.

`_with_managed_header` now puts the banner just below the closing fence when the body
opens with frontmatter, and on line 1 when it does not. Only a fence at offset 0
counts: a `---` further down is a thematic break or lives inside a code block, and
moving the banner there corrupts the file. An opening fence with no closing one is
not frontmatter either.

`copy_with_header` decided whether a file was still framework-managed by looking for
the marker on line 1. Left alone, it would have read every corrected file as
hand-authored and silently stopped refreshing it. `_is_managed` now scans the first
10 lines — bounded, so a document that merely quotes the banner deep in its body is
not mistaken for a managed copy.

Both halves ship together. Either one alone is worse than neither.

## What you will see on the next refresh

Files already written with the banner on line 1 are byte-identical to the corrected
output apart from the banner's position, so a plain re-scaffold repairs them. No
migration script, no manual edit: **the first `welcome-ai-badger` or `den-refresh`
run after this release shows a one-line move in every `.github/instructions/` file**,
and that diff is the fix landing.

A project that had already relocated those banners by hand is covered too — the
bounded scan recognises them, so they refresh instead of being preserved as
hand-authored.

## The guard worth having

`test_every_generated_instruction_file_resolves_applyto_and_description` scaffolds a
project and parses each generated file with a strict line-1 parser, asserting both
fields come back non-empty. It asserts the contract with the consumer rather than the
file's internal shape, so it stays true if the banner format changes again — which is
exactly what the old header tests could not do: they read line 1 and found the banner
there, which was the bug.
