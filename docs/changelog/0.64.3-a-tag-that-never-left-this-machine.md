# 0.64.3 — A release tag that never left this machine

`latest_release_tag` reads `git tag -l`, which is local. So a tag that was created and never
pushed satisfies every check in this guard, on the machine that holds it, indefinitely.

That happened to `ai-badger--v0.61.3` on 2026-08-01. The push reported success and the tag never
landed. The guard passed locally — and then failed in CI on **the next two pull requests**,
where a fresh clone has only remote tags and the version reads as documented-but-untagged. The
symptom surfaced on someone else's change rather than the one that caused it, which is what made
it expensive to diagnose rather than merely wrong.

## What changed

`unpushed_release_tags()` compares the local `ai-badger--v*` tags against
`git ls-remote --tags origin`. Any tag present here and absent there fails the guard, naming each
one with the `git push origin refs/tags/<tag>` that fixes it.

It is **silent when `origin` is unreachable** — no remote configured, no network, a clone with
neither. Those are all normal, and a guard that fails offline is a guard people switch off. It
adds signal when it can and says nothing when it cannot.

Only tags matching the release pattern are considered; an unrelated local tag is not a release.

## A 3.9-only method, and the guard that now catches the class

The first implementation used `str.removesuffix`, which is Python 3.9+. This repo's floor is
3.8. It passed import, passed a local run on 3.14, and failed only in CI's 3.8 lane.

`tests/test_python_floor.py` already refused builtin-generic subscripts, which fail at *import*.
A method added after the floor fails at *call* time instead — same floor, different failure
mode, invisible to every check that existed. It now refuses those too, across `engine/`,
`tooling/`, `gates/` and `features/`.

Verified by restoring the 3.9 call and watching the guard name the file and line, then removing
it again. A guard for a mistake that has been made once should be shown failing on that exact
mistake.
