# 0.68.0 — a task owns its worktree

`task_tracker.py start <id> --branch task/x` recorded a branch name and created nothing. Step 4 of
the skill said "create/switch to the task branch" in prose, which an agent can read and not do.

On 2026-08-01 that put work on `main` twice in one session. Both were caught before a push, but
only by noticing — nothing checked. A recorded name that nothing creates is worse than no field at
all: `status` prints the branch, so the tracker looks like it is managing something it never
touched.

## What changed

**`start` creates the worktree it records.** `.claude/worktrees/<taskId>`, on the branch passed to
`--branch`, and it prints the path. Idempotent, so a resumed task re-running `start` adopts the
existing one rather than failing. No branch recorded means no worktree — nothing is invented for a
task that did not ask. `--no-worktree` opts out.

**`finish` removes it — unless that would lose work.** It refuses when the worktree holds
uncommitted changes, or commits reachable from nowhere else, and reports which in
`worktree.keptBecause`. Cleanup that can silently destroy a commit is not cleanup. `--keep-worktree`
skips the removal outright.

## The second reason, found the same day

Sessions share one checkout. A concurrent session switched this repo to `main` while a push was
running its pre-push tests, so pytest ran against files the branch did not have and the push
failed on a test that passes. Nothing was lost, but the failure pointed at the wrong thing
entirely — the diagnosis cost more than the fix.

A worktree per task removes the shared mutable state that makes that possible.

## What "nowhere else" had to mean

The first implementation asked `git log --branches --not --remotes` — repo-wide — and combined it
with a check that exactly one local branch contained HEAD. That second condition is true of *any*
pushed branch, so a fully-pushed worktree refused to close whenever some unrelated branch had an
unpushed commit. A blocker nobody could act on from inside the worktree.

Measured against a scratch repo with a real remote: old logic **blocked** a fully-pushed branch,
new logic does not, and both still catch genuinely unique commits. The check is now scoped to
commits reachable from *this* HEAD and excluded by both `--remotes` and every other local branch —
precisely the set that disappears with the directory.

## Tests

`tests/test_task_owns_a_worktree.py` is new — 12 cases. Creation and idempotency; the no-branch
case; removal of a clean worktree; refusal on an uncommitted file; refusal on a
commit-and-nowhere-else; a missing worktree not being an error at all. Two cases cover the scoping
bug above, one of them with a real bare remote so the pushed-branch false positive is actually
reproducible rather than argued.

The fixture deliberately does **not** stub `subprocess`, unlike `test_task_tracker.py`'s: these
functions exist to drive git, and a fake would make every assertion vacuous.

**Rewritten:** `test_task_tracker.py::test_start_persists_title_and_branch` now passes
`--no-worktree`. It asserts persistence, and its harness forbids shelling out; a bare `start` now
shells out by design. A new sibling, `test_start_reaches_for_a_worktree_unless_told_not_to`,
asserts the flag actually gates the call — otherwise `--no-worktree` would be decoration.
