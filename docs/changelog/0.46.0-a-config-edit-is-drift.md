# 0.46.0 — a config edit is drift

[#128](https://github.com/Arasz/ai-badger/issues/128). `den-refresh`'s SKILL.md documents
`exclude` in `config.json` as the way to decline a catalog item for good. It did not work once a
project had already been refreshed once:

```
python3 refresh.py --target . --root "$AI_BADGER"      # -> reScaffolded: true, config bumped

jq '.exclude = {"invariants": ["version-changelog-required"]}' .ai-badger/config.json | sponge .ai-badger/config.json

python3 refresh.py --target . --root "$AI_BADGER"
```

```json
{"reScaffolded": false, "drift": {"changed": 0, "removed": 0, "versionChanged": 0, "newItems": 0}}
```

`.ai-badger/invariants/version-changelog-required.md` stayed on disk and stayed rendered into
every generated agent file.

## Why every existing drift signal was empty

`refresh.py`'s `has_drift` was computed purely from framework-vs-project *content* drift —
`changed`, `removed`, `orphaned`, `newItems`, `versionChanged`. `config.json` itself was read only
to validate it and hand it to the re-scaffold; its content was never compared to anything. A newly
excluded item whose scaffolded copy still matched the catalog produced none of those signals, and
because the first refresh had already advanced `config.frameworkVersion`, `versionChanged` was
empty too. The same applied to any other config-only edit — `commands`, `personaRouting`,
`agents`, `stacks` — not just `exclude`.

## The fix

A new `manifest.configHash` records what `config.json` looked like when the scaffold that wrote
the manifest ran; `drift.compare()` reports a mismatch as a new `configChanged` signal alongside
`versionChanged`, and `refresh.py` treats it as drift like everything else.

**What is hashed:** a canonicalized subset of the config — `json.dumps(..., sort_keys=True,
separators=(",", ":"))` over the config minus `$schema` and `frameworkVersion` — not the raw file
bytes. Raw bytes would call whitespace or key-order churn drift, since the scaffold writes
`indent=2` while a hand edit (`jq | sponge`, or this repo's own test fixtures) usually does not.
`frameworkVersion` is dropped because the scaffold rewrites it on every run: including it would
duplicate `versionChanged` and break the idempotency this fix depends on
(`hash(what was written) == hash(what is read back)`), turning every refresh into a re-scaffold
loop. `$schema` is dropped because it is a relative pointer whose depth varies by layout and
declares nothing about the project.

**Migration for manifests with no recorded hash.** A manifest written before this version has no
`configHash` to compare against. `_config_drift` reports `{"recorded": null, "current": "<hash>"}`
in that case — truthy, so it re-scaffolds once, and that re-scaffold records the hash. The next
refresh is quiet. In practice this is nearly free: upgrading to a framework version that carries
this fix already makes `manifest.frameworkVersion < VERSION`, so `versionChanged` was forcing that
first re-scaffold anyway; the absent-hash path only fires on its own for a hand-edited or
half-restored manifest, where re-scaffolding is the right call.

**`--force`.** Not the fix itself, but a small addition that closes a related gap: den-refresh had
no way to force a re-scaffold when the scaffold and config disagreed in a way no drift signal
modeled. The documented workaround was to leave the supported entry point and call `scaffold.py`
directly. `refresh.py --force` re-scaffolds unconditionally and reports `"forced": true`, keeping
recovery inside den-refresh.

## Behaviour changes worth knowing

- A config-only edit — `exclude`, `commands`, `personaRouting`, `agents`, `stacks` — is now
  self-executing: the next `den-refresh` applies it without a manual `scaffold.py` call.
- The re-scaffold this signal triggers rewrites the same managed files any other re-scaffold does.
  The unconditional `.ai-badger.bckp/` backup and the "review the diff before committing" guidance
  cover it the same way.
- A project whose manifest predates `configHash` re-scaffolds exactly once on its next refresh to
  record a baseline, then is quiet again. This is self-limiting, not a new steady-state re-scaffold.

## Not covered

`drift.main()` now exits 1 for any target whose `config.json` exists and whose manifest predates
`configHash` — by design, per the migration above. A target with no config at all is not drift:
`_config_drift` returns `None` there, via the `except (ValueError, OSError)` around `load_json`
(`config_path.is_file()` only spares it the exception). Every existing no-drift test in
`test_drift.py` writes a manifest with no target config, so none of them regressed.

`newStacks` is a separate, pre-existing signal that never clears: a scaffolded project's own
output — `.claude/`, the `.mjs` helpers — self-detects as new stacks, so `has_drift` stays true
across refreshes regardless of this change. It is unrelated to `configHash` and is filed on its
own; the tests here suppress it with `stack-ignore.json` so the signal under test is the only one
that can fire.
