# 0.18.0 — Plugin hooks: resolve cwd, read Hermes' kwarg names

**Issue:** #76

## Fixed

Hermes passes **no `cwd`** to any plugin hook. `ai_badger_hooks.py` had always declared
`cwd: str = ""` and used it to locate the project, so every cwd-dependent behavior has been
inert since it was written:

| Behavior | Broken because | Effect |
|---|---|---|
| `on_session_start` drift notice | no `cwd` | never shown |
| `pre_llm_call` drift line | no `cwd` | never shown |
| `pre_llm_call` MCP tool recommendations | no `cwd` **and** wrong kwarg name | never shown |
| `post_tool_call` index hit/miss logging | no `cwd` | never logged |

Verified at the call sites: `model_tools.py:1049-1064` (`post_tool_call`),
`conversation_loop.py:504-509` (`on_session_start`), `turn_context.py:1035-1045`
(`pre_llm_call`).

`pre_llm_inject_context` was broken twice over — it also read `message`, but Hermes names that
kwarg `user_message`. It now accepts both.

`_project_cwd()` is the single resolver (`cwd or os.getcwd()`), used by all three hooks.

## Why it went unnoticed

`pre_llm_inject_context` unconditionally appends the static Hermes usage hints before any
gated block, so the hook always injected *something* and looked alive. Only the parts that
needed to know which project you were in were silently absent.

## Tests

Five tests invoke each hook with the kwargs Hermes actually sends, including a negative
control asserting the drift notice stays silent outside a scaffolded project — a fix that made
it nag everywhere would be worse than the bug.
