# 0.51.0 — the Claude adjuster approves, and the project can decline

Step 6 of the [ADR-0014](../adr/0014-mcp-support-is-configuration-not-retrieval.md) rebuild.
Steps 1-5 made `mcp` a catalog feature type, moved declarations into `stack-mcp.json`, deleted
the legacy registries and taught the index to record curation and status. Every one of them
*described* servers. This is the first step that changes what the agent may **do** with one.

## What shipped

### 1. A declared server stops prompting

`features/claude/adjustments/adjust_mcp.py` is a new Claude adjustment. For every server
`declared_servers()` writes into the project `.mcp.json`, it merges two approvals into the
project `.claude/settings.json`:

- `enabledMcpjsonServers` — the server itself, so its first use is not an approval prompt;
- `permissions.allow` — `mcp__<server>__*`, so its tools are not permission prompts.

Both are documented Claude Code settings keys. On this repository the whole change is four
lines (see the PR), and it is why `CLAUDE.md` can say *"reach for the code-review-graph MCP
tools before Grep/Glob/Read"* without every call stopping to ask.

`config.mcp.approve: false` keeps the prompt for a project that wants each call confirmed.

### 2. `config.mcp.decline` — a project-side route to refuse a server

[#186](https://github.com/Arasz/ai-badger/issues/186): before step 4, `config.externalTools`'
*silence* was how a project declined a catalog-declared server. Deleting that key removed the
only decline route, and `config.exclude.mcp` cannot be it — ADR-0006 keeps `mcp` out of
`EXCLUDABLE_FEATURES` because nothing is written under an mcp item's own name.

The replacement is a named list rather than a silence:

```jsonc
// .ai-badger/config.json
"mcp": { "decline": ["rider"] }
```

Each named server lands in `disabledMcpjsonServers` (it is not launched from `.mcp.json`) and
in `permissions.deny` as `mcp__<server>__*` (its tools are blocked whatever route it arrived
by — plugin, user-global config, CLI). Deny beats allow in Claude Code's own precedence, so a
name in both lists is refused, and no allow rule is written for it.

**Declining reaches further than declaring.** ai-badger declares 1 of the 26 servers measured
on the design machine; `permissions.deny` works on all 26, because it names tools rather than
launch config. That asymmetry is the point of putting the signal in `config.json` rather than
in a per-stack override file.

### 3. `~/.claude/settings.json` is proposed, never written

ADR-0014 decision 6 — *ai-badger proposes user-global configuration; it never writes it* — was
still being broken by ai-badger itself. `McpTools.scaffold_claude_mcp_user` merged a
`scope: user` server into `~/.claude/settings.json`, backup and all. It is now
`propose_claude_mcp_user`, which prints the exact `mcpServers` snippet as a scaffold note and
touches nothing. This is the same class of overreach as
[#173](https://github.com/Arasz/ai-badger/issues/173), one layer in.

The Hermes half of the same rule (`~/.hermes/config.yaml`) is step 7 and still writes.

## What did not ship, and why

**Per-persona pruning.** Verified as real: an agent definition in `.claude/agents/*.md` accepts
`disallowedTools` with `mcp__<server>` / `mcp__<server>__*` / `mcp__*`, and that removes every
tool of the named server from that subagent. ADR-0014 lists it as the mechanism that "does more
than describe", and this step was scoped to build it.

**It has no file to write into.** ai-badger delivers personas to `.ai-badger/agents/*.md` and,
for Copilot, converts them to `.github/agents/*.agent.md`
(`features/copilot/adjustments/adjust_agents.py`). It has never written `.claude/agents/*.md`,
which is the only path Claude Code discovers subagents from — so the `.ai-badger/agents/`
copies are read as prose through the `personaRouting` table in `CLAUDE.md`, never registered as
subagents, and frontmatter added to them would be enforced by nothing.

The declaration surface was not shipped either. A `disallowedFor` key in `stack-mcp.json` that
no production code reads is exactly `targetAgents`, which this same rebuild deleted two steps
ago (step 4) for validating against a schema and being read by nothing. Shipping its
replacement in the same release would be the same defect with a new name.

So the capability is recorded here and filed as an issue, and the gate this step was given —
*verified surface only* — is met by building the two mechanisms that have a target and stopping
at the one that does not.

## Rewritten tests

A rewritten test is where a regression hides, so each is named:

- `test_settings_preservation.py`: `test_valid_user_settings_survive_with_backup` and
  `test_unparseable_user_settings_are_never_rewritten` are replaced by one
  `test_user_settings_are_neither_read_nor_written`. Both old tests asserted the merge that
  decision 6 forbids; the replacement uses an unparseable file, which a merge would have had to
  parse and a refusal note would have had to read.
- `test_stack_mcp_servers.py`: `test_claude_user_server_writes_settings_json`,
  `test_claude_user_server_merge_preserves_existing` and
  `test_claude_user_server_no_write_without_claude_agent` become
  `test_claude_user_server_is_proposed_not_written`,
  `test_claude_user_proposal_does_not_touch_an_existing_file` and
  `test_claude_user_server_not_proposed_without_claude_agent`.
- `test_stack_mcp_servers.py`: `_render_everywhere`, the WP46 characterisation harness behind
  `test_the_two_command_splitters_agree_or_are_documented_to_differ` (6 cases),
  `test_only_mcp_json_pins_the_project_cwd` and `test_env_reaches_every_destination`, now reads
  the Claude user entry back out of the proposal note. The rendering it characterises is
  unchanged; only where the rendered entry lands is.
- `test_mcp_user_tool_paths.py`: `test_claude_user_settings_keep_the_bare_command` becomes
  `test_the_claude_user_proposal_keeps_the_bare_command`.
- `test_scaffold_manifest.py`: `test_a_failing_user_scope_write_degrades_to_a_note` now explodes
  `scaffold_hermes_mcp_user` — Hermes is the only user-scope *write* left to degrade.

## Behaviour changes worth knowing

- A re-scaffolded Claude project gains `enabledMcpjsonServers` and a `permissions.allow` entry
  in its `.claude/settings.json`. Nothing else in that file is touched; it is merged into with
  `config_guard.write_json_with_backup`, exactly as hook wiring already does, and a `.bak-*`
  copy is left beside it (gitignored since 0.51.0's `.mcp.json` entry).
- A `scope: user` server no longer reaches `~/.claude/settings.json`. Anyone who relied on that
  must apply the printed snippet by hand once.
- Nothing about the adjustment is recorded in `manifest.json`: `.claude/settings.json` is merged
  into, never owned, so it is never claimed as an ai-badger file and never pruned as one.
