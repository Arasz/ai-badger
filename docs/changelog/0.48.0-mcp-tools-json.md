# 0.48.0 — the MCP tool index becomes JSON, and the hook stops importing yaml

ADR-0012 §4 decided this — "`.ai-badger/mcp-tools.json` is the format going forward" — and
deferred the migration to a dedicated issue (#145) rather than folding it into that PR. This is
that migration.

## Correction to ADR-0012 §4

ADRs are never edited after acceptance (`docs/adr/README.md`), so the correction lives here
instead: §4 says issue #145 tracks "a dual-format reader so an existing project's
`mcp-tools.yaml` is never stranded." The reader that ships is dual-format only in
`mcp_index.py` (the CLI). `ai_badger_hooks.py`'s reader is **JSON-only** — see below for why
that split is not the oversight it looks like.

## Two readers, opposite constraints

- **`ai_badger_hooks._load_mcp_index` is JSON-only.** A dual-format hook reader would keep
  `import yaml` on the hook's path permanently — the whole point of removing it (the guarded
  import from 0.47.0's fix for issue #136 is deleted, not just guarded further). A project still
  on the legacy `mcp-tools.yaml` gets no MCP recommendations until it migrates — the same
  silence a missing index already produced, not a new failure mode.
- **`mcp_index.py`'s `_read_index` is dual-format**, JSON winning when both exist. This is
  where pyyaml is affordable (the CLI already declares it) and where migration happens.
- **`mcp_index_hook.py`'s `_has_mcp_index`** accepts either file, so a curated project
  mid-migration is never told to run `init`.

## Migration happens at the write choke point

`_write_index` now: drops zero-tool sources, validates against
`schemas/mcp-tools.schema.json`, writes JSON, then renames any legacy `.yaml` file to
`.yaml.migrated` with a printed note. Every write command (`init`, `update`, `tag`, `intent`)
migrates a legacy project once, this way, visibly. The new `mcp-index migrate` command is
read-plus-write through the same two functions every other command uses — no second conversion
implementation to keep in sync — with its own exit contract for a project that wants the
conversion without also running `init`/`update` against a live MCP source.

The old file is **renamed, never deleted** — reversible, and diffable if the conversion looks
wrong.

## Zero-tool servers are dropped at write time

Five servers in this repo's own index (`dotnet-sdk`, `glider`, `glider-trace`, `llmstudio`,
`superpowers`) have `tools: {}`, violating the schema's own `minProperties: 1` — the reason
`tooling/validate.py` used to exempt this schema (`--all` never checked a YAML instance
anyway). Dropping them at write time leaves retrieval **bit-identical**: `Bm25Corpus`'s `N`
counts documents (tools), not sources, and a zero-tool source contributes no documents either
way. Migrating this repo's own index measured exactly that:

| | sources | tools | recall@3 | top-1 | false-fire | zero-on-positive |
|---|---|---|---|---|---|---|
| before | 9 | 98 | 1.000 | 0.907 | 0.267 | 0/43 |
| after | 4 | 98 | 1.000 | 0.907 | 0.267 | 0/43 |

## The crux failure mode: legacy YAML, no pyyaml, no live MCP source

`migrate` (and every write command's fallback read) refuses rather than risk a wrong parse,
with two remedies stated verbatim in the error:

```
<path> is a legacy YAML index and PyYAML is not installed, so it cannot be
safely read (it fell outside the subset this script can verify).
  Remedy 1: mcp-index needs PyYAML: pip install pyyaml (it is in engine/requirements.txt), then re-run.
  Remedy 2: regenerate — `mcp-index init --target <project> --from-json
<hermes mcp list --json output>`. This LOSES curated tags and intents.
```

### Reconsidered: the stdlib-parser rejection

The originally reviewed plan rejected a stdlib YAML-subset parser because "a subtly wrong
parse silently corrupts curated tags — worse than refusing." That argument doesn't survive
scrutiny: the file being parsed is one **this project emitted** (`yaml.dump(data,
sort_keys=False, default_flow_style=False)`), a closed, predictable shape, and the silence is
removable — re-emit the parsed structure and compare it against the source, refusing on any
difference. **Decision: implemented.** `_parse_legacy_yaml_subset` in `mcp_index.py` parses
exactly the shape `schemas/mcp-tools.schema.json` describes (not general YAML), trusts the
result only when re-emitting it reproduces the source, and returns `None` — never a wrong
value — for anything outside that: flow-style collections, unrecognized indentation, a
double-quoted scalar that both needs escaping *and* wraps past pyyaml's 80-column width (a
narrower gap, documented in the parser's own comment; plain-scalar wrapping is handled by
folding it to one line before comparing, since YAML's line-fold is defined to be lossless).
A 2000-trial randomized check — every YAML indicator character, unicode content, bool/int/
timestamp-shaped text, mixed into descriptions — never produced a wrong parse; every input
outside the subset returned the refusal, not corrupted data. Reading this repo's own real
98-tool index round-trips byte-for-byte and matches PyYAML's own parse of the same file.

This converts the crux failure mode from "no way to migrate without installing something" to
"migrate anyway, for the realistic case, or get a loud refusal naming its cost" — a genuine
improvement over "requires pyyaml or throws away curation," at the cost of a bounded, tested
parser instead of zero parser.

## Reconsidered: `_write_index`'s validation requirement

`_write_index`'s docstring calls it a local copy of `atomic_write_text` specifically because
"this script is scaffolded into projects that need not have the framework on sys.path" —
and `mcp_index.py:161` (`_bootstrap_lib`) already treats a missing framework root as
non-fatal, falling back to a built-in tag taxonomy. Requiring `FRAMEWORK_ROOT` *and*
`jsonschema` to validate on every write reverses both of those, and neither is scaffolded into
a consumer project (no `schemas/` directory is copied in, and `jsonschema` is a framework
dependency, not a consumer one).

**Decision: split by command, not a blanket hard requirement.**
- `init`/`update` **hard-refuse** when validation can't run, or when it finds errors. These
  commands overwrite most or all of the file from a freshly fetched tool list — exactly where
  an undetected schema violation (a `general`-tagged tool, a too-short intent, a zero-tool
  source) is most likely and most costly to leave unvalidated.
- `tag`/`intent` are **best-effort**: they already enforce the two fields the schema
  constrains for a single tool (tag-taxonomy membership, intent length ≥10) without
  jsonschema at all, so a missing framework root or missing `jsonschema` degrades to a
  printed note rather than stranding a one-tool curation edit that has nowhere else to happen.
  Any other pre-existing schema issue elsewhere in the file is reported as a warning, not a
  block — refusing a valid edit because of an unrelated pre-existing problem would make
  fixing tools one at a time impossible.

Where the hard refusal does apply, its message names both remedies:
`cannot validate against schemas/mcp-tools.schema.json: pass --root <framework checkout> if
the framework isn't reachable, and pip install jsonschema if it isn't installed
(engine/requirements.txt).`

## den-refresh reports, does not convert

`mcp-tools.yaml`/`.json` is project-owned; `scaffold.py` never writes it, matching 0.46.0's
precedent that a config edit is drift, not silence. `drift.compare()` now notes a not-yet-
migrated legacy index (via its existing `notes` list) so `den-refresh` surfaces it without
touching the file.

## `tooling/validate.py`'s exemption is now honest

`mcp-tools.schema.json` moves from "instances are YAML; not JSON-validated here" to
"instances live in consumer projects (`.ai-badger/mcp-tools.json`)" in
`SCHEMAS_WITHOUT_LOCAL_INSTANCES` — the same reason `config.schema.json`, `manifest.schema.json`
and `learned-skills.schema.json` already use. `test_every_schema_has_a_coverage_decision` only
asserted set equality of names, so a dedicated test now pins the reason string too.

## `tests/test_ai_badger_hooks_missing_yaml.py` is deleted, not rewritten

That file (added in 0.47.0 alongside issue #136's guarded-import fix) exercised a dynamic
`ImportError` simulation for a guarded `import yaml` this module no longer has at all —
there is nothing left to simulate the absence of. A static guard,
`test_hooks_module_has_no_yaml_dependency` in `tests/test_mcp_index_hooks.py`, replaces it:
it pins the module to never re-acquiring a `yaml` import, which is the property that made
issue #136 (a missing pyyaml silently taking four hooks down together) possible in the first
place.

## Dead template removed

`features/common/templates/mcp-tools.yaml.tmpl` was registered in `index.json` but copied by
nothing (`scaffold_templates()` seeds only `state.json`) — deleted, and `index.json`
regenerated.

## pyyaml stays a declared dependency

`features/copilot/adjustments/adjust_agents.py` and
`features/common/skills/welcome-ai-badger/scripts/mcp_tools.py` (`~/.hermes/config.yaml`) still
import it. Only `ai_badger_hooks.py` loses its import.

## Not covered

The stdlib subset parser's known gap (a double-quoted, line-wrapping scalar) is not closed —
it refuses instead, which is the documented, intentional trade-off above, not an oversight.
