# 0.88.0 — the AWM denylist judges what a command does, not how it is spelled

`awm_gate.py` promised that destructive shell commands "are never auto-approved, in either
mode". Its denylist was regexes over raw command text that assumed short-form flags, so the
promise did not hold. Measured against the gate's own pattern list:

```
DENIED   rm -rf /tmp/x                    DENIED   git push --force origin main
ALLOWED  rm --recursive --force /tmp/x    ALLOWED  git push origin +main
ALLOWED  V=-rf; rm $V /tmp/x              ALLOWED  find /tmp/x -type f -delete
```

`away` mode is the mode that exists because nobody is present to approve, so a force-push to
main auto-approved there with no oversight — which also breaches this project's own "never push
directly to the main/trunk branch".

Two changes close it. Commands are **normalised before matching**: `shlex` splits them and long
flags resolve to their short equivalents, so `rm --recursive --force` reads as `rm -r -f`.
Unparseable input is returned unchanged rather than skipped, so an unbalanced quote is not an
escape hatch. And a destructive verb whose arguments are **shell expansions this gate cannot
read** is denied on the dangerous reading — `V=-rf; rm $V` looks harmless and runs as `rm -rf`.

The push pattern now also catches the `+ref` refspec form, and `find -delete` / `find -exec`
join the list.

A denylist remains the wrong long-term shape for a mechanism that auto-approves with no human
present; an allowlist of safe verbs would be the right one. That is a larger behavioural change
than a security fix should carry, so it is filed rather than done here.

`tests/test_awm_command_normalisation.py` pins all three directions: the eight measured bypasses
are denied, the nine commands denied before the fix stay denied, and ten ordinary commands stay
auto-approvable — because a gate that denies everything is its own failure.
