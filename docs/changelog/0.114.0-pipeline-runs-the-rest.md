# 0.114.0 — run what you changed; the pipeline runs the rest

One new common invariant, `features/common/invariants/pipeline-runs-the-rest.md`, drawn from a
consuming repository's project-local draft and generalized before it was accepted.

## The evidence

A consumer had been running its whole test suite locally before every push, on a machine shared by
several concurrent agent sessions. The suite was already run in full by the pipeline on the same
commit, so the local run added no coverage — it only spent the wall clock a second time, twice per
change, on a machine that had none to spare.

The same repository then landed a pull request whose pipeline was green while four of its tests were
red. The tests were real and they failed; they carried no category marker, and every pipeline job
selected on that marker. Nothing ran them. A green run and a run that never executed the test look
identical from the outside.

Those two facts belong together: the first says stop duplicating the pipeline, and the second says
what you owe in exchange for trusting it.

## What generalizing removed

The draft was written from one repository's evidence and named its build command, its three
filtered jobs, its nightly backstop, its test-attribute idiom and the pull request that motivated
it. None of that survives. The framework serves nineteen stacks; a rule that only parses for one of
them is not an invariant, it is an instruction wearing the wrong hat.

What is left is the shape of the lesson: local scope is the build plus what your change touches; the
pipeline owns everything else; wherever a pipeline selects a subset — tags, markers, paths, suites,
globs — membership in that selection is a thing you verify rather than assume; and the cost of the
trade is that failures arrive after a push, which only works if you push early and read what comes
back. The last sentence addresses delegation, because a dispatched brief asks for a full local run
out of habit and inherits nothing.

## Why a new file rather than an edit

Three existing invariants sit near this one and none of them absorbs it.

`prove-the-check-fails` is about a check's discriminating power — whether you have watched it go red
for the defect it names. A test can satisfy it completely and still sit outside every job the
pipeline runs; proving a check can fail says nothing about whether anything executes it.

`proof-of-done` requires the acceptance criteria and the gate that checks them to be named before
the work starts. It fixes *what* proves the work; this one fixes *where that proof runs* and who is
responsible for each half.

`measure-when-it-pays` shares the cost-versus-payoff framing but its subject is empirical claims —
benchmarks, numbers you assert. Folding a verification-workflow rule into it would cost that
invariant its focus and buy nothing.

## Rendering

Eighteen common invariants now render into every scaffolded agent file. This repo's `agentDocs`
override stays at `256/17500`; the largest generated file, `HERMES.md`, moved 179 → 183 lines and
10941 → 11254 chars, with headroom in both. The framework default is untouched, so no scaffolded
project's budget moves.
