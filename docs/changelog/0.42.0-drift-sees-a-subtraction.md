# 0.42.0 — drift sees a subtraction

[#116](https://github.com/Arasz/ai-badger/issues/116). Reported from a consuming repo, then
reproduced here.

`den-refresh` detected drift that was *added* ([#104](https://github.com/Arasz/ai-badger/issues/104))
and drift that was *changed* ([#110](https://github.com/Arasz/ai-badger/issues/110)). It never
detected drift that was *subtracted*. Drop a stack from `.ai-badger/config.json` and nothing
happened:

```
reScaffolded  : False
changed       : 0
removed       : 0
newItems      : 0
newStacks     : []
versionChanged: None

1 of 1 ts-derived files ORPHANED (still on disk):
    .ai-badger/instructions/typescript.instructions.md
```

The project had declared it no longer uses TypeScript. `typescript.instructions.md` was still
delivered to the agent, and `CLAUDE.md`'s path-specific instructions table still pointed at it.

## The second failure was worse

`compare()` iterates manifest entries and asks two questions of each: does the framework source
still exist, and has its hash moved? Neither can see a config edit, so the entry looked healthy.

Meanwhile `prune_declined` — the only thing that deleted a superseded file — gated on
`config.exclude` and nothing else. So when a re-scaffold ran for some *unrelated* reason, it
rewrote `manifest.json` from the current stack list and dropped the entry, while the file stayed
on disk.

> The file then had no manifest record at all. `compare()` only walks manifest entries, and the
> pruner only reads the previous manifest. Nothing could find it again.

That is the same class of stale-copy problem as [#109](https://github.com/Arasz/ai-badger/issues/109),
one directory in — and it is why the reporter had to delete the orphans by hand.

## Two documented routes, one of which worked

`den-refresh`'s SKILL.md already stated the removal contract:

> A deleted skill, persona, invariant or instruction comes back: absence is not a declaration. To
> decline one for good, add its name to `exclude` in `config.json`.

That route worked. But the same document also sanctions editing the config directly — *"If the
config needs updating (new stacks, changed commands), edit it first, then run den-refresh"* — and
that route silently did not converge.

## The fix

`badger_lib.is_orphaned(entry, stacks)` is now the single place that decides whether a manifest
entry's stack is still configured, so drift and the re-scaffold cannot disagree about what a
dropped stack leaves behind — the same reasoning that put `config.exclude` behind one
`bl.exclusions` call.

- **`drift.compare()`** reports an `orphaned` list when it is given the resolved stack list.
  Without that list it reports nothing, because a config edit cannot be inferred from the
  framework alone. An orphaned entry is not also reported as `changed`: it is leaving, and
  upstream drift on it is noise.
- **`refresh.py`** counts `orphaned` toward `has_drift`, so the removal alone now triggers the
  re-scaffold.
- **`prune_declined` became `prune_superseded`**, covering both ways a project stops asking for a
  file: declining the item, or dropping the stack that delivered it. The safety discipline is
  unchanged and now applies to both — ownership proven by the previous manifest's recorded target
  *and* its recorded hash, an edited copy reported rather than deleted, and skill directories left
  on disk because they may hold project-local files.

## Upgrading

A refresh after this release will prune files left behind by stacks dropped in the past — that
backlog surfaces all at once. Anything edited in place is reported and kept, so review the notes
on the first run.

## Side observation, not fixed here

`detect_new_stacks` reported `['claude', 'node']` as new for a fixture whose only files were
`package.json`, `requirements.txt` and a `.ai-badger/` directory. It was noisy enough to mask
this bug twice during reproduction by forcing `reScaffolded: true` for an unrelated reason.
