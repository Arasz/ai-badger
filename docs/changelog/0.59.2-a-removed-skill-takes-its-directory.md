# 0.59.2 — a removed skill takes its directory with it

Closes [#243](https://github.com/Arasz/ai-badger/issues/243).

When the framework deleted a skill, a refresh reported it in `drift.removed`, dropped it from
`manifest.json`, and unlinked its discovery symlinks — and left `.ai-badger/skills/<name>/` on
disk. A tracked directory no manifest entry claimed, no agent could discover, and nothing would
ever update again. The refresh that performed the removal was also the only one that ever
mentioned it: `removed` fires against a manifest entry, and that entry was gone by the end of
the run.

The reporting case was a rename upstream — `create-refinement-document` → `owner-gate-review` in
0.58.0. Both directories were on disk afterwards, and only the manifest said which one was live.

## What changed

`prune_superseded` deleted files and skipped directories. It now prunes a superseded skill
directory whole — the same code path, the same reasons, the same safeguard — so a stack dropped
from `config.stacks` and a source dropped from the catalog converge the same way.

The issue's premise was half right. `orphaned` pruned *files*; skill directories were spared
regardless of why they were superseded ([0.42.0](0.42.0-drift-sees-a-subtraction.md): "skill
directories left on disk because they may hold project-local files"). That reservation is
answered rather than overridden — see below — so both cases are fixed together instead of one
gaining a second removal path.

## What is never removed

Three ways a superseded directory survives, each one reported:

- **Edited since it was scaffolded.** The recorded directory hash no longer matches, so the
  project changed something. An edit to a file *nested* inside the tree counts too — extension
  files carry their own manifest entries, and a prune that took the tree would have taken an
  edited extension with it.
- **It holds a file the project owns.** `project-local.md` and a skill's seed-once files
  ([#15](https://github.com/Arasz/ai-badger/issues/15)) are content the framework never wrote and
  cannot put back. `SkillDelivery.project_owned_files` is the one place that knows which those
  are; the prune asks it.
- **`config.exclude.skills` declines it.** Unchanged: the framework still ships that skill, the
  project may re-include it, and the exclusion notes already say the copy was left and how to
  remove it.

A refresh that silently deleted a directory somebody had put work into would be a worse failure
than the leftover it fixes, so every outcome — pruned or kept — appends a note naming the path.

## The prune moved out of `scaffold.py`

`scaffold.py` was one line under its module-line budget, and the test that guards it says to
extract a collaborator rather than compress a comment. `_superseded_reason` and
`prune_superseded` became `superseded_prune.SupersededPrune`, the tenth collaborator, reached
as `Scaffolder.superseded`. Behaviour for file entries is unchanged, including the note wording
every existing test reads.

## What you will see on the next refresh

Directories left behind by skills the framework dropped in the past surface all at once — one
note per pruned path. Anything edited or holding project-owned files is kept and named instead,
so read the notes on the first run after this release.
