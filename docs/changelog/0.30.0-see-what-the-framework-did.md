# 0.30.0 — see what the framework actually did

ai-badger has been silent about its own machinery. "Did that hook even run?" had no answer
short of adding print statements and re-scaffolding — which is how a `SessionStart` hook that
could not load survived nine releases (0.28.1), and how token tracking silently no-opped in
every scaffolded project (0.27.1). Both were invisible rather than broken-looking.

The new **`call-behaviorist`** skill turns that machinery's behaviour into a record.

## Using it

```bash
python3 .ai-badger/skills/call-behaviorist/scripts/behaviorist.py on 4h
python3 .ai-badger/skills/call-behaviorist/scripts/behaviorist.py tail
python3 .ai-badger/skills/call-behaviorist/scripts/behaviorist.py off
```

**Enabled for every project by default** — debug is something you turn on while investigating,
not per-repo bookkeeping. `--project` narrows it to the current directory when you want that.

## What a record holds

`tail` renders them readably; on disk they are compact, one JSON object per line:

```json
{"t":"2026-07-27T09:22:56+00:00","c":"ai_badger_hooks/session_start","e":"skip","v":"0.30.0","p":"/repo"}
```

`t` timestamp · `c` component · `e` event · `v` version · `p` project · `s` session. The
single-letter keys are a budget rather than cosmetics: a record must stay under `PIPE_BUF`
(4096 bytes) for concurrent appends to be atomic, and these keys repeat on every line. Fields a
caller adds keep their full names — they are the payload and do not repeat.

Two fields earn their place:

- **`version`, on every record** — the VERSION of *the copy of the code that ran*. Several
  copies of ai-badger routinely coexist: a plugin cache, a `.ai-badger/` scaffold, a framework
  checkout. When they disagree the symptoms are baffling; this makes the disagreement visible
  instead of something to deduce. The plugin-at-0.13.0-against-a-0.18.1-scaffold case that
  prompted this feature reads straight off the log.
- **`event`** distinguishes `start` from `skip`, so a hook that fired and exited early is
  distinguishable from one that never fired at all. That distinction is the entire point.

No tool input, prompt text, or file content is ever recorded.

## Off by default, and bounded

Nothing is written and no directory is created until you switch it on. `on` always takes an
expiry (default 4h, capped at 24h) checked against the wall clock on every event — no timer, no
cron. Debug logging that never switches itself off is a slow disk leak and a standing privacy
exposure.

`~/.ai-badger/debug/` is user-level and `0600`/`0700`: the log says where you work and what ran,
so it never lands in a project directory or in git. Capped at 5000 records, oldest trimmed first.

## It cannot break what it observes

`log_event` swallows its own exceptions. This contradicts the project's general no-silent-failure
stance, deliberately: a debug facility that can break the hook it is instrumenting is worse than
no debug facility. Tested by making the sink unwritable and asserting the host hook survives.

## Design notes

`debug_log.py` is **duplicated on purpose**. No runtime hook imports `badger_lib` — they are
standalone because they run from four deployment shapes where no single relative path holds.
Rather than add a bootstrap to every hook (multiplying the duplication Wave 7 exists to remove),
the module is vendored, and a test asserts the copies are byte-identical. Duplication that is
*checked* rather than hoped for. Full reasoning:
`docs/design/debug-mode-and-call-behaviorist.md`.

This release instruments `ai_badger_hooks`' session-start path. The remaining hooks
(`prompt-markers`, `task`, `mcp_index`) follow, and are best done after Wave 7 consolidates the
bootstrap shims.

## Upgrading

Re-scaffold to get the skill. Nothing changes until you run `on` — the logger is inert while
disabled, and a missing `debug_log.py` degrades to a no-op rather than breaking a hook.
