# 0.93.1 — a dot directory under `features/` is not a candidate stack

`catalog_stack_gaps` (0.92.0) walks `features/` on disk and reports every directory the index
cannot see. That is the right check against a tracked tree and the wrong one against a working
copy: local, untracked state under `features/` fails validation for the developer who has it and
nobody else.

Found immediately after 0.93.0 landed. A checkout carrying
`features/.ai-badger/task-tracking/poll_limit.pid` — untracked, not ignored, written by tooling —
turned `validate.py --all` red and took six tests with it:

```
INVALID  catalog stack membership
    - features/.ai-badger: no stack.json and no feature directory, so the index never sees it
```

CI never saw it, because CI checks out clean. That is the shape B11 describes: a check that reads
the working tree passes everywhere except the machine it matters on.

## What changed

`catalog_stack_gaps` skips directories whose name begins with `.`. No stack is named with a
leading dot, so this narrows the check by exactly the set that could never have been a stack —
`features/ghoststack` with a stub `skills.json` is still reported, verified by deliberately
creating one.

The broader fix — reading `git ls-tree HEAD` rather than the working tree, as the repo-structure
tests now do — is left for the pass that owns it. This is the one-line correction that unblocks a
red checkout.

## Still open

Whatever wrote `features/.ai-badger/task-tracking/` did so by resolving a state directory against
a working directory that happened to be `features/`. The path resolution is worth its own look;
this release only stops it breaking validation.
