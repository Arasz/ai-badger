# 0.50.0 — the stopword-count comment was wrong, and now it can't drift again

## The gap

`features/common/retrieval/tokenizer.py` documented `STOPWORDS` as "~80 common English
function words." `len(STOPWORDS)` is 109 — a 36% undercount. The figure had already propagated
once, into `docs/retrieval.md` (caught and fixed during the fact-check in #153). Filed as #156.

`docs/adr/0012-bm25-retrieval-with-a-falsifiable-eval.md` repeats the same "~80" figure. Accepted
ADRs are immutable (`docs/adr/README.md`) — they record what was believed at the time — so it is
left as-is. This entry is the forward-pointing correction: the real count is 109, not ~80.

## The fix

Replaced the free-text approximation with `STOPWORD_COUNT = 109`, a module constant the comment
points at instead of restating. A new test,
`tests/test_retrieval_tokenizer.py::test_stopword_count_matches_documented_count`, asserts
`STOPWORD_COUNT == len(STOPWORDS)` — it fails if either changes without the other, which a
comment-parsing test would only do awkwardly and a bare "fix the number" would not do at all.

## Not covered

`docs/adr/0012` still says "~80"; per policy above, that repetition is not touched here.
