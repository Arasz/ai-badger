# 0.70.2 — squash-merged content is not lost

`worktree_blockers()` (0.69.0) refused to remove a worktree holding "commits reachable from
nowhere else" — a real guard against the one case where cleanup is indistinguishable from data
loss. This repository squash-merges every PR, and a squash merge discards the branch's original
commit SHAs: the default branch gets one *new* commit with the matching tree, so `--not
--remotes` kept calling those commits unique hours after the work had shipped.

Measured on two worktrees whose PRs had already merged (#274, #276):

```
version-fix    commits not on main or any remote: 1
p2-research    commits not on main or any remote: 6
```

Both were refused. A content check told a different story:

```
version-fix    content diff vs main: 0 files          (identical)
p2-research    content diff vs main: 19 files          (all main-ahead; nothing unique)
```

`p2-research`'s 19 files were not its own — main had moved on with unrelated work after the
squash landed, and a naive tip-to-tip diff would have blamed that noise on the branch too. A
blocker that fires on every squash-merged branch is one people learn to bypass, and a guard
routinely overridden protects nothing (#278).

## What changed

`worktree_blockers()` still starts from the same reachability check (commits on `HEAD`, not on a
remote, not on any other local branch). When that finds something, it now asks one more
question before treating it as a blocker: does an equivalent patch already exist on the default
branch, regardless of SHA?

`_default_branch()` resolves the branch a squash-merged PR lands on: `git symbolic-ref
refs/remotes/origin/HEAD` where a remote sets it, falling back to whichever of `main`/`master`
exists locally. `_squash_landed()` then builds one synthetic commit for everything the worktree's
branch has added since it forked (`merge-base..HEAD`, squashed into a single tree) and asks `git
cherry <default> <synthetic>` whether an equivalent patch is already reachable from the default
branch. `cherry` compares by patch content, not tree state or SHA, so a later unrelated commit on
the default branch can't hide the match the way a tip-only diff would — this is what keeps
`p2-research`'s case correct.

Either helper failing to resolve anything (no remote and no local `main`/`master`; no common
history) falls back to the old reachability-only behaviour rather than guessing.

## What did not change

A worktree with a genuinely unpushed, unmerged commit is still refused — `_squash_landed()`
returns `False` for it, same as before this existed. `tests/test_task_owns_a_worktree.py`'s
`TestFinishRefusesToDestroyWork::test_a_commit_no_other_branch_has_blocks_removal` covers exactly
that case and was not touched.

## Tests

Three added to `TestASquashMergedWorktreeIsNotBlocked` in `tests/test_task_owns_a_worktree.py`,
all red before the change (built on a scratch repo using `git merge --squash` + commit — what
GitHub's squash-merge produces on the other side):

- `test_a_squash_merged_branch_is_not_blocked` — the simple case: one commit, squash-merged,
  default branch untouched since.
- `test_a_squash_merged_branch_stays_unblocked_after_main_moves_on` — the measured `p2-research`
  case: two commits squash-land as one, then main takes an unrelated commit on top. A bare
  tip-to-tip diff sees that later file and would refuse; this must not.
- `test_a_branch_with_real_unique_work_is_still_blocked_next_to_a_squashed_one` — a squashed
  worktree and a genuinely unmerged one side by side, so the same run proves recognising a
  squash didn't also start waving through real unique work.
