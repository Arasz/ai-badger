# 0.55.0 — commit now, and say when work is at risk

The commit hook used to end its message with "consider committing". An agent
mid-task considers it and carries on. Three changes so the work actually stops
being at risk.

## The message is an instruction

```diff
-[ai-badger] 7 uncommitted file(s) — consider committing. …
+[ai-badger] Commit now — 7 uncommitted file(s). Use Conventional Commits —
+<type>[optional scope]: <description> — see https://www.conventionalcommits.org/en/v1.0.0/. …
```

Still advisory in the only sense that matters: `additionalContext` on a
`PostToolUse` event, never `decision`, `permissionDecision` or `continue`, on any
code path. It commands; it does not gate. `0.33.0-no-third-party-tool-call-interception.md`
records why that line is not crossed.

## Commits follow Conventional Commits

The message names the form rather than assuming it is known.

The hook deliberately does **not** infer the type from the changed paths. `feat`
versus `fix` versus `refactor` states *intent*, and intent is not recoverable
from a file list — a guess there would be a confident claim about something the
hook cannot see.

## An agent that never commits is now visible to its parent

Each command that is not followed by a commit increments an unanswered count on
the project's entry. A dropped file count is the only evidence of a commit this
hook has, so that is what clears it.

At three unanswered commands the message escalates — it names the consequence
and asks for a WIP commit rather than a tidy one:

```
[ai-badger] STOP AND COMMIT — 9 uncommitted file(s) after 3 commands with no commit
in between. This work is at risk of being lost: an agent that ends here leaves it
unrecoverable. Commit what works now, even as a WIP. …
```

and the entry becomes readable by a parent:

```console
$ python3 .ai-badger/skills/commit-reminder/scripts/ensure_committed.py
1 project(s) told to commit 3+ times with no commit since:
  /repo/wt-a session sess-7 — 3 unanswered since 2026-07-31T15:42:15Z
Take over the work, commit it yourself, or stop the agent — an agent that ends here
leaves the work unrecoverable.
```

**Why a script rather than a message to the parent.** A `PostToolUse` hook can
only add context to the agent that triggered it — it has no channel to that
agent's parent, and Claude Code has no hook that would give it one. So the hook
records and the parent reads. It exits 0 even when work is at risk: reporting is
not gating.

Entries are keyed by resolved project root, which separates parallel agents
whenever they run in their own worktrees — the common shape for that fan-out.

**Not a new skill.** The read side lives in `commit-reminder` rather than a
separate `ensure-work-is-committed`, because it is the same concern — uncommitted
work — seen from the other end. A second skill would have needed its own
`SKILL_SCOPES` entry, sync, scaffold and index plumbing to split one idea in two.
The skill's `description` now covers both triggers.

## Verified end to end, not just unit-tested

Against a real git repository, running the real hook:

```
fire 1  [ai-badger] Commit now — 7 uncommitted file(s). …
fire 2  [ai-badger] Commit now — 8 uncommitted file(s). …
fire 3  [ai-badger] STOP AND COMMIT — 9 uncommitted file(s) after 3 commands …

$ ensure_committed.py        → 1 project(s) … 3 unanswered
$ git commit -m "feat: …"
$ ensure_committed.py        → No project has unanswered commit commands.
```

## Found in review, before any of this shipped

Six defects in the first cut of this change, all fixed here:

- **The Hermes hook was never updated.** It still called the removed
  marker-only API and still said "Consider committing your work" — and writing a
  bare integer over the entry **silently cleared an escalation** raised on the
  Claude side. Both hooks now go through `advance`, and a test pins that a Hermes
  edit cannot wipe the count. The Hermes test fixture used to hand-reimplement
  the ratchet, which is why the drift went unseen; it now delegates to the real
  module and stubs only `git status` and the state file.
- **`ensure_committed.py` exited non-zero on malformed state.** A non-UTF-8 file
  raised `UnicodeDecodeError` past `load_state`'s `except OSError`, and a
  non-integer `fires` raised `TypeError`. A parent runs this to find out whether
  it is losing work; crashing is a worse failure than the one being reported.
- **`since` recorded the latest command, not the first**, so a parent read "stuck
  for 0 minutes" for work stuck for twenty — understating the very risk it
  reports.
- **Finished work stayed at risk forever.** The entry only clears on a later hook
  run in that project, so a completed or deleted worktree never dropped out. The
  report now asks `git status` rather than trusting the entry alone.
- **`save_state` was not atomic.** A torn read degrades to `{}` and the next
  writer persisted that — which previously cost another project a marker, and now
  would have silently cancelled its escalation. The write is a rename.
- **Nothing tested that the escalation was wired into the hook.** Mutating the
  `fires` argument at the call site left the whole suite green. A hook-level test
  now drives `main()` three times and asserts the escalated message.

## Migration

None. `{root: <int>}` from earlier versions still loads — a bare integer reads as
a marker with no unanswered commands — so an existing state file needs no
migration and no deletion. There is a test for exactly that.

## Rewritten test worth naming

`tests/test_commit_reminder_hook.py`'s `_stub_marker_store` became
`_stub_entry_store` and now stubs `get_entry`/`set_entry`, because the hook no
longer calls `get_marker`/`set_marker`. It was only ever used to keep the tests
off the real state file, and no assertion reads it, so the rename changes
isolation plumbing rather than what any test claims. `get_marker` itself is kept
and now derives from the entry.
