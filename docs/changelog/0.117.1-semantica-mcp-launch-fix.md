# 0.117.1 — MCP Launch and Install Fixes

**Type:** PATCH
**Date:** 2026-08-14

Two MCP servers could be scaffolded into a state where they never connect. Both are
fixed here, and both now fail loudly rather than silently.

## What Changed

### MCP Server Catalog (`semantica`)

Reverts the launch command introduced in
[0.116.6](0.116.6-semantica-mcp-command-fix.md), which made the server fail to start
for every project that scaffolds it.

- `features/common/stack-mcp.json` — `semantica` launch command changed from
  `semantica mcp start` to `semantica-mcp`.
- `availability.command` changed from `semantica` to `semantica-mcp`, so the PATH gate
  probes the executable that is actually launched.

## Why

`semantica mcp start` cannot serve MCP over stdio. Its implementation
(`semantica/cli.py`, v0.6.5) is:

```python
cmd = [sys.executable, "-m", "mcp.server"]
proc = sp.Popen(cmd)
_write_pid("mcp", proc.pid)
```

Three independent faults:

1. **Wrong module.** `mcp.server.__main__` is the MCP SDK's placeholder — a bare
   `Server("mcp")` exposing zero tools. None of semantica's 12 tools are served.
2. **Missing backend.** That stub ends in `anyio.run(main, backend="trio")`, and `trio`
   is an optional anyio extra that neither install path pulls in, so it dies with
   `LookupError: Backend 'trio' is not available`.
3. **Wrong process shape.** It daemonises via `Popen` + pidfile and returns, while a
   stdio MCP server must hold the pipe in the foreground.

Reproduced identically against a `.venv` install and a `uv tool` install, so the fault is
in the command, not in how semantica is installed.

`semantica-mcp` is a console script the package already ships
(`semantica.mcp_server:main`). It resolves through PATH exactly as `semantica` does — the
concern 0.116.6 set out to fix — while running the real stdio server. Verified by
handshake: `serverInfo` `semantica/0.4.0`, 12 tools listed.

## Impact

Any project scaffolded at 0.116.6 or 0.117.0 has a `semantica` entry in `.mcp.json` that
cannot start. Re-scaffold to pick up the corrected command.

### MCP Prerequisite Scripts (`code-review-graph`)

`features/common/mcp/code-review-graph/scripts/{check,install}.py` now probe the real
`serve` entrypoint instead of trusting that the executable exists.

- `check.py` gained `can_serve()` and reports **not ready** when the server cannot start.
- `install.py` gained `verify_serves()` and returns 1 — instead of printing `SUCCESS` —
  when the installed server cannot start.
- `install.py` uses `uv pip install` when `uv` is on PATH, falling back to `pip`.

**Why.** `code-review-graph` requires `mcp<2`. Anything that pulls `mcp>=2` into the same
environment breaks `fastmcp`, and `code-review-graph serve` then dies on
`ImportError: FastMCP server support is not installed` — which is a `-32000` connect
failure in the client. pip warns about the conflict but installs anyway.

The old checks could not see this. `code-review-graph --version` exits 0 in exactly that
broken environment (measured: `code-review-graph 2.3.7`, exit 0), and `import
code_review_graph` succeeds too, because only `serve` imports fastmcp. So both scripts
reported a healthy install for a server that could not start.

## Impact

Any project scaffolded at 0.116.6 or 0.117.0 has a `semantica` entry in `.mcp.json` that
cannot start. Re-scaffold to pick up the corrected command.

Projects that installed `code-review-graph` and `semantica` into one shared `.venv` may
have a broken `code-review-graph`. Re-running `install.py` repairs it (pip resolves `mcp`
back under 2.0); if it cannot, the script now says so instead of reporting success.

## Tests

- `tests/test_mcp_semantica_catalog.py::test_semantica_stack_entry_has_required_fields`
  updated to assert the new command.
- `test_semantica_command_is_not_the_daemonising_cli_subcommand` added — a regression
  guard that fails on any command containing `mcp start`. Confirmed red against the
  0.117.0 catalog before the fix landed.
- `tests/test_code_review_graph_mcp_scripts.py` gained five cases covering the serve
  probe, the install gate, and uv preference. All five confirmed red first.

Verified against real environments, not only mocks:

| Environment | `check.py` | Old `--version` probe |
|---|---|---|
| homebrew 3.4.4, healthy | exit 0 | exit 0 |
| venv with `mcp 2.0.0`, cannot serve | **exit 1** | exit 0 (missed it) |

`install.py` run end to end into an empty directory produced a server that passed the
serve probe; re-run against a deliberately broken venv, it downgraded `mcp` to 1.29.0 and
verified the repair.
