# 0.100.0 — the release ritual's last step is checked

The ritual is four steps: bump `VERSION`, run `version_sync.py`, run `changelog_index.py` and
`index_build.py`, then re-scaffold the repo against itself. The first three each have a `--check`
lane. **The fourth had nothing.**

`scaffold_freshness_guard` is the only gate that could have seen it, and it deliberately does not.
It strips `frameworkVersion`, `frameworkCommit`, `generatedAt`, `configHash` and the
`Scaffolded by ai-badger <v>` line before comparing, and its docstring commits to that: *"A version
bump alone must not fail this."* That exemption is precisely the hole — a release that skips the
re-scaffold differs from a correct one **only** in the fields the guard ignores.

So the state below passed every gate in the repo:

```
VERSION         0.99.0
index.json      0.99.0
manifest.json   0.97.0        <- two releases stale
CLAUDE.md       "Scaffolded by ai-badger 0.97.0."

version_sync --check 0 | index_build --check 0 | changelog_index --check 0
docs_guard 0 | release_guard 0 | shipped_paths_guard 0 | deps_guard 0 | validate --all 0
scaffold_freshness_guard: "1395 path(s) compared ... only version stamps differ — PASS"
```

It is not a one-off. Three of the fourteen tags in the 0.87–0.99 window shipped it:

| tag | VERSION | manifest |
|---|---|---|
| `ai-badger--v0.90.0` | 0.90.0 | 0.89.0 |
| `ai-badger--v0.94.0` | 0.94.0 | 0.93.1 |
| `ai-badger--v0.99.0` | 0.99.0 | 0.97.0 |

All three were releases that changed no scaffolder code — two documentation releases and a test
release — so nobody thought to re-scaffold, and nothing asked.

## What changed

`version_sync.py --check` now also reads `.ai-badger/manifest.json:frameworkVersion` and the
`Scaffolded by ai-badger <v>` stamp in every generated agent file (repo root, `.ai-badger/`,
`.github/`), and fails with the remediation command when they disagree with `VERSION`.

**It reports; it never writes them.** `sync()` leaves both alone, pinned by
`test_sync_never_forges_the_scaffold_stamp`. Rewriting a stamp here would assert a scaffold that
never ran — the same class of untrue claim the check exists to catch. The stamps stay the
scaffolder's to write.

The freshness guard's stamp policy is untouched. A version bump alone still does not fail it; the
disagreement is now caught one lane earlier, by the script that already owns "the version literals
must agree with `VERSION`".

`CONTRIBUTING.md` prescribed the wrong order — §4 "re-scaffold if you touched the scaffolder" came
*before* §5's bump, and §5's checklist ended at `version_sync.py`. Follow it top to bottom and you
scaffold at the old version, bump, and stop. The re-scaffold is now the last step of §5.

## Proven

- Both detection tests watched RED first, then green.
- Run against the real stale tree: **9 stale stamps reported, exit 1**, including
  `.github/copilot-instructions.md`.
- `0.99.0 → 0.100.0` in this release was done in the corrected order, and `version_sync --check`
  now exits 0 on the result.
