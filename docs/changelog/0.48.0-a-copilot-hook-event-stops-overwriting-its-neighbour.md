# 0.48.0 — a Copilot hook event stops overwriting its neighbour

## The defects

Both in `features/copilot/adjustments/adjust_hooks.py`.

**1. Assignment, not append.**

```python
copilot_hooks["hooks"][copilot_event] = entries
```

at line ~104, and again at line ~112 in the fallback branch:

```python
copilot_hooks["hooks"][copilot_event] = [{...}]
```

Two manifest entries mapping to the same Copilot event overwrote each other — whichever the
manifest iterated last won, the other vanished with no note, no error, and no test failure.

**2. The fallback ignored the manifest's script name.**

```python
hook_scripts = list(skill_dir.glob("*_hook.py"))
if hook_scripts:
    rel_path = hook_scripts[0].relative_to(target)
```

When a manifest entry had no command in the framework's `hooks.json`, this globbed the skill's
`scripts/` directory and took whichever file the filesystem returned first — ignoring
`copilot_entry["script"]` even when the manifest named it.

## Why neither fired today

No collision exists in the current manifest, and the two skills that resolve through the
fallback branch (`prompt-markers`, `commit-reminder`) each have exactly one `*_hook.py`. Both
defects were latent, not dead: each is triggered by a change already queued behind this issue.

- **#147** proposes wiring `context-enrichment` onto `userPromptSubmitted`, where
  `prompt-markers` already lives — landed as written, the second manifest entry would silently
  delete prompt-marker handling for every Copilot project on its next scaffold.
- **#141** adds a `task-checkpoint` entry pointing at `stop_hook.py` in the `task` skill, whose
  `scripts/` directory holds four `*_hook.py` files (`drift_notice_hook.py`,
  `session_start_hook.py`, `stop_hook.py`, `user_prompt_hook.py`). Landed as written, the
  fallback would wire whichever of the four sorts first — not necessarily `stop_hook.py`.

Both PRs would have been fixing a bug they merely happened to expose, so this lands first.

## The fix

- Accumulate into the event's list (`setdefault(...).extend(...)` / `.append(...)`) rather than
  replacing it, in both the primary and fallback branches — matching the dedup discipline
  `hook_wiring.py` already uses for the Claude side.
- Honour `copilot_entry["script"]` when the manifest provides one; fall back to the glob only
  when it is absent.
- When the glob is the only option and returns more than one candidate, raise `ValueError`
  naming every candidate rather than picking one. `run_adjustments()` already wraps each
  adjustment's `adjust()` call in a broad `except Exception`, so this surfaces as a scaffold
  note instead of guessing silently.

## Tests

`tests/test_adjust_hooks_copilot.py` gained four cases, all written red-first:

1. Two manifest entries resolved through the fallback branch on one event — both survive.
2. The same collision resolved through the primary (`hooks.json`) branch — both survive.
3. A manifest entry naming a script in a four-script skill — that script is wired, not
   whichever sorts first.
4. A glob fallback with no named script and more than one candidate — refuses, naming all four.

The pre-existing single-entry, single-script regression test
(`test_copilot_session_start_wires_drift_notice_not_session_tracking`) is unchanged and still
passes, since every Copilot project today depends on that shape.

Mutation-checked by hand: reverting the fallback-branch append fix fails case 1 only; reverting
the primary-branch append fix fails case 2 only; reverting the script-name fix fails cases 3 and
4. Restoring each fix returns the suite to green.

## Not covered

Whether Copilot hooks belong under `.github/hooks/` or `.copilot/config.json` is a separate,
open question — untouched here. No new manifest entries were wired; `context-enrichment` and
`task-checkpoint` remain for #147 and #141 to land, now that the adjuster accumulates and
honours the manifest's script name correctly.

## Migration

None. Existing single-entry, single-script Copilot projects see identical output.
