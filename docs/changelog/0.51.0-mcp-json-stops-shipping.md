# 0.51.0 — `.mcp.json` stops shipping

## The defect

`.mcp.json` was tracked, and `.claude-plugin/plugin.json` carries no file allowlist — every
tracked file is part of the plugin payload. The tracked copy carried `cwd` pinned to the
maintainer's checkout and a hand-added `hermes` server pointing at
`/Users/arasz/.local/bin/hermes`. Claude Code loads a plugin's `.mcp.json` at **user** scope,
so installing ai-badger configured two permanently-broken user-global MCP servers for every
installer, in every project they opened ([#173](https://github.com/Arasz/ai-badger/issues/173)).

It was also the precise overreach [ADR-0014](../adr/0014-mcp-support-is-configuration-not-retrieval.md)
names as a rule — *ai-badger proposes user-global configuration; it never writes it* —
committed by ai-badger itself. This entry implements that ADR's decision 6 in isolation; the
larger MCP-catalog rebuild it also decides (a per-stack `mcp/` directory, retiring
`external-tools.json`) is separate follow-up work.

A second copy of the same defect was found alongside it: `.claude/settings.json.bak-20260727-162318`,
a stray `config_guard.write_with_backup` safety copy, was also tracked and also carried the
maintainer's absolute path. Both are now untracked.

## Why untracking, not just portable paths

[0.28.0](0.28.0-mcp-user-tool-paths.md) rewrote a bare command to `${HOME}`-relative form on the
premise that "`.mcp.json` is committed, and `${HOME}` resolves per machine, which an absolute
path would not." That premise covers `command`, never `cwd`:
[0.32.0](0.32.0-defects-found-by-a-real-refresh.md) already established that `${CLAUDE_PROJECT_DIR}`
expansion is documented for `command`, `args`, `env`, `url` and `headers` — **not** `cwd`, and
that omitting it is equally undocumented. There is no portable spelling for `cwd`, so a tracked
project `.mcp.json` cannot avoid carrying a real absolute path; the fix is to stop shipping the
file, not to keep looking for a placeholder that does not exist.

## What changed

- `.mcp.json` is untracked and gitignored; `.mcp.json.example` is committed in its place, with a
  placeholder `cwd` and the `hermes` command written bare (`"hermes"`, resolved on `PATH`)
  instead of hardcoded. `CONTRIBUTING.md` tells a contributor to `cp .mcp.json.example .mcp.json`
  and fill in their own checkout path.
- `.claude/settings.json.bak-20260727-162318` is deleted from tracking; `.claude/*.bak-*` is
  gitignored so a future `write_with_backup` copy cannot repeat this by accident.
- `gates/shipped_paths_guard.py` is new: it fails when a `/Users/…`, `/home/…` or `C:\Users\…`
  path appears in a tracked file, scoped to what a real leak looks like (a path-shaped segment,
  not a placeholder) rather than to a fixed username, so it would have caught this on any
  contributor's machine, not only this one. `docs/` and root `*.md` are exempt — a changelog
  entry legitimately quotes a real leaked path as the record of an incident, this one included —
  and so is `tests/`, which fabricates paths like `/Users/foo/...` on purpose to exercise
  path-handling code. Wired into `.pre-commit-config.yaml`, `.lefthook/pre-push/verify.sh` (lane
  `paths`, in the always-run set alongside `docs`/`deps`/`release`) and
  `.github/workflows/pylint.yml`.

## Behaviour changes worth knowing

Anyone who relied on this repository's own `.mcp.json` for `code-review-graph` or `hermes` must
now run `cp .mcp.json.example .mcp.json` and set `cwd` to their own checkout — it is no longer
scaffolded into a fresh clone by `git checkout` alone. Nothing else changes: `generate_mcp_json`
still writes a *scaffolded consumer project's* `.mcp.json` exactly as before, including the
`${HOME}`-relative command rewrite from 0.28.0; only this framework's own copy of the file
stops being tracked.
