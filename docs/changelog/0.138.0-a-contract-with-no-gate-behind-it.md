# 0.138.0 — a contract with no gate behind it

Reported symptom: running the `task` skill, subagents "seem to not follow instructions", and
**no worktree isolation happens unless the prompt says so**.

The second half was exactly right, and the reason is that per-agent worktree isolation was
enforced at none of the three layers this framework uses for every other invariant:

| Layer | Model lanes | Worktree isolation |
|---|---|---|
| Always-loaded discovery file | "Agent delegation" section | 0 mentions of "worktree" in CLAUDE.md **or** HERMES.md |
| Skill prose | `task/SKILL.md:82`, `prompting-rules.md:29-48` | present |
| Hook that can veto | `dispatch_gate_hook.py` | **none** |

`dispatch_gate_hook.decide()` returned as soon as it found a `model` and never read
`isolation`. It is the only script wired to `matcher: "Agent"`. The two guards under
`worktree-agent-isolation` match `Bash` and `Edit|Write|MultiEdit|NotebookEdit` — neither fires on dispatch.

The contract itself was not new: `prompting-rules.md:43` already said *"Dispatch using your
agent tool's native isolation rather than hand-made worktrees."* Nothing checked it.

## The gate fires under parallelism, not on every write

A literal reading of *"mandatory per agent at every depth"* would deny every write-capable
dispatch, including the lone sequential subagent making a small edit. That gate would be
noisy enough to get switched off, and a gate that is off enforces nothing. It now denies only
when another lane from the same session is already live — which is when sharing a tree
actually costs you: shared build output, one agent compiling against another's half-applied
edit, and no green run that says anything about its own change.

Read-only lanes are exempt, **derived from `disallowedTools` frontmatter** rather than a
persona list that would drift the moment someone adds a lane and forgets this file.

`architect` is not exempt. It disallows `Edit`/`MultiEdit`/`NotebookEdit` but keeps `Write`,
so it can still drop a file into a shared tree and break a sibling's build. Read-only means
*all* of the write tools are disallowed, not any of them — a mutation that relaxed `all` to
`any` survived the first version of the suite and is pinned now.

## What was tried and cut

A machine-wide live-session count, sweeping `/tmp/cc-socks` the way
`blast_radius_kill_guard` does. It reads **6 on an idle machine**, and the sockets carry no
`cwd`, so sessions in unrelated repositories count too. The gate would have denied every
unisolated write dispatch forever — the over-denial failure, arriving before the feature even
shipped. Two sessions colliding in one checkout is a real but different harm, already covered
by `cross_worktree_dirty_warning` and by the task skill giving each task its own worktree.

## The window, and the number nobody measured

`dispatch_ledger` is append-only with a time window rather than `PreToolUse`/`PostToolUse`
pairing. Pairing would track an agent's real lifetime, but it depends on `PostToolUse` firing
for `Agent`, which is unverified — and a missed pair leaves a stale entry that wedges the gate
closed for every later dispatch. A window ages out on its own. It still catches fan-out
because parallel dispatch is *expressed* as several `Agent` calls in one assistant message,
so siblings land milliseconds apart.

`DEFAULT_WINDOW_SECONDS = 90.0` is an estimate, and is labelled as one in the source. It
stands in for "is that agent still running", which only a pairing could answer exactly. Too
short misses a live sibling; too long denies a dispatch whose sibling already finished — and
that costs one retry carrying `isolation="worktree"`, which was the right call anyway. If
`Agent` turns out to fire `PostToolUse` reliably, releasing the entry there makes the window a
fallback and the number stops mattering.

## Still open: Hermes

Under Hermes not even the model gate runs — `ai_badger_hooks` registers exactly one
`pre_tool_call`, the memory-first gate. The `dispatch-gate` exemption in `tooling/validate.py`
justifies this with a premise that does not distinguish Hermes from Claude: *"Hermes has no
custom-agent files (support.json customAgents supported=false)"*. `support.json` records that
same flag for **claude**, which is gated regardless, resolving `.claude/agents/*.md` lanes the
framework itself scaffolds.

That kills the reason, not necessarily the conclusion — the second clause, that Hermes
subagent roles carry no per-dispatch model parameter, may well hold. Deciding needs an
observed `delegate_task` payload from a running Hermes, which this change does not have. The
two tests that prove the gap are kept as `strict=True` xfails rather than deleted: the finding
is real and measured, and the fix waits on evidence.

## Verification

Every gate here was watched going red for the defect it exists to catch, and the ones that
could not are gone (see below). Fourteen mutants before review, each reverted after confirming
the suite caught it — including the two that found real gaps: `any` vs `all` on the write-tool
check, and a shared ledger letting one test's dispatch count as the next test's sibling.

## What review found that the suite could not

An independent `code-reviewer` pass returned two blockers, both reproduced here before being
acted on. Neither was visible to a green suite and a green CI, which is the point.

**A denied dispatch was recorded as a live lane.** `record` ran before the verdict, so every
refusal left a phantom occupant that nothing removed and the count only grew. Measured:
allow, deny, then two *lone* dispatches denied in turn, told "3 agent lanes are live" and "4
agent lanes are live" when one lane existed. That is precisely the noise the parallelism-only
ruling was chosen to avoid, and the deny text stated a number that was false. Only a dispatch
that will actually enter the shared tree is recorded now — which excludes an isolated lane
(own worktree) and a denied one (never starts).

**`record` was not append-only, despite the docstring saying so.** It was a
read-modify-write, which drops entries under concurrent hook processes — the exact fan-out
the ledger exists to see. Measured 7 of 8 surviving on one run and 8 of 8 on the next two, so
the gate was an intermittent coin flip rather than a consistent failure; a deterministic
interleave loses an entry every time. Now one `O_APPEND` write per dispatch, with the
file-rewriting prune moved off the hot path behind a 500-entry threshold.

**Built-in and plugin agents were treated as writers.** `Explore` and `Plan` own no lane
file, so a parallel `Explore` fan-out — the most idiomatic parallel dispatch in this harness
— was denied and told to take a git worktree per read-only search. Gating now needs positive
proof that a lane writes, which only a lane file gives; unknown types still count as
occupants for a writer arriving beside them.

**A test that could not fail.** `test_a_broken_ledger_does_not_block` pointed `LEDGER_DIR` at
a missing directory and called it unreadable — but `record` creates the directory, and its
single dispatch was allowed on `lanes == 1` regardless. Deleting its setup line left it
green. It now records a real sibling and makes the ledger genuinely unreadable.

Four more surviving mutants are closed with tests: an unsanitised `_safe_session` (path
traversal out of `LEDGER_DIR`), a dropped malformed-line guard, `WRITE_TOOLS` missing
`NotebookEdit` — which because the check is `all` makes the exemption *more* permissive — and
`_entries` catching only `OSError` when `UnicodeDecodeError` is a `ValueError`. Two smaller
fixes came with them: entries stamped ahead of `now` (a backward clock step) were counted
forever, falsifying the claim that a window cannot wedge; and a newline in a `tool_use_id`
could forge extra entries.
