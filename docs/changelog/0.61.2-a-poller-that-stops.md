# 0.61.2 — The usage-limit poller stops

`poll_limit.py`'s `run_forever` was `while True:` with no wall-clock cap, no liveness check and
no parent check. `session_start_hook.py` launches one on every Claude Code session start, so
every session in every checkout left a daemon behind that ran until the machine rebooted.

Ten were found alive at once on one machine, aged 17 to 21 hours. Six belonged to `/private/tmp`
worktrees created for a previous day's pull requests; one of those had had its own script
deleted out from under it and was still running. `already_running()` guards via a PID file under
each checkout's own data directory, so it prevented a second poller per tree and did nothing
about the tenth tree.

The framework already states the rule this broke. From `owner-gate-review`'s SKILL.md, about its
review watch:

> The cap is mandatory: a watch with no stopping condition is a loop nobody can answer "what ends
> this?" for, and it outlives the session that started it.

## What changed

`run_forever` now has two stopping conditions.

**A wall-clock cap.** `--max-hours`, default 12, hard-ceilinged at 12 by `bounded_max_hours()` so
no caller can restore the unbounded loop. 12 hours because a usage limit can take hours to reset,
and because it is the ceiling `auto-wm` already uses for the same kind of guard.

**Nothing left to resume.** The poller exists to resume unfinished tasks when a limit lifts. After
three consecutive polls with no unfinished task in tracking, it can never do anything again, and
it exits saying so.

It also removes its PID file on the way out, so the next poller does not have to decide whether a
stale PID is alive.

## Consequences

An idle machine now ends up with no poller instead of one per checkout. `resume_cron.py` already
returns early when nothing is stalled, so a bounded poller is not replaced by a busier cron —
this only removes accumulation.

This does not stop a poller starting; a session start still launches one, correctly. It stops one
outliving the session by a day.

## A latent bug surfaced by testing it

`run_forever` had no test, because an infinite loop is not testable. Writing one exposed that
`already_running(pid_file=PID_FILE)` and the new `_has_unfinished_task` bound their module
constants as **default arguments**, frozen at import — so reassigning `poll_limit.PID_FILE` or
`PROJECT_ROOT` had no effect on them. Invisible while nothing reassigned those constants, and it
would have made any future test of this path quietly wrong. Both now resolve at call time.

Seven tests added, none changed. Suite 2553 → 2560.
