# A build is not a dotnet

`_auto_tags` in `mcp_index.py` guessed a *technology* from a name substring, not just an
*action*. The clearest case: anything containing `build` was tagged `dotnet`, so this repo's own
index carried `code-review-graph:build_or_update_graph_tool -> tags=['build', 'dotnet']` — a
knowledge-graph builder for a Python/JavaScript codebase, tagged .NET. `tags` is a ×2-weighted
BM25 field, second only to the tool's name, so a wrong tag doesn't sit inertly in a file: it makes
the tool retrievable by a query about the wrong stack, with more weight than the tool's own intent
text gets.

## What was actually guessing technology

Auditing every rule in the function surfaced three, not one:

1. **`"build" in name or "solution" in name` → `["dotnet", "build"]`.** `build` genuinely tells you
   an action; `dotnet` is a guessed technology no substring can safely claim. `solution` alone was
   worse — it fired on anything that merely *mentions* a solution, not just a tool that builds one:
   `rider:get_solution_projects`, which only lists projects, came out tagged `build` *and* `dotnet`.
2. **`"sql"/"database"/"schema"/"db"` (any) → `["database", "sql"]` together.** Rider's database
   tooling isn't SQL-exclusive — it connects to non-relational engines too — so `"database"` or
   `"schema"` in a name is not evidence of `"sql"` specifically. `"sql"` in the name is a tight
   enough alias to keep, and now only that keyword adds the `sql` tag.
3. **The tracing/OpenTelemetry rule** matched `span`, `trace`, `log`, `otel`, or a bare `service`
   (with `map` excluded to avoid double-firing with the explicit `service_map` case). This repo's
   own index had already been bitten by exactly the substring collision ADR-0012 fixed for the
   BM25 tokenizer once (`log` inside *login*) — here it was `log` inside
   `playwright:browser_handle_dialog` (*dia-**log***), tagging a dialog-handling tool
   `opentelemetry` and `tracing`. Bare `service` is even less safe — a dependency-injection
   service, a web service, anything. Only `span`, `otel`, and the literal `service_map` compound
   survive as tight aliases.

Action-inferring rules (`run`, `search`, `read`, `write`, `refactor`, `diagnostic`, `terminal`,
`navigation`, …) and the server-level rule (`playwright`/`browser` in the *server* name → `browser`)
are untouched — a name telling you what a tool *does* is a different claim than a name telling you
what *stack* it belongs to, and only the second one was overreaching.

## Re-indexing this repo, tag by tag

Isolated to the heuristic alone (same 98 tools, same intents — only `_auto_tags` differs), 11 of
98 tools changed. Two of those, read against the tool's own recorded `intent`, turned out to
deserve their old tags after all and were restored by hand rather than left to the heuristic:
`rider:build_solution` (`intent`: "Build the currently opened solution") keeps `[build, dotnet]`,
and `rider:get_services` / `rider:get_log_records` — whose intents say, respectively, "list of all
discovered services **from OpenTelemetry data**" and "log records **from OpenTelemetry
services**" — keep `[opentelemetry, tracing]` (the latter gains `diagnostic` too, on the same
reading). That is manual curation grounded in evidence already in the index, not a heuristic
guessing again.

The net change, 8 of 98 tools:

| tool | before | after |
|---|---|---|
| `code-review-graph:build_or_update_graph_tool` | `build, dotnet` | `build` |
| `rider:get_solution_projects` | `build, dotnet` | `read` |
| `rider:list_database_connections` | `database, sql` | `database` |
| `rider:list_database_schemas` | `database, sql` | `database` |
| `rider:list_schema_objects` | `database, sql` | `database` |
| `rider:get_database_object_description` | `database, sql` | `database` |
| `rider:list_schema_object_kinds` | `database, sql` | `database` |
| `rider:get_log_records` | `opentelemetry, tracing` | `diagnostic, opentelemetry, tracing` |
| `playwright:browser_handle_dialog` | `browser, opentelemetry, tracing` | `browser` |

`mcp-index validate` still passes clean (98/98) after the hand curation above; three tools
(`get_solution_projects`, `get_services`, `get_log_records`) briefly dropped to `general` before
that pass and would have failed validation left alone — exactly the "needs curation" signal the
command exists to raise.

## Retrieval eval, before and after

Run on all three fixture sets against the re-tagged index (`tooling/retrieval_eval.py`):

| set (n) | recall@1 before → after | recall@3 | false fire before → after |
|---|---|---|---|
| standard (58) | 0.930 → 0.907 | 1.000 → 1.000 | 0.267 → 0.267 |
| hard (70) | 0.442 → 0.442 | 0.481 → 0.481 | 0.333 → 0.333 |
| long (48) | 0.938 → **0.969** | 0.969 → 0.969 | 0.000 → 0.062 |

Three fixtures moved, all explained by the same mechanism — tags are a weighted BM25 field, so
removing wrong ones shifts the document-frequency (and therefore IDF) of every remaining term, not
just the ones on the tool that changed:

- **A real fix became visible**: the long-set embedded request *"...can you build the solution and
  tell me whether anything is broken..."* used to rank `rider:get_solution_projects` above
  `rider:build_solution` (both carried `build`+`dotnet`); with the false tag gone, `build_solution`
  now ranks first — the exact contamination the issue described, caught by the eval it asked for.
- **A false fire appeared** on a long-set negative ("...my brain quietly leaves the **building**").
  The tokenizer stems *building* → *build* by design (same rule that already prevents *tests*/`ts`
  collisions), and a coincidental second stem match (*opened*/*open* from the tool's own intent
  text) pushed coverage just over the gate threshold. It fires now because removing the bogus
  `build` tag from `get_solution_projects` makes `build` a rarer, more discriminating term overall
  — the same IDF math that produced the fix above.
- **One standard-set tie flipped** (`read_file` vs. `get_file_text_by_path` for *"read the contents
  of this file"*): still `hit@3`, no longer `hit@1`. Same IDF-shift mechanism, no tags on either
  tool changed.

The hard set was unaffected at every metric — none of its fixtures touch the tools whose tags
moved.

## `mcp-tags.json`'s description was stale

ADR-0014 §4: `mcp-tags.json` survives "as vocabulary for grouping, display and stack inference,
never as a matching key," but its own `description` field still said tags were "used by... hooks
for tool recommendation." Corrected to describe what ADR-0012 and ADR-0014 actually decided.

Fixes #171.
