# 0.103.0 — the run_git invariant reaches the code that violates it

`tests/test_git_invocation.py` enforced "every git invocation goes through `badger_lib.run_git`"
over `CODE_ROOTS = ("engine", "tooling", "gates")`. Those three directories hold **zero** raw git
calls. All eight live ones were outside the scanned scope, under `features/` and `.lefthook/` —
so the test that exists to catch the 0.95.0 defect could not have caught it anywhere it occurred.

## What the scope now covers

`CODE_ROOTS` gains `features` and `.lefthook`. A raw `subprocess.run(["git", ...])` added to
either — in list, tuple or `Popen` form — now fails the test.

A shipped skill script installs into a project at `.ai-badger/skills/<skill>/scripts/` with no
framework checkout to import `badger_lib` from, so "convert to `run_git`" is not available to it.
The scanner therefore accepts a second compliant spelling: a raw spawn that passes
`env=git_env(...)`. `env=os.environ`, `env=dict(os.environ)` and `env=<any other builder>` are
still strays — an `env=` keyword on its own proves nothing.

## What changed at the call sites

| Site | Decision |
| --- | --- |
| `.lefthook/pre-push/risk_mode.py` | `badger_lib.run_git` — repo-local, `engine/` is always adjacent |
| `features/common/skills/task/scripts/tracker_lib.py` | local `git_env()` |
| `features/common/skills/task/scripts/task_tracker.py` | `lib.git_env()` (it already imports `tracker_lib`) |
| `features/common/skills/commit-reminder/scripts/commit_reminder.py` | local `git_env()` |
| `features/common/skills/ai-raccoon-memory/scripts/memory_first_gate.py` | local `git_env()` |
| `features/common/skills/welcome-ai-badger/scripts/{scaffold,detect}.py` | exempt, `TODO(lane W1)` |

`test_every_standalone_git_env_drops_the_same_names` loads each standalone copy and asserts it
drops every name in `badger_lib.GIT_LOCATION_ENV`, so a name added to the original fails the
copies rather than leaving them one short. The copies are **discovered** by walking `CODE_ROOTS`
for a top-level `git_env`, not listed: the scanner clears a spawn on that name alone, so a
hand-written list would let a new module define a `git_env` that strips nothing and pass both
checks. A planted module doing exactly that fails the discovered check.

## What this does not cover

`tracker_lib.spawn_detached` takes `argv` as a variable and passes no `env`, so an AST scanner
keyed on a literal `["git", ...]` cannot see through it. No caller routes git through it today
(`poll_limit.py` passes `CLAUDE_BIN`, `session_start_hook.py` passes `python3`), but one that did
would inherit the environment unfiltered and go unreported.

## The break that was live

`verify.sh` unsets eight variables before any lane runs, but `GIT_LOCATION_ENV` names nine, and
`GIT_COMMON_DIR` is not among the eight. Measured against a linked worktree with an unrelated
repository's `GIT_COMMON_DIR` exported:

- `risk_mode.py` printed nothing instead of the task id — every `--risk` task silently reverting
  to the full gate.
- `commit_reminder.uncommitted_files()` returned `[]` — the reminder reports a clean tree.
- `memory_first_gate._main_checkout_basename()` returned the *other* repository's basename, so
  memory writes address the wrong bank.

Under `GIT_DIR` and `GIT_WORK_TREE` the same three answered with the other repository's files.
Every one of them now answers for the directory it was given. Whether a hook run ever met a set
`GIT_COMMON_DIR` in practice is not established here — what is established is that the guard was
one `unset` line in a file none of these scripts control.

`verify.sh`'s unset list is still short by five names (`GIT_COMMON_DIR`,
`GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_NAMESPACE`,
`GIT_CEILING_DIRECTORIES`); that file was out of scope for this change.
