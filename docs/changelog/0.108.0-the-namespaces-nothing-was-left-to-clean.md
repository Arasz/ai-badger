# 0.108.0 — the namespaces nothing was left to clean

`~/.hermes/skills/<project>/` is a directory of symlinks into that project's
`.ai-badger/skills/`, one namespace per project (ADR-0003). `relink_hermes_skills` keeps each
namespace honest from the inside: on every scaffold it drops the links whose skill this project
no longer holds. Nothing looked at the namespace from the outside, so nothing ever noticed a
namespace whose entire target tree had been deleted — a project renamed, a throwaway scaffold
into a `mktemp` directory, a checkout thrown away.

That failure mode is unreachable from the code, too. The project is gone; `den-refresh` cannot
be run there again; no future scaffold will ever visit its namespace. It sits in the user's home
directory accumulating dead links with no path back to a program that would remove them.

It was found by running `den-refresh` against a real machine, not by a test. Every test in this
repo patches `HOME` — correctly, and the suite is structurally incapable of seeing what the real
one holds.

## What is reported

A namespace is orphaned when **every symlink ai-badger placed in it is dangling**. One reachable
link means the project is still on disk, and its own relink owns whatever is stale inside — that
is the existing mechanism, not this one. A namespace with no ai-badger link at all is not a
namespace of ours; `~/.hermes/skills/` also holds Hermes's own category directories, and those
are never listed.

```json
"hermesNamespaces": [
  { "path": "<home>/.hermes/skills/<project>", "links": 21, "kept": 0,
    "target": "<somewhere>/<project>/.ai-badger/skills",
    "status": "reported",
    "detail": "... holds 21 link(s) into ..., which no longer exists; remove them with: den-refresh --prune-namespaces" }
]
```

`kept` counts the entries ai-badger did not place; a non-zero `kept` means the directory itself
outlives the prune.

The sweep covers **every** project's namespace, not just the one being refreshed. That is the
surprising choice and it is deliberate: scoping it to the current project would make the feature
a no-op, because the current project's tree is on disk by definition.

## What is never touched

`--prune-namespaces` removes only the links ai-badger placed, identified by the shape it writes
them in — a symlink whose target path is `<something>/.ai-badger/skills/<name>`, read rather
than resolved, because the links this looks for are exactly the ones that resolve to nothing.
The directory itself goes only when removing those links empties it.

That distinction is not academic. A read-only survey of the real `~/.hermes/skills` on
2026-08-08 found Hermes-authored skills living **inside** ai-badger namespaces — `ai-badger`
holds `agent-skill-discovery` and `framework-development`, `AiRaccoon` holds `spec-elicitation`
— alongside 47 directories holding no ai-badger link at all, against 5 that do. Those 47 are
Hermes's own (`react`, `devops`, `uncategorized`, and a `software-development` with 103 entries
in it), and the rule must never reach them. An earlier draft of this rule demanded a
directory of nothing but our links; it would have been safe and would have missed the shape a
real namespace actually has.

## Reporting is the default

`--prune-cache` set the shape and this follows it: the default names what it found and deletes
nothing, an explicit flag acts, and `den-refresh`'s `SKILL.md` step 3c tells the agent to present
the report and **ask** before passing the flag. A namespace can dangle because its drive is not
mounted right now. Deleting a user's Hermes wiring during an ordinary refresh is not something an
agent gets to decide.

## The guards, each one watched failing

Every rule above was mutated and the tests that name it went red — the
`prove-the-check-fails` invariant applied to the safety properties, not just to the happy path:

| break | what went red |
|---|---|
| a live link no longer disqualifies the directory | 3 tests |
| the link-shape check accepts any target | a Hermes category is pruned |
| a non-link entry is no longer tolerated | 6 tests |
| a symlinked namespace is treated as ours | the prune reaches through the link |
| the prune `rmtree`s instead of unlinking | a Hermes-authored skill is deleted |
| reporting acts anyway | 4 tests |
| the report stops naming the flag | the finding has no next step |

Two guards survived the first pass and so were not checks. One — an `is_symlink()` pre-check
that `readlink`'s own `OSError` already covered — was deleted. The other had a test that passed
with or without it, because the linked directory was empty; it now points at a directory of
dangling links, and the guard is provable.
