# 0.81.0 — Project-local invariants

Until now a project that wanted a rule of its own inside `CLAUDE.md`'s "Non-negotiable
invariants" section had one escape hatch: an `ai-badger:keep-start`/`keep-end` block. That
workaround renders at the end of the file, where agents rarely read, and it is not
discoverable as an invariant — nothing in the invariants section points at it, and
`config.exclude.invariants` cannot touch it.

- **Project-owned invariants**: any `*.md` under the scaffolded project's
  `.ai-badger/invariants/local/` is demoted and rendered into the invariants section of
  `CLAUDE.md`/`HERMES.md` — **after** all framework invariants, in sorted filename order.
  Files start with a single `# ` heading (it renders as `###` inside the section) and are
  project-owned: never copied into the framework catalog, never recorded in the manifest,
  never pruned, never overwritten.
- **Runtime surfacing**: the scaffold notes "rendered N project-local invariant(s) from
  .ai-badger/invariants/local/ — edit or delete the files to change them", so a project
  knows the convention is live. A local file that shares a name with a delivered invariant
  (e.g. `local/tdd-mandatory.md`) is reported: both render, and
  `config.exclude.invariants` is the way to drop the delivered one.
- **No catalog footprint**: project-local invariants are not index items — no index rebuild,
  no stack ownership, no exclusion by name (docs/authoring-a-feature.md).

**What a consumer must know:** create `.ai-badger/invariants/local/` and drop in `*.md`
files starting with a single `#`; the content propagates on the next scaffold run or
`den-refresh`. `feed-badger` will list the files as project additions — classify them as
project-specific, not framework contributions.
