# 0.28.0 — MCP servers that never started

## The problem

A scaffolded `.mcp.json` wrote each server's `command` verbatim. A catalog or project entry
naming a bare executable produced:

```json
{ "command": "cwm-roslyn-navigator", "cwd": "..." }
```

The host resolves that against **its own** PATH. .NET global tools install into
`~/.dotnet/tools`, which is on PATH only when a login shell profile puts it there. Launched
from a GUI or any non-login context, every such server failed to start — silently. On the
machine this was reported from that was seven servers at once: `cwm-roslyn-navigator`,
`dotnet-mcp`, `glider`, `glider-trace`, `ilspycmd`, `dotnet-scaffold`, `playwright`.

Nothing said so. The agent simply had fewer tools than its config claimed.

## What changed

When a server's `command` is a bare executable name that is found in a known user tool
directory, `.mcp.json` now gets the `${HOME}`-relative form instead:

```json
{ "command": "${HOME}/.dotnet/tools/cwm-roslyn-navigator" }
```

Claude Code expands `${VAR}` and `${VAR:-default}` in `.mcp.json`, including in `command`. The
rewrite therefore sidesteps PATH entirely while staying portable — `.mcp.json` is committed,
and `${HOME}` resolves per machine, which an absolute path would not.

The probed directories are the module constant `USER_TOOL_DIRS`, checked in order:
`~/.dotnet/tools`, then `~/.local/bin`. A command is only rewritten when the file actually
exists there and is executable.

Left alone: anything containing `/`, anything already starting with `${`, anything with
arguments baked into the string, and — deliberately — anything that resolves elsewhere on
PATH. `python3`, `node`, `npx` and `uvx` are system tools and stay bare and portable.

## Unresolvable commands are now reported

A bare command that resolves nowhere — not on PATH, not in a user tool directory — produces a
scaffold note naming the server, the command, and the consequence. A server that cannot start
is the bug class this release exists to fix; it should not be possible to introduce a fresh
one without being told.

## Why not `env`

Injecting `PATH` through the server's `env` block was the obvious alternative and was rejected.
Whether `env` merges into the inherited environment or replaces it is undocumented, and whether
`${PATH}` may self-reference inside an `env` entry that sets `PATH` is also undocumented. Two
unverified behaviours is not a foundation for a framework default. `${VAR}` expansion in
`command` is documented, so that is what this uses.

## Scope

`.mcp.json` only. `.github/copilot/mcp-config.json` uses Copilot's `${input:}` / `${env:}`
syntax and has no documented bare `${VAR}` expansion; `~/.claude/settings.json` and
`~/.hermes/config.yaml` are per-machine files whose expansion behaviour is likewise
undocumented. Rewriting there would trade a PATH-dependent command for a literal path that may
never expand — the same unverified-behaviour objection that ruled out `env`.

## Upgrading

Re-scaffold (`welcome-ai-badger`, or `den-refresh` on an existing project). Existing
`.mcp.json` entries are merged, not replaced, so a hand-written command is untouched; the
rewrite applies to servers this framework generates.
