# 0.50.0 — the coverage gate stops scaling with query length

The MCP retrieval gate suppressed correct matches as the query got longer, and real user
messages are long. The hook passes the **entire** user prompt to `find_relevant_tools`, so this
was most turns.

```
coverage = Σ idf(matched terms) / Σ idf(all query terms)
```

The denominator ran over every term in the query. A sentence carries a dozen words no tool
document contains; each one adds to the denominator and to nothing else, so coverage fell as
roughly `1/len(query)` regardless of how good the match was. Ranking was never affected — the
right tool still sorted first — only the decision to show it.

| query | terms | top result | coverage | fires? |
|---|---|---|---|---|
| `take a screenshot of the page` | 3 | `playwright:browser_take_screenshot` | 1.000 | yes |
| the same request inside a 19-term sentence | 19 | `playwright:browser_take_screenshot` | **0.1435** | **no** |

Since #147 wired `context-enrichment` for Claude and Copilot in this same version, the feature
was close to inert in production the moment it started running.

## What changed

The denominator now runs over the **six highest-idf query terms** instead of all of them, and
coverage is clipped to 1. Past six terms, further padding cannot move coverage at all: the
query above scores 0.3855 capped, and still 0.3855 with twenty more junk words appended, where
uncapped it decays 0.1435 → 0.0640.

The three ungated near-miss rankers — telemetry on both hook paths, and the runner's coverage
margin — take the same cap. A `gate` record whose coverage was normalised differently from the
gate would assert a comparison that never happened, which is the exact defect class the
`gate`/`no_terms` split exists to prevent.

## The fixtures came first, deliberately

`features/common/retrieval/eval/mcp_queries_long.jsonl` — 48 fixtures, mean **15.3 tokens**
(30.6 raw words, range 10–21), 32 positives with the request embedded in surrounding context
and 16 negatives of the same length that want nothing from a tool. Written and committed
**before** any candidate was evaluated, and not touched afterwards.

That ordering is the point. Both existing sets average under five tokens, which is why nothing
in the repository could distinguish the candidates below — and why an earlier round of work on
this same matcher reached a confident, wrong "the matcher is saturated" conclusion. Fixtures
written alongside a fix are fixtures the fix passes.

## The candidates, measured

All at threshold 0.20 against the real 98-tool index. The authored set is the control: it sits
at recall@3 = 1.000, so it can only move down.

| candidate | easy r@3 | easy FF | hard r@3 | hard FF | long r@3 | long FF | long zero-result |
|---|---|---|---|---|---|---|---|
| baseline (uncapped) | 1.000 | 0.267 | 0.481 | 0.333 | 0.469 | 0.000 | **16 / 32** |
| top-k idf, numerator *and* denominator | 1.000 | 0.267 | 0.481 | 0.333 | **0.000** | 0.000 | 32 / 32 |
| **cap the denominator at k=6** | **1.000** | **0.267** | **0.481** | **0.333** | **0.969** | **0.000** | **0** |
| sliding window, w=8 | 1.000 | 0.267 | 0.481 | 0.333 | 0.969 | 0.000 | 0 |
| denominator over in-corpus terms only | 1.000 | 0.267 | 0.538 | 0.611 | 1.000 | **0.875** | 0 |

**The issue's leading suggestion is degenerate, and that is the most useful thing measured
here.** Normalising over the top-k highest-idf terms — restricting the numerator to them too —
returns 0.000 on every long positive at every threshold. Because
`idf(t) = log(1 + (N − df + 0.5)/(df + 0.5))`, a term the corpus has never seen carries the
*highest* idf of all: 5.2883 here, against 4.1897 for the rarest term that actually exists. The
"most informative" terms of a long sentence are exactly the ones no document can contain, so a
numerator restricted to them is empty by construction. Capping only the denominator dodges this,
because the numerator still sums every matched term against a fixed budget.

Normalising over only the terms the corpus knows (our own fifth candidate) fires on **87.5%** of
the long negatives, and stays there up to threshold 0.50 — dropping out-of-vocabulary terms lets
any incidental word like "review" or "file" account for the whole query.

The sliding window ties the chosen fix exactly: identical returned lists on 58/58 easy and 70/70
hard fixtures, identical correctness on all 48 long ones. It was rejected on cost and semantics
rather than accuracy — it needs 8.3× the coverage evaluations on the long set (a max over
windows *per document*, versus one partial sort per query), it makes coverage depend on word
order, and it leaves each document maximising over a different denominator, so the
`(-score, -coverage, doc_id)` tie-break would be comparing incommensurable ratios.

Span extraction was not pursued. It moves the problem into a host-dependent extraction step with
its own correctness story, and the measurement bounds what it could buy: the chosen fix already
recovers 31 of 32 long positives, so the entire remaining headroom is one fixture.

## Significance

Exact McNemar against the baseline on the same fixtures, correctness being "positives hit@3,
negatives stay silent":

| set | b (fix corrects) | c (fix breaks) | exact p |
|---|---|---|---|
| easy (58) | 0 | 0 | 1.0 |
| hard (70) | 0 | 0 | 1.0 |
| long (48) | **16** | **0** | **3.05e-05** |

The 16 are every long positive the gate used to suppress, including the issue's own screenshot
reproduction. No fixture in any set moved the other way.

False fire is unchanged in **every** length bucket, which is the bar a fix that merely moved the
problem would fail:

| tokens | negatives | false fire before | after |
|---|---|---|---|
| 0–4 | 27 | 0.296 | 0.296 |
| 5–9 | 6 | 0.333 | 0.333 |
| 10–19 | 16 | 0.000 | 0.000 |

## Why the threshold is still 0.20

Not by leaving it alone. `DEFAULT_COVERAGE_THRESHOLD` was derived by sweeping the gate against
the authored set, and it was re-derived here against the new metric. It lands on the same value
for a reason that is algebraic rather than lucky: **six is the longest query in the set the
threshold was derived on**, so at or below the cap the top-six terms *are* every term, the
denominator is the same sum as before, and every control fixture keeps its exact previous
coverage — verified float by float, not one moved. The ceiling above which a true positive
disappears re-derives to **0.2089**, the identical number, so the 0.0089 headroom figure in
`docs/retrieval.md` §4 stands unchanged.

Either side of six is worse on the long set:

| cap | long recall@3 | long false fire | positives returning nothing |
|---|---|---|---|
| 3 | 1.000 | 0.750 | 0 |
| 4 | 1.000 | 0.250 | 0 |
| 5 | 0.969 | 0.125 | 0 |
| **6** | **0.969** | **0.000** | **0** |
| 7 | 0.938 | 0.000 | 2 |
| 8 | 0.906 | 0.000 | 2 |
| 10 | 0.844 | 0.000 | 5 |
| 12 | 0.562 | 0.000 | 13 |

Below six the cap starts admitting long negatives; above it long positives start disappearing
again. Six is the only value with both false fire at 0.000 and no positive returning nothing.

Like the threshold, the cap is a property of *this* index. An out-of-vocabulary term takes the
maximum idf, and a matched term's share of that maximum grows with corpus size —
`idf(df=1)/idf(df=0)` is 0.52 at 4 documents and 0.79 at 98. A much smaller consumer index is a
different measurement, and we have not made it.

## The instrument, which is half the fix

`tooling/retrieval_eval.py` reported one recall number per fixture set. Both shipped sets average
under five tokens, so a gate that held at 4 tokens and collapsed at 15 read as a gate that
worked. Every fixture now carries its tokenized length, and reports carry a `by_query_length`
breakdown — the same four metrics per bucket as `by_class`, plus the bucket's mean, ordered
shortest first, in both the human report and the `--json-out` structure.

The defect was invisible for two releases not because it was subtle, but because nothing in the
instrument was bucketed by the variable it depended on.

## Verified by running

The real Claude/Copilot hook, same payload, before and after:

```
before  {"e": "gate", "o": "playwright:browser_take_screenshot:20.01:0.14,...", "h": "0.2", "r": ""}
after   {"e": "hit",  "o": "playwright:browser_take_screenshot:20.01:0.39,...", "h": "0.2",
         "r": "playwright:browser_take_screenshot"}
```

Same query, same 98 candidates, same threshold, same extracted terms. Only the coverage moved,
0.14 → 0.39, and with it the hook's output from silence to
`[ai-badger] Relevant MCP tools: playwright:browser_take_screenshot (browser)`.

Fixes #165.
