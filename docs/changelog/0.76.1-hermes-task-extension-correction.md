# 0.76.1 — the task skill's Hermes extension told a false story

The task skill's Hermes extension (`extensions/hermes/extension.md`) claimed that
`session_start_hook.py`, `stop_hook.py` and `poll_limit.py` are "NOT scaffolded when `hermes` is
in the agent list" and that Hermes session tracking is "all native, no custom code". Both were
false: the scaffolder copies the whole `scripts/` directory regardless of the agent list (only
`config.exclude` patterns filter), so those scripts land in every project — they are simply
inert under Hermes, which executes Python plugins (`ai_badger_hooks.py`) rather than `hooks.json`,
and that plugin registers no session-tracking hook.

The extension now documents the real behaviour: the scripts are scaffolded-but-inert, the
tracker's token checkpoints are not written automatically under Hermes, and recorded task
numbers stay zero unless recorded by hand. The section title now reads "no wired equivalent"
instead of "Hermes: native".

This follows an evidence-first research record (`docs/work/2026-08-02-hermes-task-tracking.md`)
that verified — 10 measured, 4 read findings — the four task-tracking hooks are Claude-only by
design, every tracked task's checkpoints are all-zero under Hermes, and Hermes's `state.db`
demonstrably stores the per-model and per-subagent token data the tracker never reads. Whether
to wire a Hermes tracking backend (query `state.db`, or plugin hooks from `post_api_request` /
`subagent_stop`) is an open decision, not yet taken.
