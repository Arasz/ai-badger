# 0.23.0 — skill engineering, and the JavaScript that had no tests

**Review:** `docs/reviews/2026-07-26-full-project-review.md`
**Plan:** `docs/plans/2026-07-26-remediation-plan.md` (Wave 5)

The final wave of the remediation plan: the product surface an agent actually reads, and the
two gates written in the one language this repo never tested. Findings F-40 … F-47.

## Fixed

- **F-47 — the only JavaScript in the repo had no tests.** Both `.mjs` scripts are CI gates
  whose logic is regex-driven, in a repo whose first invariant is "TDD is mandatory". They now
  have 21 tests under `tests/js/`, run with `node --test` (built in since Node 18 — no new
  dependency) and wired into CI. They run the scripts as **real subprocesses** against
  throwaway projects, so what is tested is the contract CI depends on: exit code and output.
  Coverage includes required headings, `agent-section` metadata, required and forbidden
  patterns, instruction-set frontmatter and topics, directory contents, warn-without-failing,
  and every drift-rule failure mode. They live in `tests/js/`, not beside the scripts, because
  framework tests never ship inside a scaffolded skill.

- **F-41 — "TDD is mandatory" was the one invariant with no mechanism.** Its siblings each
  have a gate (`release_guard.py`, `version_sync.py --check`, `index_build.py --check`). New
  `scripts/tdd_guard.py` fails when a `.py`/`.mjs` file under `scripts/` or `features/` changed
  and nothing under `tests/` did. It is deliberately a **signal, not a proof** — no machine can
  tell a real test from an empty one — with `[no-tests]` in a commit message as an escape
  hatch that is *printed*, so an unjustified one is visible rather than silent. Catalog JSON
  and documentation do not count as code: those are covered by `validate.py --all` and review.
  It counts untracked files too, since a brand-new script is the most likely thing to lack a
  test and `git diff` never lists one.

- **F-45 — every skill description summarised its workflow.** That is the exact anti-pattern
  `superpowers:writing-skills` warns against: a description is a *dispatch* decision, so it
  must say when to reach for the skill. All eight now lead with "Use when…" and keep the
  trigger phrases a user actually types. `mcp-index`'s no longer embeds an operational
  instruction ("After adding/removing MCP servers, run update…") in the field an agent reads
  to choose between skills.

- **F-43 — the skill told the agent to run `bun`** against `#!/usr/bin/env node` scripts that
  import only `node:fs` and `node:path`. Now `node`, with the runtime contract stated: Node
  18+, no bundler, no dependencies, run from the project root.

- **F-44 — `mcp-index` paths resolved nowhere.** Eight commands used
  `skills/mcp-index/scripts/…`, which is not a path from a project root; they are now anchored
  at `.ai-badger/skills/…`. `author: Hermes Agent` on a **common** skill is corrected to
  `ai-badger`. The namespaced `metadata.hermes` block stays — hermes is a first-class agent
  here, so agent-specific metadata under its own key is legitimate; the authorship claim was
  the part that was wrong.

- **F-46 — ~124 duplicated lines of issue-reporting boilerplate** across `welcome-ai-badger`,
  `den-refresh` and `feed-badger` became one reference,
  `welcome-ai-badger/references/reporting-a-framework-bug.md`. The safety-critical rule —
  **never create an issue without explicit user approval** — is restated in each skill, so it
  survives the reference being absent.

- **F-40 — no `task` extension for copilot**, a first-class agent, while claude/github/hermes
  had 67/93/188 lines. The new one is short and honest about what is structurally different:
  Copilot has no in-session subagent primitive, so the phases run sequentially and the Phase 3
  quality gate is a re-read rather than a second opinion — which is a weaker check, and says
  so. It deliberately does not hardcode a model lineup it cannot verify.

- **F-42 — `auto-wm` described an install that never happened.** The skill said
  `welcome-ai-badger` copies it to `~/.claude/skills/auto-wm/` and merges its settings snippet;
  no script does either. Meanwhile its own "Common mistakes" warned against project files while
  the scaffolder places the skill in the project. Both are now stated as they are: the scripts
  are scaffolded per project and versioned with the framework, the state is machine-wide, and
  registering the hooks in `~/.claude/settings.json` is a one-time manual step with the
  commands written out.

## Behaviour changes worth knowing

- **CI has two new gates.** `node --test "tests/js/*.test.mjs"` and `tdd_guard.py` run on the
  3.10 matrix leg; the TDD guard is skipped on `main`.
- **A code-only PR now fails CI** unless it touches `tests/` or carries `[no-tests]`.
- **Skill descriptions changed**, which is what agents match on when choosing a skill. The
  triggers are preserved; the phrasing leads with the trigger instead of the summary.
- **`auto-wm` requires a manual one-time install step** to actually gate anything. It always
  did — now the skill says so.
