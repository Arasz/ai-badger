# 0.49.0 — a harder retrieval fixture set, and a runner to measure it

Follow-up to issue #140 (the "is there headroom left in the MCP matcher?" research), for the
half of it that was unblocked. [`docs/retrieval.md`](../retrieval.md) already established that
the shipped fixture set — 43 positive queries, 15 negative — is saturated: recall@3 is 1.000,
and mean query↔document token overlap is 0.781, meaning the fixtures are largely written in the
vocabulary of the tools they're meant to find. That reading is unchanged by this release; the
deliverable it calls for is a better fixture set and a way to run it, not a better matcher.

## Fixture repair, first and on its own

`rider:search_regex` and `rider:search_in_files_by_regex` are the same capability exposed twice
by the rider MCP server. The eval fixture for "search using a regex pattern across files" named
only `search_regex`, so the matcher was scored wrong whenever it correctly picked the other one.
Both tools are now accepted; recall@1 on the existing fixture set moves from 0.907 to 0.930 with
no matcher change. A new regression test
(`test_known_duplicate_tools_are_annotated_together`) fails the build if a future fixture
repeats the same single-answer mistake against a known duplicate pair.

## `tooling/retrieval_eval.py`

A checked-in eval runner: point it at any fixture file and any `mcp-tools.json` index and it
reports recall@1, recall@3, false-fire rate, a coverage margin, and — for a fixture set that
tags a `class` — a per-class breakdown, plus every fixture's own hit/miss row. `--json-out`
writes the same numbers as a plain JSON structure two runs can be diffed against. Stdlib only.

ADR-0004's own "100% accuracy on a 16-query spike suite" cited a script in another repo that
could not be run and could not fail (docs/adr/0012). This is what replaces every future ad-hoc
measurement script with one that runs here, under pytest, on demand.

## `mcp_queries_hard.jsonl`

70 fixtures in a file kept separate from the existing `mcp_queries.jsonl`, so the shipped
regression gate is not silently reinterpreted by a harder benchmark:

| class | n | recall@1 | recall@3 | mean overlap |
|---|---|---|---|---|
| paraphrase | 17 | 0.000 | 0.000 | 0.000 |
| user-voice | 15 | 0.200 | 0.333 | 0.229 |
| near-dup | 20 | 1.000 | 1.000 | 0.783 |
| adjacent-negative | 12 | — (false-fire 0.417) | — | n/a |
| inert-negative | 6 | — (false-fire 0.167) | — | n/a |

Overall: recall@1 0.442, recall@3 0.481, false-fire 0.333, coverage margin −0.125 — against the
saturated set's 0.930 / 1.000 / 0.267 / −0.201. The `paraphrase` class's zero overlap is
mechanically enforced by a test, not eyeballed; `near-dup`'s 100% shows the matcher correctly
disambiguating precisely-worded queries against real near-duplicate tools; `paraphrase`'s 0%
shows lexical BM25 has no signal at all once a query shares no token with its answer.

Not done, and said plainly rather than left implicit: harvesting real queries from the debug
log (issue #140's step 2) is blocked on #147 — retrieval has not executed a single query on
Claude Code yet, so there is nothing in the log to harvest. ADR-0013 (the null-result record)
stays on hold for the same reason.
