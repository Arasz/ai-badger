# 0.46.0 — an empty skill list is not an instruction

Reported in [#129](https://github.com/Arasz/ai-badger/issues/129), found while working around
[#128](https://github.com/Arasz/ai-badger/issues/128) (den-refresh cannot be forced, so the
scaffolder has to be called directly — a documented workaround, not something #128 forces; the fix
here stands on its own regardless of how #128 lands).

## What happened

`scaffold.py --skills ""` collapses to an empty list, and an empty list was treated as "this
project asks for no skills" rather than "unchanged". Three sites acted on that collapse:

- `features/claude/adjustments/adjust_skills.py` and `features/copilot/adjustments/adjust_skills.py`
  pruned every discovery symlink under `.claude/skills/` and `.github/skills/` that ai-badger
  owned — both **do** already emit a note for this (landed in `5c32bbd`, present since 0.44.0), so
  the destructive step was loud, just easy to miss among the other notes a run prints.
- `relink_hermes_skills` unlinked every owned entry in `~/.hermes/skills/<project>/` before its
  own "nothing wanted" bail-out, with **no note at all** — invisible to `git status` because that
  namespace lives outside the repo entirely.

## The fix

Two parts:

1. **Recovery at the CLI.** An omitted or explicitly empty `--skills` now means "the set already
   scaffolded", not "none": `scaffold.py` reads it back from `<target>/.ai-badger/manifest.json`
   (via the new `badger_lib.scaffolded_skill_names`, which also strips per-file extension
   provenance rows like `task/extensions/claude/extension.md`) and re-links that. A fresh target
   has no manifest to recover from, so it still scaffolds no skills and exits 0 — the existing
   "onboard with `--skills ""`" test stays honest rather than breaking.
2. **A no-prune guard at every adjustment.** `adjust_skills.py` (claude and copilot) and
   `relink_hermes_skills` now treat an empty skill list as "no evidence the project stopped
   wanting its skills" and leave owned discovery links alone, naming what was left and pointing at
   `config.exclude.skills` as the supported way to decline one. `relink_hermes_skills` also gained
   a `removed` field so a legitimate removal is reported through den-refresh's JSON report, closing
   the namespace's silence for good.

A hard refusal (non-zero exit on an empty `--skills`) was considered and rejected: it would break
the existing "onboard a repo with no skills" case and turn a legitimate empty-catalog scaffold into
an error. Recovery does the right thing instead of asking the caller to.

## Behaviour changes worth knowing

- **A project that excludes every skill via `config.exclude.skills` now keeps its discovery
  links** instead of losing them on the next scaffold — the guard cannot distinguish "declined
  everything" from "handed an empty list by mistake", and losing tidiness in a rare configuration
  beats losing all discovery in a common one. The skill bodies were already left on disk in this
  case; only the symlinks now survive alongside them. Once #128 lands (making `exclude`
  self-executing rather than needing a manual scaffold call), an all-skills-excluded project keeps
  its discovery links in one step instead of two.
- `relink_hermes_skills` now returns `{"created": [...], "removed": [...]}` instead of a bare list
  of created names; `den-refresh`'s `hermesSkillLinks` report key follows the same shape.

## Not covered

A `--skills` value that is merely *wrong* — a typo naming a skill that does not exist — still
prunes everything not named. That is the prune working as designed; only the empty degenerate case
is guarded here.
