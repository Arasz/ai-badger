# 0.53.0 — the log a failing push cites tells the truth

Closes [#212](https://github.com/Arasz/ai-badger/issues/212).

A real push failed on the `release` lane and pointed at its log. The log said:

```
.lefthook/pre-push/verify.sh: line 99: /bin/false: No such file or directory
```

That was not the failure. `release_guard.py` had refused the push over untagged
0.53.0 entries, and the log describing it had been overwritten before anyone
could read it.

## Why

`verify.sh` keys its log directory by a cksum of the checkout path:

```sh
_log_key="$(printf '%s' "$PWD" | cksum | cut -d' ' -f1)"
readonly LOG_DIR="${VERIFY_LOG_DIR:-${TMPDIR:-/tmp}/ai-badger-verify/$_log_key}"
```

The comment above it explains the keying as protection against the nested case —
"the pytest lane runs this script in a throwaway repo". That holds only for tests
that build one. `tests/test_verify_gate.py` does not: it runs the real script with
`cwd` set to the real repo root. Same path, same key, same `release.log`.

Three of those tests deliberately fail the release lane with
`AIB_PYTHON=/bin/false`. So every real push ran them in its own `pytest` lane and
stamped that error over the log its failure block was about to cite.

The failure mode is quiet and badly timed: the log is only ever read when
something is already broken, and it lies precisely then.

## What changed

The suite's gate runs now go to their own directory, through the
`VERIFY_LOG_DIR` override `verify.sh` already honours. No production change was
needed — the script was right, the tests were pointing at the wrong place.

A regression test writes a sentinel into the cited path, runs the gate, and
demands the sentinel survive. On the parent commit it fails with the same
`/bin/false` text that caused the misdiagnosis.
