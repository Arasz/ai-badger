# 0.51.0 — the index records curation, and admits when a server said nothing

Step 5 of the MCP rebuild [ADR-0014](../adr/0014-mcp-support-is-configuration-not-retrieval.md)
describes. Steps 1–4 built the catalog and deleted the legacy registries; this step is the first
that changes what a project's generated `.ai-badger/mcp-tools.json` contains.

## Tags and intents change on the next `mcp-index update`

**This is the consumer-visible effect, and it is deliberate.** `mcp-index init`/`update` now
overlay `features/<stack>/mcp/<server>/tools.json` — the hand-written catalog — over the
`_auto_tags` name heuristics for every tool the catalog describes. The heuristics survive only as
the last resort for the servers the catalog does not know, which is most of them.

Each tool entry gains an `origin` field recording which source spoke:

| `origin` | source | what `update` does to it |
|---|---|---|
| `manual` | `mcp-index tag` / `mcp-index intent` | leaves it alone — a human outranks the catalog |
| `catalog` | `features/<stack>/mcp/<server>/tools.json` | refreshes it from the catalog |
| `heuristic` | `_auto_tags` guessing from the tool name | replaces it as soon as the catalog covers the tool |

An entry written before this release has no `origin`, and a hand-edited one is indistinguishable
from a guess, so **the first `update` after upgrading rewrites the tags and intents of every
catalog-described tool**. The tools that moved are printed by name rather than changed silently.
Curation done through `mcp-index tag`/`intent` from now on is marked `manual` and is safe.

Run against this repository's own 98-tool index, the overlay re-described 5 of them — every
`code-review-graph` tool the catalog covers:

```
Updated: 9 change(s) applied.
  5 tool(s) re-described from the mcp catalog: code-review-graph:get_impact_radius_tool,
  code-review-graph:query_graph_tool, code-review-graph:semantic_search_nodes_tool,
  code-review-graph:get_architecture_overview_tool, code-review-graph:detect_changes_tool.
```

`detect_changes_tool`, for instance, moves from the server's own *"Detect changes and produce
risk-scored, priority-ordered review guidance"* to the curated *"List what changed since the last
graph update, as the starting point of a review rather than a git diff."*

### What that costs and buys, measured

`tooling/retrieval_eval.py` on all three fixture sets, before and after that same overlay (same
98 tools, same servers — only the 5 curated entries differ):

| fixture set | before | after |
|---|---|---|
| `mcp_queries.jsonl` (n=58, 43 positive) | recall@1=0.907 recall@3=1.000 false_fire=0.267 | **unchanged** |
| `mcp_queries_hard.jsonl` (n=70, 52 positive) | recall@1=0.442 recall@3=0.481 false_fire=0.333 | recall@1=**0.462** recall@3=**0.500** false_fire=**0.389** |
| `mcp_queries_long.jsonl` (n=48, 32 positive) | recall@1=0.969 recall@3=0.969 false_fire=0.062 | **unchanged** |

Three fixtures moved on the hard set, all traceable to the wording of a curated intent:

- *"what did I just break with this diff"* → `detect_changes_tool`: **miss becomes hit@3**, because
  the curated intent contains the word *diff* and the vendor description did not. That is the
  answerability point [docs/retrieval.md](../retrieval.md) makes — the fix for a paraphrase gap
  is text that answers the query, not more vocabulary — and curation is how the text gets there.
- *"run this against the database and show me what comes back"* → **hit@3 becomes hit@1**, an IDF
  side effect of five documents changing, not a claim about SQL.
- *"generate unit tests for this class"* → **silent becomes a false fire** on
  `query_graph_tool`, whose curated intent mentions *covering tests*. A real cost, stated rather
  than netted off: one fixture gained, one lost, and the hard set's false-fire rate is worse.

`_auto_tags` itself is unchanged — the heuristics audit [#171](https://github.com/Arasz/ai-badger/issues/171)
asked for finished in [0.51.0 — a build is not a dotnet](0.51.0-a-build-is-not-a-dotnet.md), which
removed the `build`→`dotnet`, `database`→`sql` and `log`→`opentelemetry` rules and kept exactly two
tight aliases with its reasoning recorded. Nothing further was removed here, and nothing was added.

## A server that reported no tools is recorded, not dropped

Every `sources[]` entry now carries a `status`. Dropping zero-tool servers at write time
([#145](https://github.com/Arasz/ai-badger/issues/145)) made *switched off* and *running but
exposing nothing* the same absence with opposite remedies — ADR-0014 decision 7.

| `status` | what the host's listing said | remedy |
|---|---|---|
| `ok` | the server reported tools | none |
| `disabled` | the host says the server is switched off | enable it |
| `empty` | enabled, asked, exposed nothing | check the server actually starts |
| `unknown` | the listing carried no tool detail at all | see below |
| `absent` | the host no longer lists it; its tools are marked `removed` | re-add it, or accept the removal |

`init`, `update` and `validate` all print the servers whose status is not `ok`, by name and status.

### `unknown` is not padding — it is the live path

The installed `hermes mcp list` has **no `--json`** (measured on hermes at
`~/.local/bin/hermes`: `error: unrecognized arguments: --json`), so `_fetch_mcp_tools` falls back
to parsing the text table, whose Tools column reads `all` and never the tool names. Calling that
`empty` would be a lie about nine servers. Two consequences:

- the fallback now also carries the table's `✓ enabled` / `✗ disabled` column, which it previously
  parsed and threw away, so `disabled` is knowable even with no tool detail;
- **an `update` over such a listing no longer marks every tool in the index `removed`.** It
  restates statuses and touches nothing else. "Not asked" is not "exposes nothing".

### There is deliberately no `unreachable`

Design §5 listed `ok | disabled | unreachable | empty`. No `hermes mcp list` mode distinguishes a
connection failure from an empty tool list, and a status nothing can set is not a status.
`claude mcp list` *does* distinguish Connected / Needs authentication / Failed to connect /
Connection error / Pending approval / Rejected; ingesting it is not wired up and is a follow-up.

`origin` is recorded **per tool**, not per source as the design wrote it: a catalog-described
server also exposes tools the catalog does not describe — `code-review-graph` ships 30 tools in
this repo's index and the catalog curates 5 — so a source-level `origin` would be false for 25
of them.

## Schemas

- `schemas/mcp-tools.schema.json`: `sources[].status` and `tools.*.origin` added;
  `sources[].tools.minProperties: 1` removed — it is what made dropping look mandatory.
  `additionalProperties: false` stays everywhere.
- `schemas/mcp-server-tools.schema.json`: `intent` gains `maxLength: 200`. The overlay copies a
  curated intent verbatim into the generated index, so the catalog is bound by that schema's own
  limit; without this, a long curated intent would make `init` refuse to write.

## `mcp_index.py` splits

The taxonomy, the name heuristics, the catalog loader and the status vocabulary move to
`features/common/skills/mcp-index/scripts/tool_descriptions.py` — *what a tool is for, and whether
its server is talking*. `mcp_index.py` keeps the index file, the commands and the CLI. It is a real
seam and not only a line-count fix, though it is also that: the module crossed pylint's 1000-line
ceiling ([#183](https://github.com/Arasz/ai-badger/issues/183) is why package-mode lint hides it).

`test_write_index_drops_zero_tool_servers_and_reports_them` →
