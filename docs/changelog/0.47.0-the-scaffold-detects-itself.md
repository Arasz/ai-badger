# 0.47.0 — the scaffold detects itself

[#134](https://github.com/Arasz/ai-badger/issues/134). A project scaffolded with
`stacks: ["python"], agents: ["claude"]` never converged:

```
=== refresh run 1 === reScaffolded= True | newStacks= ['claude', 'js']
=== refresh run 2 === reScaffolded= True | newStacks= ['claude', 'js']
=== refresh run 3 === reScaffolded= True | newStacks= ['claude', 'js']
```

Every run rewrote the project's managed files, forever. Three causes, two of them false reports
and one a design defect that would have outlived both.

## Two independent false positives

**`claude` was a wrong-field bug, not self-detection.** `refresh.py` computed `newStacks` from
`config.get("stacks", [])`, but `claude` was declared in `config.agents` — a catalog stack an
agent draws from just as much as one in `config.stacks` (`badger_lib.delivering_stacks` exists
for exactly this, and the same function in `refresh.py` already used it 14 lines above the one
that didn't). This is a re-run of #119/0.43.1: one call site missed. `.claude/` itself has been
in `detect.py`'s `_IGNORE_DIRS` since 2026-07-19 and matched nothing — it was never the trigger.

**`js` and `python` came from the refresh's own backup.** `refresh.py` copies `.ai-badger/` to
`.ai-badger.bckp/` at step 5, *before* running detection at step 6b — and `.ai-badger.bckp` was
never added to `_IGNORE_DIRS`. So every refresh detected the framework's own `.mjs` helpers and
Python hook scripts one directory over from the tree that was already excluded. The live
`.ai-badger/**/*.mjs` copies were already ignored; the backup was not.

## The design defect underneath both

Even with both false positives fixed, a project with a genuine hand-authored `tsconfig.json` +
`.ts` file would still re-scaffold on every refresh, forever, for the same structural reason: the
re-scaffold runs with the *unchanged* config, and a config that never named `ts` cannot have
`ts` delivered by rerunning it. `den-refresh/SKILL.md` already said as much — "never re-detect" —
while `newStacks` sat in the `has_drift` gate contradicting it.

## The fix

- `badger_lib.BACKUP_DIR_NAME` (`.ai-badger.bckp`) is now the single source of truth for the
  backup directory name, used by both the code that creates it (`refresh.py`) and the code that
  must ignore it (`detect.py`'s `_IGNORE_DIRS`) — they can no longer disagree.
- `refresh.py` now passes `badger_lib.delivering_stacks(config)` to `detect_new_stacks`, matching
  the call already made to `run_drift` 14 lines earlier.
- `newStacks` is dropped from the `has_drift` gate. It stays in the JSON report — a genuine
  unconfigured stack is still surfaced — it just no longer forces a re-scaffold.

## Why dropping `newStacks` from the gate loses nothing

`newStacks` never converged anything: a re-scaffold runs the same config and cannot deliver a
stack that config does not name, so every re-scaffold it triggered reproduced the exact signal
that triggered it. Since #128, `configChanged` is what actually converges the accept path: a
human edits `config.stacks` to add the new stack, the config hash changes, `configChanged` fires,
the re-scaffold delivers it and stamps the new hash, and the run after that is quiet. `newStacks`
now does only what it is good at — telling a human something worth deciding about — and nothing
it was never suited to.

## Behaviour changes worth knowing

- `reScaffolded: false` alongside a non-empty `newStacks` is now the expected shape, not a
  contradiction. `den-refresh/SKILL.md` documents both paths from there: accept (add to
  `config.stacks`, self-executing via `configChanged`) or decline
  (`.ai-badger/stack-ignore.json`, project-owned, never overwritten).
- The six `_suppress_new_stack_noise` call sites added alongside #128's tests are deleted; those
  tests now prove this fix unaided rather than relying on a stack-ignore.json workaround.
- The `docs/getting-started.md` troubleshooting entry for `newStacks: ["claude", "hermes", …]`
  right after a scaffold is deleted — it documented this bug as expected behaviour.

## Not covered

`stack-ignore.json` is unchanged: it remains the decline path for genuine third-party detection
(#54), not an answer to the framework detecting its own output — that answer was always
`_IGNORE_DIRS`, and this release is what makes it actually cover the framework's full output.
