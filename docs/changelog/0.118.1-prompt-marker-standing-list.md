# 0.118.1 — The Standing Marker List Is Now Compared Against the Catalog

**Type:** PATCH
**Date:** 2026-08-14

## What Changed

### Every agent instruction file lists every marker

`q:` / `queue:` and `i!:` / `important!:` were added to
`features/common/skills/prompt-markers/markers-context.json` and to the Hermes files, and the
Claude and Copilot files kept listing three markers:

| Source / file | Before | After |
|---|---|---|
| `features/common/templates/HERMES.md.tmpl` | 5 | 5 |
| `features/common/templates/CLAUDE.md.tmpl` | **3** | 5 |
| `HERMES.md`, `.hermes.md`, `.ai-badger/HERMES.md` | 5 | 5 |
| `CLAUDE.md`, `.ai-badger/CLAUDE.md` | **3** | 5 |
| `.github/copilot-instructions.md`, `.ai-badger/copilot-instructions.md` | **3** | 5 |

Both templates and all seven generated files now also state that a mid-turn marker bypasses
the hook.

### The list is compared, not trusted

The real source is `features/common/templates/CLAUDE.md.tmpl` and `HERMES.md.tmpl`, which
spell the list out longhand instead of deriving it from `markers-context.json`. So adding a
marker to the catalog does not add it to the templates, and nothing compared the two —
`CLAUDE.md.tmpl` kept three markers and took both Copilot files with it.

Editing the generated agent files is not a fix: `scaffold.py` regenerates them from the
templates and silently reverts the edit. (Measured while writing this change — the first
attempt patched the seven agent files, and the next scaffold run put all seven back.)

`tests/test_prompt_marker_standing_list.py` parametrises over `markers-context.json` and
asserts every marker's prefixes appear in **both templates** and in every generated agent
file. A marker added to the catalog and not to a template now fails the build. That is the
`derive-or-delete-the-list` invariant: the comparison is the fix, not the one-time edit.

## Why It Mattered

`UserPromptSubmit` fires only when a message **starts a turn**. A message queued **mid-turn**
is delivered to the model as an attachment and never passes through the hook, so its marker is
never expanded — and nothing reports a failure, because the hook was not called rather than
erroring.

Measured 2026-08-14 against a real session transcript:

| Message | Record type | Hook ran |
|---|---|---|
| Turn start | `type: "user"` with `promptSource`, `origin` | yes |
| Mid-turn | `type: "queue-operation"` + `type: "attachment"` | **no** |

Two mid-turn `f:` messages produced no `type: "user"` record at all, and no other
`UserPromptSubmit` output either — which is what separates this from a defect in the skill.
Fed the same text directly, the hook returns the correct `additionalContext` and exit 0.

**No hook can fix this**, because there is no hook event for a queued message. The standing
list in the agent file is the only mitigation, which is precisely why two of the five markers
being absent from it was the real defect.

## Tests

`tests/test_prompt_marker_standing_list.py` — 7 cases. Three were confirmed red first: the
`queue` and `important` parametrisations, and the mid-turn assertion (all seven files silent).
`test_the_marker_catalog_is_the_thing_being_compared_against` guards the guard, so a catalog
that lost its entries cannot make the parametrised cases pass vacuously.
