# 0.69.3 — skills that cannot work alone travel together

`migrate-documentation` ships no `references/` of its own. Its body names four files by relative
sibling path — three under `update-documentation/references/`, one under
`scaffold-documentation/references/` — deliberately, since a shared directory cannot ship:

> Read them where they live; do not copy them into a shared directory, which cannot ship.

All three are `optIn`. A project that named only `migrate-documentation` in `include.skills`
therefore received a skill whose **every reference path was dangling**, and nothing said so — the
scaffold reported it included, because it was (#266).

## Why it was invisible

This repository opted into all three at once, so every path resolved here. The hazard only appears
in a project that wants one of them — exactly the case nobody was running.

## What changed

`badger_lib.SKILL_GROUPS` declares skills that cannot do their job alone. Naming any member — or
the group — installs all of them:

```python
SKILL_GROUPS = {
    "documentation": ("scaffold-documentation", "update-documentation", "migrate-documentation"),
}
```

`expand_skill_groups()` runs in `Scaffolder.__init__` before the addable filter, so a grouped
sibling arrives even when the project never named it. `den-refresh` constructs the same
`Scaffolder`, so both entry points get this and cannot disagree about what a project asked for.

A project can now write `"include": {"skills": ["documentation"]}` and get the capability without
knowing the three skill names. The group name itself is never installed — it is a group, not a
skill, and delivering it would look for a directory nobody has.

**Declared, not inferred.** An earlier draft scraped the sibling paths out of each `SKILL.md` and
computed a transitive closure. It worked, but it inferred a fact the catalog should simply state:
these three are one capability. A declaration is also checkable, which the guards below rely on.

## Why they stay flat on disk

The three are grouped in configuration, not in the filesystem. **A skills directory registers
exactly one nesting level, and a directory without a `SKILL.md` is silently ignored rather than
erroring** — `scaffold-documentation/SKILL.md` records this as verified across the agents ai-badger
supports. So `.claude/skills/documentation/migrate-documentation/SKILL.md` would be invisible to
every agent, and the delivered layout has to stay flat.

Nesting them in the catalog while flattening on delivery is possible, but it reaches `index_build`,
`sync_plugin_skills` and `scaffold` together — a separate change, not this one.

## Tests

`tests/test_skill_groups.py` — 21 cases.

**The group:** naming any of the three installs all three (parametrised over each), naming
`documentation` installs the members without installing the group name, an ungrouped skill is
unchanged, an unknown name passes through for `inclusion_notes` to report, and an empty request
stays empty.

**The delivery:** all four cited files present after a scaffold, every relative path resolving *as
written* from where the skill actually sits, a pulled-in sibling discoverable at `.claude/skills/`
and not merely delivered (#261), and an empty `include` still installing nothing. Proved by
removing the expansion: three of the four go red, and the "asked for nothing" case correctly stays
green.

**Two guards** keep the declaration honest as the catalog changes: no skill may cite a sibling it
is not grouped with, and no group may name a skill the catalog does not have. A companion asserts
the scan finds the known references — an empty finding must mean "all resolve", not "the pattern
never matched".

The pattern carries a lookbehind. `../../outside/references/x.md` reaches past the skills directory
and is not a sibling reference; the first draft matched it, which would have had the guard call an
unresolvable path resolvable and never report it.

## Review round (Copilot, #275)

Three distinct findings, all real, all fixed:

- **A group name was reported as a mistake.** `expand_skill_groups` made `"documentation"` a legal
  value, but `inclusion_notes` still saw the raw config names — so a working config was reported as
  *"matches no optIn catalog skill — safe to remove from config.json"*. A note that tells someone
  to delete config that works is worse than no note, because it gets acted on. `inclusion_notes`
  now recognises a group and says which members it delivered. A genuine typo is still reported;
  that case has its own test, because a guard that stops firing hides the mistakes it was for.
- The changelog named `tests/test_sibling_reference_closure.py`, which this PR renamed to
  `tests/test_skill_groups.py` when the approach changed from inferred closure to declared group.
- `schemas/config.schema.json`'s `include` description said only `SKILL_SCOPES` names were legal.
  It now names `SKILL_GROUPS` too.

Copilot reported the first against all three copies of `scaffold.py` — catalog, plugin and
scaffolded. That is one defect seen three times, and fixing the catalog source plus re-running the
generators corrects all three, which is the point of them being generated.
